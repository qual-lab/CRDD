# 1. Purpose

本ドキュメントは、外部契約（API・データスキーマ・依存ライブラリ）を安全に変更・進化させるための基本原則を定義する。

プロダクトは時間とともに変化する。しかし、変化のたびに利用者・他システム・過去データとの契約を壊してよいわけではない。本ドキュメントは、何かを変えるときに何を壊さないかを判断するための原則を定める。

---

# 2. Basic Principle

```text
外部契約は、暗黙のうちに壊さない。
変える場合は、影響を受ける側の移行手段を用意する。
```

ここでいう外部契約とは、API、IPC、DBスキーマ、依存ライブラリなど、他のコード・他のシステム・過去のデータが前提にしているものを指す。

---

# 3. API / Interface Versioning

外部から呼び出されるAPI・IPC・イベント形式を変更する場合、呼び出し側への影響を考慮する。

## Rule

```text
既存のフィールド・パラメータの意味を変えない（変える場合は別名にする）
破壊的変更（Breaking Change）と後方互換な変更（Non-breaking Change）を区別する
破壊的変更を行う場合は、バージョンを分けるか、移行期間を設ける
呼び出し側が複数存在する場合、影響を受けるすべての呼び出し側を洗い出す
```

## Bad

```text
既存APIのレスポンスにあった`status`フィールドの意味を、「processing中」から「完了」を示すものへ
変更した。呼び出し側のコードは変更せずにリリースした。
```

## Good

```text
既存APIの`status`フィールドの意味を変える代わりに、新しいフィールド`status_v2`を追加する。
呼び出し側を全て新フィールドへ移行してから、旧フィールドをDeprecatedとしてマークし、
一定期間後に削除する。
```

# 4. Data Migration / Schema Evolution

DBスキーマ・データ構造を変更する場合、既存データとの整合性を保つ。

## Rule

```text
スキーマ変更は、既存データが不整合な状態にならない移行手順とセットで設計する
可能な限り、後方互換な移行（追加は先、削除は後）を優先する
一度きりの変換で失敗すると回復できない移行は避け、段階的に移行できる設計にする
移行前にロールバック手段（バックアップ、あるいは移行の取り消し手順）を用意する
```

[`00_10_Context_Repository_Standard.md`](00_10_Context_Repository_Standard.md)の「DBスキーマ変更は`95_Decisions`にDecision Logを残す」という既存ルールに対し、本節は「どう安全に移行するか」の実務原則を補う。

## Bad

```text
テーブルの列名を変更するマイグレーションを1回のリリースで実行した。
ロールバック手段は用意しておらず、問題が起きたら手動でDBを直す想定だった。
```

## Good

```text
新しい列名の列を追加し、両方の列にデータを書き込む期間を設ける。読み取り側を新しい列名へ
段階的に切り替え、旧列を参照するコードがなくなったことを確認してから旧列を削除する。
```

# 5. Migration and Refactor Discipline

実装そのものを移行する場合（言語の書き換え、フォルダ構成の変更、大規模リファクタリング等）にも、外部契約の変更と同じ慎重さを適用する。

## Rule

```text
挙動を変えないはずの機械的な変更（言語変換、ファイル移動、リネーム等）と、意図的な設計変更を、
別バッチ・別コミットへ厳密に分離する
機械的な変更のバッチでは、既存の自動テストスイートを「変わらないはずの基準」として使い、
テスト結果の変化から意図しない影響を検出する
両者を同じ変更に混ぜると、リグレッションが発生したときにどちらが原因か切り分けられなくなる
大規模な移行は、検証可能な単位に分割し、単位ごとに検証してから次へ進む
```

## Bad

```text
言語移行のためにファイルを書き換えるコミットの中で、ついでに気づいた設計上の改善も
一緒に反映する。移行後にテストが1件失敗したが、機械的な変換ミスなのか、設計変更による
意図した挙動変化なのか、diffを見ただけでは分からない。
```

## Good

```text
言語移行は「挙動を変えないこと」を目的とするバッチとして独立させ、既存のテストスイートが
移行前と同じ結果を返すことを都度確認する。設計上の改善は、移行が完了し安定した後に、
別のバッチとして着手する。
```

# 6. Dependency Management

外部ライブラリ・依存パッケージの追加・更新も、外部契約の一種として扱う。

## Rule

```text
新しい依存を追加する前に、必要性・保守状況・ライセンスを確認する
セキュリティ上の注意喚起（既知の脆弱性）があるライブラリは更新を優先する
メジャーバージョンアップ（破壊的変更を含みうる更新）は、変更内容を確認してから取り込む
依存の追加・大きな更新は、影響範囲が広い場合`95_Decisions`にDecision Logを残す
```

## Bad

```text
「動いたから」という理由で、パッケージのメジャーバージョンを深く確認せずに更新した。
```

## Good

```text
パッケージのメジャーバージョンアップ内容（Breaking Changes一覧）を確認し、自プロダクトが
使用している機能に影響があるかを洗い出してから更新する。影響がある場合は対応方針を先に決める。
```

---

# 7. Minimum Rule

最低限、以下を守る。

```text
外部契約を壊す変更には、移行手段をセットで用意する
破壊的変更と非破壊的変更を区別して扱う
スキーマ変更はロールバック手段を用意してから実行する
機械的な移行と意図的な設計変更を同じバッチに混ぜない
依存の更新は内容を確認してから取り込む
```

---

# 8. Final Principle

CRDDにおける進化は、過去を切り捨てることではない。

外部契約を尊重しながら変化することで、プロダクトは利用者・他システム・過去データの信頼を損なわずに成長できる。
