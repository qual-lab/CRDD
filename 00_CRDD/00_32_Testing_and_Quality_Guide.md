# 1. Purpose

本ドキュメントは、CRDDにおけるテスト・品質保証・非機能要件の基本原則を定義する。

CRDDはドキュメントと判断の継承を重視するが、それだけでは「動くもの」を保証しない。
本ドキュメントは、実装が思想どおりに正しく動くことを確認するための最低限の原則を定める。

---

# 2. Basic Principle

```text
「実装した」と「検証した」は別の状態である。
```

CRDDでは、この2つを明確に区別する。

---

# 3. Implemented vs Verified

コードが存在すること（Implemented）と、それが正しく動くと確認されていること（Verified）は分けて扱う。

```text
Implemented = コードが書かれている
Verified    = 自動テスト・検証手順を通過し、正しく動くと確認されている
```

## Rule

```text
実装されているだけの機能を「対応済み」「Verified」と表示しない
ユーザー・人間向けの状態表示は、Verifiedの基準を満たしたものだけを「完了」とする
Verifiedでない場合は、その旨を明示する（例: 実装済み・未検証）
```

これは、`00_01_CRDD_Principles.md` の「Definition of Done」（Working Software + Readable Context + Traceable Decision）における「実装が動く」「検証されている」を、実務レベルまで具体化したものである。

## Bad

```text
決済処理のコードを書いた。まだテストは書いていないが、機能一覧には「対応済み」と記載した。
```

## Good

```text
決済処理のコードを書いた。自動テストが失敗するケース（残高不足、通信断）を洗い出して通過するまでは、
機能一覧には「実装済み・未検証」と記載する。全テスト通過後に「対応済み」へ更新する。
```

# 4. Control Registry Pattern

管理すべき項目（セキュリティ統制、コンプライアンスチェック項目、機能の受け入れ条件等）が少数ではなく多数になった場合、「Implemented vs Verified」を1つのフラグではなく、項目ごとのレジストリとして構造化する。

## Rule

```text
各項目は、少なくとも以下を別フィールドとして持つ
  - implementation_status（実装段階: 未着手/実装中/実装済み等）
  - assurance_status（検証段階: 未検証/検証中/検証済み/失敗等）
  - evidence_source（何によって検証したか: テストID、検証手順等）
  - last_verified_at（最終検証日時）
implementation_statusとassurance_statusを1つのフィールドに混ぜない
「実装済み」と表示されている項目でも、assurance_statusが検証済みでなければVerifiedとして扱わない
```

これは§3「Implemented vs Verified」を、管理対象が数個ではなく数十・数百になる場面向けに構造化した具体パターンである。単一機能の合否判定には§3の原則で足りるが、多数の項目を継続的に管理する場合はこのレジストリ形式が扱いやすい。

## Bad

```text
20個のチェック項目を、1個の真偽値フラグ（対応済み/未対応）だけで管理する。「対応済み」と
書かれた項目が、実際にはコードが書かれただけで自動テストを一度も通していないことに、
後から気づく。
```

## Good

```text
チェック項目ごとに実装段階と検証段階を別フィールドで管理し、検証済みの項目だけが
一覧で「Verified」と表示される。どのテスト・手順で検証したか、いつ最後に検証したかも
項目ごとに追跡する。
```

# 5. Implementation Quality Rules

複数レイヤー（DB・API・UI等）を持つシステムでは、以下の5原則を実装前後で確認する。障害の事後分析から一般化された、レイヤードアプリケーション全般に適用できるチェックリストである。

## Rule 1: 影響範囲を宣言する

共有コンポーネント・共有ロジックを変更する前に、影響を受ける範囲（画面、他機能、既存データ）を明示的に洗い出す。

## Rule 2: フルスタックで確認する

DB・API・IPC・UIなど複数レイヤーをまたぐ変更では、「コードを読んで正しそうに見える」だけで判断しない。実際にデータが端から端まで正しく流れることを確認する。

## Rule 3: 状態分岐を網羅する

「表示された」だけでなく、想定される状態（空・エラー・境界値・並行処理等）を洗い出し、それぞれを確認する。

## Rule 4: 重複は見つけた時点で一本化する

同じロジックの重複実装を見つけたら、先送りにせず、見つけた時点で一本化する。先送りにすると重複が拡散し、修正漏れの温床になる。

## Rule 5: バックエンド変更後は再起動して確認する

ホットリロードが効かないプロセス（バックエンド・サーバープロセス等）を変更した場合、変更が反映された状態で動作確認する。

## Bad

```text
在庫更新ロジックをAPI側で修正した。画面上の表示ロジックは変えていないので、フロントは確認せずリリースした。
→ 実際にはAPIのレスポンス形式が変わっており、フロント側の在庫表示が壊れていた。
```

## Good

```text
在庫更新ロジックをAPI側で修正した。レスポンス形式が変わるため、影響範囲を確認したところ、
フロント3画面が同じAPIを参照していることが分かった。3画面すべてで実際にデータが正しく表示されることを確認してからリリースした。
```

# 6. Test Taxonomy

テストは、目的に応じて種類を区別する。種類を分けずに「テストがある/ない」だけで語ると、何を保証していて何を保証していないかが曖昧になる。

| 種類 | 目的 |
|---|---|
| Contract Test | インターフェース（API・IPC等）が約束した形式を守っているかを確認する |
| Boundary Test | 権限・データ境界を越えていないかを確認する（例: 権限外データにアクセスできないこと） |
| Characterization Test | 現在の実際の挙動を記録し、意図しない変化を検出する |
| Golden Test | 既知の正しい入出力（Golden Fixture）との比較による回帰検出 |
| Simulation Test | 生成された未知の入力に対して、パイプライン全体が破綻しないかを検証する |
| Headless DOM Test | UIの表示判断・操作・Intent発行を、実ブラウザ描画なしに検証する（外部境界はFixtureで置換する） |

## Rule

```text
テストファイル・テストケースには、どの種類のテストかが分かる名前・コメントを付ける
「テストがある」ではなく「何のテストが、何を保証しているか」を明確にする
Golden（既知の正しさの固定）とSimulation（未知入力への頑健性）は目的が異なるため、混同しない
```

## Bad

```text
目的の異なるテストケースを一つのファイルへ何でもかんでも追加していく。
どのテストが何を保証しているのか、名前だけでは分からない。
```

## Good

```text
テストの種類（Contract / Boundary / Golden等）ごとにファイルを分け、
各テストファイルの冒頭に「このテストが保証する範囲」を明記する。
```

具体的な命名パターン・ディレクトリ配置などの実装方法は、正本ではなく
`06_Architecture` 配下の実装規約文書を参照する。

# 7. AI Output Review Gate

AI（特にLLM）が生成する出力は、通常の自動テストだけでは品質を判定しきれない場合がある。この場合、人間評価による判定ゲートを設ける。

## Rule

```text
自動テストで機械的に判定できる範囲（形式・スキーマ・必須項目）は自動テストに任せる
自動テストで判定しきれない範囲（自然さ、有用性、誤解を招かないか）は、人間評価の基準を明文化する
評価基準は段階的な採点（例: A/B/C/D）とし、量的な合格基準（例: 「B以上が80%以上」）を定める
モデル・プロンプトの変更時は、このゲートを再実行して品質が劣化していないか確認する
```

## Bad

```text
AIの出力が「なんとなく良さそう」であることを確認しただけでリリースする。
基準が人によって異なり、劣化に気づかない。
```

## Good

```text
AI出力のサンプルを人間が A（そのまま使える）〜D（誤解を招く・使えない）で採点し、
「B以上が全体の80%以上」を合格基準として明文化する。プロンプトやモデルを変更するたびに
同じ基準で再評価し、劣化を検出する。
```

# 8. Non-functional Requirements

機能要件だけでなく、以下のような非機能要件も設計段階で意識する。

```text
性能（パフォーマンス要件）
アクセシビリティ
スケーラビリティ
可用性
セキュリティ（詳細は00_33_AI_Governance_and_Security_Guideを参照）
```

非機能要件の詳細な基準は、プロダクトごとに `06_Architecture` 配下で具体化する。CRDDが求めるのは、非機能要件を「後から気づく」のではなく、設計段階で意識的に検討することである。

---

# 9. Minimum Rule

最低限、以下を守る。

```text
実装済みと検証済みを区別して表示する
管理項目が多数になる場合はimplementation_statusとassurance_statusを別フィールドで管理する
複数レイヤーをまたぐ変更はフルスタックで確認する
重複コードは見つけた時点で一本化する
テストは種類を区別し、何を保証しているかを明確にする
AI出力は自動テストと人間評価ゲートを組み合わせて判定する
非機能要件を設計段階で検討する
```

---

# 10. Final Principle

CRDDにおける品質保証は、「動いているように見える」ではなく、「動くと確認されている」を基準とする。

検証されていない実装は、Context Repository上でも、ユーザーに対しても、完了として扱わない。
