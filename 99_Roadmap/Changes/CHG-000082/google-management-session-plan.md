# GoogleログインとWorkbench管理セッションの切替計画

- 対象版: v0.22／[CHG-000082](change.md)
- 基準: `cdbca1106` と着手時のパッケージ公開面の作業差分
- 状態: Google本人確認、利用者との紐付け、HTTPクライアントセッション、MCP OAuth発行・照会・同意、共有Toolと現在認可、共有起動、Host初回設定と既存管理者の紐付けの対話入口を実装済み。Workbenchは本人の招待引受とGoogleログアウトに対応する。招待の発行・再発行を含む、接続鍵を扱わないアクセス管理書込みは短命の管理セッションに接続した。AMの現行保存形式は旧鍵・旧初回の途中段階・旧公開範囲を受け付けない。旧方式を使った経緯は切替前の履歴であり、現行の共有公開能力ではない。Hostの一連の実境界、実Google・実MCPクライアント確認、全体回帰は未完了。

## 採用した範囲

### 共有の接続鍵を廃止する追加決定

共有の人の接続はGoogleログイン、共有MCPの接続はMCP向けOAuthに一本化する。共有向けの鍵の発行・提示・交換、鍵方式の初回設定、鍵での再入場を撤去し、管理者のログイン復旧はHostの明示確認によるGoogle再紐付けを使う。旧鍵からの自動紐付けや本番の旧状態の自動変換は追加しない。

単体は信頼できる個人PC向けにWorkbenchとHTTP APIを維持し、MCPは `--mcp-stdio` に限る。単体のHTTP版MCPと専用の固定Bearerは廃止する。単体のGoogleログイン、一回限りのログインリンク、外部への直接公開は追加しない。同じPC上の別ユーザーの隔離は保証しない。共有モードは一人でも使えるが、クラウドのMCPクライアントからの到達経路と実接続の評価は別とする。

以下に記録した両方式併存は切替前の基準であり、追加決定の達成を示さない。切替時には要求、アクセス管理・Server・MCP・Workbenchの設計、利用案内、配布入口、利用側の試験と品質台帳を同じ候補へ追従させる。旧鍵・内容範囲・公開範囲を含む旧保存形式は新Readerの対象とせず、旧データの自動変換や既存Hostの操作は行わない。新規Host、現行形式での既存管理者の再紐付け、および旧形式・観測不能による停止は別々に確認する。固定候補は技術独立レビュー、文書監査、不足／影響監査へ渡す。

### 共有アクセスの最終契約

| 対象 | 採用した方針 |
|---|---|
| 起動と公開 | CLIとライブラリの共有起動にGoogle、MCP OAuth、有効なGitホストを要求する。単体MCPは標準入出力。旧接続鍵と管理書込みToolを撤去し、残るToolは一覧・実呼出しとも現在認可を行う |
| 管理 | 管理書込みはWorkbenchの管理セッションに限る。既存利用者への招待再発行はadministrator専用とし、初回紐付けのためのHost操作とは分ける。独立した利用者有効状態取得は廃止する |
| 内容アクセス | CRDDロールは管理操作だけに使う。内容範囲・公開範囲を廃止し、共有登録はGitホストへの結合を必須とする。共通契約は同じ本人の実効権限（読み取り／書き込み）。GitHub Appの権限はGitHub固有の追加確認とする |
| 実行監督（D-19） | 新規要求と最初のTaskの許可には有効な入口資格を要求する。開始済みの実行はその資格・同意の寿命から分離する。本人の紐付け解除または対象への実効権限の喪失を確認した場合に止める。GitHubでは安定した本人IDとリポジトリIDを用い、対象を絞ったAppのインストール資格で現行権限を照会する。観測不能では次のTaskを始めない。子との停止通知は既存Node IPCを維持する |
| ログアウト（D-18） | 明示ログアウトではブラウザーのセッション、同じ本人のMCP認可サーバー側のセッション・同意・発行トークン、利用者のGitHubトークンを破棄する。新規利用は拒否するが、開始済みの実行は取り消さない。ブラウザーやPCを閉じる動作は明示ログアウトとして扱わない |
| 共有起動（D-17） | 一つの保存領域に対して一つの共有Serverプロセスだけを起動する。セッション・OAuth・Gitホスト連携・即時通知と所有者判定はこの境界に従う |
| 責務と配置 | アクセス管理は同期の状態・判定を所有し、OIDCとHostの対話ListenerはServer側へ移す。HTTP受付・管理セッションの受付は `transport/api-server.ts` を入口とし、プロトコル非依存のセッション状態はServiceへ置く |

RESTの状態・詳細操作、公開名、重複判定は現行入口と利用側を回帰で照合する。Gitホストの照会間隔を変更する判断と、管理セッション開始時の追加再認証はこの保存形式の切替に含めない。追加再認証はv0.22の対象外とする。

追加再認証（D-20）の保留は共有認証の所有側で追跡する。公開配置や管理セッションの発行条件を次に見直すときに再評価する。保留中は現在のブラウザーセッションで短命の管理セッションを開けるため、共有端末に通常セッションが残ったとき、提供元で本人確認し直す仕組みはない。既存の管理ロール、対象別認可、有効期限は維持する。

画面取得経路の分割（D-32改、REST-1）はv0.22で行う。Project詳細は `GET /api/projects/{projectId}`（現在認可された情報源の集約）、情報源を指定する場合は既存のリポジトリ別Project Contextを使う。Topic・Meetingの詳細も既存のリポジトリ別RESTリソースへ移した。変更正本と参照成果物はそれぞれ専用のリポジトリ別リソースへ移し、表示の `route` による切替と旧 `/api/workbench/view` を撤去した。概要は `/api/workbench/overview`、単体の起動先と共有のログイン案内は `/api/workbench/context` が返す。

取得GETでは一度きりの操作通知を消費しない。共通表示の注意表示はその要求の観測結果から生成し、記録削除の結果は書込み応答を受けたWorkbench UIの遷移中だけ引き渡す。GETが読み直し済みとして処置する記録の再取得フラグは内部キャッシュの無効化であり、利用者への通知ではない。

Projectの移管では、単体のProject詳細と情報源を指定した既存経路の整合、欠測情報源の保持、旧表示選択子でProject本文を返さないことを実HTTPで確認した。合成OAuthの共有試験7件では、ログイン済みの許可主体と不許可主体、およびBearer混在の拒否を含めて確認した。HTTP受付とOpenAPIの契約5件、Workbench UIの契約31件およびServer・UIの静的検査も成功した。UI試験は応答対象の不一致、401後のログイン画面、同じ遷移の途中での取消を含む。全ページの実ブラウザー試験やREST-1全体の完了はこの結果に含めない。

Topic・Meetingの変更では、共有の閲覧のみと書込み可能を実HTTPで分け、MCPの記録応答には表示用の権限を追加していないことを確認した。同じ対象の通常再取得には確定済みリポジトリを使う。Serverの限定12件とUIの32件、静的検査が成功した。後続の単体2件では、Manifest真正不存在時の詳細のみの読取り、不正Manifestでの拒否、一覧契約の維持も確認した。

成果物の移管では、Serverの限定24件とUIの33件に成功した。共有の公開対象一覧を構成している間の登録解除を試験用データに注入し、選択本文の読取り0回と403を確認した。実ブラウザーの成果物遷移では対象切替、履歴、遅延応答の破棄、共有応答の出所不一致、ログアウト後の非開示を確認した。単体の概要・Topic・Meetingについても実ブラウザーの全表示プロファイルで成功した。独立再レビューの追加必須指摘はない。概要APIと共通接続情報の分離、全パッケージの回帰結果はこの確認に含めない。

共通入口の分離後、Serverの限定16件とUIの33件、共有の追加HTTP 1件に成功した。旧URLは404、単体のリポジトリID省略時は共通入口と専用詳細だけを取得する。共有では匿名・有効なCookie・紐付け失効・管理状態の観測不能を分け、Gitホスト照会0を確認した。実ブラウザーでは概要・Project・Topic・Meetingの4ページを3表示幅・3拡大率の36条件で確認し、共有の成果物遷移からログアウト後の非開示まで再確認した。独立再レビューの追加必須指摘はない。全体回帰と外部の実MCPクライアント確認は別ゲートである。

R-01（基準 `8dcc9b4a6`）では、同じ利用者・外部ログインの紐付け・Gitホストのアカウントの再連携で記録が増え、共有枠を使い切る問題を是正する。連携参照と対話用資格の更新・保持条件は[Workbench Serverの連携設計](../../../06_Architecture/Details/workbench-server/01_Architecture.md)に従う。合成GitホストによるHTTPの繰返し、他利用者の新規連携、MCP同意の参照と明示解除、上限での参照保全を確認対象とする。保存形式、外部の権限照会、実行監視の頻度は変更しない。

R-10（基準 `8dcc9b4a6`）では、提供元固有の設定、発見文書の発行者の検査、検証済み発行者・テナントの受入れを、起動時に結合する提供元プロファイルへ移す。[Workbench Serverの外部本人確認設計](../../../06_Architecture/Details/workbench-server/01_Architecture.md#host-admin-cli)を正本とする。合成の追加提供元で、設定の欠測・発見文書の発行者不一致・許可外テナントとトークンの発行者不一致を拒否し、許可された具体的な発行者だけを返すことを確認する。Google以外の製品登録、保存移行、実提供元の接続、メール証明方式の追加は含めない。

同レビューのR-02〜R-09およびR-11〜R-13では、[Workbench Serverの設計](../../../06_Architecture/Details/workbench-server/01_Architecture.md)に従い、利用者・所有者ごとの容量、HTTPSのCookie、受付接続と実行所有の分離、権限確認を保った照会削減、提供元の設定検証、共有起動を照合する。試験では容量超過と他利用者の保全、Task許可前後の実HTTP切断、異なる対象・認可が混ざらないこと、追加照会の回数、および設定のない共有起動の拒否を確認する。永続状態の移行、正式対応する提供元の追加、公開REST契約の再設計は含めない。

D-23・D-25・D-26のGitホスト接続では、提供元の種類で実装を選び、ホストごとに接続先と資格を結合する。資格の設定は提供元が解釈し、連携のHTTP受付はホストごとの識別子で接続先を特定する。同一の代替提供元を二つのホストへ結合でき、別ホストや別提供元への資格搬送を拒否することを合成試験で確認した。正式対応先は `github.com` のみで、代替提供元は製品へ登録しない。

共有起動の検証は、旧鍵用の試験専用プロセスから公開CLIのOAuth起動へ切り替えた。ループバック、公開Originの転送案内、自己生成TLS終端で、OAuthの接続先案内と旧鍵の拒否を確認する。共通リスナーは取消したMCP要求の終了を待つ。OAuth同意・トークン発行後の失効はServerの別試験で確認する。試験用TLS終端は運用Proxyや外部MCPクライアントの接続を証明しない。

D-17の起動排他は、同じ保存領域・別ポートの公開CLIを別プロセスで起動して拒否を確認した。保留中のMCP処理が終了するまでは再起動を拒否し、正常終了および待受開始前のポート競合ではロックを解放する。試験用に残したロックは起動側が消去しない。実運用の異常停止後の回復は確認対象に含めない。

C-8の責務整理では、アクセス管理は発行済みの保存領域からディレクトリを提示し、Serverが共通ロックで起動排他を取得・保持・解放する。ロック名・識別子とアクセス管理の短期保存排他は変更しない。発行されていない保存領域を拒否し、ロックを残さないこともローカル試験で確認した。

公開の共有MCPでObjectiveの初回Taskを許可した後に、同じ利用者がWorkbenchからログアウトしても取消は発行しない。新規MCP要求は拒否し、開始済み実行はAppのインストール資格で本人の権限を確認して次Taskへ進める。失効が確定した場合、または同じリポジトリIDの現在名と固定した接続先が食い違った場合は対象の実行を取り消す。合成GitHub応答と子の代役で確認した。実サービスへの接続や通信切断後の実行継続を示す証拠ではない。

ログイン保留とMCP同意前の状態は、確立済みの資格とは別枠にする。ログイン後のブラウザーセッションは、本人の確認後に同じ本人の枠を先に整理する。これは容量を分離する対策であり、送信元を識別した入口の受付制御や継続的な高負荷下での利用可能性の確認を代替しない。

D-21ではアプリ内の接続元IP別制限を追加せず、[共有の公開入口での運用手順](../../../19_Workflows/04_MCP_Server.md#shared-oauth-startup)に従い、リバースプロキシで頻度制限する。実運用のプロキシ設定・負荷は未確認。

D-10では、Google本人確認とHost管理CLIの一時待受をServerへ移管し、配布入口を `crdd-server` の初期設定・再紐付けモードに統合した。旧 `crdd-access-management` は互換入口を残さず撤去した。アクセス管理には確認済み主体を受ける保存操作だけを残し、Serverへの逆依存は追加しない。実Google・実Hostの対話による保存は今回の限定確認に含めない。

D-11では、管理セッションの開始・終了のHTTP受付を `transport/api-server.ts` に集約し、セッション表・有効期限・容量を `service/access.ts` に置いた。Cookie名、URL、管理権限の条件は変更しない。局所試験では、現在の本人を観測できない開始要求が503を返し、発行済みセッションを保持すること、明示終了で元Cookieが無効になることを確認した。

D-14では、AMの公開操作から役割別内容権限とリポジトリ公開範囲の読取り・更新を撤去した。本人の管理操作候補にも旧更新を含めない。利用者一覧と登録済みリポジトリ一覧の認可は維持し、旧二種類の読取り指定は保存領域を観測する前に拒否する。内部の旧保存形式と、その形式を利用する旧認可および試験はまだ残る。

共有MCPの内容要求は、Project、Topic／Meeting、作業領域、実行定義、実行状況を含め、Gitホストで本人の権限を確認する経路だけに接続する。未連携の利用者には旧公開範囲から内容を返さず、現在の管理権限に基づく管理読取りだけは独立して維持する。旧形式を使うHTTPの内部経路と保存処理はこの変更の対象外である。

本人照会はHTTP・MCPとも同じアクセス管理の読取りから、本人・ロール・改訂を返す。旧 `contentAccess` と `permittedRepositories` を返さず、Workbenchも旧フィールドを受理しない。個々の内容要求と、管理用の登録済みリポジトリ一覧は本人照会とは別の操作である。

HTTPのProject一覧・詳細、実行活動照会、Topic／Meetingの記録操作、Workspace、実行定義、実行の照会・判断・開始・再開・取消から旧Bearerとロール別公開範囲の経路を削除した。共有はブラウザーセッションとGitホストの実効権限、単体は起動リポジトリだけを使う。開始済みの実行を監視する条件は受付資格の寿命とは分離したまま維持する。Workbench表示、AI依頼、旧管理受付の経路とAMの旧保存処理は、この段階では残る。

共有WorkbenchのAI依頼を、ブラウザーセッションと対象Gitホストでの本人の実効権限に接続した。助言は読み取り、編集と編集の取消は書き込みを要求する。初回実行前までは受付資格と認可済みの対象を再確認し、開始後は本人・対象に結合した監視へ切り替える。現在表示の選択はブラウザーセッション、保存した依頼は本人と対象リポジトリに結び付ける。Objectiveのプロジェクト照合と書き込み要件は維持する。これは公開共有OAuth経路の接続であり、旧構成の試験などが使う内部の鍵受付・保存の撤去や実Providerでの確認は含まない。

D-01では、MCPが旧初回資格を確認保存して通常接続へ進める専用経路を撤去した。`server/discover` の通常の通信能力照会、ツール受付、OAuth同意は維持する。提示済みの旧初回資格でも照会・一覧を拒否して保存を行わないことを試験する。これはMCP側の初回限定接続だけの撤去であり、通常の旧鍵・Workbench・AM内部の撤去は残る。

旧鍵の発行・失効・交換・提示・初回確認・管理読取り・鍵方式初期化をアクセス管理のRootから外した。アクセス管理内の旧保存試験は宣言元を使い、旧初回資格を拒否するServer試験は提示済み状態を試験データとして与える。管理の保存故障と応答前切断は現行の管理RESTで検証する。再確認できない管理結果は公開せず、同期保存が成立した変更は保持する。旧内部の認証と保存形式の完全撤去は別途残る。

旧 `/api/access` の読み取りとForm書込みを廃止し、内容を受け付ける処理と専用の切断監視を削除した。利用者・登録リポジトリの管理は、現在の管理セッションを使うリソース別RESTに限る。旧管理URLは資格・保存状態を読み取らずに拒否し、共有APIの旧Authorizationヘッダーの拒否も維持する。以前の内部構成を使う内容閲覧の試験は、管理のHTTP操作を現行RESTへ移し、内容閲覧に必要な旧形式の登録だけをリポジトリ内の試験用データとして用意する。

現行の管理画面は、合成ログインを使う実ブラウザーで、招待・改名・ロール変更・改訂競合時の再取得・不明応答時の自動再送なしを検証する。共有Gitのブラウザー試験は、合成Gitホスト連携後に、登録0件の画面から登録し、同じリポジトリでステージ・解除を行い、登録を解除しても作業ファイルとHEADが残ることまで確認する。内容を読めるリポジトリが0件のときはポートフォリオを返さず、ログイン・管理画面を利用できる。実Gitホストおよびリモートへの書込みはこの検証に含まない。

共有のGit書込みから、従来のBearerとロール別公開範囲による代替経路を撤去した。共有のGit操作は、Cookieで確認した本人に対象への書込み権限がある場合のステージ・解除だけを表示し、要求時にも再認可する。単体の起動リポジトリでのGit操作と、まだ移行中の旧本文・AI依頼の内部処理はこの差分では変更しない。

### 切替前の基準

切替準備として、配布CLIでは現在の管理者がGoogleに紐付いていないHostの共有OAuth起動を拒否する。合成設定と試験用Hostを使ったCLI試験1件で、起動通知・保存変更・旧方式への自動切替がないことを確認した。アクセス管理の紐付け関連6件では、鍵方式で完了済みの状態から初回紐付けを保存でき、管理者の降格で起動条件を失うことも確認した。実Googleとの往復、実Hostの切替、旧鍵経路の撤去、変更後の全体回帰はこの結果に含めない。

共有Workbenchの人のログインはGoogleに寄せ、管理書込みには別途短命の管理セッションを要求する。共有HTTPのMCPも、v0.22で手入力の接続鍵からGoogleによる本人確認を経るMCP OAuthへ切り替える。管理専用の長期鍵は作らない。MCPのアクセス管理書込み6件は一覧・Schema・呼出しから除く。許可された読み取りと通常の開発操作を維持する。単体HTTP・stdioは今回のOAuth切替の対象外。既存のHost対話による接続鍵の交換は、旧経路の利用側調査と切替が終わるまで維持する。Gmail連携、Google以外のログイン、Listenerの外部公開、HTTPの全面REST化、実行中の子プロセスの失効通知方式はこの切替に含めない。

##### Workbenchの旧MCP依存撤去契約 — 2026-10-13

Workbenchの実行時依存にはMCP Server・旧CROS Packageを含めない。単体はRepositoryの専門Owner、共有は要求資格によるAM認可後に同Hostの専門Ownerへ直接接続する。Browser向けHTTP APIと独立MCP Serverの公開能力は維持する。

旧通信専用のJSON-RPC envelopeやTool写像試験は撤去する。現在認可・失効後の旧値非表示・未選択・別Root分離・CRUD／Relation・Profile・活動の検証義務は、直接経路の管理／Browser／本文／Git試験へ維持する。これは撤去候補の設計契約であり、回帰・独立レビュー・通常CLI・共有配置が完了したことを示さない。以下の旧Remote成立記録は現在の実装Owner／依存契約に使用しない。

##### 同一ホスト旧CROSの直接接続

内部Readerに続き、Serverの`localAccessRoot`構成と専用`/api/access/connection`を局所接続した。CROS起動は配布用Logo／固定JSだけを読み、起動RepositoryのContext／Topic・Meeting／Profile Catalog／活動Readerを構成しない。未認証GETは非秘密access Model、接続POSTは確認後200の閉じたJSON（status: completed）だけを返し、通常読取りは次GETが現在資格で取得する。共有Browserで主体が混ざらないよう、CROSの通常要求は一つのAuthorization HeaderのBearerから当該要求だけのAM Contextを構成し、Server全体にログイン鍵・本人投影・接続Noticeを保持しない。重複・不正・欠落Headerは資格なし、不成立・状態不明は本人／内容非表示とする。Action Tokenは共通の用途限定入力条件であり認証ではない。各要求で現在資格と操作認可を取り直し、Aの接続をBの資格へ転用しない。切断はBrowserが鍵のmemory参照を捨てる操作で、他Browserをログアウト・資格失効させない。既存の同Process管理／鍵操作へ接続するが、Browserのmemory保持／Header送信はSource接続と鍵管理／接続の局所実Browser確認済みで、選択Repositoryの全内容入口はまだ未接続で、起動Rootへのfallbackをせず拒否する。この拒否は完成ではない。公開CLI、実Browser・共有TLS配置・全入口の終了保証は未完了であり、管理画面や局所HTTP成功からWorkbench全体成立を表示しない。

Local接続の完全Formは同Origin・Host・Content-Type・Body容量をHTTP Ownerが検査した後、`transport/api-server.ts`の`authenticateLocalConnectionForm`で検査し、受付済みの資格を`service/access.ts`の`confirmLocalCredentialConnection`へ渡す。許可fieldはactionToken／operation／tokenだけで、重複・未知field・用途差・取消は認証前拒否する。初回限定資格は既存AM確認保存へ接続し、出版完了後のfreshな通常認証に成功した場合だけ当該要求memoryの接続資格を返す。初回相関を内容Authorityへ変換しない。保存後取消は保存取消ではなく応答停止であり、次要求が現在状態を再確認する。内容操作は別途要求ごとに現在認可を取り直す。鍵・Rootは通常Model、URL、log、Browser Storageへ含めず、新Session保存は作らない。専用Local HTTP POSTは局所接続済みで、資格を完了後に保持しない。次要求は単一Authorization Headerでfresh認証する。Browser memory／Header送信はSource接続と鍵管理／接続の局所実Browser確認済みで、公開CLI、共有TLS配置、全内容入口は未接続であり、全体完成の根拠ではない。

旧鍵の接続POSTと、その応答を確認してタブ内に鍵を保持する方式は撤去した。旧方式の実ブラウザー確認は履歴であり、現行の共有ログインの実環境確認に流用しない。

##### 切替途中のCSR画面遷移

選択RepositoryのGET接続では、今回AMが確認した一つの短命許可集合から選択Root・Portfolio・同ProjectのTopic／Meetingを構成し、ContextのRepository／Project IDとmanifestを相関する。Surface・本文・一覧・Relation・Git観測とModel構築後の公開直前に、既存AMで全Rootを再観測し、管理改訂とRepository ID／Binding／manifest全契約field／workspaceIdsの正規化全集合がexact一致する場合だけ応答する。差異・不明・取消は旧内容を部分公開せず固定拒否とし、その照合後に外部I/Oを追加しない。repositoryIdは0件またはexact1件だけ受け、空1件は選択解除、重複は認証・AM・Root本文観測前に拒否する。新Session／Lock／Cacheは追加しない。起動Rootや前要求の結果へfallbackせず、直前操作・AI／Candidate結果は要求専用のnullとする。共有側Profile情報の`aiProfiles: null`は未取得を表し、0件・不存在・利用不可を意味しない。Inspector、一覧表示とAI依頼入力は同じnull意味を保持し、単体の既定Catalogを維持する。内容POST接続まで共有側の内容保存Formを無効化する。この途中GET接続は保存・本文リンク・共有配置の完成ではない。

##### Workbenchの旧鍵操作と結果搬送

WorkbenchとServerは旧鍵の発行・失効・交換をHTTPで受け付けなくなった。旧管理状態の自動変換や鍵の再提示は切替の対象外とした。

意味の正本は[Access Management詳細](../../../06_Architecture/Details/access-management/01_Architecture.md)である。Workbenchは同一Processの人間向け入力・表示と結果搬送だけを所有し、資格Store、認可、交換Recoveryを複製しない。Workbenchに別Process接続を持たない。独立MCPのBearer認証はMCP Serverが所有し、鍵操作を公開しない。

| 操作 | 処置前の対象・条件 | 結果と禁止する読み替え |
|---|---|---|
| 通常発行 | 現行administrator、既存userId | 新Secretを一回だけ表示。旧資格の失効0、交換Recovery0。表示名は認証根拠にしない |
| 独立失効 | 現行administrator、exact資格IdentityとuserIdの結合 | 指定資格だけを処置。他の資格への拡張0、発行0、Secret0、交換再入場0 |
| 指定ユーザー交換 | 現行administrator、既存対象userId・表示名、旧資格全体の失効範囲と既存発行先を処置前表示 | 同じユーザーへ一回発行。他ユーザーを保持。通常入口では追加確認Gateを要求しない |
| 全ユーザー交換 | 現行administrator、操作主体を含む失効範囲と指定した既存administrator発行先を処置前表示し、明示確認 | 全旧資格を失効、指定発行先へ一回発行。他ユーザーの再発行は通常管理で行う |

Hostの交換2操作はWorkbench Backendで実行せず、信頼したログイン済み操作者の対話CLIとして別入口へ案内する。追加認証・昇格・確認コードを設けず、既存Root／Path検証を維持する。交換の入口2種×操作2種の全4組で対象・影響を表示し、Hostの2組と全ユーザー交換の通常入口の計3組だけ明示確認する。この確認契約を通常発行・独立失効へ拡張しない。初回Host設定は通常交換とは別契約で、以下の案内境界へ接続する。

交換ではAccess Managementが旧失効前から同じexact Recovery IDへ結合する。失効・新発行・結果記録・提示結果を別事実として表示し、後段失敗だけで確認済み発行をunknownへ戻さない。通常の秘密は用途限定・短命なbackend応答から操作administrator画面へ一度だけ提示し、追加受領ボタンを設けない。対象本人への安全な引渡し・受領は製品外で観測しない。Secretの保存・再送・再表示、一般MCP／DTO・一覧・履歴・Log・Evidenceへの公開は0。次の3分岐を表示し、通常発行／独立失効に交換Recoveryを付与しない。

| 現在確認できる状態 | Workbenchの表示・導線 | 禁止する表示・操作 |
|---|---|---|
| 発行または非秘密結果記録が不明 | Credential IDとは別の非秘密な元発行Identityと既知事実に基づく現在再観測へ案内。交換由来だけ元のexact Recoveryを維持 | 成功／rollbackへの丸め、新交換の開始、通常発行への交換Recovery追加 |
| 発行・結果記録確定、提示・引渡し未確認 | 「発行済み・受け渡し未確認」と表示。本人受領は観測外。現在許可されたadministratorが既存指定／全員交換を明示選択する。新交換は別Operation／別Recoveryで、各交換内だけ同じexact Recovery | 確定未受領の断定、確定発行の不明化、秘密再表示・自動再発行、別交換成功を旧受領・rollback・取消完了と表示 |
| 現在administratorとして接続できない | 既存ログイン済みHostの交換2操作へ案内 | Workbench認可迂回、Hostへの通常発行・独立失効・追加認証の追加 |

別交換では現在対象・認可と4組の事前表示／3組の確認を再適用する。指定交換は先の鍵を含む対象ユーザーの全旧有効資格→同じ既存userIdへ一資格、他ユーザー保持。全員交換は先の鍵を含む全旧有効資格→指定既存administratorへ一資格、他ユーザーは通常再発行・再配布となる。旧元発行Identityと確定事実はAMが保持し、Workbenchは旧処理との相関を失わない。遅延した旧応答の失効済み鍵を利用可能と表示しない。

未知対象、必要な既存administratorの不存在、認可破損または安全な観測不能は処置前に停止する。userId／username／Role／Role詳細権限／Repository登録／Product Dataは交換で変更しない。資格状態は旧失効・新発行によって変わる。管理者であることから内容参照を許可せず、他ユーザー情報の表示も現在の参照許可に従う。ユーザー・Role内容設定・Repository登録／Exposureの管理はARCH-000013の9 Role分担行に従い、Role内容設定から管理権限を生成しない。Repository AI設定管理はmanager／administratorと選択Repositoryのdevelopment認可へ接続する。資格管理と内容許可は別契約のまま維持し、実認証・人間操作確認は後続Gateとする。

論理初回接続とv2目標SchemaはAM保存設計へ具体化済み。具体画面配置、公開API・結果Field、提示観測の実装／実境界・移行・本番接続は未成立。SCR-000008／BHV-000012／`PRT-000008.spec-000012`への接続はPartialである。Qualityは通常発行の失効0・Recovery0、独立失効の対象限定・発行0、交換4組表示／3組確認、鍵3分岐、元Identityと別交換の区別、MCP鍵操作0、Secret再表示0、遅延失効鍵の利用案内0、後段失敗時の既知事実保持をIT／STで導出する。ここでQA Local Item IDを推測して発行しない。旧伝播候補の限定Passは履歴。今回の最小提示方式の差分は限定再レビュー済み（最小鍵提示方式の伝播差分、全重大度0）で、QA実行済みではない。

###### 同一プロセスの旧管理POST

管理依存は構成ごとに分離する。Standaloneの限定内部DIは信頼済み構成の検証済みAM Root／Bearerを使用する。Local CROSは内部構成のAM Rootと、当該要求の単一Authorization HeaderのBearerを使用し、要求外のログイン鍵として保持しない。両構成および旧Remote接続の混在を拒否する。AM保存RootはBrowser入力から取得しない。Repository登録の対象Rootは別の明示操作入力であり、管理認可と対象Root／manifest検証を必要とする。一覧と各操作で現在認証・認可を取り直し、一覧の操作表示を実行許可として再利用しない。

| 境界 | 具体契約 |
|---|---|
| 非秘密一覧 | AMの同改訂SnapshotからユーザーのID・表示名・Role、資格のID・元発行ID・失効・提示状態、現在交換相関だけを投影する。秘密・Verifier・Salt・内部Rootは返さない |
| 鍵管理の受付 | Google設定時は短命管理セッションで `GET /api/credentials`、発行 `POST /api/users/{userId}/credentials`、失効 `DELETE /api/credentials/{credentialId}`、指定交換 `POST /api/users/{userId}/credential-exchange`、全員交換 `POST /api/credential-exchange` を利用する。書込みは同一Originの閉じたJSON・操作トークン・現在改訂・操作別の対象を要求する。旧接続鍵によるフォームと汎用画面からの資格一覧は無効。Google未設定時は既存のフォーム受付を維持する |
| 鍵提示 | 保存と`unconfirmed`記録の後、`no-store`の専用JSON一応答へ鍵を入れる。応答の`presenting`は出力開始の結果で、本人受領・提示確認・交換完了ではない。汎用`/api/workbench/view`へ鍵や直前の鍵応答を保持しない |
| 提示後 | 所有Responseの全byteの`finish`と先行故障なしを確認してから、元発行相関の`confirmed`を別保存する。HTTP終了はBrowser描画・コピー・本人受領の証明ではない。切断・取消・故障では確認や交換終了を進めず、自動再送しない |
| 交換終了 | Google設定時は開始時の同じ管理セッションを使い、新しい鍵を認可に流用しない。確認済みの前回記録を閉じるときは回復ID・発行先・交換範囲を照合し、新たに発行しない。Google未設定時の本人指定交換・全員交換は当該要求で発行した鍵を短命に使う。どちらも現在の管理権限・改訂・交換相関・提示確認を再評価し、失効・変更・不明なら記録を保持する。Host終了入口への迂回は行わない |
| Server終了 | 開始した管理要求と提示後処置を終了待機へ含める。画面用応答の任意保存を終了条件に追加しない。秘密は当該要求の短命値として解放し、新しいSession／Receipt／Recovery Storeを作らない |

旧CROS管理依存・Form・Client Modelの資格部分は、新Serverと同時配布するCSRへ一斉切替する内部契約変更である。旧形式の互換受付・秘密再取得は設けない。本人交換・全交換で接続に使用した旧鍵が失効した場合は、新しい鍵での明示接続が必要であり、応答成功から旧接続の継続を表示しない。

同Process注入による接続は、局所HTTPの出力／後処置故障と、実Browserの通常発行・本人交換・全交換の短命表示・消去・再読込・旧接続失効まで評価済みである。この限定範囲の独立再レビューは残指摘0。公開Launcher、通常接続切替および正式Local Item評価は未完了であり、Workbench資格管理全体の完成を主張しない。

##### 旧公開範囲を使う管理画面

旧方式では登録と公開範囲を関連付け、登録解除時に両方の除去を確認した。公開範囲だけを変える操作と、マネージャー自身の内容範囲設定もあった。いずれも廃止し、現行は管理ロールとGitホストでの本人の実効権限を分ける。

## 実装と切替の順序

以下の初期計画と途中経過には、旧鍵との併存や旧範囲を含む当時の判断がある。現行の採用範囲は冒頭を、公開契約はREQ-000041を参照する。途中経過は現行仕様として再利用しない。

1. アクセス管理の紐付けと現在認可、初回・再紐付けのHost手順を定義する。既存状態を自動変更せず、旧Bearer利用者を管理用に自動認定しない。新規Hostの既存初回接続確認はGoogleログインで代用しない。既存管理者を対象に、旧経路を閉じる前の切替可否を確認する。
2. Server／Workbenchに、Googleログイン開始・コールバック・管理セッション・ログアウトを接続する。標準の認可コード方式を利用し、ログイン開始と同じブラウザーに結び付けた一度限りの照合値、PKCE、IDトークンの署名・発行者・対象クライアント・期限・nonceを検査する。Google APIのアクセス権やオフライン権限は要求せず、取得したGoogleトークンを永続化しない。秘密の設定値は追跡ファイル・画面・ログへ出さない。
3. 共有MCPに認可サーバーを組み込み、対象クライアントで認可サーバー発見、ログイン、MCPリソース指定と対象違い拒否、現在認可、期限・失効、旧接続鍵からの移行を確認する。ブラウザーセッションの発行・Cookie処理へMCPのトークン発行や検証は載せない。
4. Google経路と既存管理者の再入場が成立した版で、Workbenchの旧Bearerによる管理書込みとMCPの管理書込み6件を閉じる。現行MCPの保存結果・取消・応答喪失の試験は、対応する保証をWorkbenchまたはアクセス管理の正式入口へ移し、旧Toolの直接呼出しが書込み0で終わる試験に置き換える。共有MCPの旧接続鍵はOAuthによる実クライアント接続の成立と既存利用側の移行確認後に閉じ、単体モードや別用途の既存鍵を巻き込まない。
5. [REQ-000041](../../../01_Discovery/Definitions/REQ-000041/requirement.md)、Server／Workbench／MCP・アクセス管理の設計、利用案内、設定例、試験と品質台帳を同じ版へ追従させる。固定候補で技術独立レビュー、文書監査、不足／影響監査を行う。CRDDの準拠基準は変更しない。

共有MCPの管理書込み6件は、OAuthと既存の鍵接続の両方で廃止する。本人照会と管理読取りの現在認可は維持する。従来MCPで確認していた管理保存の失敗・確定後の応答喪失はWorkbenchのHTTP境界で確認する。Workbench側の管理書込みをすべて短命管理セッションへ切り替える作業とは分けて追跡する。

Google設定時の通常管理フォームでは、短命管理セッションによるリソース別HTTPを使う。招待・再発行・GitHub付き登録、表示名、ロール、ロールの内容範囲、公開範囲、リポジトリ登録解除が対象となる。画面では各一覧の改訂を共通化せず、元の対象と一緒に保存処理へ渡す。Google未構成の運用と、Hostの初期設定・回復は維持する。

鍵管理は、Workbenchから短命管理セッションを使うリソース別HTTPに切り替えた。Google設定時は旧フォームによる操作と旧表示からの資格一覧を提供しない。交換で旧接続鍵が失効しても、提示確認・交換終了に新しい接続鍵を認可材料として使わない。開始と保存の認可はアクセス管理（AM）が保持し、サーバーは結果の公開前と鍵の送信完了後で同じ管理セッションと現在の管理者権限を確認する。鍵の再表示・自動再実行は行わない。

Googleに登録するコールバックは、ブラウザーが到達するOriginと完全一致させる。固定ポートのloopbackと、既存設定を使う共有HTTPS Originを区別し、任意Originの受付や新しい外向きListenerは設けない。実Google確認の前に対象Originと登録済みクライアントを確定する。参考: [Googleログイン仕様](https://developers.google.com/identity/openid-connect/openid-connect)、[Googleのリダイレクト先検査](https://developers.google.com/identity/protocols/oauth2/web-server#uri-validation)。

本人確認には `openid-client` 6.9.1を使う。最初の実装範囲は、固定したGoogle発行者への認可コード方式と、署名検証を通った外部主体の取得まで。本人確認結果だけでCRDDセッションを発行しない。既存のHTTP・MCPの入口、保存物およびGoogle側設定はこの段階では変更しない。

HTTPクライアントセッションはServerが発行し、Workbenchは現在の利用クライアントである。検証済みの発行者・主体識別子と、AMが確認した利用者・紐付けIDだけを使う。Google固有のIssuerやトークン検証はGoogleのログイン入口に置き、セッションの発行・解放はGoogleの実装型へ依存させない。別のログイン提供者を追加するときは、提供者別の本人確認・設定と、AMの保存済み紐付けを発行者と主体の組へ拡張する。v0.22では複数提供者の登録台帳や実行時プラグインは設けない。MCPの接続資格とセッションはこのHTTPクライアントセッションから分離する。

同じブラウザーで有効なCRDDのログイン状態があり、現在の利用者への紐付けを確認できる場合、MCPの認可画面でその本人確認を再利用する。MCPクライアントへの初回の利用許可は本人確認とは別であり、適切な要求・対象・許可なしにトークンを発行しない。別ブラウザー・期限切れ・紐付け失効時は、必要に応じてGoogleログインからやり直す。本人確認の再利用で管理書込みの許可をMCPへ移さない。
