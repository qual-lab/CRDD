# Coordinatorの実行記録・回復方式の縮小計画

成果物種別: CHG設計検討記録。
状態: 設計案。開発PCの旧状態リセットは完了。製品の回復契約、保存方式、ローテーションと移行は未実装。
対象: CHG-000082で扱うCoordinatorのDocker実行、回復、終了記録と保存領域。

## 1. 結論

現在の実行・未解決の回復に必要な状態と、診断・終了履歴を分離する。終了した操作の多数の段階Fileを永久保持せず、簡潔な終了要約へ収束させる。過去履歴の量や不一致を、新しい実行の停止理由にしない。

全Operationを一つの巨大JSONへまとめるのではなく、回復に必要な現在状態を少数Fileへ集約する。通常診断はローテーション対象とし、診断だけのためにOperationごとのDirectoryを作らない。

Docker実行環境は再利用して復元するのではなく、必要な清掃後に新しい実行単位として作り直す。ただし、使い捨ての実行環境でも残存資源の回収は必要である。

この記録は縮小の全体計画であり、Architectureの第二正本ではない。採用した内容はCoordinator／Runtime Dataの詳細設計とQualityの検証設計へ反映してから実装する。今回の計画更新だけで保存Schemaや保護されたRootの変更を採用済みと扱わない。

## 2. 保持の分類

| 種類 | 保存する意味 | 終了・清掃 |
|---|---|---|
| 認証・署名・送信同意・設定 | 現在有効な設定と許可 | 現行Ownerが管理する。ログ清掃では削除しない。 |
| 現在実行・未解決回復 | Owner、Identity、対象資源、未確定Effect、次の処置に必要な状態 | 解決するまでは保持する。件数・時間だけで消さない。終了後は稼働一覧から外す。 |
| 利用側へ未搬送の完了結果 | 結果を渡すOwnerと受理するConsumer | 受理確認後に現在状態から外す。未受理結果をログだけへ落とさない。 |
| 診断・終了要約 | 最初の失敗、後続清掃結果、過去unknown、終了分類、相関参照 | 保持期間・件数・容量を設定し、上限内でローテーションする。操作許可や稼働根拠にしない。 |
| 正式な検証Evidence | 改訂版、検証結果、観測範囲 | 検証Ownerへ保存する。RuntimeStateへ全文複製しない。 |
| Workspace・候補 | 作業中の入力と未採用成果物 | 候補Ownerへ引渡した成果物を保全してWorkspaceを清掃する。未解決回復と混同しない。 |

## 3. 現行実装から確認した縮小対象

| 対象 | 現在の保存・利用 | 予定処置 |
|---|---|---|
| Docker Taskの段階記録 | submission、receipt、Host、Lease、absence、restart等の多数JSONと伴走commit | 必要な再入場情報を現在状態へ集約する候補。更新途中の一時物を短命にする。 |
| 正常Task終了 | 既存finalizeがOperation Directoryを削除する | 新しいGCを重ねず、保持分岐と全利用側の終端接続を確認する。 |
| Project Runtimeへの回復引渡し | acknowledge／finalizeとReceipt／tombstone回収 | 未受理の結果を消さず、受理済みの記録だけ確実に回収する。 |
| Claude認証settled | 完了後も記録を保持する経路 | 認証自体は保持し、終了記録を小さな診断要約へ移す。 |
| Docker Desktop修復 | 段階ごとの記録、閉鎖・保持済み履歴 | 終端後の圧縮・廃棄を定義する。使用中の再入場・参照根拠を先に評価する。 |
| 完了済み回復Receipt | 上限拒否と一部利用側の回収 | 誰が完了を消費するかを対応付け、上限到達が不要な停止を引き起こさない終了契約にする。 |
| 通常診断 | 複数の実行単位に分散 | 秘密値を含まない構造化ログへ統合し、容量・保持上限を設定化する。 |

根拠OwnerはCoordinator／Runtime Dataの詳細設計。Source上の主な接続は`docker-recovery-runtime-internal.ts`の許可記録名、正常finalize、Project側acknowledge／finalize、`docker-recovery-journal.ts`の保存確定である。Sourceを新しい設計の正解として採用せず、保持する保証から要否を再評価する。

## 4. 回復の完成条件

新規実行の安全性、過去Attemptの終了分類、物理清掃を別々に評価する。過去unknownを成功へ変更しないが、閉じた過去履歴だけで新規実行を永久停止させない。

今回の認証Container作成前停止に対する退役候補は、旧Ownerが以後startを発行できないことと、遅延createがあっても実行開始しないことを確認した限定案である。Provider実行後、外部送信不明またはwrite可能な共有Mountへ一般化しない。再起動を通常の終了証明として一律要求せず、必要な終了境界を他の方法で確認できない場合だけ停止範囲を特定する。

現在の開発PCは人間指定により旧状態をリセット済みだが、製品利用側の未解決回復を移行時に一律削除する方式にはしない。

## 5. 実装・確認の順序

| 段階 | 成果 | Gate |
|---|---|---|
| 1. Contract確定 | 保存Producer／Consumer全数分類、成立済みCapability対応、縮小後の終了・保存契約。 | 保持する保証、利用側、現在の人間判断を説明できる。 |
| 2. 最小の回復是正 | 終了済み参照と現在使用中の分離、一次失敗の保持、既存の終了・候補引渡し・GC接続。 | 今回の停止ケースを局所再現し、安全な再開と拒否の両方を確認する。 |
| 3. 保存縮小 | 現在状態、終了要約、循環ログ、旧形式移行。 | crash、競合、未受理結果、候補保全、上限到達を局所・利用側結合で確認する。 |
| 4. 固定候補確認 | Formatter、型、Lint、必要な回帰、Architecture／Quality独立レビュー。 | 必須の未解決Gapがなく、公開入口から実境界まで接続している。 |
| 5. E2Eへ復帰 | 必要な署名候補で既存E2Eを実行する。 | 再現性のある失敗だけを分類して是正する。回復機構の追加自体を完成目標にしない。 |

保存方式全体の完成を待って原因不明のE2Eを繰り返すのではなく、段階2で今回の詰まりを先に確認する。署名対象や外部送信境界が変わる場合は、その時点で必要な人間操作・許可を示す。新しい清掃Frameworkを先に作らない。

保持する保証は、Effect前の必要な確定、書込み破損の拒否、未解決義務の保持、再入場の冪等性、一次失敗と清掃結果の分離、認証・候補・Evidence保全である。専用DB、新しい常設サービス、汎用強制削除、OS再起動の常態化は目的外。

## 6. 必須の反証

正常、失敗、取消、親Process喪失、書込み途中・終了直前のcrash、清掃の再実行、Project側acknowledge前後、候補保持とWorkspace削除、ログ上限到達を確認する。診断ログを失っても回復制御状態が失われないこと、終了履歴を消しても現在の稼働判定が変わらないこと、観測不能を不存在へ畳まないことを確認する。

| 観点 | 確認する反証 |
|---|---|
| 正常・異常・取消 | 終了したのに使用中参照が残る。一次失敗が清掃結果で上書きされる。 |
| 親Process喪失・遅延create | 観測時点の不存在だけで安全と判定し、旧Ownerが後からEffectを発行する。 |
| 保存確定 | Effect前後・終了直前のcrashで義務や結果が失われる。 |
| Consumer | acknowledge前に結果を消す。重複受理で回復が再活性化する。 |
| 候補・認証 | Workspace清掃がPatch、認証、署名鍵、同意、Evidenceまで削除する。 |
| ローテーション | 上限到達で未解決義務を削除する。診断欠損が回復成功やAuthorityになる。 |
| 再入場・移行 | 二重Writer、旧記録の無条件廃棄、清掃再実行による別対象削除。 |
| 完成主張 | 現在一覧が空であることを、過去Effect不存在や全E2E Passと表示する。 |

## 8. フォルダ・ファイル構成案

### 8.1 Repositoryに属するCoordinator実行状態

Repository固有のTask現在状態、回復、未搬送結果、診断は、検証済みRepository Rootの`.crdd/coordinator/`へ置く。以前の「Coordinator実行制御全体をAppDataへ置く」案は撤回する。Dockerを使うことだけでRepository外へ保存しない。

```text
<repository-root>/.crdd/
└ coordinator/
   ├ state.json
   ├ state.lock
   ├ state.pending.json    # 保存中だけ。異常残存は保存Ownerが処置
   └ history.jsonl         # 上限付き終了要約・最小診断
```

| 配置 | 意味 |
|---|---|
| `coordinator/state.json` | `activeOperations`、`unresolvedRecoveries`、`pendingDeliveries`を中心とする現在状態の閉集合。履歴・診断・Evidenceを追加し続けない。 |
| `coordinator/state.lock` | 状態更新用の実排他。Fileの存在だけで使用中と判定せず、取得・所有・解放を実観測する。 |
| `coordinator/state.pending.json` | 保存確定のための短命な一時物。crash後の判定・清掃条件を持つ。 |
| `coordinator/history.jsonl` | 終了要約と最小限の診断。件数・期間・byte上限を有限にし、実行や回復を許可する根拠にしない。 |

Coordinator側のRepository単位の単一Writerを採用方針とし、排他取得後、同一Directoryの`state.pending.json`への保存・確認と`state.json`への置換を第一候補とする。保存確定、crash後の再入場、二重起動の拒否を実環境で確認する。atomic replaceを耐久確定と同一視しない。複数ConsumerはこのWriterへ接続し、新しい複数Writer用Lock Frameworkを作らない。

`state.pending.json`は状態更新の内部処理であり、`tmp/<operation-id>/work/`は展開・変換・比較等の再生成可能な作業領域である。更新途中の状態を一般的な一時物として削除しない。残存pendingがある場合は新しい保存で上書きせず、排他下でSchema、Identity、元世代・新世代と現在値を照合して再入場する。既存の`tmp/.operations/.staging/`は別契約の配置であり、今回の名前合わせでは変更しない。

状態更新用の排他を、AI実行中・人間判断待ちの全時間へ延長しない。長時間処理の所有・予約は現在状態で表し、各更新の直前に世代と所有を再確認する。Lock Fileが古いという理由だけで奪取・削除しない。OSの排他保証と異常終了時の解放を確認するまで`state.lock`を実装済みと扱わない。

終了情報は同じOperation／仕事Identityと終了世代へ結び、終了要約の保存確認後に現在状態から除去する。保存確認前に除去しない。要約保存後・除去前のcrashでは同じ終了を二重記録しない再入場を設計し、本文履歴の再生からAuthorityや仕事状態を復元しない。保持上限による履歴回収と同じ未搬送終了情報が衝突しないよう、状態更新と履歴更新を既存Ownerの同じ排他範囲で順序付ける。

`state.json`はTaskの再開情報であり、編集した内容からOS操作の許可が自動的に生じるものではない。資源処置前には署名済みRuntimeが対象Identity、所有関係、現在状態を確認する。Repositoryの移動・削除、worktree差、複製された状態を別の実行として誤採用しない条件を設計する。

新設名はASCII小文字`kebab-case`、新しい設定キーは`camelCase`とする。既存の契約値・Identity・公開結果は名前を揃えるために変更しない。履歴は一つの`history.jsonl`を上限内へ縮める方向とし、世代別DirectoryやFileを恒久追加しない。履歴再書込みの短命Fileが必要な場合は、具体的な保存確定契約へ明示して終了後に回収する。四つの通常名だけで、更新途中Fileすら一切存在しないという保証にはしない。

現行の保護領域へ保存する契約からの変更を伴うため、Runtime Data／Coordinator／Platform Accessの正本と利用側を同時に改訂する。Path置換だけで旧保護保証を撤去しない。

### 8.2 Repository内の成果物・一時領域

```text
<repository-root>/
├ .crdd/
│  ├ coordinator/recovery/host-terminal/  # 既存の利用側接続。Authorityではない
│  ├ project-runtime/                    # 既存の状態・結果・決定・回復Owner
│  ├ candidates/<candidate-id>/          # 未採用成果物と候補の回復
│  ├ verification/<verification-id>/
│  │  ├ started.json
│  │  ├ result.json
│  │  ├ complete.json
│  │  └ artifacts/
│  └ tmp/
│     ├ .operations/                     # 現行の一時操作管理
│     └ <operation-id>/work/             # 必要な実行隔離。終了後清掃
└ 99_Roadmap/Changes/CHG-000082/Evidence/  # 正式検証記録
```

これは関係する既存配置の抜粋であり、空Directoryを全て作る指示ではない。`.crdd`直下へ診断Markdownや回復JSONを置かない。OS資源の操作AuthorityをRepository内のファイルへ移さない。Execution Intelligence、Release、Communication、CROS等の別Ownerの保存構造も、この縮小を理由に統合しない。

実装は既存の`40_Develop/coordinator`、`40_Develop/platform-access`、必要なProject Runtime利用側へ置く。`template/tools`は入口と設定を維持し、新しいログサービスや回復Subsystemを増設しない。

`coordinator/recovery/host-terminal/`は現行の接続であり、刷新後の必須Directoryを意味しない。単一状態へ搬送できるかを確認して廃止・移行を判断し、同じ回復の第二正本として残さない。

### 8.2.1 Project Runtimeとの責務・引渡し

2026-10-05の人間確認でProject Runtimeも共通構成へ計画更新した。2026-10-06現在は一体state、lease終了、結果受理後整理、30日期間historyと受付世代を本番へ接続し、旧記録をフロントAIが保全確認後に清掃した。本番保存Port接続・移行未実施という当初表示は履歴に限定する。[②の現在結果](261005_project-runtime-phase2.md#35-最終署名候補と全回帰の処置)を参照する。Candidateの7日保持実装とCoordinator記録縮小は②の成立へ含めない。

| 保存Owner | 所有する状態 | 所有しないもの |
|---|---|---|
| `.crdd/project-runtime/` | 依頼、待ち行列、仕事全体の進行、受理済み結果、人間の判断、候補採用・統合とその回復。 | 個々のProvider実行資源の制御状態と清掃の第二正本。 |
| `.crdd/coordinator/` | 個々のAI実行、取消、資源回収、未解決の実行回復、結果引渡し。 | 仕事全体の待ち行列、人間の採用判断、受理後の結果履歴。 |
| `.crdd/candidates/` | 候補Patch等の本体、由来、候補固有の適用・破棄・回復。 | Providerの稼働状態と仕事全体の進行。 |

Project Runtimeが依頼し、CoordinatorがAI実行と必要な回収を行い、その結果をProject Runtimeへ渡す。AI実行の終了と、人間の採用・統合を含む仕事全体の完了を同一視しない。結果搬送と清掃の完了は独立に評価し、清掃未解決を隠して仕事全体の完成を主張しない。

`pendingDeliveries`は未受理の搬送状態だけを保持する。Consumerが同じ結果Identityを耐久的に受理したと確認した後、Coordinator側から搬送状態を除去する。受理前のcrashでは再搬送し、受理後・除去前のcrashでは重複受理を安全に処置する。両方へ同じ結果履歴を永久保存しない。搬送完了でも残る実行回復義務は別に保持する。

Coordinatorの直接利用も維持し、Project Runtimeへの依存を必須化しない。直接利用のConsumerについても、結果の受理・終了接続を明示する。Project Runtimeがいないことを理由に未搬送結果を永久保持したり、無条件に捨てたりしない。

| CROSの登録・横断状態 | CROS専用OS Root。 | CRDDのRepository状態やCoordinator履歴を混在させない。 |

署名は固定された配布Runtimeを検証するためのものである。変化する`state.json`、JSONL、候補Patchへ毎回Release署名を求めない。保存確定と読取り時検証は、Release署名とは別の契約として実現する。秘密鍵をAppDataへ移すことや、新しい署名鍵を作ることも今回の方針に含めない。

現行`RuntimeState`と`CandidateStore`は切替前の整理対象であり、刷新後のTask状態・候補の第二保存先として残さない。旧記録はフロントAIの切替前確認・清掃対象とし、Runtimeへ旧形式の互換読取りを残さない。必要成果物・未完了参照は別Ownerで処置する。Repository外に残す最小項目が確定するまで、新しいAppData配置Treeを採用済みとして示さない。

## 9. 縮小後の回復判断

| 現在の状況 | 処置 | 完成条件 |
|---|---|---|
| 対象と所有者が確定し、通常回収できる | 既存の停止・回収・結果搬送を自動で完了する。 | 必要な実資源の不存在、結果受理、現在一覧からの除去。 |
| 過去結果はunknownだが、安全な分離を確認できる | 過去unknownを保持した終了分類へ移す限定経路を評価する。例外判断が必要な場合だけ人間へ返す。 | 旧Ownerが新しいEffectを発行できないこと、遅延要求の影響、旧領域非再利用、候補・Evidence保全。 |
| 使用中・対象不明・観測不能が残る | 新しいEffectを止め、不足する観測を示す。必要なら既存の限定再起動を選ぶ。 | 不明を不存在へ変換しない。具体的な未確認Riskが解消するまで停止する。 |

人間が普段意識しないファイルを毎回承認させる方式にはしない。自動処置できる既知の範囲は自動化し、リスク受容・新しい破壊的操作・対象の不確定だけを人間判断へ戻す。

unknownの終了経路は今回の限定Recovery Classとして実装する。Provider本体起動前、外部送信なし、共有書込みEffectなし、旧OwnerのEffect不能、遅延createの無害化、現在実資源不存在を全て確認できるケースに限る。他ケースへの一般化は別の実例・反証後に判断する。

回復は通常のHuman Surfaceへ露出させず、既知の範囲はバックグラウンドで解決する。自動処置不能の場合だけ、「再認証」「Docker再起動」等の必要な具体操作と影響を示す。承認が必要な操作はその境界を維持する。大量の未解決回復を管理するUIを新機能として増設せず、Runtimeの不具合として是正する。

回復一覧と使用中一覧は、終了済み参照を含む過去集合と現在の生きた所有者集合を区別する。比較方法は防ぐRiskから導き、完全一致を部分一致へ機械置換しない。

## 10. 失敗・終了結果と保持上限

| 記録 | 必須の意味 |
|---|---|
| 最初の失敗 | 段階、理由、相関参照。後続失敗で置換しない。 |
| 後続失敗 | 清掃・搬送等の段階と理由。件数上限と省略件数を持ち、必須の未解決義務は省略しない。 |
| 清掃 | 完了／未完了／観測不能、対象と終了後の観測。 |
| 回復 | exact Identity、残る義務、次の処置、利用側への搬送状態。 |
| 最終状態 | 成功、失敗、取消、過去結果不明の終了を区別する。全体Passへ丸めない。 |

外部境界では要求前、要求発行、受理、結果応答、耐久記録を区別する。Provider生出力、認証値、Prompt本文を診断へ複製しない。相関に必要な最小情報だけを保持する。

循環ログの各イベントは、UTC・タイムゾーン付きの時刻、操作Identity、イベント順序を持つ。同時刻のイベントを時刻だけで並べない。所要時間は単調時計で計測し、日時との差から代用しない。発生時刻を取得できない場合は記録時刻と区別し、推測で補完しない。

| 対象 | 上限到達時の扱い |
|---|---|
| 終了診断 | 単一の`history.jsonl`を件数・保持期間・容量の上限で循環させる。世代別の履歴ファイルを蓄積せず、起動時に履歴再生しない。 |
| 現在実行 | 同時実行の許可範囲を超えた新規処理を停止する。既存処理を容量対策として捨てない。 |
| 未解決回復 | 自動期限切れにしない。解決・移送が必要な現在状態として示す。 |
| 未搬送完了結果 | Consumerの受理・回収接続を修正する。必要な結果を上限のため消さない。 |
| 一時領域 | 所有者と参照の終了を確認して清掃する。年齢だけでは削除しない。 |

Project Runtimeの通常履歴については、人間確認により保持期間を30日へ固定し、件数・合計Byteによる削除上限は採用しない。未受領・未解決の現在状態と正式Evidenceはこの期間制限の対象外とする。その他のOwnerについての保持設定と`maxSecondaryFailures`は別途評価し、Project Runtimeの採用値を暗黙に横展開しない。

ログ欠損・破損は診断不足として扱い、操作許可や回復成功にしない。一方、通常ログの出力不能だけで制御状態を失わない。Effect前に必要な制御状態を保存できない場合は、そのEffectを発行しない。

## 11. 保存確定と移行

以下を設計で明示し、単なる「JSONを置換する」実装へ省略しない。

- 制御SnapshotのWriter、競合更新の排除、改訂確認、破損検出、必要な保存確定。
- Effect発行前後、結果搬送前後、現在状態からの除去前後のcrashに対する再入場。
- ログWriterとローテーションの競合。循環ログは制御状態の入力にしない。
- `state.pending.json`残存の所有者と確定済み／未確定の判別。名前だけで回復Authorityにしない。
- 清掃の再実行と終了後の不存在。成功応答だけから資源不存在を推定しない。

新版では現在の記録確定・未解決処置を保持する一方、旧実行記録の保存Schema、伴走commitと履歴再生を永続互換契約として維持しない。

2026-10-05の人間判断により、Coordinator／Project Runtime／Dockerの短命な実行記録は新形態へ刷新する。旧全世代のRuntime内変換、互換Reader／Writer、Fallbackは採用しない。移行時の旧処理停止・必要成果物の保全・用途別Rootのお掃除をフロントAIが行い、新しい受付世代から開始する。既存の利用操作は新版で検証する。現在使用中・必要参照を持つ記録の無条件削除とは区別する。

正常finalizeの保持分岐、Project側acknowledge／finalize、Claude認証settled、Docker修復の閉鎖記録、完了回復Receiptについて、移行前後のOwner・Consumer・保存確定・必要な実境界検証を対応付ける。既存Git履歴とVerification Evidenceを基準に、未対応の成立済みCapabilityを残さない。

開発PCの明示リセットは製品移行の代替ではない。旧版利用者の認証・同意・候補・Evidence、未解決操作を対象にした移行試験を別途行う。

## 15. ①〜④共通の増加防止

整理は旧Fileを別Directoryへ移すだけで完了しない。新規作成する領域には用途、保持Owner、利用側、終了条件、物理清掃の契機と保持上限を与える。全領域へ一律JSONL化や期限削除を適用しない。

| 種類 | 増加を止める方法 | 消してはならないもの |
|---|---|---|
| 現在状態 | 現在値を更新し、終了・受理済みの項目を除く。世代Snapshotの恒久累積を避ける。 | 未解決の義務、未受理結果、移行中の必要世代。 |
| 通常診断 | File容量・世代数・総容量に上限を設けて循環する。Operation単位Directoryを増設しない。 | 診断へ混入させてはならない制御状態。 |
| 一時作業／試験中間物 | 正常・失敗・取消の終了時に回収する。中断残存は既存Ownerの次回再入場で処置する。 | 参照中、所有不明、観測不能な対象。 |
| 検証結果 | 判断に必要な結果とHashをCHG／品質成果物へ昇格する。完了資料は担当者が参照終了を確認して回収する。 | 監査・Release・未解決Findingから必要な根拠。 |
| Candidate | 採用／破棄の決定と利用側の受理を終端にする。未処置Candidateの数・容量を可視化する。 | 未搬送のPatchや人間の判断待ち成果物。 |
| Release／Build入力 | 現在候補と必要な比較基準へ限定する。置換・破棄済みの展開物と再生成物を回収する。 | 現行署名対象Tree、参照中の旧版、唯一の必要根拠。 |

保持の評価単位は既存ComponentとCHG／検証単位とする。新しい全領域共通DB、常設監視Service、回復Frameworkを作らない。保持上限は各Ownerの契約または設定で数値化し、未設定を無制限の許可にしない。ただし上限に達したからという理由だけで、保全対象を消さない。参照中の必要物が上限を超える場合は、新しい不要な生成を止め、必要な内容・期間・容量を担当者が再評価する。

清掃の契機は、各処理の終端、CHG／検証Gateの終了、候補の置換・破棄、および中断後の次回再入場へ接続する。終了ごとに清掃のための新しいDirectoryと履歴を作らず、実施要約は既存のOwner記録を更新する。今回の分類一覧・旧Launcher退避も作業資料であり、永久保存を既定にしない。

①では、次のE2Eに必要な能力を持つ一時Scriptについて、元の改訂版固定、相対import、入力と結果の関係を保持する。旧Scriptの移動だけで正式入口へ昇格したとは表示しない。正式入口化が必要な能力は、実装と試験のOwnerへ接続して新しい固定候補で確認する。②〜④へ引き渡す物は対象と理由を明示し、①の未分類物を隠すための退避にしない。

現在のWorkflowは検証記録の自動削除を許可していない。この計画は自動期限削除の採用や、既存記録の削除許可を拡張しない。保持上限と清掃の実装・移行は、各段階でCanonical設計、利用側と検証へ接続してから完了を判断する。
