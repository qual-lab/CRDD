# 同じProjectの複数Workspace実行：変更計画

- 対象: `CHG-000082`、基準 `9c1f5ca60`。提案の比較元は `f0d0c38`。
- 状態: 同じProject・Milestoneの複数Graphの保存、Workspace単位の長期Lease、設定済みのServer受付からObjective子Processへの接続を実装。実Gitと別子Processによる並列実行、同一Workspaceの二重起動拒否、片側の強制終了、別のServer受付Processからの再入場を限定確認した。既存データの実切替、実AI・Docker、リリース判定は対象外。未確認の観点は第3節と第4節に示す。
- 人間判断: 同じProject・Milestoneでも登録済みの別Workspace上のGraphを並列に実行できること。正式な受入・採用や共有技術資源の排他を緩めない。
- 経路: 実行・保存・公開契約と状態切替をまたぐ非自明な変更。実装前に技術・保存・公開入口を照合し、固定候補で独立レビュー、不足／影響監査と文書監査を行う。準拠基準・リリース判断は対象外。全体回帰、実AI、Docker、既存保存物の操作はこの着手範囲に含めない。

## 所有と識別

| 境界 | 正本 | 保存と実行の意味 |
|---|---|---|
| Repository | 既存の単一Snapshot | 短期保存Lock・本文CAS・耐久出版。別Queueの保存で全体改訂が進んでも、対象の世代・元実行・認可が同じならfreshな版の対象行だけを更新する。 |
| Project／Milestone | 共有の定義と正式な受入・採用 | Graphの完了とは別に確定する。取込先の現在状態・世代が変われば採用を再判定し、先に完了したGraphや候補を消さない。 |
| 受付済みGraph | 既存の `queueId` | 受付内容とWorkspace参照、受付済み計画版、Graphの世代とOwner、Task／Attempt／結果／回復の相関。再送、再計画、再入場で別Graphを選ばない。 |
| Workspace | 正規のRepositoryと登録済みWorkspace ID | 長期Leaseの競合キー。作成・廃棄・切替・採用など必要な操作が同じ競合境界を使う。物理実体は別に照合し、差替えで別キーを発行しない。 |
| 共有技術資源 | 既存Owner | Provider Home、共有Git、Docker回復、Processの清掃不明はWorkspaceから独立した制限。範囲を特定できない場合は非競合と推定しない。 |

採用候補は単一Snapshot内の状態分離。Workspace別にStateを分けると正式な受入・複数資源の相関とCASが分散し、既存保証を再実装するため採らない。同一Project全体を長期排他にすると、今回必要な同一Project内の並列性を満たさない。実行の受付識別子を新設する案は、既存Queueが再送・元要求・回復と結合しているため採らない。Directは初期版ではRepository内の実行と競合する。Workspace IDの省略だけでDirectを推定せず、実行先を確定できない要求は開始しない。

## 2. 保存形式と切替

- 共有の現行定義と、既に受け付けたGraphが参照する変更不能な計画版を分ける。計画本文は同じ版で共有し、Graphの選定・進捗・実行上の判断は共有しない。再計画は元Queueだけを新しい計画版へ結合し、正式採用が必要な状態を暗黙に上書きしない。
- Projectの現行行には世代と受入状態もあるため、行全体を固定計画版として扱わない。Project・Milestone・純粋な計画本文を結合する既存の定義Hashを再使用する。新規受付は同一Projectの存在で省略せず、同一Queueの同一要求の再送と、別Queueの初期化を分ける。
- 取得回復参照はRepository・Project・Queue・Lease種別から生成し、別Queueの取得に同じ参照を使わない。物理Lockの名前は回復参照と分ける。別Queueが同じWorkspaceで取得するLockの名前は同じだが、Lockの所有・解除の照合値は各実行のOwner世代と元の実体を保持する。従来の耐久Intent、取得証拠、解放Intent、物理解放、終了証拠を省略しない。
- 解放が確定したAの履歴退役は、同じScopeを取り直したBのLockをAの解放未確認とみなさない。Aの元世代の確定証拠とIntent不存在で判定し、証拠欠測なら停止する。Workspaceの物理操作も、実行取得と同じ短期保存Lock内で競合を相互に観測する。
- Repositoryの短期Lockの競合を、保存の失敗やEffect不明と同じ終端にしない。まだ操作を発行していないことが確認できる競合だけ、有界・取消可能な待機で再評価する。Effect発行後、保存確定不明、Lock喪失はこの待機経路に入れない。
- Objective受付の最初の保存読取りでは、Lockが存在して保存未発行と確定した拒否だけを待つ。待機は最大750msで、呼出しの取消・時間切れを区別する。共有Serverでは親に現在認可を再確認し、単体Serverでは確定済みのRoot・主体と取消を使う。他のWriterの生存やLockの安全な解放は推定せず、自動処置しない。複数段階の保存は操作全体を再送せず、各段の取得・確定に分けて検証する。
- Objectiveの長期Lease取得では、予約の保存前の競合だけを取消・再認可付きで待つ。予約確定後、物理取得前の取消はIntentと元回復参照を保全して停止する。物理Lock取得後は既に発行した処置の証拠だけを、同じOwner・同じIntentで保存する。この確定は取消済みでも省略しない。証拠保存で待った場合はTaskを始める前に共有Serverの現在認可を再確認し、拒否・観測不能なら既存Leaseの解放・回復だけを行う。期限内に確定できなければ元の回復ID・Intent・物理記録を保持し、再取得しない。
- Objectiveの終結では、元Queueの終端保存、解放Intent、物理解放、終了証拠、Queue所有解除を区別する。解放開始と同時に新規のLease借用を停止する。保存段階だけを個別に待ち、解放Intentが確定する前は物理Lockを削除せず、物理解放後に終了証拠やQueue所有解除が未確定でも物理解放を繰り返さない。不明なものは元の回復参照に結び付ける。
- 初回Queue受付・受付済みGraphの実行準備・Queue選択・所有／実行への遷移と、Task予約・引渡しでは、その保存の未発行を確認できる競合だけを取消・現在認可付きで待つ。初回は選定を繰り返さない。実開始通知と結果保存は既に委譲した同じAttemptに限り、要求取消後も元の結果を保存する。Executorを再発行しない。委譲後の保存で待機した場合、次のTaskを予約する前に現在認可を再確認する。新しいTaskの予約前で、先行Taskがあればその終端も確定済みの取消・認可拒否は、回復待ちにせず対象Queueを取消で終結する。
- 初回Queueの限定検証では、同じ短期Lock内で2回出版すること、2回目の失敗時には初期版と保留物を保持すること、競合後の認可が通る場合だけ選定一回・実行一回となることを実Filesystemで確認した。Server子のWorkspace候補読取りも、真正な対象なしと短期Lockの競合を区別し、認可を確認した後だけ読み直す。登録済みの別Workspaceを使う複数Graphの通し検証は第4節に示す。
- 引渡し保存後・委譲前のWorkspace確認でも、短期Lockの競合だけを待つ。取消や認可拒否は、同じAttemptを外部未発行として閉じてからQueueを取り消す。保存観測不能なら予約や保留物を保全し、清掃済みへ変換しない。Leaseの物理解放と証拠保存が成立してもQueueの元世代を残し、既存の所有者喪失時の回復経路へ接続する。一時的な観測不能からの解放・同じQueueの回復再入場は実Filesystemで確認した。対象Queueと相関しない保存領域の回復参照は公開しない。
- 旧v9の実物には触れない。混在版のWriterで同じ保存領域を使用しない。未確定Intentや旧ロックの意味を推測で埋めず、新規空Stateへ自動置換しない。旧版での終結・検証済み変換が必要なケース、終端履歴とID再使用拒否を保つ条件は、切替前に明文化して検証する。データの削除・書換え・実際の移行はこの計画の記録だけでは承認しない。

## 3. 回帰と完了境界

基準は [先行回帰の記録](Evidence/261125_file-io-git-regression.md#file-io-git-regression-final-20261125) と現在のLease・Queue・Workspace・回復の契約試験。基準の合格は新実装の合格に流用しない。

再計画の限定試験は、同じProject・Milestoneで元Task IDが同じ二つの失敗実行を用意し、一方の差し替えだけを保存する。Queue、管理実行、固定計画、他方のLease証拠は相互に上書きしない。Task照会のHTTP・MCPは既存入口で任意の `queueId` を受け、該当Graphの固定計画と進捗へ結合する。複数Graphで未指定なら有効な共有定義だけを返す。

1. 実Filesystem・別Processで同Scope／別Scopeの取得を比較する。Intent保存前、保存後で物理取得前、物理取得後で確定前、解放中、Owner喪失、観測不能を分ける。B実行中にAを回復し、A回復中にBを終了しても両方の元証拠を保持する。
2. A/Bが同一Project・Milestone、同じTask IDという条件を省略しない。再計画中・受入途中・履歴確定中の上書き、旧世代、異Scope、管理領域の実体差、全体CASだけが進む場合を個別に反証する。
3. 共有Provider Home／GitはWorkspaceが異なっても競合を維持する。別のWorkspace IDが同じ実体を指す別名・重複登録は、独立とみなさず処置前に拒否する。Directとの競合、対象Workspaceの破棄拒否、別Workspaceの作成許可、採用先の状態変化も確認する。ノード起動の代役を使う試験から実AIまたは実Dockerの成功を推定しない。

## 4. Processと利用側の接続

CRDD ServerがGraphごとのCoordinator子Processを起動する。短期保存Lockは子の起動待ち・実行中・取消待ちに保持しない。Queueの二重起動防止はEMの耐久状態が正本であり、親のProcessハンドルを状態台帳にしない。最初の要求に結合した通知、開始前取消、開始後取消、遅延・重複通知、子終了と清掃の区別、失効した認可、Server再起動後の生存／不存在／観測不能を、本番接続と実子の合成試験で確認する。

Server共通操作から、同じProject・Milestone・Task IDの2件を、実Git Worktreeと別Node子Processで同時実行する。開始通知前の引渡し済みAを強制終了し、正式な再開で元Queueを回復している間も、開始通知済みBの所有世代・実行状態を保持する。同じWorkspaceへの別要求は未発行で停止する。選定・Provider委譲だけを代役にし、保存・排他・実行先確認・子終了・再入場および公開結果は実装を通す。受付で確認済みのSnapshotは同じ要求の照合に引き継ぎ、初回作成が競合した場合の確定判定は既存のWriter内で行う。

A/Bが実行中のとき、Bの廃棄はGit操作も保存変更も行わずに拒否し、同じProjectの別Workspace Cは共有Gitの排他を保ったまま作成できた。A/BのQueue行・Lease Intentは不変。Workspace操作に残っていたProject全体の使用中判定を対象Queueの実行先で判定するよう是正した。Directと実行先不明は競合扱いを維持する。自前の試験領域内の実ジャンクションで、登録済みの別IDが同じWorktreeを指すと実行先確定を拒否し、保存は不変であることを確認した。リンク作成が許されない環境のスキップは合格に数えない。

別Workspaceに対して開始通知を保存した後、Serverの要求を取り消し、既存IPCを通して当該子Processに届けた。合成Providerが清掃確認済みの取消を返したとき、そのQueue・Taskだけが取消となり、元Leaseは解放された。別の実行中QueueとTask、Lease Intentは取消の前後で不変で、その後に通常終結できた。取消側のWorktree本文は不変。実Providerの取消や清掃確認が取れない場合の外部資源消失を、この確認からは推定しない。

共有の取込先がAの採用で進んだ場合、Bの初回要求に残っていた旧HEADはGitが変更要求未発行として拒否する。その場合だけ同じ操作LockとCASでBを元の固定済み候補へ戻し、新しいHEADは利用者の明示要求で受け付ける。Bの固定証拠とAの採用結果、各Queueの相関は保持する。既存の採用意図への再入場では、今回の観測が未発行でも以前の発行を否定できないため、元の取込先を保持する。追加のGit確認や新しい永続項目は設けない。

別のServer受付Processから元Queueへ再入場し、稼働中のBは既存の実行中と判定して二重に始めず、元BのPIDを観測不能にした場合は元Bの回復参照だけを返し、どちらも保存状態を変えないことを確認した。Aの子の終了を観測した後は、別のServer受付Processから元Aを再開し、Bの所有世代と進捗が不変であることを確認した。稼働中・不存在のPID確認は実OS、観測不能はそのPIDの生存照会に対する故障注入である。

別のケースでは、外部実行の開始通知前にServer受付の親Processだけを強制終了した。元の子PIDの不存在とWorktree未変更を確認し、別の親から同じQueueへ再入場した。取消が完全に保存されていれば観測だけを返し、元世代が残っていれば既存の回復経路で元Queueを確定する。完了・取消・採用待ちが保存されていても所有世代が残る間は、再送を清掃確認済みにしない。明示再開で元Leaseの解放だけを確定する場合は、現在の認可・元要求・同じ状態を照合し、新規実行のためのHEAD比較やWorkspace準備を行わない。その再開で新しいTaskを発行せず、採用可否や履歴整理の処置も行わない。HEADが進んだ後も元世代だけを確定し、旧改訂での新規実行は拒否することを、取消・採用待ちの実保存と公開受付の契約試験で確認した。実Provider開始後の強制終了や外部資源清掃の保証には一般化しない。

解放証拠が作られる前に元Ownerが消失した場合も、完了・取消・採用待ちまで確定している同世代のQueueでは、元Leaseの回収だけを行い、その状態・結果参照・再開条件を保つ。解放証拠がない取消と採用待ちを実Ownerの強制終了で再現し、元PIDの不存在、元Leaseの回収証拠、所有世代の解除、Task保存不変を確認した。

上記の通し試験は成功回を確認したが、限定回帰中の一回ではAが実行前にLease取得未確定で保全停止した。その後の再実行成功をもって原因解消とは判定しない。再入場の証拠と、同時受付時の取得確定の安定性を分けて確認する。

通し試験に失敗時だけの段階診断を追加し、試験作成のSnapshotから対象WorkspaceのQueue、取得・回復意図、証拠の種類を、物理Leaseの存在観測と分けて記録する。通常環境の6回の追加実行で元の取得未確定は再現しなかった。短期Lockの待機上限、未確認時の保全、製品の公開結果は変更していない。

取得未確定の調査とは別に、同一Projectの別Workspaceの子Processで、片方の回復予約と確定の間に他方の物理解放・解放証拠の保存を完了させる交錯を固定する。回復対象のPID不存在は実観測し、両Queueの証拠を各一件、Intentと物理Leaseの残存なしを検証する。保存中の別Processの本文を試験親が読み続けるとWindowsの保存と干渉し得るため、子の解放完了の合図で同期し、証拠は処置後に観測する。

取得処理の段階別観測を付けた10回の連続実行では、この停止は再現しなかった。観測用の差し替えは撤去し、待機上限を根拠なく延長しない。先行読取り後に同じ要求IDのQueueが確定した場合は、新しいWriterが同内容を観測結果へ接続し、異内容を拒否することを検証した。いずれも先行する保存本文を変更せず、Executorは発行しない。終端後の結果投影とWorkspace相関も、未発行と確認できる短期Lockの競合だけを同じ読取りで待つ。最後のQueue照合と採用判定は一回のWorkspace状態読取りを共有する。相関を確認できない停止を採用可にせず、実行済みの記録を変更しない。純粋な競合残りと、読取り自身のLockの解放不明を分け、後者だけを回復要の未確認として閉じる。Repository全体の回復参照は元Queueの結果へ混ぜない。

共有Provider Homeについて、自己生成領域の実Lockを親が保持中、別Nodeが同じ結合の取得を拒否され、別結合は取得可能であること、親の元File・本文は不変で通常解放後に再取得できることを確認した。実Provider Home、AppData、認証、Dockerは使用していない。

HTTP／MCPの既存共通配送を利用する。対象Queueの入力・結果・取消・再認可問い合わせだけをIPCで結び付け、Serverの共有tokenや認可コールバックを子へ渡さない。子側の実行先の現在実体確認と親側の公開直前の再認可は維持する。切断・Server終了は既存Signalから対象子へ伝達し、確実に終了を確認できないときは解放済み・資源不存在と判定しない。CLIは単独Process入口を維持し、Server所有のWorkspace操作をCoordinatorへ戻さない。

HTTP／MCPの実行状態照会は、認可済みProjectに加えて任意の `queueId` を受け取る。指定時は同じQueueの保存行と開始候補だけを照合し、Serverは要求と異なるQueueの結果を公開しない。分離Workspaceの明示照会は、共有HEADが進んでもそのQueueの受付時改訂だけを観測できる。新規実行を許可する根拠にはしない。Directと未指定の現在HEAD条件は維持し、省略時に対象が曖昧なら観測不能とする。取消済みQueueの明示照会は開始候補を返さず、活動一覧でも現在の選択肢から外す。Workbenchは既存の活動照会が同じ保存版で作った要約を、Repository IDとQueue IDの組で選択する。選択時の再読取りと、Project履歴のGraphへの付け替えは行わない。

Objective子Processの正式結果と進捗投影は、元要求とRepository・認証主体から受付と同じ方法で特定したQueueに照合する。Queue付きの回復義務はこの照合に通った場合だけ公開する。Queue行を公開しない停止でも、EMが同じ元Queueから導出するLease取得回復参照は維持する。別Queueの参照と、Repository全体など元Queueとの結合を確認できない回復参照は公開しない。結果未確認は回復不要や資源不存在を意味せず、耐久記録を変更しない。

品質受入は正式なGit採用とは別である。分離Workspaceでは元Queueの採用証拠と現在HEADを照合し、Directでは採用を求めず計画改訂と現在HEADを照合する。Queue指定がない場合だけ、同じProject・Milestoneの候補が一件であることを求める。共有Milestoneの受入済みを別Queueの完了に流用しない。正式な受入は既存のライブラリ入口だけで、HTTP・MCP・Workbench・CLIに新しい入口は追加していない。別候補の採用で現在HEADが進めば、先行候補のGit採用・結果は保持されるが、先行HEADの証拠だけで新たな品質受入は行えない。並列実行と明示Git採用の成立を、全Graphの正式品質受入・終結の提供とみなさない。

Graph再入場のLease回復では、最初のOwner状態の読取りと回復後のQueue読取りだけが短期保存Lockの未発行競合を待ち直す。Owner喪失の観測、Intent保存、物理回復、証拠確定はこの待機で再発行しない。単なる読取り競合を新たな回復義務へ変換せず、確認済みの元Queueの回復参照がある場合は失わない。実短期Lockを用いた限定試験で、待機中の取消・再認可拒否はOwner観測せず、競合解消後は一度だけ観測して生存Ownerと保存本文を保全することを確認した。既存認可を確認できない場合は回復対象を公開しない。

この計画上の設計単位と限定反証が成立するまでは、並列実行を提供済みと表示しない。

## 5. 最終確認後の追補

- Queue選択の公開入口は対象Queue IDを必須にした。既存の本番呼出しは元Queueを指定済み。省略・不正IDでは保存を読まず、別Workspaceが実行中でも対象の選択・待機状態を変えない。Directとの競合は維持する。
- 実Git・別Processの並列試験に、片側のLease回復確定直後の短期ロック競合とServerからの取消を加えた。応答は元Queueとそれに結合した回復参照を保持し、Taskを新規発行せず、他方のQueueを変更しない。その後、元要求を明示再開する。
- 専用Chromeで本番の活動Panelに合成の取得断面を渡し、複数の並び替えと選択中のGraphが消えたときの表示を確認した。別Repositoryの同一Queue IDを同じ対象とみなさず、明示選択後だけ他方を表示する。HTTP取得全体や全画面の評価ではない。
