# 既存同意再利用の親Agent表示案

## 結論

親Agentは「既存同意を再利用したか」だけでなく、目的、Provider、送信情報、許可範囲、停止条件を最初の文で示す。範囲内継続では追加質問や確認コードを求めず、外部送信なしとは表現しない。範囲変更または許可判定不能では送信停止を明示する。

## 表示案

| 場面 | 最初の文例 | 必要時の詳細 | 可能な操作 | 避ける誤認 |
|---|---|---|---|---|
| 初回判断 | 「この依頼では、`{目的}`のために`{Provider}`へ`{情報}`を送る可能性があります。既存許可の実値を確認してから進めます。」 | Provider、情報、目的、撤回手段、影響を実値で提示する。説明雛形であり実行Authorityではない。 | 許可範囲の確認、必要ならユーザー承認待ち。 | 雛形だけで送信可能と扱うこと。未確認の取消コマンドやボタンを提示すること。 |
| 範囲内継続 | 「`{情報}`を`{Provider}`へ送り、`{目的}`を継続します。これは既存許可の範囲内です。」 | 同じ目的、分類、送信先、権限内である根拠を短く示す。README Evidenceでは2回目に同じ承認境界で再承認を要求しなかった。 | 追加確認なしで継続。履歴へ既存同意再利用として記録。 | 質問、確認コード要求、または「外部送信なし」と言うこと。 |
| 送信範囲変更 | 「送信先または送信情報が既存許可から変わるため、ここで送信を停止します。」 | 変更前後のProvider、情報、目的、影響、撤回手段を実値で並べ、承認後にのみ再開する。 | ユーザー承認を求める。未承認なら候補を破棄または保留。 | 既存許可を拡張解釈すること。撤回手段の未確認値を創作すること。 |
| 許可判定不能 | 「既存許可の範囲を確認できないため、Providerへの送信を停止します。」 | 不明な項目、照合不能な理由、再開に必要な確認を示す。 | 調査、ユーザー確認、または送信なしで可能な作業へ限定。 | 不明を暗黙許可にすること。停止中に送信を試すこと。 |

## 確認項目

| 区分 | 確認項目 | 失敗条件 |
|---|---|---|
| 正常（範囲内） | 同じ目的、Provider、送信情報、権限内で、文例に質問・確認コード要求がない。何がどのProviderへ送られるかを説明している。 | 外部送信なしと表現する。追加承認を不要に細分化する。 |
| 準正常（変更） | 差分、影響、撤回手段の実値確認を促し、送信停止を明示する。 | 変更後の送信を承認前に継続する。雛形をAuthorityにする。 |
| 異常（判定不能） | 不明項目を列挙し、Provider送信停止と再開条件を示す。 | 判定不能のまま既存同意再利用として扱う。 |

## 残る確認

- 初回・変更時のProvider、情報、目的、撤回手段、影響は実値を確認して提示する必要がある。
- README Evidenceの観測は「Runtimeの既存同意再利用時の追加入力0回」と「親による初回追加承認1回、2回目は再要求なし」を分離して扱う。
- 本件はCLIテキストの机上評価であり、ユーザーテストとは別である。
- Graphic制作・視覚品質は対象外。画面実装を行う場合は別途UI評価が必要である。
