# UX-000029のSPEC分析

成果物種別: SPEC分析（UX観点）
分析単位: `UX-000029`
状態: 分析済み

## 1. 正式入力

- UX定義: [UX-000029 作業・変更・根拠・品質を迷わず辿る](../../../02_UX/Definitions/UX-000029/ux_definition.md)

IA、UIまたはREQを直接読んで不足を補完しない。この分析はUX定義から、利用者に観測できる振る舞いと失敗だけを導く。

## 2. 振る舞いへ引き継ぐ利用者成果

未完了、変更理由、全影響パス、成立根拠および現在品質を役割の違いとともに辿れる

| 観点 | UX定義から受け取る内容 |
|---|---|
| 利用者／状況 | [製品全体の利用者像](../../../02_UX/02_Personas.md)の「CRDD作成者・保守者」 |
| 利用のきっかけ | 変更の現在地や根拠を調べる時 |
| 目的 | 作業・変更・根拠・品質を役割別に辿る |
| 利用者成果 | 未完了、変更理由、全影響パス、成立根拠および現在品質を役割の違いとともに辿れる |
| 必要な情報 | Work、Change、変更対象ファイル、根拠、観測した改訂版、品質を分ける |
| 重要場面 | 変更の影響漏れを確認する場面 |
| 避ける失敗 | 同じ説明を複製し代表ファイルだけで済ませる |
| 守る品質 | 正本を分け全影響ファイルを列挙する |
| 検証意図 | 責任者の混同、代表パスだけの表示、根拠の遡及上書きおよびGit差分への丸投げを反証する |

## 3. 観測可能にする契機・結果・失敗

```text
[製品全体の利用者像](../../../02_UX/02_Personas.md)の「CRDD作成者・保守者」
        │ 変更の現在地や根拠を調べる時
        ▼
作業・変更・根拠・品質を役割別に辿る
        │
        ├─ 成立   → 未完了、変更理由、全影響パス、成立根拠および現在品質を役割の違いとともに辿れる
        ├─ 不成立 → 同じ説明を複製し代表ファイルだけで済ませる
        └─ 不明   → 推測せず不足情報または再確認先
```

- ★ 判断点: 変更の影響漏れを確認する場面
- 成功は処理の開始ではなく、「正本を分け全影響ファイルを列挙する」を守って利用者成果を観測できる結果で判定する。
- UXが要求しない取消、回復、Authorityまたは外部Effectをひな型だけから追加しない。

## 4. 受入条件と適用範囲

- 正常: 未完了、変更理由、全影響パス、成立根拠および現在品質を役割の違いとともに辿れる
- 失敗: 同じ説明を複製し代表ファイルだけで済ませる
- 品質: 正本を分け全影響ファイルを列挙する
- 判断不能: 不足を補完せず、何を再確認すべきかを返す。
- 下流へは「IAは作業の一連の流れのNavigationとEntity関係を分け、Release・Quality Assurance・Checkerは各責任者境界を維持する。」を失わず渡す。

IA観点が与える対象、関係、状態、可視性、保存・開示条件と組み合わせても、利用者成果、失敗、検証意図を弱めない。具体的なAPI、Process、保存方式または画面はここで決めない。
