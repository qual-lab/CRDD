## 2. 正式入力から保持する利用者成果

鍵の発行・独立失効・交換はadministrator専用固定で、Role詳細権限のON／OFF設定を設けない。通常鍵操作は同一Process Workbench backendだけで提供し、MCPには秘密値の有無を問わず鍵操作の一覧・Schema・登録・dispatchを公開しない。通常Host回復はログイン済みローカル操作者を信頼する対話CLIで交換2操作だけを扱い、追加認証・専用資格・承認コード・OS管理者昇格を要求しない。既存Root／Path検証を維持する。manager／administratorはユーザー登録・表示名変更、developer／managerの割当て・詳細権限、Repository登録・登録解除・公開範囲を管理する。administratorの付与・解除・降格を含むRole変更、administrator詳細権限と鍵3操作はadministratorだけが管理する。developerへ管理操作、managerへ管理者専用操作を設定で委譲しない。

## 3. 契機・条件・結果・失敗

通常管理は管理権限を持つ主体からユーザーを登録し、表示名／Roleを変更し、ユーザーに資格を結合する。Role詳細権限はRoleが所有し、一つの現行Roleを用いる。鍵交換は同じuserId・Roleを保持し旧資格を以後の要求で拒否し、新Secretを一度だけ返す。

認証済み利用者の自身表示、非認証入口へのユーザー情報0、現在他ユーザー参照を許可されていない主体への他ユーザー一覧・存在・件数0を別々に保持する。Repository非開示対象の存在・名前・件数も漏らさない。
Role変更は次の認可へ反映する。鍵交換の成功は開始済み操作の取消完了ではない。資格状態は有効／失効／不明を保持し、新しい永続resetting状態は作らない。Secretを一覧・ログ・Evidence・会話・Repositoryへ保存／再表示しない。

指定ユーザー交換／全員交換は操作範囲、通常管理／Hostは入口・Authorityとして別軸にする。両入口で同じ2操作を扱い、ユーザーID・表示名・Role・詳細権限・Repository登録・Product Dataを保持する。対象は表示名ではなく既存userIdで固定する。特別ユーザー・追加権限・回復専用Bootstrapを作らず、認可設定破損の修復を鍵交換に含めない。初回設定は未初期化確定時の明示開始として別に扱い、既存状態の鍵回復へ転用しない。

| 操作 | 失効範囲 | 新資格の発行先 | 保持する違い |
|---|---|---|---|
| 指定ユーザー交換 | 対象userIdの全旧有効資格 | 同じ既存userId | 他ユーザーの鍵を保持 |
| 全員交換 | 全ユーザーの全旧有効資格 | 指定した既存administrator userId | 他ユーザーはその管理者による通常の再発行・再配布まで旧資格利用不能 |

通常入口は同一Process Workbenchの固定administrator権限、Host入口はログイン済みローカル操作者を確認する。Host入口と全員交換は人間の明示確認を必要とする。

対象既存userId、全員交換の指定既存administrator、必要な資格集合・現行Role権限、入口Authorityと必要な明示確認を処置前に確認する。対象不明・管理者不存在・必要状態を安全に確認不能・認可設定破損では新しいEffectを発行しない。事前条件確認、旧資格失効、新資格発行、結果確定・受領を区別する。失効後に発行自体または結果記録が未確定となった場合は、確定した失効範囲と発行結果の不明を非秘密の耐久情報として同じRecovery IDへ保持し、再入場時は現在状態を再観測する。再観測なしに完了・rollback・未失効・開始済み取消済みを推定せず、Secretを再表示しない。記録は操作種別・入口・対象・発行先・既知処置・発行結果・再入場を相関し、保存Schemaや新Storeはここで決めない。
入口Authority→操作範囲・対象userId・失効集合・発行先・保持情報の確認→同じRecoveryの現在地→既存ユーザーの新資格で再入場を辿る。管理権限から内容Accessを推定せず、Repository単体利用へ資格を要求しない。

userIdは正式入力の採用済みUUID制約を継承する。版・Schema・生成方式をここで決めない。

### 登録解除と鍵の受け渡しの条件・結果

登録解除は対象の登録と対応Exposureを同じ受理操作で除去する。事前の別操作による公開解除を必須にせず、以後の対象CROSアクセスを停止する。他Repositoryの登録／Exposureと対象Repository本体・Product Dataは保持する。両関係の除去を確認できる場合だけ解除完了を返し、片方残存または確認不能を成功へ畳まない。物理Transaction・Schema・Store方式はここで決めない。

発行自体または結果記録が不明なら、Credential IDとは別の非秘密な元発行Identityで現在再観測し、新交換を開始しない。交換由来だけ元のsame exact Recoveryを保持し、通常発行へ交換Recoveryを新設しない。発行・結果記録が確定し配送／受領だけ未確認なら、「発行済み・受け渡し未確認」と示し、確定事実を維持する。Secretの保存・再表示・自動再発行はしない。現在認可されたadministratorが人間の明示した既存交換を新しく開始でき、そのOperation／Recoveryは元処理とは別にする。現在の管理認証を失った場合は、Workbench認可を迂回せず既存Host交換入口へ案内する。

元発行と新交換の事実・Identityを別に保持する。指定ユーザー交換は先の発行鍵を含む対象userIdの全旧有効資格を失効し同じ既存userIdへ発行する。全員交換は先の発行鍵を含む全ユーザーの全旧有効資格を失効し、指定した既存administratorへ発行する。他ユーザーは通常の再発行・再配布を要する。各交換内では同じexact Recoveryを保持するが、新交換を元処理の再開として扱わない。新交換成功は旧Secretの受領・rollback・開始済み操作取消を証明しない。現在状態で失効した旧鍵を、遅延した元応答から利用可能と案内しない。

## 4. 処置と他観点との統合

独立した資格失効は、対象資格とWorkbenchの固定administrator権限を確認して失効し、以後の要求で拒否する。新資格を自動発行せず、鍵交換と開始済み操作の取消とは別に扱う。結果不明時は既知対象・状態を保持し、取消完了や過去Effect 0を推定しない。

確定済みRecovery ID・種別・対象・既知処置結果を非秘密の耐久情報としてProcess喪失後も保持する。同じ回復へ再入場する際は現在状態を再観測し、記録の存在だけからHostのログイン済み操作者やEffect／回復完了を推定しない。新Store・保存方式はこの分析で決めない。

## 初回Host設定の条件・状態・結果

UX-000035が所有する初回設定は、ログイン済みHost操作者による明示的な開始として扱う。既存OSユーザーの管理Root／Pathを確認し、管理状態と途中の初期化記録の双方で未初期化が確認された場合だけ受理する。既存Credential、追加認証、専用資格、承認コード、OS管理者昇格を要求しない。MCP・自動起動の初期化要求は受理しない。

| 条件・現在状態 | 処置・結果 |
|---|---|
| 未初期化を確認し明示開始 | 管理用表示名を受け取り、最初のadministratorユーザーをUUIDで作成し、同じuserIdへ鍵を発行・結果記録する。Secretは一度だけ渡す。受け取り後の通常管理への接続までを初回成立として扱う |
| 既存管理状態・ユーザー・管理者あり | 初回設定を拒否する。鍵喪失は既存Host交換2操作の責務とし、管理者不存在・Role／認可破損を初期化で修復しない |
| 確認済み途中状態 | 作成UUID・発行・結果記録・配送・受領を別事実として保持する。既知の非秘密な元初期化試行だけを相関し、作成済み・発行済みを未初期化へ戻さない |
| 発行または結果記録が未確認 | 元の確認済み初期化試行を再観測する。新しい交換・再初期化・自動再発行を開始しない |
| 発行・結果記録確定、配送／受領だけ未確認 | 確定事実を保持し、作成済みadministratorを対象とした既存Hostの指定ユーザー交換だけを別明示操作として利用できる。元Secretの再表示・再発行はしない |
| 管理状態または初回試行の有無を観測不能・不明 | 新Effect前に停止する。明示開始前の未試行・不明から既存の試行や対象UUIDを推定しない。双方の未初期化を確認した後の明示開始による新規作成はこの停止対象ではない。単一ファイル不存在、別Root、読取り失敗、破損、Lock使用中、未解決回復を未初期化へ読み替えない |

管理状態と確認済みの初期化試行の情報は、ユーザー成立前には既存の管理能力の情報として扱い、成立後に作成UUID・接続資格との関係を持つ。新しいDomain Object・安定ID・一般Recoveryは追加しない。保存・相関方式はArchitectureで具体化する。

受入・負の検証義務は、明示開始と双方の未初期化確認、最初のUUIDと同一userIdへの鍵結合、発行／記録／配送／受領の分離、途中状態の全体完了誤認0、既存・不明状態の初期化Effect 0、Secret保存・再表示・自動再発行0、MCP公開0とする。初期化は既存回復の抜け道にせず、Repository登録・Exposure・内容閲覧を自動付与せず、Product Dataを変更しない。未初期化確定と明示開始後の一度作成・一度受領、確認済み途中への再入場で元試行を再観測し、別UUID・追加鍵の自動作成と自動再初期化が0であることを別々に観測する。

## 検証意図

登録だけまたはExposureだけの除去を解除成功にせず、孤立Exposureを現在公開中として示さないこと、他対象・本体の保持、発行／記録不明と受け渡しだけ未確認の分岐、元発行IdentityとCredential IDの区別、通常発行への交換Recovery新設0、明示新交換の別Identityと対象範囲、現在認可・Host案内、Secret再表示／自動再発行0、遅延旧応答の失効鍵利用案内0を反証する。新交換成功から元Secret受領・rollback・取消完了を推定しない。既存の全4組事前表示・3組明示確認を維持する。

| 交換の入口と操作 | 事前表示 | 明示確認 |
|---|---|---|
| 通常Workbench × 指定ユーザー | 対象ID・表示名、失効範囲、発行先、保持情報 | 追加確認なし |
| 通常Workbench × 全員 | 同上 | 必須 |
| Host CLI × 指定ユーザー | 同上 | 必須 |
| Host CLI × 全員 | 同上 | 必須 |

固定administrator以外の通常鍵操作、MCPの鍵操作一覧・Schema・登録・dispatch、通常Host回復からの発行・単独失効を拒否する境界を確認する。Hostに追加認証を要求せず既存Root／Pathを保持し、交換全4組で対象・影響を事前表示、Hostまたは全員交換の3組だけ明示確認する。8操作の許可／拒否を確認する。managerによるadministrator表示名変更は許可し、administratorの付与・解除・降格・詳細権限・鍵操作、developerの管理操作、Role設定による固定割当ての迂回は拒否する。manager自身の範囲変更は変更前認可と明示更新、次要求での現行Role・Exposure・実アクセスの再評価を分ける。登録だけの公開・内容取得、登録解除によるProduct Data削除、管理拒否による自身表示・許可内利用の拒否を反証する。対象・現行認可・必要状態を確認不能なら新Effectなしで停止し、既知結果と不明を区別する。

同名・改名時の対象維持、名前非Authority、三可視境界、Role変更の次認可反映、鍵交換のID・Role保持／旧資格拒否と取消分離、秘密非保存を確認する。2操作の対象範囲・既存発行先、入口Authority差、情報保持、処置前停止、発行／記録不明は元発行Identityの再観測（交換由来だけsame exact Recovery）、確定発行・受け渡しだけ未確認は別明示交換を検証へ渡す。未決の具体処置や実測成功を創作しない。

独立失効の成功／拒否／応答喪失を鍵交換や取消へ置換しないこと、回復の処置前中断／処置後に発行自体または結果記録が不明でも同じ確定済み元発行Identityを保持して再観測し、確定発行の受け渡しだけ未確認とは区別することを検証義務へ渡す。
