## 1. 正式入力

## 2. 振る舞いへ引き継ぐ利用者成果

stdio MCPとlocalhost HTTPのどちらでも、同じ入力・権限・状態・結果で仕事を続けられる

| 観点 | UX定義から受け取る内容 |
|---|---|
| 利用者／状況 | 開発者 |
| 利用のきっかけ | ローカルMCPの通信方式を選ぶ時 |
| 目的 | 通信方式を変えても同じ公開契約・入力・権限判断で操作する |
| 利用者成果 | stdio MCPとlocalhost HTTPのどちらでも、同じ入力・権限・状態・結果で仕事を続けられる |
| 必要な情報 | 処理結果、公開契約、通信方式、外部作用の発行有無を分ける |
| 重要場面 | 入口を切り替えて同じ仕事を開始・継続する場面 |
| 避ける失敗 | 通信方式によって入力・権限判断・状態・結果の意味が変わる |
| 守る品質 | 公開契約・入力・権限判断・状態・結果を通信方式間で一致させる |
| 検証意図 | stdio MCPとlocalhost HTTPで入力・権限判断・状態・結果が変わること、および失敗した通信方式と外部作用の発行有無を識別できない表示を反証する |

## 3. 観測可能にする契機・結果・失敗

```text
開発者
        │ ローカルMCPの通信方式を選ぶ時
        ▼
通信方式を変えても同じ公開契約・入力・権限判断で操作する
        │
        ├─ 成立   → stdio MCPとlocalhost HTTPのどちらでも、同じ入力・権限・状態・結果で仕事を続けられる
        ├─ 不成立 → 通信方式によって入力・権限判断・状態・結果の意味が変わる
        └─ 不明   → 推測せず不足情報または再確認先
```

- ★ 判断点: 入口を切り替えて同じ仕事を開始・継続する場面
- 成功は処理の開始ではなく、「公開契約・入力・権限判断・状態・結果を通信方式間で一致させる」を守って利用者成果を観測できる結果で判定する。
- UXが要求しない取消、回復、Authorityまたは外部Effectをひな型だけから追加しない。

## 4. 受入条件と適用範囲

- 正常: stdio MCPとlocalhost HTTPのどちらでも、同じ入力・権限・状態・結果で仕事を続けられる
- 境界: 「入口を切り替えて同じ仕事を開始・継続する場面」で、成立・不成立・判断不能を分け、「通信方式によって入力・権限判断・状態・結果の意味が変わる」へ至る状態を正常へ畳まない
- 失敗: 通信方式によって入力・権限判断・状態・結果の意味が変わる
- 品質: 公開契約・入力・権限判断・状態・結果を通信方式間で一致させる
- 判断不能: 不足を補完せず、何を再確認すべきかを返す。
- SPEC定義では、上記の利用者成果、成立条件、失敗条件および判断不能を失わず保持する。
