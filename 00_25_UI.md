# 1. Purpose and Boundary

UIは、UX OutcomeとIA Structureを、利用者が認識、判断、操作、理解、回復できるUI Contractと、実装可能なVisual / Graphic / Assetへ変換する工程である。

```text
何を最初に認識するか
何を判断するために、どの根拠を見るか
どのActionを実行できるか
処理状態と結果をどう理解するか
失敗、権限不足、競合からどう回復するか
どのScreen、State、Variantで一貫して成立させるか
```

UIは見た目の好みだけを決める工程ではない。Figma、Screenshot、代表画面、Component一覧の完成もUI Contractと対象Scope Coverageの代替にならない。Business Rule、Authority、System State Transition、Data LifecycleはBehavior Specificationまたは上位・ArchitectureのAuthorityへ戻す。

# Phase Process Contract

本章はUI工程の入口、変換、責務Coverage、出口、Phase Gate、Auditの正本である。後続章は本ContractをArtifact構造とSkill実行へ具体化し、独自の完了条件を持たない。Artifactの統合・分割・配置は[`00_03_Documentation.md`](00_03_Documentation.md)に従う。

## Phase Entry Contract

UIは対象Scopeについて、次を受け取る。

- Source REQ / UX / IA、Preserved UX Intent、Experience Principle
- Target Actor、Feature / Use Case / User Action、Pairing Unit Candidate
- IA Object / Responsibility / Navigation / State Concept / Glossary
- Information Priority、UI Obligation、Behavior Obligation
- Platform、Brand、Accessibility、Locale、Display等のConstraint
- IA Coverage Summary、Open Gap、Human Review Result
- 既存UI、Pattern、Component、Visual ArtifactとそのAuthority / Revision

通常は[IAのExit and Handoff](00_23_IA.md#exit-and-handoff)から受け取る。IA Object / Responsibility、UX Intent、対象Scope、人間Reviewが不足する場合はIAまたはUXへ戻す。IAが`Partial — Human Authorized`の場合、UIは承認されたScopeだけを扱い、未網羅項目、Risk、後続Ownerを引き継ぐ。

## Transformation Contract

UX IntentとIA責務を、Screen / Surface、Screen Flow、Information Hierarchy、Action、Feedback、Presentation State、Accessibility、Responsive / Platform Variant、Component / Pattern、Design Token、Final Visual、Asset、Motionへ変換する。

UI ContractとGraphic / Visual Designは同じUI工程で扱えるが、Property Authorityを混同しない。

```text
UI Contract
= Information Hierarchy、Action、Interaction、Feedback、Presentation State、Accessibility

Graphic / Visual Design
= Color、Typography、Icon、Illustration、Image、Effect、Motion、Final Visual
```

## Required Responsibility Coverage

対象Scope全体について、次の責務を網羅する。

| Responsibility | Required Context |
|---|---|
| Source and Principle | Source REQ / UX / IA、Purpose、Preserved Intent、UI Principle、Non-goal、Constraint |
| Screen / Surface Inventory | 全Logical Screen / Surface、Purpose、IA Responsibility、Status、Artifact Reference |
| Flow and Structure | Entry、Screen Flow、Branch、Back、Cancel、Error Flow、Information Hierarchy、Decision Evidence |
| UI Contract | Primary / Secondary Action、Feedback、Normal / Loading / Empty / Error / Permission / Disabled / Conflict / Unknown、Recovery |
| Responsive / Variant | Role、Platform、Device / Display、Brand、Locale、Text Expansion、State Variant |
| Design System | Semantic Token、Component / Pattern、Component State、Variant、利用Rule、Exception |
| Graphic / Visual | 全Screen / 主要StateのFinal Visual、Asset、Motion、Source Master、Export / Naming / Version Rule |
| Quality and Trace | Usability、Universal Design、Accessibility、Visual Quality、`pairs_with SPEC-*`、Coverage、Open Gap、Evidence |

AIまたは個人Dataを扱うScopeでは、Trust Surface、Source / Provenance、不確実性、AI ProposalとHuman Decisionの区別、Consent、Human Control、Settingsへの遷移、Avoided Harmも判定する。

## Screen, State, and Variant Coverage

「全Screen」はProduct全体を毎回作り直す意味ではない。承認済みFeature / Change / Release Scope内の全Logical Screen / Surface、主要User Flow、適用するState、Role / Platform / Brand / Display / Locale Variantを指す。

各Use Case / User Action、Screen / Surface、State、Variantと各UI責務を、`Complete for Scope`、`Partial — Human Authorized`、`Blocked`、`Not Started`、`Not Applicable`で追跡する。`Not Applicable`には人間が確認した理由を必要とする。

代表画面、Happy Path、Wireframe、Final Visual、または一部Componentの完成を、対象Scope全体のUI完了と表現してはならない。

## Human Decisions

人間は情報優先度、主要Action、UI Principle、Visual Direction、重要Trade-off、Accessibility Risk、Behavior SpecificationとのConflict、`Not Applicable`、部分Handoffを決定する。AIは候補、Coverage Gap、Pattern、Conflictを提示できるが、Business Rule、Authority、Risk Acceptanceを自己決定しない。

## Exit and Handoff

UIとBehavior Specificationは並行・反復して具体化してよい。Behavior DraftからUIを検討したり、UIから新しいBehavior Gapを発見したりできるが、片側の進捗を他方またはPair Reviewの完了とみなさない。

通常のArchitecture Handoffは、対象Scopeが`Complete for Scope`で、人間Reviewを通過し、対応Behavior Specificationとの[Pair Review](00_24_UI_Behavior_Specification.md#26-exit-and-pair-gate)を完了し、[Architecture Phase Entry Contract](00_27_Architecture.md#phase-entry-contract)を満たす場合に限る。

対象Architectureが既に承認済みで変更不要な場合も、その対象Revisionと適用根拠を示す。UIから実装へ暗黙に直行しない。部分Handoffには、対象Scope、未作成Screen / State / Variant、Pair Gap、Risk、受信先、後続Ownerの人間承認を必要とする。

## Phase Gate Criteria

- Source REQ / UX / IA、対象Use Case / User ActionへTraceできる
- Screen / Surface Inventoryが対象Scope、State、Variantを網羅している
- Information Priority、Action、Feedback、Normal / Loading / Empty / Error / Permission / Conflict / Unknown / Recoveryを適用範囲で定義している
- Wireframe / Prototype、UI Contract、Final Visual、Assetが対象Scopeで対応している
- Design Token、Component / Pattern、Responsive / Platform / Locale Variantを必要範囲で判定している
- Usability、Universal Design、Accessibility、Visual Qualityを対象ArtifactとEvidenceに対してReviewしている
- Behavior SpecificationとのPair Coverageが完了し、重大Conflictがない
- AI / Personal Data ScopeではTrust、Consent、Provenance、Human Control、Avoided Harmを判定している
- Coverage Gap、`Not Applicable`、部分Handoff承認を記録している
- Architecture Phase Entry Contractを満たす

## Phase Audit Checklist

- Screen / Surface、State、Variant、Flow、Final VisualのInventory漏れ
- Screenshot、Figma、代表画面、Happy Pathだけによる完了判定
- Wireframe、UI Contract、Final Visual、Asset間のCoverage不一致
- UIによるBusiness Rule、Authority、System State Transition、Data Lifecycleの創作
- UI ContractとBehavior SpecificationのPair Gapまたは片側だけの修正
- Design Token、Component State、Responsive / Platform / Locale Variantの適用漏れ
- Accessibility原則名だけの記載、対象Screen / Finding / Evidenceの欠落
- Trust SurfaceへのSettings ActionやFuture-plan Informationの混在、形だけのConsent UI
- External Visual ArtifactのAuthority、Version、Source Master、利用条件の欠落
- Source Trace、Coverage Summary、Open Gap、Human Review、Decision / Rationaleの欠落
- Architectureまたは実装への暗黙Handoff

# 2. UI Artifact Model

## 2.1. Screen Inventory, Flow, and Wireframe

Screen / Surface Inventoryは対象ScopeのCoverage Viewである。各Logical Screen / Surfaceについて、Purpose、IA Responsibility、Use Case、State / Variant、Wireframe、UI Contract、Final Visual、paired SPEC、Status、Gapを追跡する。

Screen FlowはEntry、Navigation、Branch、Modal、Back、Cancel、Error / Recovery FlowとContext維持を示す。IA Navigationの意味を変更せず、具体的なSurface間Interactionへ変換する。

Wireframe / PrototypeはInformation Hierarchy、First Recognition、Decision Evidence、Action、主要文言、State、Responsive / Variantを検討するArtifactである。操作できるPrototypeを実Behaviorまたは完成UIとみなさない。

## 2.2. UI Contract and Presentation State

UI Contractは、利用者が何を認識し、どの根拠で判断し、何を操作し、結果をどう理解・回復するかを正本化する。

```text
Good:
利用者はTopic Card内で、重要度だけでなく、
重要と判断した理由、Source Evidence、次Actionを同じ視野で確認できる。

Appearance only:
Cardは角丸で、重要度を赤く表示する。

Behavior leakage:
重要TopicはAIが自動的に承認する。
```

ActionのTrigger、Business Rule、Permission、Failure、Cancel / Undo / Retryが不明な場合はOpen GapとしてBehavior Specificationへ戻す。UI側で推測して確定しない。

Presentation StateはSystem Stateの見た目上の複製ではない。利用者が区別すべきNormal、Loading、Empty、Partial、Success、Unknown、Error、Permission、Disabled、Conflict、Cancelled、Recovering等を、[`00_24_UI_Behavior_Specification.md`](00_24_UI_Behavior_Specification.md)に従って対応づける。

## 2.3. Design Token, Component, and Pattern

少なくとも適用範囲で次を定義する。

```text
Semantic Color
Typography
Spacing
Sizing / Grid
Radius
Elevation / Layer / Effect
Opacity
Interaction State
Motion Duration / Easing
```

すべてのProductに大規模Design Systemを要求しないが、画面ごとの恣意的な値で代替しない。Reusable Component、Layout Pattern、Component State、Variant、利用Rule、Screen-specific Exceptionを識別する。

## 2.4. Graphic / Visual, Asset, and External Artifact

対象Scopeの全Screen / 主要State / Variantについて、Final Visual、Color / Typographyの実適用、Icon、Illustration、Image、Texture / Effect、Motion、Visual Coverageを扱う。

Graphic Assetは配置済みOutputだけでなく、編集可能なSource Master、利用条件、License / Provenance、Export Format、Naming、Versionを追跡する。MotionではTrigger、Duration、Easing、Reduced Motion時の代替も示す。

Figma等の外部ArtifactがAuthorityを持つ場合、RepositoryからPurpose、Authority Property、対象Frame / Component、Versionまたは確認時点、Source / Export、関連UI / SPEC、未反映Gapを辿れるようにする。Figmaの内容をMarkdownへ全複製する必要はない。

### UI and Visual Quality

UsabilityはLearnability、Efficiency、Memorability、Errors、Satisfactionを確認し、必要に応じてNielsen Heuristicsを利用する。

Universal DesignはEquitable Use、Flexibility in Use、Simple and Intuitive Use、Perceptible Information、Tolerance for Error、Low Physical Effort、Size and Space for Approach and Useを検討する。

Accessibilityは対象Platformに応じて、Contrast、色以外の識別、Keyboard / Focus、Screen Reader / Semantic Label、Text Scale / Expansion、Error Identification、Motion Reduction、Touch / Pointer Target、Locale / Reading Orderを確認する。

Visual Qualityでは、UI Coverageとの一致、Hierarchy、Consistency、Component / State / Variant、Brand / Platform差分、Source Master、再編集性、Export条件を確認する。

品質原則名を記載しただけでVerifiedとしない。対象Screen / State / Variant、Finding、Disposition、Evidenceを残す。検証Evidenceの扱いは[`00_29_Verification.md`](00_29_Verification.md)を正本とする。

## 2.5. Trust, Consent, and AI UI

Trust Surfaceは、現在有効なData利用、AI動作、Source、保証、制限、未確認範囲を理解する責務を持つ。Consent / Settingsの変更Actionと、利用者向けFuture-plan Informationを現在の保証へ混在させない。

AI Scopeでは必要に応じて次を区別する。

```text
AI Proposed
Human Reviewed
Approved
Execution Requested
Executed
Verified
```

Consent UIは、対象Purpose、送信Data、Scope、変更・撤回方法、影響を理解可能にし、Behavior Specificationの実行停止・取消条件とPairにする。DestructiveまたはExternal ActionではConfirmationだけでなく、対象、影響、Authority、Impact Preview、Cancel / Undo / Recoveryを示す。

## 2.6. Stable Context, Evidence, and Decision

`UI-*`は複数Artifactや下流工程から参照し、独立Review、置換、影響追跡を必要とする認識、操作、Feedback、Presentation State等のUI Contract意味単位へ付与する。文書名・Screen名・Figma Frame名・文書番号とStable Context IDを同一視せず、一つのUI Artifact内に複数の`UI-*`が存在してよい。

全Screen、全Component、全Figma Layer、Asset、Visual File、Evidence、Decisionへ機械的にUI IDを発行しない。UI Contractは`pairs_with SPEC-*`、Source UX / IA、Verification等とRelationで接続する。

UI判断の根拠は対象Artifact内または最も近い親Folderの`Evidence/`へ置く。情報優先度、主要Action、Visual Direction、重要Pattern、Accessibility Riskの決定は、結果となるCanonical UI Artifactの`Decision / Rationale`へ理由、Evidence、代替、影響を残す。

# 3. Guided Skill Adapter

## 3.1. Runtime Authority

`skill.ui.contract`は、Phase Process Contractを[`00_11_Skill.md`](00_11_Skill.md)のRun Lifecycle、Guided Interaction、Human Review、Handoffに従って実行するUI固有Adapterである。本書ではRun Status、Pause / Resume、共通Question Rule、Subagent Lifecycle、Artifact Registrationを再定義しない。

開始時は、利用者が何を見て判断し、どの操作とFeedbackで進み回復するかを整理し、Business RuleはBehavior Specificationと対にして扱うことを説明する。

## 3.2. UI-specific Progression

| Step | UI固有の変換 | Result |
|---|---|---|
| Load and Scope | IA Coverage、Pairing Unit、既存UI / Patternを対応づける | UI Coverage Queue |
| Inventory | Screen / Surface、State、Variant、Flowを列挙する | Screen Inventory |
| Contract | Recognition、Information Priority、Action、Feedback、Recoveryを定義する | UI Contract |
| Structure | Wireframe、Flow、Responsive、Component / Patternを具体化する | UI Structure |
| Visualize | Token、Final Visual、Asset、Motionを対象Coverageへ展開する | Visual Contract |
| Review and Handoff | Quality、Pair、Coverage、人間判断を確認する | Architecture Handoffまたは別Route |

## 3.3. UI-specific Question Topics

| Topic | Question Intent |
|---|---|
| User Goal | この場面で達成することは何か |
| First Recognition | 最初に気付くべき情報は何か |
| Decision Evidence | 判断に同時提示すべき根拠は何か |
| Primary Action | 次に取るActionと優先順位は何か |
| Feedback | 操作結果をどう理解できるか |
| State / Recovery | Loading、Empty、Unknown、Error、Permission等をどう理解・回復するか |
| Accessibility | 色、Keyboard、Screen Reader、Text、Motion等の制約は何か |
| Variant | Role、Platform、Display、Brand、Localeで何が変わるか |

情報が多すぎる場合は判断に直接必要な情報と参照情報を分け、複数Primary Actionは頻度、価値、不可逆性、例外性で整理する。Figma等が存在する場合はVisual Evidenceとして読み、Contractにない表現とArtifactにないContractをGapとして抽出する。

## 3.4. Adaptive Route and Escalation

| Condition | Route |
|---|---|
| UX IntentまたはIA Responsibilityが不足 | UX / IA |
| Behavior、Permission、Failure、Persistenceが未決 | Behavior Specification / Pair Review |
| Business Rule、Authority、不可逆Actionが未決 | Human Decision |
| UI / SPECが重大Conflict | Pair Review / 上流再開 |
| Platform、Visual、Accessibilityの専門判断が必要 | Expert Review / Prototype |
| 技術成立性またはArchitecture制約が支配的 | Architecture / Technical Spike |

Subagentを使う場合は[`00_10_Agent.md`](00_10_Agent.md)に従い、Screen Coverage、Wireframe、UI Contract、Token / Component、Usability、Accessibility等の限定Scopeを委譲できる。UI Contract、Visual Direction、Pair Review、Handoffの統合と人間確認はParent Agentが行う。

# 4. Review, Handoff View, and Feedback

## 4.1. UI-specific Human Review

共通Review Contractは[`00_11_Skill.md`](00_11_Skill.md#61-human-review)に従う。UI Reviewでは追加で次を確認する。

- UX IntentとIA ResponsibilityがInformation Priority、Action、Flowへ残っている
- UIがBusiness Rule、Authority、System Stateを創作していない
- Scope内の全Screen、State、Variant、Final VisualをCoverageで示している
- Figma、Wireframe、UI Contract、Visual、AssetのRevisionとGapが一致している
- Usability、Accessibility、Visual QualityのFindingとRiskを隠していない
- Behavior SpecificationとのPair Conflictと部分承認範囲を誤認なく示している

## 4.2. UI Artifact / Handoff View

次はUI責務をProject内で表現する標準Viewであり、独立File数を要求しない。

```text
Scope / Coverage Summary / Open Gap
Source REQ / UX / IA / Pairing Unit
UI ID / Revision / Status
Purpose / Preserved UX Intent / UI Principle
Screen / Surface Inventory / Flow
IA Object / Responsibility / Information Priority
First Recognition / Decision Evidence
Primary / Secondary Action / Feedback / Recovery
Presentation State / Accessibility / Responsive / Variant
Wireframe / Prototype / UI Contract Reference
Token / Component / Pattern / Exception
Final Visual / Asset / Motion / Source Master Reference
pairs_with SPEC / Pair Review Result
Quality Finding / Evidence / Risk
Decision / Rationale
Human Review Result
```

Architectureへの共同Handoff条件は[Pair Review Handoff](00_24_UI_Behavior_Specification.md#62-review-and-handoff)を正本とする。UI側はこのViewへの参照とUI Coverage Stateを欠落なく渡す。

## 4.3. Feedback to UI Context

Behavior Specification、Architecture、実装、Verification、運用から、Information Priority、Action、Feedback、State、Accessibility、Visual / Componentに関するLearningが得られた場合はUIへ戻す。同じ意味の明確化は同じ`UI-*`のRevisionを更新し、意味を置換する場合は新しい`UI-*`を発行して`supersedes`で接続する。

実装やFigmaの都合だけでUI Contractを無断変更せず、Evidenceと人間判断を結果となるUI Artifactへ反映し、Pair Relation、Screen Coverage、影響する下流Contextを再確認する。

# 5. Final Principle

```text
UIは、代表画面やFinal Visualを一つ作って終わる工程ではない。
対象Scopeの全Screen、State、Variantについて、
利用者の認識・判断・操作・回復とVisualを、Behaviorと検証へ接続する。
```
