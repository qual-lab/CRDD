# 一つの課題をたどる探索記録

成果物種別: Discovery分析

探索ID: `EXP-XXXXXX`
状態: （探索中／要求採用／保留／棄却。実装・検証・リリース状態は書かない）
主な情報源・根拠: （参照と、そこから確認できる範囲）
判断する人: （記入）
記録の性質: （探索時の記録／既存記録からの再構成）
下流の主要CHG: （CHG-XXXXXX／未作成。Discoveryの理由と下流状態をここへ複製しない）

> 一つの課題について、何に困り、どう考え、何を選んだかを後から人がたどれるように残す。完成した製品や設計の説明書にはしない。

## 事前入力の理解確認（発火した場合）

人間から構想、既存案、会話または添付資料が与えられ、AIが問題、必要性、望ましい変化または対象外を再構成した場合だけ記録する。AIが最初にどう理解したか、人間が何を修正・追加したか、有力な代替または反証との比較で何が維持・変更されたか、最終的に何を現在理解として確認したかを、物語を壊さない短い文章または図で示す。

人間が問題や要求を抽象的に説明できることを前提にしない。最近の具体的な出来事、実際の作業、迷い、待ち、探し直し、回避策、反例または具体案の比較から得た断片を、AIが問題仮説へ整理して返す。発言が少ないことを同意または問題不存在へ読み替えず、確認できない内容は未確認として残す。

問題、望ましい変化、保持条件、対象外または重要な前提の解釈差が、要求候補や後続設計を変え得る場合、人間理解の確認は必須である。AIだけで文章を完成できても、人間との一致を確認できていない探索を通常完了にしない。確認できない場合は、未確認範囲と影響を示し、部分的な引き渡しの承認待ちまたは停止として扱う。

抽象的な意図だけでは境界を確認できない場合は、最小の具体例、利用場面、Flow、情報構造または設定例を具体化プローブとして示す。人間が指摘した一致、違和感、不足および過剰から、保持する意味と捨てる具体を分ける。プローブの名称、ID、画面、Schema、技術または配置を、確認なしに要求や採用済み設計へ昇格しない。本文には会話全文でなく、判断を変えたプローブ、人間の修正、保持した意味および確認後の現在理解を残す。

```text
AIの事前理解
    ↓ 人間による修正・追加
修正後の問題理解
    ↓ 有力な代替・反証との比較
確認済みの現在理解
    ↓ 別の判断
要求候補の採用／保留／棄却
```

理解確認と要求採用を同じ判断として書かない。発火しない場合はこの節を削除し、Checklistへ理由を残す。

## きっかけ

誰がどの状況で何をしていたか、当時成立していた前提や代替、最初に起きた出来事や違和感を、前提を知らない人にも分かる言葉で書く。情報源と、そこから確認できる範囲・確認できない範囲も示す。

## 本当の問題は何だったか

具体的な観察または根拠を示し、目に見えた症状と、その奥にあると考えた問題を分ける。確認できた事実と解釈も混ぜず、誰にどんな影響があり、放置すると何が起きるかを示す。必要なら「前提→観察→影響→解くべき問題」の因果図を置く。

## こうすれば解けると考えた

原因について何を疑い、どうすれば問題を解けると考えたかを書く。比較した別案、選択理由、失敗・リスク・制約、判断を変える反証条件も示し、単一の結論へ飛ばない。候補を比べる必要がある場合だけ表を使う。

## 選んだこと、選ばなかったこと

現在の判断、守るもの、対象外を簡潔に示す。採用、不採用、保留を区別し、理解の確認と採用判断を分ける。

## 後から分かったこと

仮説を強めた事実、弱めた事実、判断を変えた転換点を書く。まだ確かめていないこと、人間による確認または判断が必要なことも隠さない。

## 採用した要求

人間が要求として採用した内容だけを、`REQ-XXXXXX`、要求本文、必要性、対象範囲、制約、検証義務および採用判断とともに示す。まだ採用していない仮説や候補へ`REQ-*`を付けない。採用要求がない場合は、その理由を一文で示す。

## 現在地と次への引き渡し

現在の状態、UXその他へ渡す内容、検証すべきこと、未確認のまま渡すこと、戻り先を示す。複数の探索を統合した利用体験やサービス提供の流れはUXで扱う。

## 補足分析（必要な場合）

上の節へ無理に入れると意味が分かりにくくなる補足だけを書く。見出しは内容に合わせて具体的に言い換えてよい。同じ種類の補足が複数の探索で繰り返される場合は、次回のひな型見直しで独立した標準項目にするか検討する。補足がなければ、この節は削除する。

この章順は読みやすさのための基本形であり、題材に合わせて見出しを言い換えたり、近い節をまとめたりしてよい。ただし、人が「本当の問題」「解決仮説」「選択」「仮説を変えた根拠」「現在地」を本文から答えられること。

## Checklist

各項目を本文から実際に評価する。`[x]`は必要な処置を本文へ残した状態、`[ ]`は未評価でひな型だけに許される状態、`OPEN`は評価済みだが必要な処置が未完了の状態、`FAIL`は不適合、`N/A`は非該当を表す。`OPEN / FAIL / N/A`は、`状態: 理由 — 項目本文`の形で理由と対象項目を残す。完成成果物へ`[ ]`を残さない。

- [ ] 情報源と、情報源から確認できる範囲を示した。
- [ ] 事前入力からAIが意味を再構成した場合、AIの事前理解、人間の修正および確認後の現在理解を区別した。
- [ ] 現在案を変え得る有力な代替または反証を人間と突き合わせるか、該当する案がない理由を示した。
- [ ] 人間理解の確認と、要求・方針の採用判断を分けた。
- [ ] 人間が抽象的な問題や要求を言語化できることを前提にせず、具体的な出来事、行動、迷い、回避策または比較から問題仮説を引き出した。
- [ ] 発言の少なさ、回答不能または沈黙を、同意、問題不存在または要求採用へ読み替えていない。
- [ ] 確認できた事実と、そこから導いた解釈・仮説を区別した。
- [ ] 解決策ではなく、本質的な問題を説明した。
- [ ] 技術名称を除いても、誰が何に困っているか理解できる。
- [ ] 影響を受ける人または判断する人を特定した。
- [ ] どのような変化を期待するか説明した。
- [ ] 原因と解決に関する仮説を、事実として扱っていない。
- [ ] 未確認事項と不確実性を明示した。
- [ ] 人間による確認または判断が必要かを評価した。
- [ ] 情報不足をAIの推測だけで補っていない。
- [ ] 失敗、リスク、制約および対象外を評価した。
- [ ] 採用、不採用、保留を区別した。
- [ ] 次工程が保持すべき問題、変化および条件を示した。
- [ ] 情報不足時にDiscoveryへ戻す条件を示した。
- [ ] 因果、比較または時系列を図示する必要性を判定し、作成または理由付きN/Aとして処置した。
- [ ] 補足分析へ必須情報を退避していない。
