# IA分析: 公式の識別と保証を混同せず見分ける

成果物種別: IA分析
分析対象: [UX-000031](../../../02_UX/Definitions/UX-000031/ux_definition.md)
状態: 分析済み

## 1. UXから受け取る意味

| 観点 | この分析で受け取る内容 |
|---|---|
| 利用者 | CRDD閲覧者 |
| 場面 | 公式らしい入口や視覚素材を見つけた時 |
| 目的 | 識別表示と保証の根拠を分けて確認する |
| 得たい結果 | 見た目だけを信頼根拠にせず適切な入口を選べる |
| 重要場面 | 公式表示を信頼判断へ用いる直前 |
| 避ける失敗 | アイコンや見た目を署名・準拠・品質保証と誤認する |
| 守る品質 | 識別表示と検証可能な信頼根拠を別に示す |

画面、API、保存形式は決めず、上記の利用者成果を情報の単位と関係へ変換する。

## 2. 情報候補と関係

| 情報Object | 利用者にとっての意味 | 同一性と関係の基準 |
|---|---|---|
| 配布物 | 公式表示・署名・準拠・品質主張を確認する対象 | Artifact IdentityとRevisionで識別する |
| 公式識別 | 識別表示と保証の根拠を分けて確認する際に、「公式識別」の意味・状態・対象範囲を他の情報と取り違えないための情報 | 所有する文脈、安定した識別情報、関連対象で同じものと別のものを区別する |
| 配布者 | 成果物（Artifact）を作成・配布した主体 | 配布者（Publisher） Identity |
| 署名確認 | 識別表示と保証の根拠を分けて確認する際に、「署名確認」の意味・状態・対象範囲を他の情報と取り違えないための情報 | Artifact Identity・署名・確認時点へ結ぶ |
| 準拠状況 | CRDD契約への準拠 | 適用範囲（Profile）＋結果（Result） |
| 品質上の主張 | 識別表示と保証の根拠を分けて確認する際に、「品質上の主張」の意味・状態・対象範囲を他の情報と取り違えないための情報 | 対象、判定時点、情報源で識別し、不明を正常へ丸めない |


```text
                       [O: 署名確認]
                              │ 配布者を確認する
                              ▼
[O: 配布者] ──公式表示を支える──▶ [O: 公式識別] ◀──準拠を示す── [O: 準拠状況]
                                      ▲
                                      │ 保証範囲を限定する
                               [O: 品質上の主張]

[O: 配布物] ──識別される──▶ [O: 公式識別]
```

図中の`[O:]`は情報Objectだけを表す。利用者、判断行為、利用者成果はObjectへ置き換えない。関係名と向きは、同じ対象を追跡し、誤った統合を避けるための情報上の関係であり、画面遷移や実装依存を表さない。

### Canonical化候補

| 接続先 | 分析Object | Canonical Object | 処置 | 判断理由 |
|---|---|---|---|---|
| IA-000015 | 配布物 | 配布物 | Same | 評価対象となるArtifactを保持する |
| ― | 公式識別 | ― | Not Applicable | IA-000015の配布物のIdentityと配布者との関係へ保持し、配布物そのものへ変換しない |
| IA-000015 | 配布者 | 配布者 | Same | 誰がArtifactを出したかを保持する |
| IA-000015 | 署名確認 | 完全性 | Rename | Artifactが改変されていないという同じ意味をCanonical表示へ揃える |
| IA-000015 | 準拠状況 | 準拠 | Rename | Contractへの適合という同じ意味をCanonical表示へ揃える |
| IA-000015 | 品質上の主張 | 品質主張 | Same | 準拠・完全性・公式性から独立して保持する |

この対応は分析結果からCanonical定義を再構築するための候補である。`Split`または`Merge`でも元の利用者向け意味を失わず、正式入力にないObjectを追加しない。

## 3. 状態・可視性・導線・責任

| 観点 | 分析結果 |
|---|---|
| 状態 | 識別済み（identified）／確認済み（verified）／信頼済み（trusted）／品質確認済み（quality_assured）を別軸にする |
| 可視性 | 「公式表示を信頼判断へ用いる直前」では、識別表示と検証可能な信頼根拠を別に示すために必要な状態と不足を判断対象と同じ文脈で示す。詳細な識別情報と根拠は必要時に辿れるようにし、非開示対象は存在自体を推測表示しない。 |
| 導線 | 公式識別→配布者→署名確認→準拠状況→品質上の主張。結果なし、判断待ち、失敗または状態不明の場合も、根拠か安全な戻り先を失わない。 |
| 責任 | 配布物・署名・配布者Identityを提供する責任と、準拠・品質の評価結果を記録する責任を分ける。 |
| 時間的な意味 | 識別済み（identified）／確認済み（verified）／信頼済み（trusted）／品質確認済み（quality_assured）を別軸にするの区別を保持する。現在値、古い値、履歴または不明を同じ正常状態へ丸めない。 |
| 情報の優先度 | まず「識別表示と保証の根拠を分けて確認する」の判断に必要な対象・状態・判断要否を示し、識別情報と根拠は必要時に辿れるようにする。 |
| 情報のまとまり | CRDD閲覧者が「公式らしい入口や視覚素材を見つけた時」に「見た目だけを信頼根拠にせず適切な入口を選べる」を得るための対象・状態・根拠・次の行動を同じ文脈で扱う。 |
| 判断権限 | 導入環境の信頼方針を決める主体がTrust Policyと利用可否を決め、Publisherの署名だけで信頼を強制しない。利用者は提示された情報から次の行動を選ぶが、正本の意味・状態を無断で変更しない。 |
| 重要な失敗 | アイコンや見た目を署名・準拠・品質保証と誤認する |
| 制約・対象外 | 画面、UI部品、API、DB、Class、保存形式および具体的な振る舞いをIAで確定しない。 |
| 人間判断 | UXから継承した未確認事項はCRDD閲覧者を代表する利用者とQual-Labが判断する。IA固有の追加判断はない。正式入力にないObject、状態または責任を追加する必要が生じた場合は人間の決定権限者へ戻す。 |
| IAへ戻す条件 | UI／SPEC分析またはQuality Analysis / IAで、Object・同一性・関係・状態・可視性・時間的な意味が不足または競合すると判明した場合。 |
| 検証意図 | 「公式表示を信頼判断へ用いる直前」に、アイコンや見た目を署名・準拠・品質保証と誤認することを避け、識別表示と検証可能な信頼根拠を別に示すことを確認できる必要がある。 |

ここで示す主体は、情報契約上必要な機能責任を表し、特定の人物・組織・Componentへの割当を確定しない。後続工程は、この責任境界を保ったまま実際の主体へ割り当てる。

### 未確認事項と判断

| 区分 | 内容 |
|---|---|
| UXから継承する確認事項 | REQ-000035: 識別表示が入口発見を助けながら信頼誤認を増やさないか、権利情報の許容確認負担 |
| 判断者 | CRDD閲覧者を代表する利用者とQual-Lab。 |
| 現在判定 | 後続の実利用確認が必要。現在のUX定義をCanonical化する判断を止める事項ではない。 |
| 未確認時の影響 | 利用者成果、重要場面、失敗および品質期待を仮説として保持し、定量条件や実現方式を確定しない。 |
| IAで追加した未確認事項 | なし。正式入力にない定量条件、状態値または実現方式を追加しない。 |
| IA固有の追加人間判断 | なし。UXから継承した判断をIAで確定済みにしない。 |
| Discoveryへ戻す条件 | 想定した利用者、問題、望ましい変化または制約が誤っていると判明した場合。 |

## 4. 現実照合の参考情報（正式入力ではない）

この節は後続のReality Auditへ引き継ぐ参考情報であり、IA Candidateを導く正式入力ではない。前節までをUX Definitionから再導出した結果として優先する。


| 照合対象 | 結果 |
|---|---|
| UXから導いた意味 | 対象・状態・導線は前節までを正とする。 |
| 現行構造 | 署名・公開文書が根拠を持つ。公式表示だけで全保証を成立させない。 |
| 採用境界 | 現行の名称や状態値は、UX由来の意味と一致する範囲だけを照合根拠にする。実装にだけ存在する区分はIA定義へ逆流させない。 |

## 5. IA処置

[IA-000015](../../Definitions/IA-000015/ia_definition.md)へ接続する。上記7軸を接続先へ保持し、複数UXを統合する場合も対象固有の状態、失敗、導線を消さない。UXから継承する未確認事項を、判断者と影響を含めて接続先へ保持する。

## 6. 後続工程が保持する意味

| 接続先 | 保持する意味 |
|---|---|
| UI（UX＋IAの正式入力） | 情報の優先度、可視性、状態差、まとまり、見つけ方および関係の理解を保持する。 |
| SPEC（UX＋IAの正式入力） | 対象の識別、関係、状態、可視条件、責任および時間的な意味を保持する。 |
| Quality Analysis / IA（伴走） | 「見た目だけを信頼根拠にせず適切な入口を選べる」の成立条件、「アイコンや見た目を署名・準拠・品質保証と誤認する」という失敗および前章の検証意図を保持する。 |

ArchitectureやSourceへ直接引き渡さない。UI／SPECは、UX DefinitionとIA Definitionの双方を正式入力として分析する。

## 7. 補足分析

なし。必須情報は第1章から第7章に保持する。現行文書・実装との比較は第4章の参考情報として分離し、Canonical IAの根拠には用いない。
