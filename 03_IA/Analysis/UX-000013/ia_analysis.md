# IA分析: Roleで許可されたRepositoryだけをリモート利用する

成果物種別: IA分析
分析対象: [UX-000013](../../../02_UX/Definitions/UX-000013/ux_definition.md)
状態: 分析済み（今回変更範囲の限定独立レビュー済み）

## 1. UXから受け取る意味

| 観点 | この分析で受け取る内容 |
|---|---|
| 利用者 | ユーザーCredentialで接続する開発者／プロジェクト運営者／PM |
| 場面 | リモート接続を開始・再接続する時 |
| 目的 | Roleで許可されたRepositoryだけへ接続する |
| 得たい結果 | 場所が変わっても開示範囲を理解して安全に使える |
| 重要場面 | 利用可能情報を表示する時 |
| 避ける失敗 | 表示名から本人性・権限を推定する、非認証／非管理者へユーザー情報を漏らす、権限・公開・実アクセスを同一視して利用不能や部分可視を成功へ丸める |
| 守る品質 | 現在のRoleで許可されたRepository範囲だけを開示し、不足や非開示対象を補完しない |

画面、API、保存形式は決めず、上記の利用者成果を情報の単位と関係へ変換する。

## 2. 情報候補と関係

userIdのUUID制約は正式UXから継承する。IAは安定した同一性を扱い、UUID版・Schema・生成方式を決定しない。

| 情報Object | 利用者にとっての意味 | 同一性と関係の基準 |
|---|---|---|
| ユーザー | 認証された接続主体。表示名は自身の表示に使い本人性や権限の根拠にしない | 安定userId。表示名の同名・改名でIdentityを変えず、一つの現行Roleへ結ぶ |
| 接続資格 | 接続を認証しユーザーへ結ぶ資格 | Credential IDとuserId。Secretを永続情報へ含めない |
| Role | 利用者がRemote CROSで利用できる情報・操作範囲の分類 | `administrator`／`manager`／`developer`のRole ID |
| Role詳細権限 | 現行Roleが許す情報・操作範囲 | Role IDに結ぶ。ユーザーやCredentialへ個別追加権限を持たせない |
| Repository Exposure | 許可範囲へ公開されているRepository | Repository IDと公開対象範囲。Role権限や実アクセスと別に扱う |
| 実アクセス可能性 | 公開対象の情報を実際に取得できるか | Repository IDと現在の確認結果。公開済みから利用可能を推定しない |
| 接続中の作業単位 | 一回の認証済み接続文脈 | Session IDとCredential ID、userId。Credentialへ過去のRole権限を固定しない |
| システム管理能力 | Credential管理やServer設定を行う能力 | 現行Role詳細権限の管理許可から判定し、内容閲覧範囲とは分ける |
| Repository情報範囲 | RepositoryがProject／Commercial／Topic／Meeting等のどの範囲を所有するかという宣言 | Repository IDと情報範囲の組で識別する |
| リポジトリ | 現行Role権限・Exposure・実アクセスから利用可否を判断する内容正本の境界 | Repository IDで識別する。Repository情報範囲は所有責務として別に扱う |

```text
[O: 接続資格] ──認証する──▶ [O: ユーザー]
      │                          │ 一つの現行Role
      │                          ▼
      │                      [O: Role]
      │                          ├─持つ──▶ [O: Role詳細権限]
      │                          │                   │ 許可範囲への公開を別確認
      │                          │                   ▼
      │                          │          [O: Repository Exposure]
      │                          │                   │ 実際の取得可否を別確認
      │                          │                   ▼
      │                          │          [O: 実アクセス可能性]
      │                          │                   │ 対象
      │                          │                   ▼
      │                          │             [O: リポジトリ]
      │                          │                   ▲ 所有責務
      │                          │          [O: Repository情報範囲]
      └─接続を識別──▶ [O: 接続中の作業単位]

[O: Role詳細権限] ──管理許可──▶ [O: システム管理能力]
```

図中の`[O:]`は情報Objectだけを表す。利用者、判断行為、利用者成果はObjectへ置き換えない。関係名と向きは、同じ対象を追跡し、誤った統合を避けるための情報上の関係であり、画面遷移や実装依存を表さない。

### Canonical化候補

| 接続先 | 分析Object | Canonical Object | 処置 | 判断理由 |
|---|---|---|---|---|
| IA-000009 | ユーザー | ユーザー | Same | 安定IDと表示専用名を区別し、Credentialと現行Roleの間へ結ぶ |
| IA-000009 | 接続資格 | 接続資格 | Same | ユーザーへ結ぶ認証資格として保持する |
| IA-000009 | Role | Role | Same | ユーザーの現行Roleとして保持する |
| IA-000009 | Role詳細権限 | Role詳細権限 | Same | Roleが所有する許可範囲を保持する |
| IA-000009 | Repository Exposure | Repository Exposure | Same | 公開対象を権限と実アクセスから分離する |
| IA-000009 | 実アクセス可能性 | 実アクセス可能性 | Same | 現在の取得可否を公開設定だけから推定しない |
| IA-000009 | 接続中の作業単位 | 接続中の作業単位 | Same | 一回の認証済みSessionとして保持する |
| IA-000009 | システム管理能力 | 管理能力 | Rename | 内容閲覧権限とは別のServer管理能力として保持する |
| IA-000009 | Repository情報範囲 | Repository情報範囲 | Same | ProjectはDEV、CommercialはMGMT等、Repositoryが所有する情報責務を宣言する |
| IA-000009 | リポジトリ | リポジトリ | Same | Role権限・公開対象・実アクセスを分けて利用可否を判断する内容正本として保持する |

この対応は分析結果からCanonical定義を再構築するための候補である。`Split`または`Merge`でも元の利用者向け意味を失わず、正式入力にないObjectを追加しない。

## 3. 状態・可視性・導線・責任

| 観点 | 分析結果 |
|---|---|
| 状態 | 利用可能（available）／接続資格が必要（credential_required）／開示制限（restricted）／利用不能（unavailable）／不明（unknown） |
| 可視性 | 利用可能情報を表示する時は、現在のRoleで許可されたRepository範囲だけを開示する。自身の表示名は認証後に確認できるが、非認証入口にユーザー情報、非管理者に他ユーザー一覧・存在・件数を開示しない。非開示Repositoryの存在・名前・件数も推測表示しない。 |
| 導線 | 接続資格→ユーザー→現行Role詳細権限→Repository Exposure→実アクセス可能性→利用可能なRepository。Repository情報範囲は情報責務として別に辿る。接続中の作業単位とシステム管理能力は別に辿る。結果なし、失敗または状態不明の場合も、根拠か安全な戻り先を失わない。 |
| 責任 | ユーザー識別・表示名／Role設定、Credentialの発行・リセット、Role詳細権限の管理、Exposure設定、実アクセス確認、Repository情報範囲の宣言、SessionおよびSystem管理能力を分ける。 |
| 時間的な意味 | 利用可能（available）／接続資格が必要（credential_required）／開示制限（restricted）／利用不能（unavailable）／不明（unknown）の区別を保持する。現在値、古い値、履歴または不明を同じ正常状態へ丸めない。Role権限変更は次の認可へ反映し、通常リセットでID・Roleを維持しても開始済み操作の取消完了は推定しない。 |
| 情報の優先度 | まず自身の現在表示名とRole内で実際に利用できるRepository、部分可視・状態および次の行動を示し、識別情報と根拠は必要時に辿れるようにする。 |
| 情報のまとまり | プロジェクト運営者／PMが「リモート接続を開始・再接続する時」に「場所が変わっても開示範囲を理解して安全に使える」を得るための対象・状態・根拠・次の行動を同じ文脈で扱う。 |
| 判断権限 | Repository Ownerが情報範囲を、CROS管理者が最小ユーザー情報・CredentialとRole詳細権限を、利用者がSession内の次行動を決める。AdministratorであることからManagement内容の閲覧権限を推定しない。 |
| 重要な失敗 | 利用不能なリポジトリの存在や内容を推測表示する |
| 制約・対象外 | 画面、UI部品、API、DB、Class、保存形式および具体的な振る舞いをIAで確定しない。 |
| 人間判断 | UXから継承した未確認事項はプロジェクト運営者／PMを代表する利用者とQual-Labが判断する。IA固有の追加判断はない。正式入力にないObject、状態または責任を追加する必要が生じた場合は人間の決定権限者へ戻す。 |
| IAへ戻す条件 | UI／SPEC分析またはQuality Analysis / IAで、Object・同一性・関係・状態・可視性・時間的な意味が不足または競合すると判明した場合。 |
| 検証意図 | 利用可能情報を表示する時に、Role外Repositoryの存在や内容を推測表示せず、現行Role権限、Exposure、実アクセスの未成立を区別し、部分可視を全体成立へ畳まないこと、自身表示・非認証非開示・他ユーザー非開示と名前非Authorityを確認できる必要がある。 |

ここで示す主体は、情報契約上必要な機能責任を表し、特定の人物・組織・Componentへの割当を確定しない。後続工程は、この責任境界を保ったまま実際の主体へ割り当てる。

### 未確認事項と判断

| 区分 | 内容 |
|---|---|
| UXから継承する確認事項 | REQ-000011: プロジェクト運営者／PMが「許可された作業領域だけへ接続する」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |
| UXから継承する追加事項 | REQ-000041: 自身の表示名と安定ID、現行Role範囲と利用不能理由を誤認しない表示・接続負担 |
| 判断者 | プロジェクト運営者／PMを代表する利用者とQual-Lab。 |
| 現在判定 | 後続の実利用確認が必要。現在のUX定義をCanonical化する判断を止める事項ではない。 |
| 未確認時の影響 | 利用者成果、重要場面、失敗および品質期待を仮説として保持し、定量条件や実現方式を確定しない。 |
| IAで追加した未確認事項 | なし。正式入力にない定量条件、状態値または実現方式を追加しない。 |
| IA固有の追加人間判断 | なし。UXから継承した判断をIAで確定済みにしない。 |
| Discoveryへ戻す条件 | 想定した利用者、問題、望ましい変化または制約が誤っていると判明した場合。 |

## 4. 現実照合の参考情報（正式入力ではない）

この節は後続のReality Auditへ引き継ぐ参考情報であり、IA Candidateを導く正式入力ではない。前節までをUX Definitionから再導出した結果として優先する。


| 照合対象 | 結果 |
|---|---|
| UXから導いた意味 | 対象・状態・導線は前節までを正とする。 |
| 現行構造 | CROS Architectureに設計候補がある。システム管理能力（system administration）を内容閲覧へ流用しない。 |
| 採用境界 | 現行の名称や状態値は、UX由来の意味と一致する範囲だけを照合根拠にする。実装にだけ存在する区分はIA定義へ逆流させない。 |

## 5. IA処置

[IA-000009](../../Definitions/IA-000009/ia_definition.md)へ接続する。ユーザー、Credential、現行Role詳細権限、Repository Exposure、実アクセス可能性、Repository情報範囲、Session、管理能力および三つのユーザー可視境界を接続先へ保持し、複数UXを統合する場合も対象固有の失敗と導線を消さない。

## 6. 後続工程が保持する意味

| 接続先 | 保持する意味 |
|---|---|
| UI（UX＋IAの正式入力） | 情報の優先度、可視性、状態差、まとまり、見つけ方および関係の理解を保持する。 |
| SPEC（UX＋IAの正式入力） | 対象の識別、関係、状態、可視条件、責任および時間的な意味を保持する。 |
| Quality Analysis / IA（伴走） | 「場所が変わっても開示範囲を理解して安全に使える」の成立条件、「利用不能なリポジトリの存在や内容を推測表示する」という失敗および前章の検証意図を保持する。 |

ArchitectureやSourceへ直接引き渡さない。UI／SPECは、UX DefinitionとIA Definitionの双方を正式入力として分析する。

## 7. 補足分析

なし。必須情報は第1章から第7章に保持する。現行文書・実装との比較は第4章の参考情報として分離し、Canonical IAの根拠には用いない。
