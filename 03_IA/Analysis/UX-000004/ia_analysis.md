# IA分析: 失敗後の再試行・回復を選ぶ

成果物種別: IA分析
分析対象: [UX-000004](../../../02_UX/Definitions/UX-000004/ux_definition.md)
状態: 分析済み

## 1. UXから受け取る意味

| 観点 | この分析で受け取る内容 |
|---|---|
| 利用者 | プロジェクト運営者／PM |
| 場面 | 失敗・取消・切断後に仕事を続ける時 |
| 目的 | 再試行・回復・清掃の違いを理解する |
| 得たい結果 | 失敗後に状態確認、再試行、回復および清掃を取り違えず、外部作用（Effect）の二重実行を避けて次の行動を選べる |
| 重要場面 | 同じ外部作用（Effect）を再発行する直前 |
| 避ける失敗 | 結果不明の処理を新規実行して外部作用（Effect）の二重実行を起こす |
| 守る品質 | 外部作用（Effect）状態・回復対象の識別情報・終了条件を示す |

画面、API、保存形式は決めず、上記の利用者成果を情報の単位と関係へ変換する。

## 2. 情報候補と関係

| 情報Object | 利用者にとっての意味 | 同一性と関係の基準 |
|---|---|---|
| 失敗 | 再試行・回復・清掃の違いを理解する際に、「失敗」の意味・状態・対象範囲を他の情報と取り違えないための情報 | 所有する文脈、安定した識別情報、関連対象で同じものと別のものを区別する |
| 外部変更の状態 | 再試行・回復・清掃の違いを理解する際に、「外部変更の状態」の意味・状態・対象範囲を他の情報と取り違えないための情報 | 対象、判定時点、情報源で識別し、不明を正常へ丸めない |
| 回復 | 残存を処置し、終了後を確認するまで残る義務 | 同一の回復対象識別子（Recovery Identity） |
| 再試行 | 依頼を実行した個別試行 | 依頼（Request）に属する試行識別子（Attempt ID） |
| 外部作用 | 外部に残り得る変更 | 依頼＋試行＋作用対象で識別する |
| 終了確認 | 作用と残存が閉じたことの観測 | 回復対象＋確認時点＋観測根拠で識別する |
| 回復義務 | 失敗後に解消が必要な残存状態 | 回復対象識別子（Recovery Identity） |
| 回復処置 | 回復義務を解消する操作 | Recovery Identity＋処置識別子で識別する |
| 試行 | 依頼を実行した一回の試み | 依頼（Request）＋試行識別子（Attempt ID） |
| 次の行動 | 観測結果に基づく安全な選択 | 終了確認＋判断時点で識別する |


```text
[O: 失敗]
      │ 作用の残存を伴う場合がある
      ▼
[O: 外部変更の状態]
      │ 必要性を決める
      ▼
[O: 回復]
      │ 解消後に許す
      ▼
[O: 再試行]

[O: 外部作用] ──残存時に生む──▶ [O: 回復義務] ──解消する──▶ [O: 回復処置]
[O: 試行] ──結果を確認する──▶ [O: 終了確認] ──選べるようにする──▶ [O: 次の行動]
```

図中の`[O:]`は情報Objectだけを表す。利用者、判断行為、利用者成果はObjectへ置き換えない。関係名と向きは、同じ対象を追跡し、誤った統合を避けるための情報上の関係であり、画面遷移や実装依存を表さない。

### Canonical化候補

| 接続先 | 分析Object | Canonical Object | 処置 | 判断理由 |
|---|---|---|---|---|
| ― | 失敗 | ― | Not Applicable | IA-000003の「状態・可視性・時間的な意味」節へ、失敗を独立Objectではなく状態・可視条件として保持する |
| ― | 外部変更の状態 | ― | Not Applicable | 外部作用の状態として保持し、独立Objectへ変換しない |
| ― | 回復 | ― | Not Applicable | 回復義務と回復処置の関係を表す利用者向け概念として保持する |
| ― | 再試行 | ― | Not Applicable | 試行と次の行動の状態・関係として保持し、独立Objectへ変換しない |
| IA-000003 | 外部作用 | 外部作用 | Same | 外部に残り得る変更を保持する |
| IA-000003 | 終了確認 | 終了確認 | Same | 作用と残存が閉じたことの観測を保持する |
| IA-000003 | 回復義務 | 回復義務 | Same | 失敗後に解消が必要な残存状態を保持する |
| IA-000003 | 回復処置 | 回復処置 | Same | 義務を解消する操作を保持する |
| IA-000003 | 試行 | 試行 | Same | 一回ごとの実行を保持する |
| IA-000003 | 次の行動 | 次の行動 | Same | 観測結果に基づく安全な選択を保持する |

この対応は分析結果からCanonical定義を再構築するための候補である。`Split`または`Merge`でも元の利用者向け意味を失わず、正式入力にないObjectを追加しない。

## 3. 状態・可視性・導線・責任

| 観点 | 分析結果 |
|---|---|
| 状態 | 失敗後の作用なし／作用済み／不明、回復要／不要 |
| 可視性 | 「同じ外部作用（Effect）を再発行する直前」では、外部作用（Effect）状態・回復対象の識別情報・終了条件を示すために必要な状態と不足を判断対象と同じ文脈で示す。詳細な識別情報と根拠は必要時に辿れるようにし、非開示対象は存在自体を推測表示しない。 |
| 導線 | 失敗→外部変更の状態→回復→再試行。結果なし、判断待ち、失敗または状態不明の場合も、根拠か安全な戻り先を失わない。 |
| 責任 | 実行状態を記録する責任が依頼・試行・作用・結果・回復義務を同じ識別子で記録する。 |
| 時間的な意味 | 失敗後の作用なし／作用済み／不明、回復要／不要の区別を保持する。現在値、古い値、履歴または不明を同じ正常状態へ丸めない。 |
| 情報の優先度 | まず「再試行・回復・清掃の違いを理解する」の判断に必要な対象・状態・判断要否を示し、識別情報と根拠は必要時に辿れるようにする。 |
| 情報のまとまり | プロジェクト運営者／PMが「失敗・取消・切断後に仕事を続ける時」に「失敗後に状態確認、再試行、回復および清掃を取り違えず、外部作用（Effect）の二重実行を避けて次の行動を選べる」を得るための対象・状態・根拠・次の行動を同じ文脈で扱う。 |
| 判断権限 | 依頼者または運用責任者が取消・再試行・回復・結果採用を決め、記録責任は外部作用を推測確定しない。利用者は提示された情報から次の行動を選ぶが、正本の意味・状態を無断で変更しない。 |
| 重要な失敗 | 結果不明の処理を新規実行して外部作用（Effect）の二重実行を起こす |
| 制約・対象外 | 画面、UI部品、API、DB、Class、保存形式および具体的な振る舞いをIAで確定しない。 |
| 人間判断 | UXから継承した未確認事項はプロジェクト運営者／PMを代表する利用者とQual-Labが判断する。IA固有の追加判断はない。正式入力にないObject、状態または責任を追加する必要が生じた場合は人間の決定権限者へ戻す。 |
| IAへ戻す条件 | UI／SPEC分析またはQuality Analysis / IAで、Object・同一性・関係・状態・可視性・時間的な意味が不足または競合すると判明した場合。 |
| 検証意図 | 「同じ外部作用（Effect）を再発行する直前」に、結果不明の処理を新規実行して外部作用（Effect）の二重実行を起こすことを避け、外部作用（Effect）状態・回復対象の識別情報・終了条件を示すことを確認できる必要がある。 |

ここで示す主体は、情報契約上必要な機能責任を表し、特定の人物・組織・Componentへの割当を確定しない。後続工程は、この責任境界を保ったまま実際の主体へ割り当てる。

### 未確認事項と判断

| 区分 | 内容 |
|---|---|
| UXから継承する確認事項 | REQ-000002: プロジェクト運営者／PMが「複数AIへ任せる範囲と権限を理解する」を行う際の判断基準、許容負担、利用環境および失敗後の選択／REQ-000021: プロジェクト運営者／PMが「切断後に同じ依頼へ戻る」を行う際の判断基準、許容負担、利用環境および失敗後の選択／REQ-000024: プロジェクト運営者／PMが「境界を越えた結果を同じタスクへ受け取る」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |
| 判断者 | プロジェクト運営者／PMを代表する利用者とQual-Lab。 |
| 現在判定 | 後続の実利用確認が必要。現在のUX定義をCanonical化する判断を止める事項ではない。 |
| 未確認時の影響 | 利用者成果、重要場面、失敗および品質期待を仮説として保持し、定量条件や実現方式を確定しない。 |
| IAで追加した未確認事項 | なし。正式入力にない定量条件、状態値または実現方式を追加しない。 |
| IA固有の追加人間判断 | なし。UXから継承した判断をIAで確定済みにしない。 |
| Discoveryへ戻す条件 | 想定した利用者、問題、望ましい変化または制約が誤っていると判明した場合。 |

この節は後続のReality Auditへ引き継ぐ参考情報であり、IA Candidateを導く正式入力ではない。前節までをUX Definitionから再導出した結果として優先する。


| 照合対象 | 結果 |
|---|---|
| UXから導いた意味 | 対象・状態・導線は前節までを正とする。 |
| 現行構造 | 実行編成（Coordinator）と実行時データ部品（runtime-data）に回復記録がある。API要求成功だけで作用完了を推定しない。 |
| 採用境界 | 現行の名称や状態値は、UX由来の意味と一致する範囲だけを照合根拠にする。実装にだけ存在する区分はIA定義へ逆流させない。 |

## 5. IA処置

[IA-000003](../../Definitions/IA-000003/ia_definition.md)へ接続する。上記7軸を接続先へ保持し、複数UXを統合する場合も対象固有の状態、失敗、導線を消さない。UXから継承する未確認事項を、判断者と影響を含めて接続先へ保持する。

## 6. 後続工程が保持する意味

| 接続先 | 保持する意味 |
|---|---|
| UI（UX＋IAの正式入力） | 情報の優先度、可視性、状態差、まとまり、見つけ方および関係の理解を保持する。 |
| SPEC（UX＋IAの正式入力） | 対象の識別、関係、状態、可視条件、責任および時間的な意味を保持する。 |
| Quality Analysis / IA（伴走） | 「失敗後に状態確認、再試行、回復および清掃を取り違えず、外部作用（Effect）の二重実行を避けて次の行動を選べる」の成立条件、「結果不明の処理を新規実行して外部作用（Effect）の二重実行を起こす」という失敗および前章の検証意図を保持する。 |

ArchitectureやSourceへ直接引き渡さない。UI／SPECは、UX DefinitionとIA Definitionの双方を正式入力として分析する。

## 7. 補足分析

なし。必須情報は第1章から第7章に保持する。現行文書・実装との比較は第4章の参考情報として分離し、Canonical IAの根拠には用いない。
