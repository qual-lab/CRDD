# IA分析: Meeting内容を候補化し採否を判断する

成果物種別: IA分析
分析対象: [UX-000014](../../../02_UX/Definitions/UX-000014/ux_definition.md)
状態: 分析済み

## 1. UXから受け取る意味

| 観点 | この分析で受け取る内容 |
|---|---|
| 利用者 | プロジェクト運営者／PM |
| 場面 | Meeting後に決定・Topic・Actionを整理する時 |
| 目的 | 会議の内容を候補として整理し正本へつなぐ |
| 得たい結果 | 会話と採用判断を混同せず仕事を継続できる |
| 重要場面 | 候補を採用または却下する場面 |
| 避ける失敗 | 会議記録が自動的に正本へ昇格する |
| 守る品質 | 候補・判断・反映結果を区別する |

画面、API、保存形式は決めず、上記の利用者成果を情報の単位と関係へ変換する。

## 2. 情報候補と関係

| 情報Object | 利用者にとっての意味 | 同一性と関係の基準 |
|---|---|---|
| 会議項目 | 会議内の観察・問い・判断候補 | Meeting内Identity |
| 候補 | 正本更新前の提案 | 候補（Candidate） ID |
| 論点との関係 | TopicとCandidateの接続 | 対象Identity＋関係種別で識別する |
| 採否判断 | 採用・却下・保留 | 権限（Authority）と改訂版（Revision） |
| 責任者 | 会議の内容を候補として整理し正本へつなぐ際に、「責任者」の意味・状態・対象範囲を他の情報と取り違えないための情報 | 主体、対象範囲、有効時点で識別する |
| 会議 | 会議項目が生まれた場 | Meeting IDで識別する |
| 論点 | 会議後も継続して扱う問題や判断対象 | Topic IDで識別する |

```text
[O: 会議]
      │ 含む
      ▼
[O: 会議項目]
      │ 生む
      ▼
[O: 候補] ◀──処置する── [O: 採否判断] ◀──決定する── [O: 責任者]
      │
      │ 既存論点と比較する
      ▼
[O: 論点との関係]
      │ 接続する
      ▼
[O: 論点]
```

図中の`[O:]`は情報Objectだけを表す。利用者、判断行為、利用者成果はObjectへ置き換えない。関係名と向きは、同じ対象を追跡し、誤った統合を避けるための情報上の関係であり、画面遷移や実装依存を表さない。

### Canonical化候補

| 接続先 | 分析Object | Canonical Object | 処置 | 判断理由 |
|---|---|---|---|---|
| IA-000010 | 会議項目 | 会議項目 | Same | 候補化の元となる項目を保持する |
| IA-000010 | 候補 | 候補 | Same | 採用前の情報として保持する |
| IA-000010 | 論点との関係 | 関係 | Rename | 候補とTopicの接続自体を保持する |
| IA-000010 | 採否判断 | 判断 | Rename | 候補の採用・却下・保留を保持する |
| ― | 責任者 | ― | Not Applicable | IA-000010の「責任と判断権限」表へ、責任者を独立Objectではなく機能責任・権限として保持する |
| IA-000010 | 会議 | 会議 | Same | 会議項目が生まれた時間境界を保持する |
| IA-000010 | 論点 | 論点 | Same | 会議後も継続して扱う問題または判断対象を保持する |

この対応は分析結果からCanonical定義を再構築するための候補である。`Split`または`Merge`でも元の利用者向け意味を失わず、正式入力にないObjectを追加しない。

## 3. 状態・可視性・導線・責任

| 観点 | 分析結果 |
|---|---|
| 状態 | 観測済み（observed）／候補（candidate）／採用（adopted）／却下（rejected）。会話と正本を分ける |
| 可視性 | 「候補を採用または却下する場面」では、候補・判断・反映結果を区別するために必要な状態と不足を判断対象と同じ文脈で示す。詳細な識別情報と根拠は必要時に辿れるようにし、非開示対象は存在自体を推測表示しない。 |
| 導線 | 会議項目→候補→論点との関係→採否判断→責任者。結果なし、判断待ち、失敗または状態不明の場合も、根拠か安全な戻り先を失わない。 |
| 責任 | 会議記録者がMeeting ItemとCandidateを作成し、論点正本を管理する主体がRelationを更新する。 |
| 時間的な意味 | 観測済み（observed）／候補（candidate）／採用（adopted）／却下（rejected）。会話と正本を分けるの区別を保持する。現在値、古い値、履歴または不明を同じ正常状態へ丸めない。 |
| 情報の優先度 | まず「会議の内容を候補として整理し正本へつなぐ」の判断に必要な対象・状態・判断要否を示し、識別情報と根拠は必要時に辿れるようにする。 |
| 情報のまとまり | プロジェクト運営者／PMが「Meeting後に決定・Topic・Actionを整理する時」に「会話と採用判断を混同せず仕事を継続できる」を得るための対象・状態・根拠・次の行動を同じ文脈で扱う。 |
| 判断権限 | 対象の判断を確定する主体がCandidateの採用・却下・保留を確定し、記録者は自動昇格しない。利用者は提示された情報から次の行動を選ぶが、正本の意味・状態を無断で変更しない。 |
| 重要な失敗 | 会議記録が自動的に正本へ昇格する |
| 制約・対象外 | 画面、UI部品、API、DB、Class、保存形式および具体的な振る舞いをIAで確定しない。 |
| 人間判断 | UXから継承した未確認事項はプロジェクト運営者／PMを代表する利用者とQual-Labが判断する。IA固有の追加判断はない。正式入力にないObject、状態または責任を追加する必要が生じた場合は人間の決定権限者へ戻す。 |
| IAへ戻す条件 | UI／SPEC分析またはQuality Analysis / IAで、Object・同一性・関係・状態・可視性・時間的な意味が不足または競合すると判明した場合。 |
| 検証意図 | 「候補を採用または却下する場面」に、会議記録が自動的に正本へ昇格することを避け、候補・判断・反映結果を区別することを確認できる必要がある。 |

ここで示す主体は、情報契約上必要な機能責任を表し、特定の人物・組織・Componentへの割当を確定しない。後続工程は、この責任境界を保ったまま実際の主体へ割り当てる。

### 未確認事項と判断

| 区分 | 内容 |
|---|---|
| UXから継承する確認事項 | REQ-000012: プロジェクト運営者／PMが「会議の内容を候補として整理し正本へつなぐ」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |
| 判断者 | プロジェクト運営者／PMを代表する利用者とQual-Lab。 |
| 現在判定 | 後続の実利用確認が必要。現在のUX定義をCanonical化する判断を止める事項ではない。 |
| 未確認時の影響 | 利用者成果、重要場面、失敗および品質期待を仮説として保持し、定量条件や実現方式を確定しない。 |
| IAで追加した未確認事項 | なし。正式入力にない定量条件、状態値または実現方式を追加しない。 |
| IA固有の追加人間判断 | なし。UXから継承した判断をIAで確定済みにしない。 |
| Discoveryへ戻す条件 | 想定した利用者、問題、望ましい変化または制約が誤っていると判明した場合。 |

## 4. 現実照合の参考情報（正式入力ではない）

この節は後続のReality Auditへ引き継ぐ参考情報であり、IA Candidateを導く正式入力ではない。前節までをUX Definitionから再導出した結果として優先する。


| 照合対象 | 結果 |
|---|---|
| UXから導いた意味 | 対象・状態・導線は前節までを正とする。 |
| 現行構造 | プロジェクト運営（project-operation）設計に作成から終了までの流れ（Lifecycle）がある。媒体名で分類せず目的と継続性で分類する。 |
| 採用境界 | 現行の名称や状態値は、UX由来の意味と一致する範囲だけを照合根拠にする。実装にだけ存在する区分はIA定義へ逆流させない。 |

## 5. IA処置

[IA-000010](../../Definitions/IA-000010/ia_definition.md)へ接続する。上記7軸を接続先へ保持し、複数UXを統合する場合も対象固有の状態、失敗、導線を消さない。UXから継承する未確認事項を、判断者と影響を含めて接続先へ保持する。

## 6. 後続工程が保持する意味

| 接続先 | 保持する意味 |
|---|---|
| UI（UX＋IAの正式入力） | 情報の優先度、可視性、状態差、まとまり、見つけ方および関係の理解を保持する。 |
| SPEC（UX＋IAの正式入力） | 対象の識別、関係、状態、可視条件、責任および時間的な意味を保持する。 |
| Quality Analysis / IA（伴走） | 「会話と採用判断を混同せず仕事を継続できる」の成立条件、「会議記録が自動的に正本へ昇格する」という失敗および前章の検証意図を保持する。 |

ArchitectureやSourceへ直接引き渡さない。UI／SPECは、UX DefinitionとIA Definitionの双方を正式入力として分析する。

## 7. 補足分析

なし。必須情報は第1章から第7章に保持する。現行文書・実装との比較は第4章の参考情報として分離し、Canonical IAの根拠には用いない。
