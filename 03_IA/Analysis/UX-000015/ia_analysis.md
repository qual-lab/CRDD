# IA分析: 複数プロジェクトを根拠付きで比較する

成果物種別: IA分析
分析対象: [UX-000015](../../../02_UX/Definitions/UX-000015/ux_definition.md)
状態: 分析済み

## 1. UXから受け取る意味

| 観点 | この分析で受け取る内容 |
|---|---|
| 利用者 | 経営・管理層 |
| 場面 | 複数プロジェクトの一覧の優先度を判断する時 |
| 目的 | 複数プロジェクトを根拠付きで比較する |
| 得たい結果 | 重要差分から必要なプロジェクトだけを掘り下げられる |
| 重要場面 | 要約から優先判断へ進む直前 |
| 避ける失敗 | 単一Scoreや欠測した集計で健全性を断定する |
| 守る品質 | 比較値から根拠・古さ・不足へ戻れる |

画面、API、保存形式は決めず、上記の利用者成果を情報の単位と関係へ変換する。

## 2. 情報候補と関係

| 情報Object | 利用者にとっての意味 | 同一性と関係の基準 |
|---|---|---|
| プロジェクト | 論理的な案件・活動 | プロジェクト識別子（Project ID） |
| 読取り投影 | 比較に使う各プロジェクトの要約 | Project ID＋対象範囲＋観測時点で識別する |
| 網羅範囲 | 複数プロジェクトを根拠付きで比較する際に、「網羅範囲」の意味・状態・対象範囲を他の情報と取り違えないための情報 | 対象、判定時点、情報源で識別し、不明を正常へ丸めない |
| 観測時点 | 複数プロジェクトを根拠付きで比較する際に、「観測時点」の意味・状態・対象範囲を他の情報と取り違えないための情報 | 情報源の識別情報と改訂版または観測時点で識別する |
| 開示範囲 | 複数プロジェクトを根拠付きで比較する際に、「開示範囲」の意味・状態・対象範囲を他の情報と取り違えないための情報 | 対象、判定時点、情報源で識別し、不明を正常へ丸めない |


```text
[O: プロジェクト] ──比較用に投影する──▶ [O: 読取り投影]
      ├── 要約範囲を示す ───▶ [O: 網羅範囲]
      ├── 観測時点を示す ───▶ [O: 観測時点]
      └── 開示可能範囲を示す ─▶ [O: 開示範囲]
```

図中の`[O:]`は情報Objectだけを表す。利用者、判断行為、利用者成果はObjectへ置き換えない。関係名と向きは、同じ対象を追跡し、誤った統合を避けるための情報上の関係であり、画面遷移や実装依存を表さない。

### Canonical化候補

| 接続先 | 分析Object | Canonical Object | 処置 | 判断理由 |
|---|---|---|---|---|
| IA-000006 | プロジェクト | プロジェクト | Same | 同じ論理Projectの識別を保持する |
| IA-000006 | 読取り投影 | 読取り投影 | Same | 比較に使う要約をRead Modelとして保持する |
| IA-000006 | 網羅範囲 | 対象範囲 | Rename | 投影が含む／含まない範囲を保持する |
| ― | 観測時点 | ― | Not Applicable | IA-000006の「状態・可視性・時間的な意味」節へ、観測時点を独立Objectではなく状態・可視条件として保持する |
| ― | 開示範囲 | ― | Not Applicable | IA-000006の「状態・可視性・時間的な意味」節へ、開示範囲を独立Objectではなく状態・可視条件として保持する |

この対応は分析結果からCanonical定義を再構築するための候補である。`Split`または`Merge`でも元の利用者向け意味を失わず、正式入力にないObjectを追加しない。

## 3. 状態・可視性・導線・責任

| 観点 | 分析結果 |
|---|---|
| 状態 | complete／partial／開示制限（restricted）／stale／競合あり（conflicting） |
| 可視性 | 「要約から優先判断へ進む直前」では、比較値から根拠・古さ・不足へ戻れるために必要な状態と不足を判断対象と同じ文脈で示す。詳細な識別情報と根拠は必要時に辿れるようにし、非開示対象は存在自体を推測表示しない。 |
| 導線 | プロジェクト要約→網羅範囲→観測時点→開示範囲。結果なし、判断待ち、失敗または状態不明の場合も、根拠か安全な戻り先を失わない。 |
| 責任 | Repository正本を管理する主体がRepositoryとBindingを保ち、プロジェクト運営主体がProject項目を更新し、読取り投影を生成する責任が投影を作る。 |
| 時間的な意味 | complete／partial／開示制限（restricted）／stale／競合あり（conflicting）の区別を保持する。現在値、古い値、履歴または不明を同じ正常状態へ丸めない。 |
| 情報の優先度 | まず「複数プロジェクトを根拠付きで比較する」の判断に必要な対象・状態・判断要否を示し、識別情報と根拠は必要時に辿れるようにする。 |
| 情報のまとまり | 経営・管理層が「複数プロジェクトの一覧の優先度を判断する時」に「重要差分から必要なプロジェクトだけを掘り下げられる」を得るための対象・状態・根拠・次の行動を同じ文脈で扱う。 |
| 判断権限 | 論理プロジェクトの結合を確定する主体が論理Projectへの結合を、Repository正本を管理する主体が公開可能範囲を確定する。利用者は提示された情報から次の行動を選ぶが、正本の意味・状態を無断で変更しない。 |
| 重要な失敗 | 単一Scoreや欠測した集計で健全性を断定する |
| 制約・対象外 | 画面、UI部品、API、DB、Class、保存形式および具体的な振る舞いをIAで確定しない。 |
| 人間判断 | UXから継承した未確認事項は経営・管理層を代表する利用者とQual-Labが判断する。IA固有の追加判断はない。正式入力にないObject、状態または責任を追加する必要が生じた場合は人間の決定権限者へ戻す。 |
| IAへ戻す条件 | UI／SPEC分析またはQuality Analysis / IAで、Object・同一性・関係・状態・可視性・時間的な意味が不足または競合すると判明した場合。 |
| 検証意図 | 「要約から優先判断へ進む直前」に、単一Scoreや欠測した集計で健全性を断定することを避け、比較値から根拠・古さ・不足へ戻れることを確認できる必要がある。 |

ここで示す主体は、情報契約上必要な機能責任を表し、特定の人物・組織・Componentへの割当を確定しない。後続工程は、この責任境界を保ったまま実際の主体へ割り当てる。

### 未確認事項と判断

| 区分 | 内容 |
|---|---|
| UXから継承する確認事項 | REQ-000013: 経営・管理層が「複数プロジェクトを根拠付きで比較する」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |
| 判断者 | 経営・管理層を代表する利用者とQual-Lab。 |
| 現在判定 | 後続の実利用確認が必要。現在のUX定義をCanonical化する判断を止める事項ではない。 |
| 未確認時の影響 | 利用者成果、重要場面、失敗および品質期待を仮説として保持し、定量条件や実現方式を確定しない。 |
| IAで追加した未確認事項 | なし。正式入力にない定量条件、状態値または実現方式を追加しない。 |
| IA固有の追加人間判断 | なし。UXから継承した判断をIAで確定済みにしない。 |
| Discoveryへ戻す条件 | 想定した利用者、問題、望ましい変化または制約が誤っていると判明した場合。 |

## 4. 現実照合の参考情報（正式入力ではない）

この節は後続のReality Auditへ引き継ぐ参考情報であり、IA Candidateを導く正式入力ではない。前節までをUX Definitionから再導出した結果として優先する。


| 照合対象 | 結果 |
|---|---|
| UXから導いた意味 | 対象・状態・導線は前節までを正とする。 |
| 現行構造 | CROSの横断投影候補を利用できる。単一の評価値（Score）や非開示プロジェクト（Project）の存在を推測しない。 |
| 採用境界 | 現行の名称や状態値は、UX由来の意味と一致する範囲だけを照合根拠にする。実装にだけ存在する区分はIA定義へ逆流させない。 |

## 5. IA処置

[IA-000006](../../Definitions/IA-000006/ia_definition.md)へ接続する。上記7軸を接続先へ保持し、複数UXを統合する場合も対象固有の状態、失敗、導線を消さない。UXから継承する未確認事項を、判断者と影響を含めて接続先へ保持する。

## 6. 後続工程が保持する意味

| 接続先 | 保持する意味 |
|---|---|
| UI（UX＋IAの正式入力） | 情報の優先度、可視性、状態差、まとまり、見つけ方および関係の理解を保持する。 |
| SPEC（UX＋IAの正式入力） | 対象の識別、関係、状態、可視条件、責任および時間的な意味を保持する。 |
| Quality Analysis / IA（伴走） | 「重要差分から必要なプロジェクトだけを掘り下げられる」の成立条件、「単一Scoreや欠測した集計で健全性を断定する」という失敗および前章の検証意図を保持する。 |

ArchitectureやSourceへ直接引き渡さない。UI／SPECは、UX DefinitionとIA Definitionの双方を正式入力として分析する。

## 7. 補足分析

なし。必須情報は第1章から第7章に保持する。現行文書・実装との比較は第4章の参考情報として分離し、Canonical IAの根拠には用いない。
