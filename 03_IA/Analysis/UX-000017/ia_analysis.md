# IA分析: 実行時データを安全に保持・清掃する

成果物種別: IA分析
分析対象: [UX-000017](../../../02_UX/Definitions/UX-000017/ux_definition.md)
状態: 分析済み

## 1. UXから受け取る意味

| 観点 | この分析で受け取る内容 |
|---|---|
| 利用者 | 実行環境の導入・運用者 |
| 場面 | 実行時データを作成または清掃する時 |
| 目的 | 実行時データの所有場所と一連の状態変化を理解する |
| 得たい結果 | 保存場所の内部構造を推測せず、保持すべき状態と一時物を区別して安全に作業を継続・終了できる |
| 重要場面 | 永続化または削除の直前 |
| 避ける失敗 | subdirectoryや別基点フォルダへ同名データを作る |
| 守る品質 | 用途別領域とcleanup条件を明示する |

画面、API、保存形式は決めず、上記の利用者成果を情報の単位と関係へ変換する。

## 2. 情報候補と関係

| 情報Object | 利用者にとっての意味 | 同一性と関係の基準 |
|---|---|---|
| 実行データ | 用途を持つ実行時情報 | 責任者（Owner）＋目的（Purpose）＋識別子（Identity） |
| 責任者 | 実行時データの所有場所と一連の状態変化を理解する際に、「責任者」の意味・状態・対象範囲を他の情報と取り違えないための情報 | 主体、対象範囲、有効時点で識別する |
| 基点フォルダ | 実行データの管理基点 | 検証済みRootで識別する |
| 永続性 | 再起動後も必要か | 一時（temporary）／保持必要（durable） |
| 保持期間 | 保持する期間と上限 | 実行データ（Data Item）へ結ぶ |
| 清掃根拠 | 終了後の不存在根拠 | 対象と観測へ結合 |


```text
[O: 基点フォルダ]
      │ 含む
      ▼
[O: 実行データ] ◀──所有する── [O: 責任者]
      ├── 保持性を持つ ─────────▶ [O: 永続性]
      ├── 保持条件を持つ ────────▶ [O: 保持期間]
      └── 終了後の不存在を確認する ─▶ [O: 清掃根拠]
```

図中の`[O:]`は情報Objectだけを表す。利用者、判断行為、利用者成果はObjectへ置き換えない。関係名と向きは、同じ対象を追跡し、誤った統合を避けるための情報上の関係であり、画面遷移や実装依存を表さない。

### Canonical化候補

| 接続先 | 分析Object | Canonical Object | 処置 | 判断理由 |
|---|---|---|---|---|
| IA-000012 | 実行データ | 実行データ | Same | 通常時と失敗後の同じData Itemとして扱う |
| ― | 責任者 | ― | Not Applicable | IA-000012の「責任と判断権限」表へ、責任者を独立Objectではなく機能責任・権限として保持する |
| IA-000012 | 基点フォルダ | 実行データの基点 | Rename | 同じRuntime領域を識別・回復する基点として表示を明確にする |
| IA-000012 | 永続性 | 永続性 | Same | 再生成可否と回復要否を保持する |
| IA-000012 | 保持期間 | 保持条件 | Rename | 期間だけでなく参照・回復条件を含める |
| IA-000012 | 清掃根拠 | 清掃根拠 | Same | 削除許可と終了後不存在のEvidenceを保持する |

この対応は分析結果からCanonical定義を再構築するための候補である。`Split`または`Merge`でも元の利用者向け意味を失わず、正式入力にないObjectを追加しない。

## 3. 状態・可視性・導線・責任

| 観点 | 分析結果 |
|---|---|
| 状態 | 一時（temporary）／保持必要（durable）／回復必要（recovery_required）／清掃可能（eligible_for_cleanup）／不明（unknown） |
| 可視性 | 「永続化または削除の直前」では、用途別領域とcleanup条件を明示するために必要な状態と不足を判断対象と同じ文脈で示す。詳細な識別情報と根拠は必要時に辿れるようにし、非開示対象は存在自体を推測表示しない。 |
| 導線 | 実行データ→責任者→基点フォルダ→永続性→保持期間→清掃根拠。結果なし、判断待ち、失敗または状態不明の場合も、根拠か安全な戻り先を失わない。 |
| 責任 | 実行データを管理する主体がData Item・Durability・Retentionを記録し、回復・清掃を実行する主体が義務と清掃根拠を更新する。 |
| 時間的な意味 | 一時（temporary）／保持必要（durable）／回復必要（recovery_required）／清掃可能（eligible_for_cleanup）／不明（unknown）の区別を保持する。現在値、古い値、履歴または不明を同じ正常状態へ丸めない。 |
| 情報の優先度 | まず「実行時データの所有場所と一連の状態変化を理解する」の判断に必要な対象・状態・判断要否を示し、識別情報と根拠は必要時に辿れるようにする。 |
| 情報のまとまり | 実行環境の導入・運用者が「実行時データを作成または清掃する時」に「保存場所の内部構造を推測せず、保持すべき状態と一時物を区別して安全に作業を継続・終了できる」を得るための対象・状態・根拠・次の行動を同じ文脈で扱う。 |
| 判断権限 | Repository／実行基盤を管理する主体が保持方針を、回復完了と削除可否を確定する主体が回復完了と削除可否を確定する。利用者は提示された情報から次の行動を選ぶが、正本の意味・状態を無断で変更しない。 |
| 重要な失敗 | subdirectoryや別基点フォルダへ同名データを作る |
| 制約・対象外 | 画面、UI部品、API、DB、Class、保存形式および具体的な振る舞いをIAで確定しない。 |
| 人間判断 | UXから継承した未確認事項は実行環境の導入・運用者を代表する利用者とQual-Labが判断する。IA固有の追加判断はない。正式入力にないObject、状態または責任を追加する必要が生じた場合は人間の決定権限者へ戻す。 |
| IAへ戻す条件 | UI／SPEC分析またはQuality Analysis / IAで、Object・同一性・関係・状態・可視性・時間的な意味が不足または競合すると判明した場合。 |
| 検証意図 | 「永続化または削除の直前」に、subdirectoryや別基点フォルダへ同名データを作ることを避け、用途別領域とcleanup条件を明示することを確認できる必要がある。 |

ここで示す主体は、情報契約上必要な機能責任を表し、特定の人物・組織・Componentへの割当を確定しない。後続工程は、この責任境界を保ったまま実際の主体へ割り当てる。

### 未確認事項と判断

| 区分 | 内容 |
|---|---|
| UXから継承する確認事項 | REQ-000015: 実行環境の導入・運用者が「実行時データの所有場所と一連の状態変化を理解する」を行う際の判断基準、許容負担、利用環境および失敗後の選択／REQ-000022: 実行環境の導入・運用者が「残存資源の由来・保持・清掃・回復を理解する」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |
| 判断者 | 実行環境の導入・運用者を代表する利用者とQual-Lab。 |
| 現在判定 | 後続の実利用確認が必要。現在のUX定義をCanonical化する判断を止める事項ではない。 |
| 未確認時の影響 | 利用者成果、重要場面、失敗および品質期待を仮説として保持し、定量条件や実現方式を確定しない。 |
| IAで追加した未確認事項 | なし。正式入力にない定量条件、状態値または実現方式を追加しない。 |
| IA固有の追加人間判断 | なし。UXから継承した判断をIAで確定済みにしない。 |
| Discoveryへ戻す条件 | 想定した利用者、問題、望ましい変化または制約が誤っていると判明した場合。 |

## 4. 現実照合の参考情報（正式入力ではない）

この節は後続のReality Auditへ引き継ぐ参考情報であり、IA Candidateを導く正式入力ではない。前節までをUX Definitionから再導出した結果として優先する。


| 照合対象 | 結果 |
|---|---|
| UXから導いた意味 | 対象・状態・導線は前節までを正とする。 |
| 現行構造 | 実行時データ部品（runtime-data package）と`.crdd`規則がある。名前や経過時間だけで削除しない。 |
| 採用境界 | 現行の名称や状態値は、UX由来の意味と一致する範囲だけを照合根拠にする。実装にだけ存在する区分はIA定義へ逆流させない。 |

## 5. IA処置

[IA-000012](../../Definitions/IA-000012/ia_definition.md)へ接続する。上記7軸を接続先へ保持し、複数UXを統合する場合も対象固有の状態、失敗、導線を消さない。UXから継承する未確認事項を、判断者と影響を含めて接続先へ保持する。

## 6. 後続工程が保持する意味

| 接続先 | 保持する意味 |
|---|---|
| UI（UX＋IAの正式入力） | 情報の優先度、可視性、状態差、まとまり、見つけ方および関係の理解を保持する。 |
| SPEC（UX＋IAの正式入力） | 対象の識別、関係、状態、可視条件、責任および時間的な意味を保持する。 |
| Quality Analysis / IA（伴走） | 「保存場所の内部構造を推測せず、保持すべき状態と一時物を区別して安全に作業を継続・終了できる」の成立条件、「subdirectoryや別基点フォルダへ同名データを作る」という失敗および前章の検証意図を保持する。 |

ArchitectureやSourceへ直接引き渡さない。UI／SPECは、UX DefinitionとIA Definitionの双方を正式入力として分析する。

## 7. 補足分析

なし。必須情報は第1章から第7章に保持する。現行文書・実装との比較は第4章の参考情報として分離し、Canonical IAの根拠には用いない。
