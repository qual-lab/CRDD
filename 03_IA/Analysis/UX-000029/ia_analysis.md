# IA分析: 作業・変更・根拠・品質を迷わず辿る

成果物種別: IA分析
分析対象: [UX-000029](../../../02_UX/Definitions/UX-000029/ux_definition.md)
状態: 分析済み

## 1. UXから受け取る意味

| 観点 | この分析で受け取る内容 |
|---|---|
| 利用者 | CRDD作成者・保守者 |
| 場面 | 変更の現在地や根拠を調べる時 |
| 目的 | 作業・変更・根拠・品質を役割別に辿る |
| 得たい結果 | 変更理由と全影響パスを重複なく確認できる |
| 重要場面 | 変更の影響漏れを確認する場面 |
| 避ける失敗 | 同じ説明を複製し代表ファイルだけで済ませる |
| 守る品質 | 正本を分け全影響ファイルを列挙する |

画面、API、保存形式は決めず、上記の利用者成果を情報の単位と関係へ変換する。

## 2. 情報候補と関係

| 情報Object | 利用者にとっての意味 | 同一性と関係の基準 |
|---|---|---|
| 作業 | Roadmap上で未完了の仕事 | Item IDで識別する |
| 変更 | 採用した変更意図 | CHG ID |
| 変更対象ファイル | 変更が入った物理ファイル | Repository-relative Path |
| 根拠 | 実行条件と観測結果 | 改訂版（Revision）へ結合 |
| 観測した改訂版 | 確認対象の固定版 | 改訂版の識別子（Revision Identity） |
| 品質状態 | 現在の保証状態 | ScopeとEvidenceから評価 |


```text
[O: 作業]
      │ 変更として記録される
      ▼
[O: 変更]
      ├── 影響する ──▶ [O: 変更対象ファイル]
      └── 理由を持つ ─▶ [O: 根拠]
                              │ 観測対象版を固定する
                              ▼
                       [O: 観測した改訂版]
                              │ 品質判断を支える
                              ▼
                       [O: 品質状態]
```

図中の`[O:]`は情報Objectだけを表す。利用者、判断行為、利用者成果はObjectへ置き換えない。関係名と向きは、同じ対象を追跡し、誤った統合を避けるための情報上の関係であり、画面遷移や実装依存を表さない。

### Canonical化候補

| 接続先 | 分析Object | Canonical Object | 処置 | 判断理由 |
|---|---|---|---|---|
| IA-000016 | 作業 | ロードマップ項目 | Rename | 未完了の変更単位として保持する |
| IA-000016 | 変更 | 変更 | Same | 意図と構造差を持つChangeとして保持する |
| IA-000016 | 変更対象ファイル | 変更ファイル | Rename | Changeの物理的影響先として保持する |
| IA-000016 | 根拠 | 検証根拠 | Rename | 何を確認したかと結果を持つ根拠として表示を明確にする |
| IA-000016 | 観測した改訂版 | 改訂版 | Rename | 同じRevisionをCanonical表示へ揃える |
| IA-000016 | 品質状態 | 品質状態 | Same | Designed／Executed／Passed等の状態を保持する |

この対応は分析結果からCanonical定義を再構築するための候補である。`Split`または`Merge`でも元の利用者向け意味を失わず、正式入力にないObjectを追加しない。

## 3. 状態・可視性・導線・責任

| 観点 | 分析結果 |
|---|---|
| 状態 | 計画済み（planned）／進行中（in_progress）／確認済み（verified）／公開済み（released）と品質状態を別にする |
| 可視性 | 「変更の影響漏れを確認する場面」では、正本を分け全影響ファイルを列挙するために必要な状態と不足を判断対象と同じ文脈で示す。詳細な識別情報と根拠は必要時に辿れるようにし、非開示対象は存在自体を推測表示しない。 |
| 導線 | 作業→変更→変更対象ファイル→根拠→観測した改訂版→品質状態。結果なし、判断待ち、失敗または状態不明の場合も、根拠か安全な戻り先を失わない。 |
| 責任 | 変更担当がRoadmap Item・Change・Changed File・Remediationを更新し、Reviewer／Quality担当がFinding・Evidence・Quality Stateを記録する。 |
| 時間的な意味 | 計画済み（planned）／進行中（in_progress）／確認済み（verified）／公開済み（released）と品質状態を別にするの区別を保持する。現在値、古い値、履歴または不明を同じ正常状態へ丸めない。 |
| 情報の優先度 | まず「作業・変更・根拠・品質を役割別に辿る」の判断に必要な対象・状態・判断要否を示し、識別情報と根拠は必要時に辿れるようにする。 |
| 情報のまとまり | CRDD作成者・保守者が「変更の現在地や根拠を調べる時」に「変更理由と全影響パスを重複なく確認できる」を得るための対象・状態・根拠・次の行動を同じ文脈で扱う。 |
| 判断権限 | 変更Ownerが是正案を、独立ReviewerがFinding解消を、公開可否を決める主体が公開可否をそれぞれ確定する。利用者は提示された情報から次の行動を選ぶが、正本の意味・状態を無断で変更しない。 |
| 重要な失敗 | 同じ説明を複製し代表ファイルだけで済ませる |
| 制約・対象外 | 画面、UI部品、API、DB、Class、保存形式および具体的な振る舞いをIAで確定しない。 |
| 人間判断 | UXから継承した未確認事項はCRDD作成者・保守者を代表する利用者とQual-Labが判断する。IA固有の追加判断はない。正式入力にないObject、状態または責任を追加する必要が生じた場合は人間の決定権限者へ戻す。 |
| IAへ戻す条件 | UI／SPEC分析またはQuality Analysis / IAで、Object・同一性・関係・状態・可視性・時間的な意味が不足または競合すると判明した場合。 |
| 検証意図 | 「変更の影響漏れを確認する場面」に、同じ説明を複製し代表ファイルだけで済ませることを避け、正本を分け全影響ファイルを列挙することを確認できる必要がある。 |

ここで示す主体は、情報契約上必要な機能責任を表し、特定の人物・組織・Componentへの割当を確定しない。後続工程は、この責任境界を保ったまま実際の主体へ割り当てる。

### 未確認事項と判断

| 区分 | 内容 |
|---|---|
| UXから継承する確認事項 | REQ-000033: CRDD作成者・保守者が「作業・変更・根拠・品質を役割別に辿る」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |
| 判断者 | CRDD作成者・保守者を代表する利用者とQual-Lab。 |
| 現在判定 | 後続の実利用確認が必要。現在のUX定義をCanonical化する判断を止める事項ではない。 |
| 未確認時の影響 | 利用者成果、重要場面、失敗および品質期待を仮説として保持し、定量条件や実現方式を確定しない。 |
| IAで追加した未確認事項 | なし。正式入力にない定量条件、状態値または実現方式を追加しない。 |
| IA固有の追加人間判断 | なし。UXから継承した判断をIAで確定済みにしない。 |
| Discoveryへ戻す条件 | 想定した利用者、問題、望ましい変化または制約が誤っていると判明した場合。 |

## 4. 現実照合の参考情報（正式入力ではない）

この節は後続のReality Auditへ引き継ぐ参考情報であり、IA Candidateを導く正式入力ではない。前節までをUX Definitionから再導出した結果として優先する。


| 照合対象 | 結果 |
|---|---|
| UXから導いた意味 | 対象・状態・導線は前節までを正とする。 |
| 現行構造 | Roadmap／CHG／Quality／Releaseの責務分離済み。Git履歴を実行基盤（Runtime）成立の必須条件にしない。 |
| 採用境界 | 現行の名称や状態値は、UX由来の意味と一致する範囲だけを照合根拠にする。実装にだけ存在する区分はIA定義へ逆流させない。 |

## 5. IA処置

[IA-000016](../../Definitions/IA-000016/ia_definition.md)へ接続する。上記7軸を接続先へ保持し、複数UXを統合する場合も対象固有の状態、失敗、導線を消さない。UXから継承する未確認事項を、判断者と影響を含めて接続先へ保持する。

## 6. 後続工程が保持する意味

| 接続先 | 保持する意味 |
|---|---|
| UI（UX＋IAの正式入力） | 情報の優先度、可視性、状態差、まとまり、見つけ方および関係の理解を保持する。 |
| SPEC（UX＋IAの正式入力） | 対象の識別、関係、状態、可視条件、責任および時間的な意味を保持する。 |
| Quality Analysis / IA（伴走） | 「変更理由と全影響パスを重複なく確認できる」の成立条件、「同じ説明を複製し代表ファイルだけで済ませる」という失敗および前章の検証意図を保持する。 |

ArchitectureやSourceへ直接引き渡さない。UI／SPECは、UX DefinitionとIA Definitionの双方を正式入力として分析する。

## 7. 補足分析

なし。必須情報は第1章から第7章に保持する。現行文書・実装との比較は第4章の参考情報として分離し、Canonical IAの根拠には用いない。
