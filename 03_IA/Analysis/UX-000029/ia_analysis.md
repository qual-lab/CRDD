# IA分析: 作業・変更・根拠・品質を迷わず辿る

成果物種別: IA分析
分析対象: [UX-000029](../../../02_UX/Definitions/UX-000029/ux_definition.md)
状態: 分析済み

## 1. UXから受け取る意味

| 観点 | この分析で受け取る内容 |
|---|---|
| 利用者 | CRDD作成者・保守者 |
| 場面 | 変更の現在地や根拠を調べる時 |
| 目的 | 作業・変更・根拠・品質を役割別に辿る |
| 得たい結果 | 変更理由と全影響パスを重複なく確認できる |
| 重要場面 | 変更の影響漏れを確認する場面 |
| 避ける失敗 | 同じ説明を複製し代表ファイルだけで済ませる |
| 守る品質 | 正本を分け全影響ファイルを列挙する |

画面、API、保存形式は決めず、上記の利用者成果を情報の単位と関係へ変換する。

## 2. 情報候補と関係

| 候補 | 利用者にとっての意味 | 識別・関係 |
|---|---|---|
| 見分ける対象 | Work、変更（Change）、変更ファイル（Changed File）、検証根拠（Evidence）、Observed 改訂版（Revision）、品質状態（Quality State） | 対象を同一視せず、「Roadmap→Change→対象ファイル→Evidence→Quality→Release」の順に関係付ける。識別できない対象は既知の対象へ推定統合しない。 |
| 根拠と次の行動 | Roadmap→Change→対象ファイル→Evidence→Quality→Release | 起点、判断対象、根拠、戻り先を同じ流れとして辿れるようにする。 |

```text
[O: CRDD作成者・保守者の判断] --確認する--> [O: Work]
[O: Work] --根拠と次の行動を辿る--> [O: 変更理由と全影響パスを重複なく確認できる]
```

## 3. 状態・可視性・導線・責任

| 観点 | 分析結果 |
|---|---|
| 状態 | 計画済み（planned）／進行中（in_progress）／確認済み（verified）／公開済み（released）と品質状態を別にする |
| 可視性 | 変更の影響漏れを確認する場面では、正本を分け全影響ファイルを列挙するために必要な状態と不足を判断対象と同じ文脈で示す。詳細な識別情報と根拠は必要時に辿れるようにし、非開示対象は存在自体を推測表示しない。 |
| 導線 | Roadmap→Change→対象ファイル→Evidence→Quality→Release。結果がない、判断待ち、または状態不明の場合も、根拠か安全な戻り先を失わない。 |
| 責任 | CRDD作成者・保守者は「作業・変更・根拠・品質を役割別に辿る」ために必要な判断を行う。システムは「変更理由と全影響パスを重複なく確認できる」を支える対象・状態・根拠を示し、「同じ説明を複製し代表ファイルだけで済ませる」という誤認を生まない責任を持つ。 |

## 4. 現行文書・実装との照合

| 照合対象 | 結果 |
|---|---|
| UXから導いた意味 | 対象・状態・導線は前節までを正とする。 |
| 現行構造 | Roadmap／CHG／Quality／Releaseの責務分離済み。Git履歴を実行基盤（Runtime）成立の必須条件にしない。 |
| 採用境界 | 現行の名称や状態値は、UX由来の意味と一致する範囲だけを照合根拠にする。実装にだけ存在する区分はIA定義へ逆流させない。 |

## 5. IA処置

[IA-000016](../../Definitions/IA-000016/ia_definition.md)へ接続する。上記7軸を接続先へ保持し、複数UXを統合する場合も対象固有の状態、失敗、導線を消さない。試作上の理解しやすさは未確認として下流へ渡す。
