# IA分析: 入口を変えても同じ仕事を続ける

成果物種別: IA分析
分析対象: [UX-000012](../../../02_UX/Definitions/UX-000012/ux_definition.md)
状態: 分析済み

## 1. UXから受け取る意味

| 観点 | この分析で受け取る内容 |
|---|---|
| 利用者 | 開発者 |
| 場面 | ローカルMCPの通信方式を選ぶ時 |
| 目的 | 通信方式を変えても同じ公開契約・入力・権限判断で操作する |
| 得たい結果 | stdio MCPとlocalhost HTTPのどちらでも、同じ入力・権限・状態・結果で仕事を続けられる |
| 重要場面 | 入口を切り替えて同じ仕事を開始・継続する場面 |
| 避ける失敗 | 通信方式によって入力・権限判断・状態・結果の意味が変わる |
| 守る品質 | 公開契約・入力・権限判断・状態・結果を通信方式間で一致させる |

画面、API、保存形式は決めず、上記の利用者成果を情報の単位と関係へ変換する。

## 2. 情報候補と関係

| 情報Object | 利用者にとっての意味 | 同一性と関係の基準 |
|---|---|---|
| 処理結果 | 通信方式を変えても同じ公開契約・入力・権限判断で操作する際に、「処理結果」の意味・状態・対象範囲を他の情報と取り違えないための情報 | 元の依頼・対象・改訂版へ結び、別の結果と混同しない |
| 公開依頼 | 公開入口へ渡す処理目的・対象・必要な許可を一つにした依頼 | Request Identityで識別する |
| 公開契約 | 入力と結果の意味 | Contract ID＋改訂版（Revision） |
| 通信方式 | 公開契約を運ぶ通信手段 | 通信方式種別（Transport Kind）で識別する |
| 外部作用の発行状態 | 依頼から外部作用が発行されたかを示す状態 | 依頼（Request）／試行（Attempt）へ結合し、判定時点を保持する |


```text
[O: 公開依頼] ──従う─────────┐
                                    ▼
[O: 通信方式] ──運ぶ───────▶ [O: 公開契約]
                                    │ 同じ意味で返す
                                    ▼
                              [O: 処理結果]
                                    │ 作用の有無を明示する
                                    ▼
                         [O: 外部作用の発行状態]
```

図中の`[O:]`は情報Objectだけを表す。利用者、判断行為、利用者成果はObjectへ置き換えない。関係名と向きは、同じ対象を追跡し、誤った統合を避けるための情報上の関係であり、画面遷移や実装依存を表さない。

### Canonical化候補

| 接続先 | 分析Object | Canonical Object | 処置 | 判断理由 |
|---|---|---|---|---|
| IA-000008 | 処理結果 | 公開結果 | Rename | 入口によらず同じ意味で返す結果とする |
| IA-000008 | 公開依頼 | 公開依頼 | Same | 公開入口へ渡す要求単位として保持する |
| IA-000008 | 公開契約 | 公開契約 | Same | 公開入口が守るApplication Contractとして保持する |
| IA-000008 | 通信方式 | 通信手段 | Rename | 契約を運ぶTransportとして分離する |
| IA-000008 | 外部作用の発行状態 | 作用状態 | Rename | 要求受付とEffect成立を分けて保持する |

この対応は分析結果からCanonical定義を再構築するための候補である。`Split`または`Merge`でも元の利用者向け意味を失わず、正式入力にないObjectを追加しない。

## 3. 状態・可視性・導線・責任

| 観点 | 分析結果 |
|---|---|
| 状態 | 受付前／受付済み／作用前失敗／作用後失敗／結果あり |
| 可視性 | 「入口を切り替えて同じ仕事を開始・継続する場面」では、公開契約・入力・権限判断・状態・結果を通信方式間で一致させるために必要な状態と不足を判断対象と同じ文脈で示す。詳細な識別情報と根拠は必要時に辿れるようにし、非開示対象は存在自体を推測表示しない。 |
| 導線 | 公開依頼→公開契約→通信方式→処理結果→外部作用の発行状態。結果なし、判断待ち、失敗または状態不明の場合も、根拠か安全な戻り先を失わない。 |
| 責任 | 公開契約と結果を作る責任が公開契約と結果を生成し、依頼・通信・結果を運ぶ責任が依頼・通信・結果搬送を担当する。 |
| 時間的な意味 | 受付前／受付済み／作用前失敗／作用後失敗／結果ありの区別を保持する。現在値、古い値、履歴または不明を同じ正常状態へ丸めない。 |
| 情報の優先度 | まず「通信方式を変えても同じ公開契約・入力・権限判断で操作する」の判断に必要な対象・状態・判断要否を示し、識別情報と根拠は必要時に辿れるようにする。 |
| 情報のまとまり | 開発者が「ローカルMCPの通信方式を選ぶ時」に「stdio MCPとlocalhost HTTPのどちらでも、同じ入力・権限・状態・結果で仕事を続けられる」を得るための対象・状態・根拠・次の行動を同じ文脈で扱う。 |
| 判断権限 | 呼出元が依頼と作用許可を与え、公開契約を管理する主体が公開契約の意味を確定する。利用者は提示された情報から次の行動を選ぶが、正本の意味・状態を無断で変更しない。 |
| 重要な失敗 | 通信方式によって入力・権限判断・状態・結果の意味が変わる |
| 制約・対象外 | 画面、UI部品、API、DB、Class、保存形式および具体的な振る舞いをIAで確定しない。 |
| 人間判断 | UXから継承した未確認事項は開発者を代表する利用者とQual-Labが判断する。IA固有の追加判断はない。正式入力にないObject、状態または責任を追加する必要が生じた場合は人間の決定権限者へ戻す。 |
| IAへ戻す条件 | UI／SPEC分析またはQuality Analysis / IAで、Object・同一性・関係・状態・可視性・時間的な意味が不足または競合すると判明した場合。 |
| 検証意図 | 「入口を切り替えて同じ仕事を開始・継続する場面」に、通信方式によって入力・権限判断・状態・結果の意味が変わることを避け、公開契約・入力・権限判断・状態・結果を通信方式間で一致させることを確認できる必要がある。 |

ここで示す主体は、情報契約上必要な機能責任を表し、特定の人物・組織・Componentへの割当を確定しない。後続工程は、この責任境界を保ったまま実際の主体へ割り当てる。

### 未確認事項と判断

| 区分 | 内容 |
|---|---|
| UXから継承する確認事項 | REQ-000006: 開発者が「stdioとHTTPで同じ意味の操作を行う」を行う際の判断基準、許容負担、利用環境および失敗後の選択／REQ-000010: プロジェクト運営者／PMが「入口が違っても同じプロジェクト操作を行う」を行う際の判断基準、許容負担、利用環境および失敗後の選択／REQ-000028: 開発者が「入口が違っても同じCRDD正本と判断境界を使う」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |
| 判断者 | 開発者を代表する利用者とQual-Lab。 |
| 現在判定 | 後続の実利用確認が必要。現在のUX定義をCanonical化する判断を止める事項ではない。 |
| 未確認時の影響 | 利用者成果、重要場面、失敗および品質期待を仮説として保持し、定量条件や実現方式を確定しない。 |
| IAで追加した未確認事項 | なし。正式入力にない定量条件、状態値または実現方式を追加しない。 |
| IA固有の追加人間判断 | なし。UXから継承した判断をIAで確定済みにしない。 |
| Discoveryへ戻す条件 | 想定した利用者、問題、望ましい変化または制約が誤っていると判明した場合。 |

## 4. 現実照合の参考情報（正式入力ではない）

この節は後続のReality Auditへ引き継ぐ参考情報であり、IA Candidateを導く正式入力ではない。前節までをUX Definitionから再導出した結果として優先する。


| 照合対象 | 結果 |
|---|---|
| UXから導いた意味 | 対象・状態・導線は前節までを正とする。 |
| 現行構造 | MCP stdioとlocalhost HTTPは通信方式の接続部（Transport adapter）である。通信エラーと業務結果を分ける。 |
| 採用境界 | 現行の名称や状態値は、UX由来の意味と一致する範囲だけを照合根拠にする。実装にだけ存在する区分はIA定義へ逆流させない。 |

## 5. IA処置

[IA-000008](../../Definitions/IA-000008/ia_definition.md)へ接続する。上記7軸を接続先へ保持し、複数UXを統合する場合も対象固有の状態、失敗、導線を消さない。UXから継承する未確認事項を、判断者と影響を含めて接続先へ保持する。

## 6. 後続工程が保持する意味

| 接続先 | 保持する意味 |
|---|---|
| UI（UX＋IAの正式入力） | 情報の優先度、可視性、状態差、まとまり、見つけ方および関係の理解を保持する。 |
| SPEC（UX＋IAの正式入力） | 対象の識別、関係、状態、可視条件、責任および時間的な意味を保持する。 |
| Quality Analysis / IA（伴走） | 「stdio MCPとlocalhost HTTPのどちらでも、同じ入力・権限・状態・結果で仕事を続けられる」の成立条件、「通信方式によって入力・権限判断・状態・結果の意味が変わる」という失敗および前章の検証意図を保持する。 |

ArchitectureやSourceへ直接引き渡さない。UI／SPECは、UX DefinitionとIA Definitionの双方を正式入力として分析する。

## 7. 補足分析

なし。必須情報は第1章から第7章に保持する。現行文書・実装との比較は第4章の参考情報として分離し、Canonical IAの根拠には用いない。
