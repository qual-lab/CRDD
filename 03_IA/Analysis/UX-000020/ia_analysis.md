# IA分析: 利用環境の信頼方針で実行基盤を選ぶ

成果物種別: IA分析
分析対象: [UX-000020](../../../02_UX/Definitions/UX-000020/ux_definition.md)
状態: 分析済み

## 1. UXから受け取る意味

| 観点 | この分析で受け取る内容 |
|---|---|
| 利用者 | 実行環境の導入・運用者 |
| 場面 | 実行基盤を導入または更新する時 |
| 目的 | 実行環境の信頼の各要素を別々に評価する |
| 得たい結果 | 準拠、改ざん有無、配布者、公式表示および実行許可を区別し、自分の環境の方針で公式版・派生版・組織版を選べる |
| 重要場面 | 実行を信頼すると判断する場面 |
| 避ける失敗 | 一つの署名表示を全保証と誤認する |
| 守る品質 | 保証要素と決定権限を分離表示する |

画面、API、保存形式は決めず、上記の利用者成果を情報の単位と関係へ変換する。

## 2. 情報候補と関係

| 情報Object | 利用者にとっての意味 | 同一性と関係の基準 |
|---|---|---|
| 準拠状況 | CRDD契約への準拠 | 適用範囲（Profile）＋結果（Result） |
| 改ざん有無 | 実行環境の信頼の各要素を別々に評価する際に、「改ざん有無」の意味・状態・対象範囲を他の情報と取り違えないための情報 | Artifact Identity・改訂版・確認時点へ結ぶ |
| 配布者 | 成果物（Artifact）を作成・配布した主体 | 配布者（Publisher） Identity |
| 信頼方針 | 利用環境が信頼する条件 | Policy 責任者（Owner）＋改訂版（Revision） |
| 導入先 | 実行環境の信頼の各要素を別々に評価する際に、「導入先」の意味・状態・対象範囲を他の情報と取り違えないための情報 | 検証済みの対象と範囲へ結び、表示名だけで同一視しない |
| 配布物 | 準拠・完全性・配布者を評価する対象 | Artifact IdentityとRevisionで識別する |

```text
                              [O: 配布者]
                                    │ 配布する
                                    ▼
[O: 信頼方針] ──利用可否を評価する──▶ [O: 配布物]
                                    ├── 導入される ────▶ [O: 導入先]
                                    ├── 評価対象になる ─▶ [O: 準拠状況]
                                    └── 完全性を示す ───▶ [O: 改ざん有無]
```

図中の`[O:]`は情報Objectだけを表す。利用者、判断行為、利用者成果はObjectへ置き換えない。関係名と向きは、同じ対象を追跡し、誤った統合を避けるための情報上の関係であり、画面遷移や実装依存を表さない。

### Canonical化候補

| 接続先 | 分析Object | Canonical Object | 処置 | 判断理由 |
|---|---|---|---|---|
| IA-000015 | 準拠状況 | 準拠 | Rename | Contractへの適合という同じ意味をCanonical表示へ揃える |
| IA-000015 | 改ざん有無 | 完全性 | Rename | Artifactが改変されていないという同じ意味をCanonical表示へ揃える |
| IA-000015 | 配布者 | 配布者 | Same | 誰がArtifactを出したかを保持する |
| IA-000015 | 信頼方針 | 信頼方針 | Same | 利用環境が所有するTrust Policyを保持する |
| ― | 導入先 | ― | Not Applicable | IA-000015の利用場面と判断権限へ、信頼方針を適用する環境として保持し、配布物そのものへ変換しない |
| IA-000015 | 配布物 | 配布物 | Same | 評価対象となるArtifactを保持する |

この対応は分析結果からCanonical定義を再構築するための候補である。`Split`または`Merge`でも元の利用者向け意味を失わず、正式入力にないObjectを追加しない。

## 3. 状態・可視性・導線・責任

| 観点 | 分析結果 |
|---|---|
| 状態 | 確認済み（verified）／未確認（unverified）／信頼済み（trusted）／非信頼（not_trusted）を別軸にする |
| 可視性 | 「実行を信頼すると判断する場面」では、保証要素と決定権限を分離表示するために必要な状態と不足を判断対象と同じ文脈で示す。詳細な識別情報と根拠は必要時に辿れるようにし、非開示対象は存在自体を推測表示しない。 |
| 導線 | 準拠状況→改ざん有無→配布者→信頼方針→導入先。結果なし、判断待ち、失敗または状態不明の場合も、根拠か安全な戻り先を失わない。 |
| 責任 | 配布物・署名・配布者Identityを提供する責任と、準拠・品質の評価結果を記録する責任を分ける。 |
| 時間的な意味 | 確認済み（verified）／未確認（unverified）／信頼済み（trusted）／非信頼（not_trusted）を別軸にするの区別を保持する。現在値、古い値、履歴または不明を同じ正常状態へ丸めない。 |
| 情報の優先度 | まず「実行環境の信頼の各要素を別々に評価する」の判断に必要な対象・状態・判断要否を示し、識別情報と根拠は必要時に辿れるようにする。 |
| 情報のまとまり | 実行環境の導入・運用者が「実行基盤を導入または更新する時」に「準拠、改ざん有無、配布者、公式表示および実行許可を区別し、自分の環境の方針で公式版・派生版・組織版を選べる」を得るための対象・状態・根拠・次の行動を同じ文脈で扱う。 |
| 判断権限 | 導入環境の信頼方針を決める主体がTrust Policyと利用可否を決め、Publisherの署名だけで信頼を強制しない。利用者は提示された情報から次の行動を選ぶが、正本の意味・状態を無断で変更しない。 |
| 重要な失敗 | 一つの署名表示を全保証と誤認する |
| 制約・対象外 | 画面、UI部品、API、DB、Class、保存形式および具体的な振る舞いをIAで確定しない。 |
| 人間判断 | UXから継承した未確認事項は実行環境の導入・運用者を代表する利用者とQual-Labが判断する。IA固有の追加判断はない。正式入力にないObject、状態または責任を追加する必要が生じた場合は人間の決定権限者へ戻す。 |
| IAへ戻す条件 | UI／SPEC分析またはQuality Analysis / IAで、Object・同一性・関係・状態・可視性・時間的な意味が不足または競合すると判明した場合。 |
| 検証意図 | 「実行を信頼すると判断する場面」に、一つの署名表示を全保証と誤認することを避け、保証要素と決定権限を分離表示することを確認できる必要がある。 |

ここで示す主体は、情報契約上必要な機能責任を表し、特定の人物・組織・Componentへの割当を確定しない。後続工程は、この責任境界を保ったまま実際の主体へ割り当てる。

### 未確認事項と判断

| 区分 | 内容 |
|---|---|
| UXから継承する確認事項 | REQ-000018: 実行環境の導入・運用者が「実行環境の信頼の各要素を別々に評価する」を行う際の判断基準、許容負担、利用環境および失敗後の選択／REQ-000025: 実行環境の導入・運用者が「信頼する配布者と手元例外を自分で定める」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |
| 判断者 | 実行環境の導入・運用者を代表する利用者とQual-Lab。 |
| 現在判定 | 後続の実利用確認が必要。現在のUX定義をCanonical化する判断を止める事項ではない。 |
| 未確認時の影響 | 利用者成果、重要場面、失敗および品質期待を仮説として保持し、定量条件や実現方式を確定しない。 |
| IAで追加した未確認事項 | なし。正式入力にない定量条件、状態値または実現方式を追加しない。 |
| IA固有の追加人間判断 | なし。UXから継承した判断をIAで確定済みにしない。 |
| Discoveryへ戻す条件 | 想定した利用者、問題、望ましい変化または制約が誤っていると判明した場合。 |

## 4. 現実照合の参考情報（正式入力ではない）

この節は後続のReality Auditへ引き継ぐ参考情報であり、IA Candidateを導く正式入力ではない。前節までをUX Definitionから再導出した結果として優先する。


| 照合対象 | 結果 |
|---|---|
| UXから導いた意味 | 対象・状態・導線は前節までを正とする。 |
| 現行構造 | 成果物署名（artifact-signing）が完全性・配布者（Publisher）の根拠を支える。Qual-Lab署名を唯一の実行資格にしない。 |
| 採用境界 | 現行の名称や状態値は、UX由来の意味と一致する範囲だけを照合根拠にする。実装にだけ存在する区分はIA定義へ逆流させない。 |

## 5. IA処置

[IA-000015](../../Definitions/IA-000015/ia_definition.md)へ接続する。上記7軸を接続先へ保持し、複数UXを統合する場合も対象固有の状態、失敗、導線を消さない。UXから継承する未確認事項を、判断者と影響を含めて接続先へ保持する。

## 6. 後続工程が保持する意味

| 接続先 | 保持する意味 |
|---|---|
| UI（UX＋IAの正式入力） | 情報の優先度、可視性、状態差、まとまり、見つけ方および関係の理解を保持する。 |
| SPEC（UX＋IAの正式入力） | 対象の識別、関係、状態、可視条件、責任および時間的な意味を保持する。 |
| Quality Analysis / IA（伴走） | 「準拠、改ざん有無、配布者、公式表示および実行許可を区別し、自分の環境の方針で公式版・派生版・組織版を選べる」の成立条件、「一つの署名表示を全保証と誤認する」という失敗および前章の検証意図を保持する。 |

ArchitectureやSourceへ直接引き渡さない。UI／SPECは、UX DefinitionとIA Definitionの双方を正式入力として分析する。

## 7. 補足分析

なし。必須情報は第1章から第7章に保持する。現行文書・実装との比較は第4章の参考情報として分離し、Canonical IAの根拠には用いない。
