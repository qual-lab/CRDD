# IA分析: 目的と受入条件で節目を委ねる

成果物種別: IA分析
分析対象: [UX-000005](../../../02_UX/Definitions/UX-000005/ux_definition.md)
状態: 分析済み

## 1. UXから受け取る意味

| 観点 | この分析で受け取る内容 |
|---|---|
| 利用者 | プロジェクト運営者／PM |
| 場面 | プロジェクトの成果をまとめて任せる時 |
| 目的 | 目的と受入条件で節目を委ねる |
| 得たい結果 | 内部タスクを追わず統合済みの完成を判断できる |
| 重要場面 | タスク成功と節目完成を区別する |
| 避ける失敗 | タスク件数を完成と誤認する |
| 守る品質 | 統合・品質・判断待ちを分けて示す |

画面、API、保存形式は決めず、上記の利用者成果を情報の単位と関係へ変換する。

## 2. 情報候補と関係

| 情報Object | 利用者にとっての意味 | 同一性と関係の基準 |
|---|---|---|
| プロジェクト | 同じ目的・節目・作業を束ねる仕事のまとまり | Project IDで識別する |
| 目的 | Milestoneを成立させる目的 | Milestoneに属する安定ID |
| 受入条件 | 上位成果を受け入れる条件 | Milestone／Objectiveへ結合 |
| 節目 | 人が委ね受入を判断する到達点 | Projectに属する安定ID |
| 作業 | 実行可能な仕事単位 | Objectiveと作業識別子（Task Identity） |
| 統合状態 | 目的と受入条件で節目を委ねる際に、「統合状態」の意味・状態・対象範囲を他の情報と取り違えないための情報 | 対象、判定時点、情報源で識別し、不明を正常へ丸めない |
| 品質 | 目的と受入条件で節目を委ねる際に、「品質」の意味・状態・対象範囲を他の情報と取り違えないための情報 | 対象、判定時点、情報源で識別し、不明を正常へ丸めない |
| 再開条件 | 目的と受入条件で節目を委ねる際に、「再開条件」の意味・状態・対象範囲を他の情報と取り違えないための情報 | 適用対象、所有者、改訂版で識別する |


```text
                 ┌── 節目として区切る ──▶ [O: 節目] ──成立条件を持つ──▶ [O: 受入条件]
[O: プロジェクト] ──持つ──▶ [O: 目的] ─────┤
                 └── 作業へ分ける ─────▶ [O: 作業] ──統合される──▶ [O: 統合状態]
                                                                                  │
                                                                                  │ 品質判断を支える
                                                                                  ▼
                                                                             [O: 品質]

[O: 再開条件] ──同じ節目へ戻す──▶ [O: 節目]
```

図中の`[O:]`は情報Objectだけを表す。利用者、判断行為、利用者成果はObjectへ置き換えない。関係名と向きは、同じ対象を追跡し、誤った統合を避けるための情報上の関係であり、画面遷移や実装依存を表さない。

### Canonical化候補

| 接続先 | 分析Object | Canonical Object | 処置 | 判断理由 |
|---|---|---|---|---|
| IA-000002 | プロジェクト | プロジェクト | Same | 同じ目的と受入を共有する仕事のまとまりを保持する |
| IA-000002 | 目的 | 目的 | Same | 委任範囲と節目の目的を保持する |
| IA-000002 | 受入条件 | 受入条件 | Same | 候補を受け入れる判定条件を保持する |
| IA-000002 | 節目 | 節目 | Same | 節目を独立した判断点として保持する |
| IA-000002 | 作業 | 作業 | Same | 状態を持つ実行対象を保持する |
| ― | 統合状態 | ― | Not Applicable | IA-000002の「状態・可視性・時間的な意味」節へ、統合状態を独立Objectではなく状態・可視条件として保持する |
| ― | 品質 | ― | Not Applicable | IA-000002の「状態・可視性・時間的な意味」節へ、品質を独立Objectではなく状態・可視条件として保持する |
| ― | 再開条件 | ― | Not Applicable | IA-000002の「状態・可視性・時間的な意味」節へ、再開条件を独立Objectではなく状態・可視条件として保持する |

この対応は分析結果からCanonical定義を再構築するための候補である。`Split`または`Merge`でも元の利用者向け意味を失わず、正式入力にないObjectを追加しない。

## 3. 状態・可視性・導線・責任

| 観点 | 分析結果 |
|---|---|
| 状態 | Task完了／Objective受入／Milestone受入を別にする |
| 可視性 | 「タスク成功と節目完成を区別する」では、統合・品質・判断待ちを分けて示すために必要な状態と不足を判断対象と同じ文脈で示す。詳細な識別情報と根拠は必要時に辿れるようにし、非開示対象は存在自体を推測表示しない。 |
| 導線 | 目的→受入条件→節目→作業→統合状態→品質→再開条件。結果なし、判断待ち、失敗または状態不明の場合も、根拠か安全な戻り先を失わない。 |
| 責任 | プロジェクト運営者／PMが目的・節目・作業・受入条件を更新し、実行担当が作業状態を提供する。 |
| 時間的な意味 | Task完了／Objective受入／Milestone受入を別にするの区別を保持する。現在値、古い値、履歴または不明を同じ正常状態へ丸めない。 |
| 情報の優先度 | まず「目的と受入条件で節目を委ねる」の判断に必要な対象・状態・判断要否を示し、識別情報と根拠は必要時に辿れるようにする。 |
| 情報のまとまり | プロジェクト運営者／PMが「プロジェクトの成果をまとめて任せる時」に「内部タスクを追わず統合済みの完成を判断できる」を得るための対象・状態・根拠・次の行動を同じ文脈で扱う。 |
| 判断権限 | 人間の決定権限者が委任範囲・受入・採否を確定し、実行担当はその権限を代行しない。利用者は提示された情報から次の行動を選ぶが、正本の意味・状態を無断で変更しない。 |
| 重要な失敗 | タスク件数を完成と誤認する |
| 制約・対象外 | 画面、UI部品、API、DB、Class、保存形式および具体的な振る舞いをIAで確定しない。 |
| 人間判断 | UXから継承した未確認事項はプロジェクト運営者／PMを代表する利用者とQual-Labが判断する。IA固有の追加判断はない。正式入力にないObject、状態または責任を追加する必要が生じた場合は人間の決定権限者へ戻す。 |
| IAへ戻す条件 | UI／SPEC分析またはQuality Analysis / IAで、Object・同一性・関係・状態・可視性・時間的な意味が不足または競合すると判明した場合。 |
| 検証意図 | 「タスク成功と節目完成を区別する」に、タスク件数を完成と誤認することを避け、統合・品質・判断待ちを分けて示すことを確認できる必要がある。 |

ここで示す主体は、情報契約上必要な機能責任を表し、特定の人物・組織・Componentへの割当を確定しない。後続工程は、この責任境界を保ったまま実際の主体へ割り当てる。

### 未確認事項と判断

| 区分 | 内容 |
|---|---|
| UXから継承する確認事項 | REQ-000003: プロジェクト運営者／PMが「目的と受入条件で節目を委ねる」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |
| 判断者 | プロジェクト運営者／PMを代表する利用者とQual-Lab。 |
| 現在判定 | 後続の実利用確認が必要。現在のUX定義をCanonical化する判断を止める事項ではない。 |
| 未確認時の影響 | 利用者成果、重要場面、失敗および品質期待を仮説として保持し、定量条件や実現方式を確定しない。 |
| IAで追加した未確認事項 | なし。正式入力にない定量条件、状態値または実現方式を追加しない。 |
| IA固有の追加人間判断 | なし。UXから継承した判断をIAで確定済みにしない。 |
| Discoveryへ戻す条件 | 想定した利用者、問題、望ましい変化または制約が誤っていると判明した場合。 |

## 4. 現実照合の参考情報（正式入力ではない）

この節は後続のReality Auditへ引き継ぐ参考情報であり、IA Candidateを導く正式入力ではない。前節までをUX Definitionから再導出した結果として優先する。


| 照合対象 | 結果 |
|---|---|
| UXから導いた意味 | 対象・状態・導線は前節までを正とする。 |
| 現行構造 | プロジェクト実行状態の管理（Project Runtime）は階層を持つ。作業（Task）件数を上位完成へ丸めない。 |
| 採用境界 | 現行の名称や状態値は、UX由来の意味と一致する範囲だけを照合根拠にする。実装にだけ存在する区分はIA定義へ逆流させない。 |

## 5. IA処置

[IA-000002](../../Definitions/IA-000002/ia_definition.md)へ接続する。上記7軸を接続先へ保持し、複数UXを統合する場合も対象固有の状態、失敗、導線を消さない。UXから継承する未確認事項を、判断者と影響を含めて接続先へ保持する。

## 6. 後続工程が保持する意味

| 接続先 | 保持する意味 |
|---|---|
| UI（UX＋IAの正式入力） | 情報の優先度、可視性、状態差、まとまり、見つけ方および関係の理解を保持する。 |
| SPEC（UX＋IAの正式入力） | 対象の識別、関係、状態、可視条件、責任および時間的な意味を保持する。 |
| Quality Analysis / IA（伴走） | 「内部タスクを追わず統合済みの完成を判断できる」の成立条件、「タスク件数を完成と誤認する」という失敗および前章の検証意図を保持する。 |

ArchitectureやSourceへ直接引き渡さない。UI／SPECは、UX DefinitionとIA Definitionの双方を正式入力として分析する。

## 7. 補足分析

なし。必須情報は第1章から第7章に保持する。現行文書・実装との比較は第4章の参考情報として分離し、Canonical IAの根拠には用いない。
