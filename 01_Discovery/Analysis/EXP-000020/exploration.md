# 複数のリポジトリを、一つのプロジェクトとして見る

成果物種別: Discovery分析
探索ID: `EXP-000020`
状態: 要求採用
主な情報源: プロジェクト、Commercial、Topics、Meetingsの分離構想
判断する人: Qual-Lab
記録の性質: プロジェクト／Commercial／Topics／Meetings分離の対話とCROS設計候補から再構成
時系列根拠: 2026-09-13に固定したv0.21構想群で、単一リポジトリ作業の次に扱う依存順とした。

## きっかけ

Commercial、Topics、Meetings、Communicationなどを、必要に応じて別リポジトリへ分けたいという話が出た。情報の種類や読める人が違うため、何でも一つのリポジトリへ集めるのは現実的ではない。

代表例では、一つの案件に開発者向けリポジトリと経営・管理層向けリポジトリがあり、同じプロジェクトに属しながら読める人と所有する情報が異なる。逆に小さな案件では、一つのリポジトリだけで全情報を持つ方が自然である。

| 構成 | 成立させたいこと |
|---|---|
| 一つのプロジェクト・一つのリポジトリ | 横断統合なしでも通常利用できる |
| 一つのプロジェクト・複数リポジトリ | 責務とアクセス境界を保って一つに見せる |
| 一部リポジトリだけ利用可能 | 見えない情報を推定せず、不足として扱う |
| 同じ責務を複数リポジトリが宣言 | 探索順で選ばず競合を返す |

## 最初に混同していたもの

一つのプロジェクトは一つのリポジトリだ、と考えると話が簡単に見える。しかし実際には、一つの案件が製品、開発、管理、Commercialなど複数のリポジトリを持ち得る。逆に、一つのリポジトリの名前や配置だけからプロジェクト全体を推定するのも危険である。

## 置いた仮説

Project IDとRepository IDを分け、各リポジトリが「どのプロジェクトに属し、何を担当するか」を宣言すれば、一つの論理プロジェクトとして束ねられると考えた。

```text
プロジェクト PRJ-001
  ├─ リポジトリ PRJ-001-DEV   開発・品質
  └─ リポジトリ PRJ-001-MGMT  プロジェクト・Commercial
```

各リポジトリは自分の情報だけを持つ。プロジェクト全体を一箇所へコピーせず、CROSが許可された範囲だけを読み取って投影する。

| 仮説 | 問題 | 採否 |
|---|---|---|
| 基準リポジトリ配下へ他リポジトリをぶら下げる | 基準側が全プロジェクトの所有者に見え、障害・権限境界も集中する | 不採用 |
| 各リポジトリへプロジェクト情報を複製する | 同期と現行性の正本が分からなくなる | 不採用 |
| Project ID、Repository ID、検証済み基点フォルダを分けて解決する | 同居と分離の両方を表現できる | 採用 |

識別情報分離だけでは十分ではない。責務、利用可否、出典、競合を失って統合した場合は、同じProject IDでも安全な横断統合とは扱えない。

## 守ること

- 読めないリポジトリを「存在しない」「問題なし」と扱わない。
- 別リポジトリの本文を同期用に複製しない。
- リポジトリの実アクセス境界を、CROSの要約で迂回しない。
- 同じ役割を複数リポジトリが名乗った時は、探索順で勝手に選ばない。

## 現在の判断

プロジェクト、リポジトリ、実際の基点フォルダとの結び付けは別の識別情報として扱う。細かな権限管理製品は作らず、リポジトリのアクセス境界と作業領域への公開範囲を利用する。

## 次工程で確かめること

一つのリポジトリだけのプロジェクト、複数リポジトリのプロジェクト、読めない情報源、役割の競合を代表例にする。UXでは、通常の利用者へ裏側のリポジトリ分割を意識させず、不足だけは隠さない体験を作る。

## 採用した要求

`REQ-000009`: 論理プロジェクト、各リポジトリおよび検証済み実行基点フォルダは、相互に代用しない独立した識別情報として結び付けられなければならない。

`REQ-000020`: 複数リポジトリを一つのプロジェクトとして解決する場合、各リポジトリの出典、責務、利用可否、欠測および競合を保ち、探索順や複製された本文から正本を推定してはならない。
