# 同じProject Runtimeを、複数の入口から使う

成果物種別: Discovery分析
探索ID: `EXP-000015`
状態: 要求採用
主な情報源: v0.20.0、CHG-000064
判断する人: Qual-Lab
記録の性質: CHG-000064、MCP stdio／HTTP設計と検証記録から再構成
時系列根拠: v0.20.0とCHG-000064を起点とする。

## きっかけ

Project RuntimeをAIや外部ツールから使うにはMCPが必要だった。AIツールと直接つなぐ標準入出力（stdio）だけでなく、このPC内のアプリから使うHTTP入口も求められた。しかし、入口ごとに別の処理や結果形式を作ると、同じProject Runtimeの仕事が入口によって変わってしまう。

当時の前提はLocalhost上の利用であり、リモート公開や独立した認証基盤を作ることではなかった。必要だったのは、MCP利用側の接続方式が違っても、同じProject Runtimeの操作と結果を利用できることである。

| 利用側 | 必要な入口 | 共通でなければ困ること |
|---|---|---|
| Desktop AI 利用側 | stdio MCP | ツール名、入力、結果、Error意味 |
| 手元 App／別プロセス | Streamable HTTP | プロジェクトの識別情報、権限、状態、取消 |
| 実行基盤保守 | 共通診断 | どの通信方式で失敗したかと外部作用（Effect）の有無 |

## 本当の問題は何だったか

HTTPがないこと自体ではない。通信方式ごとに状態、権限判断、失敗分類を持つと、同じプロジェクトへ異なる答えを返すことが問題だった。

```text
同じ目的
   ├─ stdio固有の解釈 ─→ 結果 A
   └─ HTTP固有の解釈 ─→ 結果 B
                         ↓
入口によってプロジェクトの意味が変わる
```

## こうすれば解けると考えた

MCPを通信方式だけを受け持つ薄い接続部とし、標準入出力と、このPCだけから接続できるHTTP（localhost HTTP）のどちらも、同じ公開アプリケーション契約（Application Contract）へ接続することにした。手元利用ではリモートServerの運用を要求しない。

| 方向 | 評価 | 採否 |
|---|---|---|
| HTTP用のプロジェクト APIを別実装する | 入口は早く作れるが、意味契約が二重化する | 不採用 |
| すべての手元入口をMCP Server経由にする | 一つに見えるが、Workbench等の手元利用までServerへ依存する | 不採用 |
| MCPを通信方式に限定し、共通アプリケーション契約（Application Contract）を使う | 入口差を保ちつつ仕事の意味を統一できる | 採用 |

stdioとHTTPで正常時だけ一致しても十分ではない。不正入力、判断待ち、回復要求、取消および終了後状態が同じ意味にならなければ、この仮説は成立しない。

## 選んだこと、選ばなかったこと

- stdioとlocalhost HTTPは同じ意味契約を使う。
- MCPはプロジェクト状態や更新権限の所有者にならない。
- v0.20ではリモート公開、汎用認証Server、複数リポジトリ横断を扱わない。
- 入口が存在するだけで、上位機能全体の完成を主張しない。

## 後から分かったこと

手元 HTTPが成立すると、別Hostからの接続も同じ延長に見えた。しかしリモートでは、暗号化、接続資格情報、作業領域の範囲、応答喪失後の再取得が必要になる。単にlisten先を広げるだけでは安全なリモート MCPにならない。

## 現在地と次への引き渡し

ローカルMCP／HTTPでは、通信方式が違っても同じ公開契約を使う方向を採用した。リモート利用は別の探索として扱い、人間とAIの入口を同じ契約へ揃える課題へ接続している。

## 採用した要求

`REQ-000006`: 手元のstdio MCPとlocalhost HTTPはProject Runtimeの同じ公開アプリケーション契約（Application Contract）を利用し、通信方式固有の状態、権限判断または結果意味を持ってはならない。
