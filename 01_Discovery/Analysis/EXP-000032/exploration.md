# TopicとMeetingをどの入口からも同じように扱う

成果物種別: Discovery分析
探索ID: `EXP-000032`
状態: 要求採用
主な情報源・根拠: Topic／Meetingの既存探索、v0.22のMCP・Workbench範囲に関する人間との対話
判断する人: Qual-Lab
記録の性質: v0.22開始時の再Discovery
下流の主要CHG: 未作成

> 本探索はMCP Tool名や画面を先に決めるものではない。TopicとMeetingを日常の仕事として扱う時、どの入口でも失ってはならない能力と履歴境界を確認する。

## 事前入力の理解確認

AIは当初、Topic／MeetingのMCPを一覧・詳細取得から始め、書込みは後で評価する段階導入だと理解した。人間との確認で、最終的に必要なのは読取りだけではなく、登録、編集、削除、一覧および取得を一通り実装することであると修正された。

```text
AIの事前理解
「まず一覧・取得を成立させ、書込みは後で判断する」
        ↓ 人間による修正
「TopicとMeetingの両方で、
  登録・削除・編集・一覧・取得を一通り実装したい」
        ↓ 現在理解
MCPとWorkbenchは閲覧専用Viewではなく、
Topic／Meetingの日常操作を同じApplication Capabilityから利用する。
ただし削除が履歴破壊を意味するかは未確定。
```

## きっかけ

Project ContextでProject全体の現在地は把握できるが、継続論点の詳細、会議の内容、両者の関係および会議後の候補処置までは扱えない。AIへ依頼する場合もWorkbenchを使う場合も、利用者が結局Markdownファイルを直接探して操作しなければならないなら、「仕事の入口」を統一できない。

既存の[Topic／Meeting探索](../EXP-000023/exploration.md)では、Meeting、Topicおよび正式正本を分け、Meetingから候補を経て正本へ反映する必要性を採用した。ただし、TopicとMeeting自体の日常的な登録・編集・削除・一覧・取得を、どの入口からどう利用するかは要求として明示していなかった。

## 本当の問題は何だったか

問題はMCP Toolが不足していることだけではない。入口ごとにファイル探索、入力項目、状態変更、削除の意味および失敗時の扱いが分かれると、同じTopic／Meetingを扱っているのに結果と履歴が一致しなくなることである。

```text
Chat Agent      Workbench      Local Tool      直接編集
     │              │              │              │
     └──────────────┴──────┬───────┴──────────────┘
                            ↓
                同じApplication Capability
                            ↓
                 Topic／Meetingの正本とLifecycle
```

利用者に必要なのは、特定のファイル操作を覚えることではなく、論点と会議記録を安全に作成・確認・訂正・終了でき、どの入口でも同じ結果へ到達できることである。

## こうすれば解けると考えた

TopicとMeetingそれぞれに、登録、編集、削除、一覧および取得のApplication Capabilityを設ける。MCP、Workbench、CLIその他の入口は、その共通能力を利用し、独自の状態Storeや独自Lifecycleを作らない。

| 操作 | Topicで守る意味 | Meetingで守る意味 | 主な未確認事項 |
|---|---|---|---|
| 登録 | 継続して扱う論点としてIdentityと初期状態を作る | 時間境界、参加主体、Sourceを持つ時点記録を作る | 必須入力、Draftの有無、重複判定 |
| 編集 | 現在状態、説明、関係、所有者、昇格先を更新する | 誤りの訂正、整理、Relation追加を行い、当時記録を無言で改変しない | 訂正履歴、同時更新、変更Authority |
| 削除 | 誤登録、取下げ、終了、履歴保持を区別する | 誤登録、撤回、訂正、保持義務を区別する | 物理削除を許す条件、Relation残存、復旧 |
| 一覧 | Open、停止、判断待ち、関係、更新順等から探す | 日時、参加主体、関連Topic、未処理候補等から探す | 初期Filter、並び順、Pagination |
| 取得 | 現在状態、経緯、Relation、根拠、次の処置を読む | 当時記録、Decision／Action／Topic候補、反映結果を読む | 本文量、関連情報の深さ、欠測表示 |

### 比較した代替

| 方向 | 利点 | 問題 | 現在の扱い |
|---|---|---|---|
| 汎用Artifact CRUDを一つ作る | API数を減らせる | Topic／Meeting固有のLifecycle、訂正、候補、Authorityが見えなくなる | 単独案として不採用 |
| 各入口がMarkdownを直接操作する | 実装を早く始められる | 入力検証、競合、削除、結果が入口ごとに分かれる | 不採用 |
| Topic／Meeting別Application Capabilityを共有する | 固有の意味を守り、複数入口で結果を統一できる | 契約と検証対象が増える | 採用候補 |
| 読取りだけ先に公開する | 初期Riskを抑えられる | 日常操作は直接編集へ戻り、入口統一が完成しない | 段階実装には使えるが完成形にはしない |

## 選んだこと、選ばなかったこと

TopicとMeetingの両方について、登録、編集、削除、一覧および取得をv0.22の完成候補へ含める。MCPとWorkbenchは別々に実装せず、同じApplication Capabilityを利用する。通常操作をCommit済み状態のみに限定せず、未CommitのRepository状態でも正本を安全に扱える必要がある。

汎用Filesystem CRUD、MCP固有Store、Workbench固有StoreおよびMeetingから正本への無確認自動反映は採用しない。

削除を無条件の物理消去とすることは選ばない。一方、誤って登録したものまたは余計に作成したものは、Relationを持つ場合でも物理削除できるようにする。削除前に対象、全Relation、失われる内容、Relationへの処置および復旧可能性を利用者へ示し、明示確認を得る。削除対象以外を連鎖削除せず、削除後に無効なRelationを残さない。

正当な履歴として成立しているTopicまたはMeetingは、単に現在不要になったという理由では物理削除せず、終了、撤回または訂正として扱う。

### Topicへ登録する境界

人間理解の確認により、Topicは単発の問い合わせや明確なTODOをすべて登録する箱ではなく、Meeting、単発問い合わせ、観察その他から生じ、時間を越えて調査・判断・状態を追う必要がある論点だと整理した。具体的な変更を採用した後の実行・検証はCHGが所有し、Topicはその前段にある問題理解と判断の土台を所有する。

```text
問い合わせ・気付き・依頼
        ↓
一度の回答または明確な操作で閉じる
        ├─ Yes → Topicにしない
        └─ No
             ↓
   調査・比較・人間判断・情報待ち・継続追跡が必要
             ↓
           Topic
             ↓ 変更を採用
            CHG
```

単発問い合わせや即時完了できるTODOは、件数集計のためだけにTopicへ登録しない。問い合わせを別Entityまたは軽量な運用記録として保持・集計する案も比較したが、記録負荷と新しい正本境界を増やすためv0.22では採用しない。必要性が実利用で確認された場合に、新しいDiscoveryとして扱う。したがってv0.22では、Repository、MCP、WorkbenchまたはCROSが観測していない問い合わせを推測して件数表示せず、問い合わせ全般の集計可能性を完成主張に含めない。

同じ問い合わせが繰り返される、回答に調査や判断が必要になる、次のMeetingや外部情報待ちへ持ち越す、または複数のAction／CHGへ分かれ得る場合は、個々の問い合わせを保存する代わりに、継続して扱う論点そのものをTopicへ昇格する候補とする。すべてのTopicがCHGになるとは限らず、回答、現状維持、別Topicへの統合、保留または別Ownerへの移管で終了できる。

### Meetingを閉じる境界

Meetingは決まった形式のMarkdownとしてRepositoryに保存し、Project ContextはMeeting本文を複製せず、直近Meeting、未処置の結果および未完了ActionをOwner Relation付きで投影する。録音、文字起こしおよび会議中のリアルタイムAI支援はv0.22のMeeting管理へ含めない。

Meetingを、会議後のActionがすべて完了するまで開き続ける案も比較した。しかし、会議自体が終わった状態と、後続作業が残る状態が混ざり、Meetingが長期的な課題管理の箱になる。このため、MeetingはActionの完了ではなく、記録の確認と全Outcomeの処置先が確定した時点で閉じる。

```text
Meeting終了
    ↓
記録を確認
    ↓
Outcomeを全件処置
    ├─ その場で完了
    ├─ 明確なMeeting Actionとして担当・期限・完了条件を設定
    ├─ 継続判断が必要なためTopicへ昇格
    ├─ 採用済み変更としてCHGへ接続
    ├─ 所有正本へ反映
    └─ 理由付きで不採用・対応不要
    ↓
MeetingをClose
```

Close後も未完了Actionの現在状態は更新できるが、会議当時の記録、発言、判断またはOutcomeを無言で書き換えない。Meetingの状態、記録の確認状態、Outcomeの処置状態およびActionの実行状態は異なる意味として扱う。継続的な理解・判断・経緯の追跡が必要になったActionは、未完了という理由だけでなく、その必要性を根拠にTopicへ昇格する。

### Repository分離と単一Repositoryの両立

TopicとMeetingの契約は、DEV用とMGMT用で別の仕組みにしない。一方、Repository分離を情報境界として使うProjectでは、DEV RepositoryとMGMT Repositoryがそれぞれ自分の範囲のTopicとMeetingを保持し、内容を相互に複製しない。同じLogical Projectに属することや題材が似ていることを理由に、Identityまたは本文を自動統合してはならない。

Repository分離は必須ではない。開示範囲を分ける必要がなく、一つのRepositoryでProjectを運営できる場合は、DEV／MGMTという物理分離を作らず、そのRepository内でTopicとMeetingを成立させてよい。複数Repositoryを使う場合も、各Topic／MeetingのOwner Repositoryは一つとし、CROSは現在の主体が参照できる項目を統合表示するだけで、別の正本を作らない。

```text
単一Repository Project
└ Topic／Meetingを同じRepositoryで保持

Repository分離Project
├ DEV  ─ Topic／Meeting（開発範囲）
└ MGMT ─ Topic／Meeting（管理範囲）
          ↓
   CROSは許可された範囲だけ投影
```

複数の情報境界へ関係する論点は、機密内容を横断複製せず、必要なら各Repositoryが所有する別のTopicへ分ける。相互Relationは、相手の存在を開示できる場合だけ保持する。

## 後から分かったこと

Project ContextとProject Runtime Stateの区別を整理したことで、Topic／MeetingもProject Context内へ埋め込む情報ではなく、Project Contextから詳細へ進む独立能力だと明確になった。

また、既存REQ-000012はMeetingから候補を経てTopicまたは正本へ反映する流れを所有するが、Topic／Meeting自体の全操作を所有していない。既存要求へ無理に吸収せず、理解確認後に独立要求へ昇格する必要がある。

## 採用した要求

[REQ-000039](../../Definitions/REQ-000039/requirement.md)を採用した。TopicとMeetingの登録、編集、削除、一覧および取得を共通Application Capabilityとして提供し、Relationを持つ誤登録も影響表示と人間確認後に削除できることを要求する。

## 現在地と次への引き渡し

登録、編集、削除、一覧および取得と、Relationを持つ誤登録の削除境界に加え、即時に閉じる問い合わせ／TODOをTopic化せず、継続追跡が必要になった論点だけをTopicへ昇格する境界を要求へ反映した。Meetingは構造化Markdownを正本とし、Action完了ではなく記録確認とOutcome全件処置をClose条件にする。単一Repositoryでも成立し、Repository分離を使う場合はDEV／MGMTが同じ契約の下で別の正本を保持する。次はUXで利用者、確認負担、重要場面、失敗および回復を分析し、IA以降で入力、結果、状態、Authority、競合、Failureおよび回復を具体化する。MCPのTool名、Resource URI、画面、詳細なMarkdown構造および実装技術は後工程で決める。
