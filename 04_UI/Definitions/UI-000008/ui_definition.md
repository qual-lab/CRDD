## 利用者成果と統合判断

鍵の発行・独立失効・交換はadministrator専用固定で、Role詳細権限のON／OFF設定を設けない。通常鍵操作は同一Process Workbench backendだけで提供し、MCPには秘密値の有無を問わず鍵操作の一覧・Schema・登録・dispatchを公開しない。通常Host回復はログイン済みローカル操作者を信頼する対話CLIで交換2操作だけを扱い、追加認証・専用資格・承認コード・OS管理者昇格を要求しない。既存Root／Path検証を維持する。manager／administratorはユーザー登録・表示名変更、developer／managerの割当て・詳細権限、Repository登録・登録解除・公開範囲を管理する。administratorの付与・解除・降格を含むRole変更、administrator詳細権限と鍵3操作はadministratorだけが管理する。developerへ管理操作、managerへ管理者専用操作を設定で委譲しない。

## 管理操作の固定分担

| 管理操作 | developer | manager | administrator |
|---|---|---|---|
| ユーザー登録・表示名変更 | 不許可 | 許可 | 許可 |
| developer／managerの割当て・変更 | 不許可 | 許可 | 許可 |
| administratorの付与・解除・降格を含むRole変更 | 不許可 | 不許可 | 許可 |
| developer／managerの詳細権限設定 | 不許可 | 許可 | 許可 |
| administratorの詳細権限設定 | 不許可 | 不許可 | 許可 |
| 鍵の発行・独立失効・交換 | 不許可 | 不許可 | 許可 |
| Repository登録・登録解除 | 不許可 | 許可 | 許可 |
| Repository公開範囲設定 | 不許可 | 許可 | 許可 |

固定の管理能力は現行Roleと上表の割当てから判定し、Role詳細権限の内容設定から派生させない。manager自身の内容範囲変更も、変更前の現在の管理認可→明示的なRole内容範囲／Exposure更新→次の要求で現行Role・Exposure・実アクセスを再評価、の順に分ける。更新受理だけでは内容取得可能とせず、管理者にも内容を自動付与しない。

administratorの表示名変更はmanagerにも許可するが、administratorの付与・解除・降格と詳細権限は許可しない。ユーザー登録・表示名／Role／業務設定の変更を鍵発行・失効と同一視しない。Repository登録・公開設定・内容の実在を別に扱い、登録だけで公開せず、登録解除では対応Exposureも同時除去し、他登録／Exposure・Repository本体・Product Dataを保持する。

指定ユーザー交換／全員交換は操作範囲、通常管理／Hostは入口・Authorityとして別軸にする。両入口で同じ2操作を扱い、ユーザーID・表示名・Role・詳細権限・Repository登録・Product Dataを保持する。対象は表示名ではなく既存userIdで固定する。特別ユーザー・追加権限・回復専用Bootstrapを作らず、認可設定破損の修復を鍵交換に含めない。初回設定は未初期化確定時の明示開始として別に扱い、既存状態の鍵回復へ転用しない。

通常入口は同一Process Workbenchの固定administrator権限、Host入口はログイン済みローカル操作者を確認する。Host入口と全員交換は人間の明示確認を必要とする。

処置前に対象ID・表示名、失効範囲、既存発行先、保持情報を示す。全員交換では操作中の管理者自身の旧鍵も失効し、新Secretは一度だけ受け取ることを明示する。失効後に発行自体または結果記録が未確定となった場合は、失効確定範囲と新資格発行結果の不明を別に示し、同じRecoveryへ戻る確認先を示す。現在再観測前に完了・rollback・旧資格利用可能・開始済み操作取消済みと表示せず、Secretを再表示しない。対象不明・管理者不存在・必要状態を安全に確認不能・認可設定破損では処置前停止を示す。

画面上で操作を隠すことだけを認可成立の根拠にしない。処置前のSPEC判定に対応する拒否・不明を、許可された情報だけで示す。developerの管理拒否は自身表示や許可内の内容利用を拒否する意味ではない。

### 登録解除と鍵の受け渡しの表示・案内

登録解除は対象の登録と対応Exposureを同じ受理操作で除去する。事前の別操作による公開解除を必須にせず、以後の対象CROSアクセスを停止する。他Repositoryの登録／Exposureと対象Repository本体・Product Dataは保持する。処置前に同時除去と保持範囲を表示し、結果では両関係の除去確認と内容保持を区別して示す。登録解除完了は開始済み操作の取消完了を証明しない。両関係の除去確認済みでも既存操作終了が未観測なら、解除完了とは別に未観測を保持し、取消成功・過去Effect 0・実資源終了へ読み替えない。新しい取消処置は追加しない。

発行自体または結果記録が不明なら、Credential IDとは別の非秘密な元発行Identityで現在再観測し、新交換を開始しない。交換由来だけ元のsame exact Recoveryを保持し、通常発行へ交換Recoveryを新設しない。発行・結果記録が確定し配送／受領だけ未確認なら、「発行済み・受け渡し未確認」と示し、確定事実を維持する。Secretの保存・再表示・自動再発行はしない。現在認可されたadministratorが人間の明示した既存交換を新しく開始でき、そのOperation／Recoveryは元処理とは別にする。現在の管理認証を失った場合は、Workbench認可を迂回せず既存Host交換入口へ案内する。

元発行と新交換の事実・Identityを別に保持する。指定ユーザー交換は先の発行鍵を含む対象userIdの全旧有効資格を失効し同じ既存userIdへ発行する。全員交換は先の発行鍵を含む全ユーザーの全旧有効資格を失効し、指定した既存administratorへ発行する。他ユーザーは通常の再発行・再配布を要する。各交換内では同じexact Recoveryを保持するが、新交換を元処理の再開として扱わない。新交換成功は旧Secretの受領・rollback・開始済み操作取消を証明しない。現在状態で失効した旧鍵を、遅延した元応答から利用可能と案内しない。

## 初回Host設定の認識・操作・結果

正式入力の初回設定を、通常管理・既存ユーザーの鍵交換とは別の場面として扱う。ログイン済みHost操作者が明示的に開始し、管理用表示名を入力し、最初のadministratorユーザーのUUIDとそのユーザーに結合した鍵を一度だけ受け取る。表示名は識別補助であり認証・Authorityではない。初回設定に既存Credentialを要求せず、MCP・自動起動からは提供しない。

| 現在確認できる状態 | 認識・操作・Feedback |
|---|---|
| 未初期化を確認 | 管理状態と途中の初期化記録の双方が未初期化と確認された時だけ、明示開始→表示名入力→最初の管理者作成→鍵の一度だけの受け取り→通常管理への導線を示す |
| 既存状態あり | 初回設定を拒否する。鍵喪失は既存Host交換へ案内し、管理者不存在・認可破損を初回設定で修復しない |
| 確認済みの途中状態 | 作成済みUUID、発行、結果記録、配送、受領の確認範囲を分ける。同じ非秘密の元初期化試行へ戻り、作成済み・発行済みを未初期化へ戻さない |
