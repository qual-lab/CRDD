## 2. UIへ引き継ぐ利用者成果

| 観点 | UX定義から受け取る内容 |
|---|---|
| 利用者／利用状況 | 製品全体の利用者像にある「開発者」 |
| 利用のきっかけ | ツールで処理を始める時 |
| 目的 | 固定Commitに対応するツール／実行基盤と利用可能性を知る |
| 得たい結果 | 現在リポジトリと目的に対応する標準ツールを見つけ、利用可能性・外部作用の権限・開発実行・公式実行を区別して選べる |
| 独立した利用者成果 | 現在リポジトリと目的に対応する標準ツールを見つけ、利用可能性・外部作用（Effect）の権限・開発実行・公式実行を区別して選べる |
| 重要な場面 | 発見したツール／実行基盤を起動する直前 |
| 避ける失敗 | 版不一致・欠落実行基盤・改ざんManifestを対応版と誤認する |
| 守る品質 | Commit・配布集合・Manifest・実行基盤の対応を検証する |

## 3. 必要な認識・操作・Feedback

```text
ツールで処理を始める時
        ↓
確認すること: 機能、利用可否、決定権限、リポジトリ Commit、配布物、Manifest、実行基盤 Bindingを分ける
        ↓
利用者の目的: 固定Commitに対応するツール／実行基盤と利用可能性を知る
        │
        ├─ ★ 判断点: 発見したツール／実行基盤を起動する直前
        ├─ ⚠ 避ける失敗: 版不一致・欠落実行基盤・改ざんManifestを対応版と誤認する
        └─ ✓ 必要なFeedback: Commit・配布集合・Manifest・実行基盤の対応を検証する
        ↓
現在リポジトリと目的に対応する標準ツールを見つけ、利用可能性・外部作用の権限・開発実行・公式実行を区別して選べる
```

このUXからUIへ渡す中心は、特定の部品や内部処理ではなく、「発見したツール／実行基盤を起動する直前」で利用者が「現在リポジトリと目的に対応する標準ツールを見つけ、利用可能性・外部作用の権限・開発実行・公式実行を区別して選べる」へ進める認識・判断・Feedbackである。

## 4. 状況による体験差

| 状況 | この利用者成果で必要な体験 |
|---|---|
| 利用開始 | 「ツールで処理を始める時」で、対象と判断に必要な前提を理解できる |
| 成果成立 | 「現在リポジトリと目的に対応する標準ツールを見つけ、利用可能性・外部作用の権限・開発実行・公式実行を区別して選べる」を、Commit・配布集合・Manifest・実行基盤の対応を検証するという条件で確認できる |
| 成果不成立 | 「版不一致・欠落実行基盤・改ざんManifestを対応版と誤認する」を避け、理由と安全な戻り先を理解できる |
| 判断不能 | 不明な事実を補完せず、何を確認しなければ判断できないか分かる |
| 判断・許可 | 誰が何を決めるかと、許可前後の状態を区別する |

上表にない処理中、取消、回復その他の状態を、共通テンプレートだけを根拠に追加しない。必要性はこのUXの意味とIA観点の情報構造をUI定義で統合して判断する。

## 6. IA観点との統合時に確認すること

IA観点の分析が「機能、利用可否、決定権限、リポジトリ Commit、配布物、Manifest、実行基盤 Bindingを分ける」を識別・状態・関係・可視性・導線として表現できるかを確認する。UI定義では「fresh clone、submodule、版不一致、欠落実行基盤、改ざんManifest、未登録能力の推測表示および一覧からの決定権限発行を反証する」を確かめられる形を保つ。必要情報をここで推測して先取りしない。
