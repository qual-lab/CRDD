## 2. UIへ引き継ぐ利用者成果

| 観点 | UX定義から受け取る内容 |
|---|---|
| 利用者／利用状況 | 製品全体の利用者像にある「実行環境の導入・運用者」 |
| 利用のきっかけ | 実行基盤を導入または更新する時 |
| 目的 | 実行環境の信頼の各要素を別々に評価する |
| 得たい結果 | 準拠、改ざん有無、配布者、公式表示および実行許可を区別し、自分の環境の方針で公式版・派生版・組織版を選べる |
| 独立した利用者成果 | 準拠、改ざん有無、配布者、公式表示および実行許可を区別し、自分の環境の方針で公式版・派生版・組織版を選べる |
| 重要な場面 | 実行を信頼すると判断する場面 |
| 避ける失敗 | 一つの署名表示を全保証と誤認する |
| 守る品質 | 保証要素と決定権限を分離表示する |

## 3. 必要な認識・操作・Feedback

```text
実行基盤を導入または更新する時
        ↓
確認すること: 準拠状況、改ざん有無、配布者、方針、導入先を分ける
        ↓
利用者の目的: 実行環境の信頼の各要素を別々に評価する
        │
        ├─ ★ 判断点: 実行を信頼すると判断する場面
        ├─ ⚠ 避ける失敗: 一つの署名表示を全保証と誤認する
        └─ ✓ 必要なFeedback: 保証要素と決定権限を分離表示する
        ↓
準拠、改ざん有無、配布者、公式表示および実行許可を区別し、自分の環境の方針で公式版・派生版・組織版を選べる
```

このUXからUIへ渡す中心は、特定の部品や内部処理ではなく、「実行を信頼すると判断する場面」で利用者が「準拠、改ざん有無、配布者、公式表示および実行許可を区別し、自分の環境の方針で公式版・派生版・組織版を選べる」へ進める認識・判断・Feedbackである。

## 4. 状況による体験差

| 状況 | この利用者成果で必要な体験 |
|---|---|
| 利用開始 | 「実行基盤を導入または更新する時」で、対象と判断に必要な前提を理解できる |
| 成果成立 | 「準拠、改ざん有無、配布者、公式表示および実行許可を区別し、自分の環境の方針で公式版・派生版・組織版を選べる」を、保証要素と決定権限を分離表示するという条件で確認できる |
| 成果不成立 | 「一つの署名表示を全保証と誤認する」を避け、理由と安全な戻り先を理解できる |
| 判断不能 | 不明な事実を補完せず、何を確認しなければ判断できないか分かる |
| 判断・許可 | 誰が何を決めるかと、許可前後の状態を区別する |

上表にない処理中、取消、回復その他の状態を、共通テンプレートだけを根拠に追加しない。必要性はこのUXの意味とIA観点の情報構造をUI定義で統合して判断する。

## 6. IA観点との統合時に確認すること

IA観点の分析が「準拠状況、改ざん有無、配布者、方針、導入先を分ける」を識別・状態・関係・可視性・導線として表現できるかを確認する。UI定義では「一つの署名やブランド表示への全保証集約とQual-Lab署名だけの実行資格化を反証する」を確かめられる形を保つ。必要情報をここで推測して先取りしない。
