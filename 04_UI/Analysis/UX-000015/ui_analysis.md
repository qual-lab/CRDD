## 1. 正式入力

- UX定義: [UX-000015 複数プロジェクトを根拠付きで比較する](../../../02_UX/Definitions/UX-000015/ux_definition.md)

IAやREQを直接読んで不足を補完しない。この分析はUX定義から利用者観点だけを導き、情報構造はIA観点の分析に委ねる。

## 2. UIへ引き継ぐ利用者成果

| 観点 | UX定義から受け取る内容 |
|---|---|
| 利用者／利用状況 | 製品全体の利用者像にある「経営・管理層」 |
| 利用のきっかけ | 複数プロジェクトの一覧の優先度を判断する時 |
| 目的 | 複数プロジェクトを根拠付きで比較する |
| 得たい結果 | 重要差分から必要なプロジェクトだけを掘り下げられる |
| 独立した利用者成果 | 許可されたプロジェクトの重要差を比較し、網羅範囲と根拠を保ったまま必要なプロジェクトだけを掘り下げられる |
| 重要な場面 | 要約から優先判断へ進む直前 |
| 避ける失敗 | 単一Scoreや欠測した集計で健全性を断定する |
| 守る品質 | 比較値から根拠・古さ・不足へ戻れる |

## 3. 必要な認識・操作・Feedback

```text
複数プロジェクトの一覧の優先度を判断する時
        ↓
確認すること: プロジェクト Summary、網羅範囲、観測時点、開示範囲を分ける
        ↓
利用者の目的: 複数プロジェクトを根拠付きで比較する
        │
        ├─ ★ 判断点: 要約から優先判断へ進む直前
        ├─ ⚠ 避ける失敗: 単一Scoreや欠測した集計で健全性を断定する
        └─ ✓ 必要なFeedback: 比較値から根拠・古さ・不足へ戻れる
        ↓
重要差分から必要なプロジェクトだけを掘り下げられる
```

このUXからUIへ渡す中心は、特定の部品や内部処理ではなく、「要約から優先判断へ進む直前」で利用者が「重要差分から必要なプロジェクトだけを掘り下げられる」へ進める認識・判断・Feedbackである。

## 4. 状況による体験差

| 状況 | この利用者成果で必要な体験 |
|---|---|
| 利用開始 | 「複数プロジェクトの一覧の優先度を判断する時」で、対象と判断に必要な前提を理解できる |
| 成果成立 | 「重要差分から必要なプロジェクトだけを掘り下げられる」を、比較値から根拠・古さ・不足へ戻れるという条件で確認できる |
| 成果不成立 | 「単一Scoreや欠測した集計で健全性を断定する」を避け、理由と安全な戻り先を理解できる |
| 判断不能 | 不明な事実を補完せず、何を確認しなければ判断できないか分かる |
| 判断・許可 | 誰が何を決めるかと、許可前後の状態を区別する |

上表にない処理中、取消、回復その他の状態を、共通テンプレートだけを根拠に追加しない。必要性はこのUXの意味とIA観点の情報構造をUI定義で統合して判断する。

IA観点の分析が「プロジェクト Summary、網羅範囲、観測時点、開示範囲を分ける」を識別・状態・関係・可視性・導線として表現できるかを確認する。UI定義では「非開示プロジェクトの存在漏えい、単一Score断定および網羅範囲差の消去を反証する」を確かめられる形を保つ。必要情報をここで推測して先取りしない。
