## 2. UIへ引き継ぐ利用者成果

| 観点 | UX定義から受け取る内容 |
|---|---|
| 利用者／利用状況 | 製品全体の利用者像にある「プロジェクト運営者／PM」 |
| 利用のきっかけ | 委任した仕事の応答を待つ時 |
| 目的 | 現在の実行状態と必要な判断を確認する |
| 得たい結果 | 内部ログを読まず、実行中・待機・停止と現在必要な判断を理解できる |
| 独立した利用者成果 | 内部ログを読まず、実行中・待機・停止と現在必要な判断を理解できる |
| 重要な場面 | 応答がなく待機か停止かを判断する場面 |
| 避ける失敗 | 古い観測や一律表示を進捗・完了と誤認する |
| 守る品質 | 観測時点・停止理由・必要な判断を行動可能に示す |

## 3. 必要な認識・操作・Feedback

```text
委任した仕事の応答を待つ時
        ↓
確認すること: タスク State、AI提供元 State、判断、入力、取消、および再試行・回復・再開を区別した次の行動を関連付ける
        ↓
利用者の目的: 現在の実行状態と必要な判断を確認する
        │
        ├─ ★ 判断点: 応答がなく待機か停止かを判断する場面
        ├─ ⚠ 避ける失敗: 古い観測や一律表示を進捗・完了と誤認する
        └─ ✓ 必要なFeedback: 観測時点・停止理由・必要な判断を行動可能に示す
        ↓
内部ログを読まず、実行中・待機・停止と現在必要な判断を理解できる
```

このUXからUIへ渡す中心は、特定の部品や内部処理ではなく、「応答がなく待機か停止かを判断する場面」で利用者が「内部ログを読まず、実行中・待機・停止と現在必要な判断を理解できる」へ進める認識・判断・Feedbackである。

## 4. 状況による体験差

| 状況 | この利用者成果で必要な体験 |
|---|---|
| 利用開始 | 「委任した仕事の応答を待つ時」で、対象と判断に必要な前提を理解できる |
| 成果成立 | 「内部ログを読まず、実行中・待機・停止と現在必要な判断を理解できる」を、観測時点・停止理由・必要な判断を行動可能に示すという条件で確認できる |
| 成果不成立 | 「古い観測や一律表示を進捗・完了と誤認する」を避け、理由と安全な戻り先を理解できる |
| 判断不能 | 不明な事実を補完せず、何を確認しなければ判断できないか分かる |
| 待機 | 何を待つかと、待っている間に選べる行動を誤認させない |
| 取消 | 取消要求と実際の停止・後始末完了を同じ結果として扱わない |
| 回復／再開 | 同じ対象へ戻る条件と、未解消の義務を区別する |
| 判断・許可 | 誰が何を決めるかと、許可前後の状態を区別する |

上表にない処理中、取消、回復その他の状態を、共通テンプレートだけを根拠に追加しない。必要性はこのUXの意味とIA観点の情報構造をUI定義で統合して判断する。

## 6. IA観点との統合時に確認すること

IA観点の分析が「タスク State、AI提供元 State、判断、入力、取消、および再試行・回復・再開を区別した次の行動を関連付ける」を識別・状態・関係・可視性・導線として表現できるかを確認する。UI定義では「無反応、偽の進捗、AI提供元差の誤表示、停止中の実行表示、および再試行・回復・再開を取り違える案内を反証する」を確かめられる形を保つ。必要情報をここで推測して先取りしない。
