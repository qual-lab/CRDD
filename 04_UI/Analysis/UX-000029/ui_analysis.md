## 1. 正式入力

- UX定義: [UX-000029 作業・変更・根拠・品質を迷わず辿る](../../../02_UX/Definitions/UX-000029/ux_definition.md)

IAやREQを直接読んで不足を補完しない。この分析はUX定義から利用者観点だけを導き、情報構造はIA観点の分析に委ねる。

## 2. UIへ引き継ぐ利用者成果

| 観点 | UX定義から受け取る内容 |
|---|---|
| 利用者／利用状況 | 製品全体の利用者像にある「CRDD作成者・保守者」 |
| 利用のきっかけ | 変更の現在地や根拠を調べる時 |
| 目的 | 作業・変更・根拠・品質を役割別に辿る |
| 得たい結果 | 変更理由と全影響パスを重複なく確認できる |
| 独立した利用者成果 | 未完了、変更理由、全影響パス、成立根拠および現在品質を役割の違いとともに辿れる |
| 重要な場面 | 変更の影響漏れを確認する場面 |
| 避ける失敗 | 同じ説明を複製し代表ファイルだけで済ませる |
| 守る品質 | 正本を分け全影響ファイルを列挙する |

## 3. 必要な認識・操作・Feedback

```text
変更の現在地や根拠を調べる時
        ↓
確認すること: Work、Change、変更対象ファイル、根拠、観測した改訂版、品質を分ける
        ↓
利用者の目的: 作業・変更・根拠・品質を役割別に辿る
        │
        ├─ ★ 判断点: 変更の影響漏れを確認する場面
        ├─ ⚠ 避ける失敗: 同じ説明を複製し代表ファイルだけで済ませる
        └─ ✓ 必要なFeedback: 正本を分け全影響ファイルを列挙する
        ↓
変更理由と全影響パスを重複なく確認できる
```

このUXからUIへ渡す中心は、特定の部品や内部処理ではなく、「変更の影響漏れを確認する場面」で利用者が「変更理由と全影響パスを重複なく確認できる」へ進める認識・判断・Feedbackである。

## 4. 状況による体験差

| 状況 | この利用者成果で必要な体験 |
|---|---|
| 利用開始 | 「変更の現在地や根拠を調べる時」で、対象と判断に必要な前提を理解できる |
| 成果成立 | 「変更理由と全影響パスを重複なく確認できる」を、正本を分け全影響ファイルを列挙するという条件で確認できる |
| 成果不成立 | 「同じ説明を複製し代表ファイルだけで済ませる」を避け、理由と安全な戻り先を理解できる |
| 判断不能 | 不明な事実を補完せず、何を確認しなければ判断できないか分かる |

上表にない処理中、取消、回復その他の状態を、共通テンプレートだけを根拠に追加しない。必要性はこのUXの意味とIA観点の情報構造をUI定義で統合して判断する。

## 6. IA観点との統合時に確認すること

IA観点の分析が「Work、Change、変更対象ファイル、根拠、観測した改訂版、品質を分ける」を識別・状態・関係・可視性・導線として表現できるかを確認する。UI定義では「責任者の混同、代表パスだけの表示、根拠の遡及上書きおよびGit差分への丸投げを反証する」を確かめられる形を保つ。必要情報をここで推測して先取りしない。
