## 2. UIへ引き継ぐ利用者成果

| 観点 | UX定義から受け取る内容 |
|---|---|
| 利用者／利用状況 | 製品全体の利用者像にある「プロジェクト運営者／PM」 |
| 利用のきっかけ | Meeting後に決定・Topic・Actionを整理する時 |
| 目的 | 会議の内容を候補として整理し正本へつなぐ |
| 得たい結果 | 会話と採用判断を混同せず仕事を継続できる |
| 独立した利用者成果 | 会話・観察・仮説・候補・決定を区別し、既存Topicとの関係を根拠付きで判断して所有正本へ戻せる |
| 重要な場面 | 候補を採用または却下する場面 |
| 避ける失敗 | 会議記録が自動的に正本へ昇格する |
| 守る品質 | 候補・判断・反映結果を区別する |

## 3. 必要な認識・操作・Feedback

```text
Meeting後に決定・Topic・Actionを整理する時
        ↓
確認すること: Meeting Item、候補、Topic Relation、判断、責任者を結ぶ
        ↓
利用者の目的: 会議の内容を候補として整理し正本へつなぐ
        │
        ├─ ★ 判断点: 候補を採用または却下する場面
        ├─ ⚠ 避ける失敗: 会議記録が自動的に正本へ昇格する
        └─ ✓ 必要なFeedback: 候補・判断・反映結果を区別する
        ↓
会話と採用判断を混同せず仕事を継続できる
```

このUXからUIへ渡す中心は、特定の部品や内部処理ではなく、「候補を採用または却下する場面」で利用者が「会話と採用判断を混同せず仕事を継続できる」へ進める認識・判断・Feedbackである。

## 4. 状況による体験差

| 状況 | この利用者成果で必要な体験 |
|---|---|
| 利用開始 | 「Meeting後に決定・Topic・Actionを整理する時」で、対象と判断に必要な前提を理解できる |
| 成果成立 | 「会話と採用判断を混同せず仕事を継続できる」を、候補・判断・反映結果を区別するという条件で確認できる |
| 成果不成立 | 「会議記録が自動的に正本へ昇格する」を避け、理由と安全な戻り先を理解できる |
| 判断不能 | 不明な事実を補完せず、何を確認しなければ判断できないか分かる |

上表にない処理中、取消、回復その他の状態を、共通テンプレートだけを根拠に追加しない。必要性はこのUXの意味とIA観点の情報構造をUI定義で統合して判断する。
