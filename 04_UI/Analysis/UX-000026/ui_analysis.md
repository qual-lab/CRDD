## 2. UIへ引き継ぐ利用者成果

| 観点 | UX定義から受け取る内容 |
|---|---|
| 利用者／利用状況 | 製品全体の利用者像にある「CRDD作成者・保守者」 |
| 利用のきっかけ | 変更の検証計画を作る時 |
| 目的 | 試験層ごとの保証と未確認範囲を理解する |
| 得たい結果 | 最終E2E前に外部境界の問題を局所化できる |
| 独立した利用者成果 | 各試験層が確認したこと・未確認範囲・時間や費用を理解し、必要な検証と高負荷試験の実行有無を選べる |
| 重要な場面 | 外部境界を結合する各段階 |
| 避ける失敗 | 単発成功や試験件数から一連の状態変化全体を保証する |
| 守る品質 | 開始から清掃まで段階的に反証する |

## 3. 必要な認識・操作・Feedback

```text
変更の検証計画を作る時
        ↓
確認すること: Test Layer、対象範囲、一連の状態変化 根拠、決定権限、Not Executed Stateを結ぶ
        ↓
利用者の目的: 試験層ごとの保証と未確認範囲を理解する
        │
        ├─ ★ 判断点: 外部境界を結合する各段階
        ├─ ⚠ 避ける失敗: 単発成功や試験件数から一連の状態変化全体を保証する
        └─ ✓ 必要なFeedback: 開始から清掃まで段階的に反証する
        ↓
最終E2E前に外部境界の問題を局所化できる
```

このUXからUIへ渡す中心は、特定の部品や内部処理ではなく、「外部境界を結合する各段階」で利用者が「最終E2E前に外部境界の問題を局所化できる」へ進める認識・判断・Feedbackである。

## 4. 状況による体験差

| 状況 | この利用者成果で必要な体験 |
|---|---|
| 利用開始 | 「変更の検証計画を作る時」で、対象と判断に必要な前提を理解できる |
| 成果成立 | 「最終E2E前に外部境界の問題を局所化できる」を、開始から清掃まで段階的に反証するという条件で確認できる |
| 成果不成立 | 「単発成功や試験件数から一連の状態変化全体を保証する」を避け、理由と安全な戻り先を理解できる |
| 判断不能 | 不明な事実を補完せず、何を確認しなければ判断できないか分かる |
| 判断・許可 | 誰が何を決めるかと、許可前後の状態を区別する |

上表にない処理中、取消、回復その他の状態を、共通テンプレートだけを根拠に追加しない。必要性はこのUXの意味とIA観点の情報構造をUI定義で統合して判断する。

## 6. IA観点との統合時に確認すること

IA観点の分析が「Test Layer、対象範囲、一連の状態変化 根拠、決定権限、Not Executed Stateを結ぶ」を識別・状態・関係・可視性・導線として表現できるかを確認する。UI定義では「一部Passからの全体品質推定、単発成功だけの一連の状態変化保証および未指示の高負荷実行を反証する」を確かめられる形を保つ。必要情報をここで推測して先取りしない。
