## 1. 正式入力

## 2. UIへ引き継ぐ利用者成果

| 観点 | UX定義から受け取る内容 |
|---|---|
| 利用者／利用状況 | 製品全体の利用者像にある「開発者」 |
| 利用のきっかけ | ローカルMCPの通信方式を選ぶ時 |
| 目的 | 通信方式を変えても同じ公開契約・入力・権限判断で操作する |
| 得たい結果 | stdio MCPとlocalhost HTTPのどちらでも、同じ入力・権限・状態・結果で仕事を続けられる |
| 独立した利用者成果 | stdio MCPとlocalhost HTTPのどちらでも、同じ入力・権限・状態・結果で仕事を続けられる |
| 重要な場面 | 入口を切り替えて同じ仕事を開始・継続する場面 |
| 避ける失敗 | 通信方式によって入力・権限判断・状態・結果の意味が変わる |
| 守る品質 | 公開契約・入力・権限判断・状態・結果を通信方式間で一致させる |

## 3. 必要な認識・操作・Feedback

```text
ローカルMCPの通信方式を選ぶ時
        ↓
確認すること: 処理結果、公開契約、通信方式、外部作用の発行有無を分ける
        ↓
利用者の目的: 通信方式を変えても同じ公開契約・入力・権限判断で操作する
        │
        ├─ ★ 判断点: 入口を切り替えて同じ仕事を開始・継続する場面
        ├─ ⚠ 避ける失敗: 通信方式によって入力・権限判断・状態・結果の意味が変わる
        └─ ✓ 必要なFeedback: 公開契約・入力・権限判断・状態・結果を通信方式間で一致させる
        ↓
stdio MCPとlocalhost HTTPのどちらでも、同じ入力・権限・状態・結果で仕事を続けられる
```

このUXからUIへ渡す中心は、特定の部品や内部処理ではなく、「入口を切り替えて同じ仕事を開始・継続する場面」で利用者が「stdio MCPとlocalhost HTTPのどちらでも、同じ入力・権限・状態・結果で仕事を続けられる」へ進める認識・判断・Feedbackである。

## 4. 状況による体験差

| 状況 | この利用者成果で必要な体験 |
|---|---|
| 利用開始 | 「ローカルMCPの通信方式を選ぶ時」で、対象と判断に必要な前提を理解できる |
| 成果成立 | 「stdio MCPとlocalhost HTTPのどちらでも、同じ入力・権限・状態・結果で仕事を続けられる」を、公開契約・入力・権限判断・状態・結果を通信方式間で一致させるという条件で確認できる |
| 成果不成立 | 「通信方式によって入力・権限判断・状態・結果の意味が変わる」を避け、理由と安全な戻り先を理解できる |
| 判断不能 | 不明な事実を補完せず、何を確認しなければ判断できないか分かる |
| 判断・許可 | 誰が何を決めるかと、許可前後の状態を区別する |

上表にない処理中、取消、回復その他の状態を、共通テンプレートだけを根拠に追加しない。必要性はこのUXの意味とIA観点の情報構造をUI定義で統合して判断する。

## 6. IA観点との統合時に確認すること

IA観点の分析が「処理結果、公開契約、通信方式、外部作用の発行有無を分ける」を識別・状態・関係・可視性・導線として表現できるかを確認する。UI定義では「stdio MCPとlocalhost HTTPで入力・権限判断・状態・結果が変わること、および失敗した通信方式と外部作用の発行有無を識別できない表示を反証する」を確かめられる形を保ち、下流へ「IAは通信方式、外部作用の発行有無、結果および次の処置を関連付ける。SPECは公開結果と通信方式 errorを分け、ArchitectureとVerificationは両入口の意味同値性と、外部作用の発行前後を取り違えないことを保証する。」を渡す。必要情報をここで推測して先取りしない。
