# UX-000011のUI分析

成果物種別: UI分析（UX観点）
分析単位: `UX-000011`
状態: 分析済み

## 1. 正式入力

- UX定義: [UX-000011 プロジェクト・リポジトリ・基点フォルダを区別して対象を選ぶ](../../../02_UX/Definitions/UX-000011/ux_definition.md)

IAやREQを直接読んで不足を補完しない。この分析はUX定義から利用者観点だけを導き、情報構造はIA観点の分析に委ねる。

## 2. UIへ引き継ぐ利用者成果

| 観点 | UX定義から受け取る内容 |
|---|---|
| 利用者／利用状況 | 製品全体の利用者像にある「プロジェクト運営者／PM」 |
| 利用のきっかけ | 参照または操作対象を選ぶ時 |
| 目的 | プロジェクト・リポジトリ・基点フォルダを区別して対象を確認する |
| 得たい結果 | 論理プロジェクトを一つに見ながら、参照・実行・回復の対象リポジトリと基点フォルダを取り違えずに選べる |
| 独立した利用者成果 | 論理プロジェクトを一つに見ながら、参照・実行・回復の対象リポジトリと基点フォルダを取り違えずに選べる |
| 重要な場面 | 外部作用（Effect）対象を確定する直前 |
| 避ける失敗 | 同名や近いパスを同じ対象と誤認する |
| 守る品質 | 各識別情報と物理基点フォルダの結合を明示する |

## 3. 必要な認識・操作・Feedback

```text
参照または操作対象を選ぶ時
        ↓
確認すること: プロジェクト、リポジトリ、基点フォルダ、Bindingを分ける
        ↓
利用者の目的: プロジェクト・リポジトリ・基点フォルダを区別して対象を確認する
        │
        ├─ ★ 判断点: 外部作用（Effect）対象を確定する直前
        ├─ ⚠ 避ける失敗: 同名や近いパスを同じ対象と誤認する
        └─ ✓ 必要なFeedback: 各識別情報と物理基点フォルダの結合を明示する
        ↓
論理プロジェクトを一つに見ながら、参照・実行・回復の対象リポジトリと基点フォルダを取り違えずに選べる
```

このUXからUIへ渡す中心は、特定の部品や内部処理ではなく、「外部作用（Effect）対象を確定する直前」で利用者が「論理プロジェクトを一つに見ながら、参照・実行・回復の対象リポジトリと基点フォルダを取り違えずに選べる」へ進める認識・判断・Feedbackである。

## 4. 状況による体験差

| 状況 | この利用者成果で必要な体験 |
|---|---|
| 利用開始 | 「参照または操作対象を選ぶ時」で、対象と判断に必要な前提を理解できる |
| 成果成立 | 「論理プロジェクトを一つに見ながら、参照・実行・回復の対象リポジトリと基点フォルダを取り違えずに選べる」を、各識別情報と物理基点フォルダの結合を明示するという条件で確認できる |
| 成果不成立 | 「同名や近いパスを同じ対象と誤認する」を避け、理由と安全な戻り先を理解できる |
| 判断不能 | 不明な事実を補完せず、何を確認しなければ判断できないか分かる |
| 回復／再開 | 同じ対象へ戻る条件と、未解消の義務を区別する |

上表にない処理中、取消、回復その他の状態を、共通テンプレートだけを根拠に追加しない。必要性はこのUXの意味とIA観点の情報構造をUI定義で統合して判断する。

## 6. IA観点との統合時に確認すること

IA観点の分析が「プロジェクト、リポジトリ、基点フォルダ、Bindingを分ける」を識別・状態・関係・可視性・導線として表現できるかを確認する。UI定義では「名前やパスの類似だけから対象識別情報を推定する操作を反証する」を確かめられる形を保ち、下流へ「IAはプロジェクト、リポジトリ、基点フォルダおよびBindingを別Entityとして関連付ける。UIは通常表示と情報源詳細を分け、Architectureは検証済み識別情報を公開結果まで保持する。」を渡す。必要情報をここで推測して先取りしない。
