# IA-000002のUI分析

成果物種別: UI分析（IA観点）
分析単位: `IA-000002`
状態: 分析済み

## 1. 正式入力

- IA定義: [IA-000002 目的・節目・Task・受入・判断](../../../03_IA/Definitions/IA-000002/ia_definition.md)

UXやREQを直接読んで不足を補完しない。この分析はIA定義から情報設計観点だけを導き、利用者成果と操作体験はUX観点の分析に委ねる。

## 2. UIへ引き継ぐ情報構造

内部Taskを逐次操作せず、何をどこまで誰へ任せ、何をもって受け入れるか理解する。

| 対象 | 利用者にとっての意味 | 識別・関係 |
|---|---|---|
| プロジェクト（Project） | 継続する活動の境界 | プロジェクト識別子（Project ID） |
| 節目（Milestone） | 人が委ね受入を判断する到達点 | Projectに属する安定ID |
| 目的（Objective） | Milestoneを成立させる目的 | Milestoneに属する安定ID |
| 作業（Task） | 実行可能な仕事単位 | Objectiveと作業識別子（Task Identity） |
| 決定権限 | 誰が何を決められるか | 対象・主体・時点へ結合 |
| 受入条件 | 上位成果を受け入れる条件 | Milestone／Objectiveへ結合 |

UIでは「プロジェクト（Project）、節目（Milestone）、目的（Objective）、作業（Task）、決定権限、受入条件」の識別と関係を維持する。同名・近似値、未観測・不存在、現在値・古い値を表示都合でまとめない。

## 3. 表示の優先順位とNavigation

| 利用場面 | 最初に見分ける対象 | 区別する状態 | 次の導線 |
|---|---|---|---|
| `UX-000002`／プロジェクト運営者／PM／複数AIへ仕事を委ねる時 | 目的、対象範囲、担い手、決定権限、入力、候補、取消、回復 | 準備中／許可待ち／実行中／停止。権限発行前後を分ける | 目的→範囲と担い手→許可→実行 |
| `UX-000003`／プロジェクト運営者／PM／委任した仕事の応答を待つ時 | 作業（Task）、実行主体、現在状態、判断、入力、次の行動 | 開始可能（ready）／実行中（running）／入力・判断待ち（waiting）／停止（blocked）／完了（completed）／失敗（failed） | Task→現在状態→判断要否→待機・入力・取消・回復 |
| `UX-000005`／プロジェクト運営者／PM／プロジェクトの成果をまとめて任せる時 | プロジェクト（Project）、節目（Milestone）、目的（Objective）、作業（Task）、受入条件、統合状態、品質 | Task完了／Objective受入／Milestone受入を別にする | Milestone→目的と受入条件→Task根拠→受入判断 |

```text
目的・節目・Task・受入・判断
        ↓
対象と現在状態
        ↓
不足・制限・競合
        ↓
関係・根拠
        ↓
判断／回復／次の対象
```

内部ID、生Log、実装詳細は最初の結論へ混在させず、根拠を掘り下げる段階で示す。

## 4. 表示差と開示境界

IA定義が要求する状態区分:

- `UX-000002`: 準備中／許可待ち／実行中／停止。権限発行前後を分ける
- `UX-000003`: 開始可能（ready）／実行中（running）／入力・判断待ち（waiting）／停止（blocked）／完了（completed）／失敗（failed）
- `UX-000005`: Task完了／Objective受入／Milestone受入を別にする

IA定義が要求する導線と責任:

- プロジェクト運営者／PM: 複数AIへ仕事を委ねる時に「複数AIへ任せる範囲と権限を理解する」ために必要な判断を行う。システムは「暗黙の範囲拡張や回復不能」を避けられるよう、委任状態・停止理由・回復先を行動可能に示す。
- プロジェクト運営者／PM: 委任した仕事の応答を待つ時に「現在の実行状態と必要な判断を確認する」ために必要な判断を行う。システムは「古い観測や一律表示を進捗・完了と誤認する」を避けられるよう、観測時点・停止理由・必要な判断を行動可能に示す。
- プロジェクト運営者／PM: プロジェクトの成果をまとめて任せる時に「目的と受入条件で節目を委ねる」ために必要な判断を行う。システムは「タスク件数を完成と誤認する」を避けられるよう、統合・品質・判断待ちを分けて示す。

値なし、未観測、古い値、競合、部分取得、開示制限および結果不明は、それぞれ利用者の次の判断が異なる場合に別の表示状態として扱う。開示できない対象は、その存在自体を示せるかも決定権限に従う。

## 6. UX観点との統合時に確認すること

UX観点の分析が求める利用者成果、重要場面、操作およびFeedbackに対し、「目的・節目・Task・受入・判断」の対象・状態・関係・導線が過不足なく判断材料を提供するかをUI定義で確認する。IAからUIへ引き渡す固有の意図は「UIは上位状態と根拠の優先度を、SPECは受入・取消・再開条件を定める。」であり、利用者の目的をここで推測して先取りしない。
