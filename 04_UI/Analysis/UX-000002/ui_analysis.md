## 1. 正式入力

IAやREQを直接読んで不足を補完しない。この分析はUX定義から利用者観点だけを導き、情報構造はIA観点の分析に委ねる。

## 2. UIへ引き継ぐ利用者成果

| 観点 | UX定義から受け取る内容 |
|---|---|
| 利用者／利用状況 | 製品全体の利用者像にある「プロジェクト運営者／PM」 |
| 利用のきっかけ | 複数AIへ仕事を委ねる時 |
| 目的 | 複数AIへ任せる範囲と権限を理解する |
| 得たい結果 | 実行前に誰へ何をどこまで任せるかを理解し、暗黙の範囲拡張なく仕事を委ねられる |
| 独立した利用者成果 | 実行前に誰へ何をどこまで任せるかを理解し、暗黙の範囲拡張なく仕事を委ねられる |
| 重要な場面 | 外部作用（Effect）の前の委任境界 |
| 避ける失敗 | 暗黙の範囲拡張や回復不能 |
| 守る品質 | 委任状態・停止理由・回復先を行動可能に示す |

## 3. 必要な認識・操作・Feedback

```text
複数AIへ仕事を委ねる時
        ↓
確認すること: 目的、対象範囲、担い手、決定権限、候補結果、入力、取消、回復を分ける
        ↓
利用者の目的: 複数AIへ任せる範囲と権限を理解する
        │
        ├─ ★ 判断点: 外部作用（Effect）の前の委任境界
        ├─ ⚠ 避ける失敗: 暗黙の範囲拡張や回復不能
        └─ ✓ 必要なFeedback: 委任状態・停止理由・回復先を行動可能に示す
        ↓
実行前に誰へ何をどこまで任せるかを理解し、暗黙の範囲拡張なく仕事を委ねられる
```

このUXからUIへ渡す中心は、特定の部品や内部処理ではなく、「外部作用（Effect）の前の委任境界」で利用者が「実行前に誰へ何をどこまで任せるかを理解し、暗黙の範囲拡張なく仕事を委ねられる」へ進める認識・判断・Feedbackである。

## 4. 状況による体験差

| 状況 | この利用者成果で必要な体験 |
|---|---|
| 利用開始 | 「複数AIへ仕事を委ねる時」で、対象と判断に必要な前提を理解できる |
| 成果成立 | 「実行前に誰へ何をどこまで任せるかを理解し、暗黙の範囲拡張なく仕事を委ねられる」を、委任状態・停止理由・回復先を行動可能に示すという条件で確認できる |
| 成果不成立 | 「暗黙の範囲拡張や回復不能」を避け、理由と安全な戻り先を理解できる |
| 判断不能 | 不明な事実を補完せず、何を確認しなければ判断できないか分かる |
| 取消 | 取消要求と実際の停止・後始末完了を同じ結果として扱わない |
| 回復／再開 | 同じ対象へ戻る条件と、未解消の義務を区別する |
| 判断・許可 | 誰が何を決めるかと、許可前後の状態を区別する |

上表にない処理中、取消、回復その他の状態を、共通テンプレートだけを根拠に追加しない。必要性はこのUXの意味とIA観点の情報構造をUI定義で統合して判断する。

## 6. IA観点との統合時に確認すること

IA観点の分析が「目的、対象範囲、担い手、決定権限、候補結果、入力、取消、回復を分ける」を識別・状態・関係・可視性・導線として表現できるかを確認する。UI定義では「対象範囲の拡張、未承認決定権限および不明な実行主体を反証する」を確かめられる形を保つ。必要情報をここで推測して先取りしない。
