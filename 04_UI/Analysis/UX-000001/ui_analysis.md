# UX-000001のUI分析

成果物種別: UI分析（UX観点）
分析単位: `UX-000001`
状態: 分析済み

## 1. 正式入力

- UX定義: [UX-000001 意味レビューへ集中できる事前確認](../../../02_UX/Definitions/UX-000001/ux_definition.md)

IAやREQを直接読んで不足を補完しない。この分析はUX定義から利用者観点だけを導き、情報構造はIA観点の分析に委ねる。

## 2. UIへ引き継ぐ利用者成果

| 観点 | UX定義から受け取る内容 |
|---|---|
| 利用者／利用状況 | 製品全体の利用者像にある「CRDD作成者・保守者」 |
| 利用のきっかけ | 成果物をレビューへ渡す前 |
| 目的 | 意味レビュー前に機械判定できる不備を落とす |
| 得たい結果 | 人が意味と判断へ集中できる |
| 独立した利用者成果 | 同じ対象と条件なら機械的不備と修正箇所を先に理解し、意味レビューへ集中できる |
| 重要な場面 | 機械指摘と意味判断を分ける |
| 避ける失敗 | 検査範囲や理由が分からない |
| 守る品質 | 同じ入力へ同じ指摘と修正可能な場所を返す |

## 3. 必要な認識・操作・Feedback

```text
成果物をレビューへ渡す前
        ↓
確認すること: 対象、検査条件、指摘、Location、Responsibilityを関連付ける
        ↓
利用者の目的: 意味レビュー前に機械判定できる不備を落とす
        │
        ├─ ★ 判断点: 機械指摘と意味判断を分ける
        ├─ ⚠ 避ける失敗: 検査範囲や理由が分からない
        └─ ✓ 必要なFeedback: 同じ入力へ同じ指摘と修正可能な場所を返す
        ↓
人が意味と判断へ集中できる
```

このUXからUIへ渡す中心は、特定の部品や内部処理ではなく、「機械指摘と意味判断を分ける」で利用者が「人が意味と判断へ集中できる」へ進める認識・判断・Feedbackである。

## 4. 状況による体験差

| 状況 | この利用者成果で必要な体験 |
|---|---|
| 利用開始 | 「成果物をレビューへ渡す前」で、対象と判断に必要な前提を理解できる |
| 成果成立 | 「人が意味と判断へ集中できる」を、同じ入力へ同じ指摘と修正可能な場所を返すという条件で確認できる |
| 成果不成立 | 「検査範囲や理由が分からない」を避け、理由と安全な戻り先を理解できる |
| 判断不能 | 不明な事実を補完せず、何を確認しなければ判断できないか分かる |

上表にない処理中、取消、回復その他の状態を、共通テンプレートだけを根拠に追加しない。必要性はこのUXの意味とIA観点の情報構造をUI定義で統合して判断する。

## 5. UI処置

| UI候補 | 処置 | 保持する利用者成果 | 判断理由 |
|---|---|---|---|
| [UI-000001 事前検査と意味レビューへの案内](../../Definitions/UI-000001/ui_definition.md) | New | 意味レビューへ集中できる事前確認 | この利用者成果を認識・操作・Feedbackとして独立して扱う |

## 6. IA観点との統合時に確認すること

IA観点の分析が「対象、検査条件、指摘、Location、Responsibilityを関連付ける」を識別・状態・関係・可視性・導線として表現できるかを確認する。UI定義では「結果の決定性、対象箇所、理由および意味判断との境界を確認する」を確かめられる形を保ち、下流へ「品質は決定論性と誤検知を、文書化規則は人が理解できる指摘を、Verificationは意味監査との境界を具体化する。」を渡す。必要情報をここで推測して先取りしない。
