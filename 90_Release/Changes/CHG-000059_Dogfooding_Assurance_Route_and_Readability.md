- 判断日: 2026-09-02
- 対象: v0.18～v0.18.1のDogfoodingと外部レビューから確認した、保証活動、変更経路および人間可読性の横断改善
- 対象リリース: `v0.19.0`
- 変更分類: `breaking`

## 1. 契機と変更意図

v0.18～v0.18.1では、Runtimeの安全性と完成品質を高める一方、レビュー・監査・再確認の反復、当初計画からの経路変更、および規範文書を初見で理解する負荷が発生した。人間の決定権限者は、規範や保証活動を一律に軽くするのではなく、既存の仕組みが実際にどう機能したかを観測し、その根拠から後で最適化できるようにする方針を採用した。

本変更は次を一つの横断改善として扱う。

1. 採用可能な結果までに使った保証活動のコストを観測する。
2. 計画した変更経路と実際の変更経路、その差と有効だった検証を観測可能にする。
3. 人間可読性を既存の文書監査の責務として具体化する。
4. 内容の正しさと文書の所有先を分け、共通規則、Toolの設計、反復手順、実装規約、検証および履歴が責務を越えて第二の正本になっていないか確認する。
5. 会話から成果物への意味変換、曖昧な範囲の非拡張、成果物成熟度、外部表現の主張強度および未評価範囲と完了表示を一貫させる。
6. 部分実装と上位Capabilityの完成を分け、完成に必要な保証を漏れなく列挙した集合と結果field間の相関不変条件を設計、実装、検証および表示へ接続する。
7. 実行環境が提供する意味を必要保証から設計・検証へ接続し、要求、受理、Effect、観測および耐久的確定を区別する。是正では変更した意味から回帰面を導出し、後工程の直列Loopを減らす。

## 2. 目指さないこと

- Light／Heavy等のProfileへCRDD規範を分割しない。
- 新しい自動経路決定機構、経路専用データベースまたは登録簿を作らない。
- 人間可読性専用の監査、Checkerまたは文字数による合否判定を作らない。
- 監査数、根拠量または保証活動の削減自体を成功指標にしない。
- 既存CHGを機械的に遡及更新しない。
- Provider Task、Project Runtimeの利用機能または既存のRuntime Authorityを拡張しない。Release manifestのA→B昇格は、署名済みbyteを壊さず運ぶための限定Filesystem Effectとして実装・検証する。

## 3. 変更経路の計画

- 計画した主な経路: [変更トレース](../../12_Change.md) → [エージェント](../../10_Agent.md)／[概要](../../00_Overview.md) → [品質保証](../../16_Quality_Assurance.md)／[進捗管理](../../15_Progress.md) → [文書化](../../03_Documentation.md)／[文書監査](../../51_Document_Audit.md) → [準拠監査](../../52_Conformance_Audit.md)／[不足・影響監査](../../53_Gap_Impact_Audit.md) → 利用側ひな型・Project Runtimeの有用性評価
- 選択理由: 変更経路は変更トレース、保証コストは品質保証、可読性は文書化と文書監査がそれぞれ正本責務を持ち、AI入口、ひな型、準拠およびProject Runtime評価へ直接伝播するため。
- 予定する検証: 全体Checker、品質保証・変更工程の専門レビュー、文書監査、準拠監査、不足／影響監査。
- 重要な非選択経路: [セキュリティ原則](../../01_Principles.md)に基づくセキュリティレビューと[RuntimeのE2E検証](../../07_Quality/03_Verification_Design.md)は、実装、Authority、Effect、Recovery、Providerまたは外部送信境界を変更しないため非選択。新しい可読性専用監査は、既存の[文書監査](../../51_Document_Audit.md)と責務が重複するため非選択。

## 4. 適用境界と代表例

| 区分 | 代表例 | 期待する処置 |
|---|---|---|
| 発火 | 非自明な変更で、複数の工程・監査候補から経路を選び、実行中に別工程や検証を追加した | 計画した主な経路、実際の経路、差の理由、追加処置、有効だった検証を既存CHGまたは根拠へ残す |
| 非発火 | 誤字修正、一意な変換、既存判断を変えない機械更新 | 経路記録を増やさず、必要な通常確認だけを行う |
| 境界 | 計画と実績は異なるが、新しい影響を処置し、差の理由を説明できる | 差を失敗にせず、工程改善の観測として保持する |
| 判定情報不足 | 影響工程、決定権限または必要な検証を安全に限定できない | 経路を捏造せず、不足情報と確認先を示して停止または再整理する |

可読性では、表示名の直感性、一言説明、用語依存、文の複雑さおよび情報構造を確認する。文字数や用語数だけで不合格にせず、読み違いが判断、義務、例外、実装、検証または引き渡しへ影響し得る場合に指摘事項とする。

利用側Feedbackから、会話上の口語を正本や外部成果物へそのまま移すこと、曖昧な指示を成果物数や削除範囲の最大解釈へ広げること、単一の`Draft`で異なる成熟度を丸めること、表現変換で根拠より強い量・因果・比較・確実性を示すこと、および未評価の必須観点を残して全体`Pass`や公開準備完了を表示することを、同じ意味変換と可読性の問題として追加した。専用文書や新しい監査は作らず、文書化、エージェント、品質保証、外部コミュニケーション、文書監査および利用側ひな型へ接続する。

今回追加した上位完成と相関不変条件の境界は、次の代表ケースで確認する。field名だけでは発火または非発火を決めず、その項目が共同で結果や利用側の処置を決めるかを契約から判定する。

| 区分 | 代表例 | 期待する処置 |
|---|---|---|
| 発火 | 複数のAdapterとRecovery保証から構成されるRuntime Capability | 保証、担当責任者、観測および利用側処置がすべて接続するまで上位完成を表示せず、部分接続として扱う |
| 非発火 | 純粋な文字列変換、単一の内部関数、または上位完成を主張せず利用側処置を共同決定しない`{width, height}` | 存在しない上位保証一覧や相関不変条件を作らず、通常の実装・試験契約を用いる |
| 境界 | `{status, retryable}` | 組合せが再試行、停止その他の利用側処置を決める場合だけ相関不変条件を発火する。独立した説明値なら非発火とする |
| 判定情報不足 | 完成に必要な保証の担当責任者または利用側を特定できない候補 | 保証や相関を捏造せず、対象限定の未評価結果、不足情報および確認先を示して上位完成を主張しない |

実行環境の意味と是正影響の新しい確認軸は、次の代表ケースで過剰適用と情報不足時の扱いを確認する。

| 区分 | 代表例 | 期待する処置 |
|---|---|---|
| 発火 | 外部Processを所有し、取消後のProcess不存在を保証する変更 | 対象OS／Runtimeの起動、終了要求、終了観測および子孫Processの意味を確認し、必要保証から設計契約と反証試験へ接続する。是正時はProcess状態、回復、公開結果等の意味的な回帰面を導出する |
| 非発火 | 同一Process内の決定的な文字列変換、または意味を変えない誤字是正 | 存在しない外部資源や重いlifecycle契約を作らず、通常の実装・文書確認だけを行う |
| 境界 | `write()`の結果を利用側が観測可能な完了根拠に使う | API仕様だけで完了意味を確定できれば契約へ固定する。重要な意味が曖昧で限定実測により後工程の高い是正費用を減らせる場合だけ小規模実測を行う |
| 判定情報不足 | 対象Runtimeの版、情報源または実環境での観測方法を確定できない | 後段の成立を推定せず、保証に依存しない代替境界、未対応／未評価としての停止、または不足根拠だけを得る限定確認のいずれかへ閉じる |

## 5. 保証コストの観測

既存の運用上の有用性指標へ、レビュー回数、独立レビュー回数、監査回数、再レビュー／再監査回数、検証実行時間、完了までの検証反復数、根拠生成量、指摘事項数および是正回数を候補として追加する。すべての対象へ全項目を要求せず、比較目的、観測可能性および判断を変える可能性に応じて選ぶ。未測定値を0へ補正しない。

評価単位は実装時間ではなく、品質条件を満たす採用可能な結果までの総コストである。保証活動が少ないことだけを成功とせず、後工程指摘、残存リスク、人間負荷および有効だった検証と合わせて評価する。

## 7. 検証と完了条件

- 全体CheckerがError 0、Warning 0である。
- 独立した品質保証・変更工程レビューが、保証コストの所有、合否との分離および過剰適用の防止を確認する。
- 文書監査が、表示名、一言説明、用語依存、文の複雑さ、情報構造および文字数Gate非採用を確認する。
- 文書監査が、各項目が対象文書の目的、対象、決定権限および成果物種別に属し、別文書の第二の正本を作っていないことを確認する。
- 文書監査が、会話から成果物への意味変換、曖昧な範囲の非拡張、成果物成熟度、外部表現の主張強度および未評価範囲と完了表示の整合を確認する。

- 文書監査が、部分接続、本番未接続、未評価および上位完成表示の区別と正本配置を確認し、アーキテクチャ／品質保証の専門成立性を代替しない。
- 準拠監査と不足／影響監査が、正本、AI入口、ひな型、Project Runtime評価および既存監査への伝播を確認する。
- 指摘是正後の固定改訂版で再確認し、計画した経路と実際の経路、その差、有効だった検証を本CHGへ戻す。

## 8. 実際の経路・影響・逸脱

当初計画した正本・AI入口・ひな型・監査への伝播後、CRDD自身の文書監査を追加した。文書監査は、入口文書の条件過密、READMEの利用手順と移行案内の圧縮、英語CHANGELOGの伝播漏れに加え、`19_Maintenance.md`がTool固有の実装・Security・検証契約を所有していた責務混在を検出した。

実際の経路は、文書化／文書監査から保守、内部ツール・コーディング規約、Coordinator／Windowsプラットフォームアクセスのアーキテクチャ、Workflowおよび検証設計へ拡大した。この差は新しいRuntime変更ではなく、新しい所有先確認をCRDD自身へ適用した結果である。移管では既存のBCP 14強度、TCB、Provider Home、Mount Grant、Process、Fakeと実環境、Build／Runtimeの意味を保持した。既存Runtimeの挙動、移行結果および公開済みv0.18.1履歴は変更していない。

機械Checkerはリンク・アンカー・構造の成立に有効だったが、文章の過密さ、英日差分および正しい内容の誤配置は検出しなかった。文書監査は可読性と所有先の不整合、準拠／不足・影響監査は英語CHANGELOGと利用側・変更トレースへの伝播不足、専門レビューはSecurity／Runtime契約の意味保持を確認する役割として有効だった。

3つの固定改訂版を3系統で確認し、2回是正した。固定改訂版`008c583`では、当時の対象についてCheckerがMarkdown 396件、local link 2,778件、anchor 949件、Error 0、Warning 0で終了し、全独立確認が`Pass`、残る指摘事項0となった。指摘、共通原因、未測定値および非該当範囲は[検証結果](../../07_Quality/Verification_Results/2026-09-02_Dogfooding_Assurance_Route_Readability_Verification.md)に記録する。この結果は、後続で追加した意味変換、状態表示、上位完成、相関不変条件および三値観測の確認結果には流用しない。

その後の利用側Feedbackでは、文書の読みやすさだけでなく、情報源から成果物への意味変換と状態表示に共通原因があることを確認した。追加差分は`03_Documentation.md`、`10_Agent.md`、`16_Quality_Assurance.md`、`17_Communication.md`、`51_Document_Audit.md`、公式／利用側の`AGENTS.md`およびCommunicationひな型へ反映した。`008c583`の確認結果をこの追加差分へ流用せず、Project Runtimeの後続一般化と合わせた新しい[Source A署名前監査](../../07_Quality/Verification_Results/2026-09-03_Project_Runtime_Source_A_Pre_Sign_Audit.md)を実行した。初回固定改訂版で検出したRelease closure契約と公開文書への伝播のMajor 2件を是正し、`1f3f49b`の限定再確認はCritical／Major／Minor 0件でPassした。この結果は署名前の論理候補の成立であり、署名、実Provider／実Docker E2EまたはRelease完了へ読み替えない。

Project Runtimeの責務分離候補に対する独立レビューでは、一部のPlatform操作と単体試験の成立を境界全体の完成へ過大表示し得ること、および個別fieldが許容値でも成功表示とcleanup／Recovery義務が矛盾し得ることを検出した。共通原因は、設計から試験への接続一般ではなく、上位Capabilityの完成に必要な保証を漏れなく列挙して判定する規則と、複数fieldの相関不変条件が明示不足だったことである。Tool固有の状態名や実装方式は共通規範へ持ち込まず、`27_Architecture.md`、`10_Agent.md`、`16_Quality_Assurance.md`、`51_Document_Audit.md`および公式／利用側の`AGENTS.md`へ一般化した。

後続の公開Process E2E検証器の独立確認では、Process handle取得をOS起動成功、標準エラーへの`write()`呼出しを観測成立として扱った不足と、選定・開始を別々に検査して全体順序および実行横断のIdentity一意性を失った不足を検出した。同じFindingは、結合設計と実行環境の意味の双方を根本原因に持ち、是正後の影響展開不足でもあったため、排他的な原因分類へ丸めない。根本原因、事前予測可能性、検出工程および是正増幅を別軸で扱う。Architectureには、実行資源の必要保証から対象環境の実際の意味、失敗・観測不能、契約および反証へ接続する規則と、要求発行、handle取得、受理、Effect成立、完了通知、観測および耐久的確定の分離を追加した。Quality Assuranceには各段階の検証接続、Maintenanceには変更した意味から回帰面を導出する是正前確認を追加した。新しい工程、Platform知識集、固定Schemaまたは全変更へのSpikeは追加しない。

Source A署名後のManifest取込みでは、stagingからRepositoryへ人手で内容を転記した結果、編集処理が末尾LFを1 byte追加し、署名済みfileのSHA-256と不一致になった。同じ種類の問題は過去にもEvidence保存時の末尾LF追加として観測され、今回も手動copyを正規経路に残したことでRelease境界へ再発した。個別にLFを削る処置ではなく、A→Bを専用の昇格Effectへ変更した。昇格入口は署名、Source A Commit／Tree、Runtime実行集合、Policy、Native成果物、現在HEADをEffect前に結合し、Manifestをparse／serializeせず不透明な安定byteとして扱う。最終Pathへ段階writeせず、同一Filesystemの排他的hard linkで完成済みfileだけをatomicに公開し、同一file object、byte数、SHA-256および署名済み配布条件を再確認してからsource名を外す。中断後はsourceのみ、同じfile objectを指す二名、destinationのみの三状態から再開し、別Identity、内容変化または観測不能を削除しない。これにより、編集器、Shell encoding、末尾改行、部分fileおよび手作業の取り違えを正式経路から除く。

## 9. 既知の制限と後続評価

本変更は観測契約を整えるものであり、現時点で最適な変更経路、最小保証コストまたは可読性の単一尺度を確定しない。一定量の実績が蓄積した後、経路不足の共通パターン、保証コストと品質の関係、および文書監査で繰り返す可読性指摘を、追加変更の根拠として再評価する。
