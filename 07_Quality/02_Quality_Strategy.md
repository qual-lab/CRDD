# CRDD内部ツールの品質方針

成果物種別: Quality横断方針
状態: v0.21.0 Canonical
担当責任者: Qual-Lab
公開済み基準: v0.20.1

## 1. 何を品質として守るか

CRDDは、上流工程で明らかにした利用者成果、情報の意味、操作、振る舞い、責務境界、失敗時の安全性および回復を、実装と利用側まで失わないことを品質保証の中心に置く。

```text
[上流の成立条件]
          │ 全Canonical IDを一行以上処置
          ▼
[Quality Analysis]
  Mapping／検証義務／Same・New・Merge
          ↓
[Quality Definitions]
  検証目標／どう確認するか
          ↓
[自動試験／手動・Hybrid確認]
          ↓
[対象改訂版のEvidence]
          ↓
[現在の品質状態]
```

## 2. 主な品質Risk

| Risk | 利用者・運用への影響 | 主な検証方針 |
|---|---|---|
| 上流の意図が後工程で欠落する | 実装は動くが望んだ結果にならない | Canonical IDの全数Coverageと工程間の逆引き |
| 部品のPassを上位Capabilityの完成にする | 実利用やE2Eで初めて未接続が発覚する | 原因層から関連1〜2 block、必要なSTへの段階的結合 |
| 外部実行環境の意味を推測する | 要求は成功したがEffect、結果搬送、終了が成立しない | 要求、受理、開始、Effect、結果、終了後のライフサイクル全体を観測 |
| 責務変更で副次Consumerが取り残される | 署名、Release、Recovery等の希な経路で失敗する | 宣言と実Sourceから独立に導出したConsumer集合の一致 |
| 試験数やcoverage率を保証と誤認する | 未観測の失敗、資源、Authorityを見逃す | 必要な観測、期待した失敗理由、終了後条件で評価 |
| 実行できないPT／LTが通常監査を停める | 現実的でない費用や時間を要求する | 必須要求の場合だけGateにし、実行は人間の明示許可と強制可能な上限を必要とする |

## 3. 試験段階と責務

QualityはREQ、UX、IA、UI、SPECおよびArchitectureを横断して、それぞれが所有する異なる種類の成立条件を検証体系へ接続する。試験段階を情報源工程へ固定対応させず、各検証義務と観測境界からUT／IT／ST／UATを選ぶ。

| 試験段階 | 主に確認するもの | 自動化の方針 |
|---|---|---|
| UT | Module、Function、Component内部、判断分岐 | `40_Develop`のCode近接試験で分岐網羅率100%を既定目標とする。数値だけでPassにしない |
| IT | Component、Port／Adapter、Store、Process、OS、Container、Network、Transport間 | 正常・準正常・異常・終了後を反復可能にする |
| ST | 複数の詳細領域で作る上位Capability、利用者成果、情報利用 | 本番と同じCompositionまたは説明可能な同等構成で、公開結果と終了後を確認 |
| UAT | 採用した要求が実際の利用目的に適合するか | 判断権限が必要な部分は人間が確認。理由付きで非該当にできる |
| PT／LT | 性能要求、同時実行、長時間蓄積、枯渇、劣化、回収 | テスト設計は可。実行は人間が対象・上限・費用／Credit・中止・cleanupを明示し、runnerが強制できる場合に限る |

回帰試験（RT）は独立した試験段階ではない。変更した意味とその利用側から、各試験段階の既存試験を選択して再実行する。

## 4. 確認の順序

1. Canonical Definitionと成立条件の母集団を固定する。
2. Quality AnalysisでRisk、失敗、試験段階、実行形態を決める。
3. Quality DefinitionでUT／IT／ST／UATの適用を全段階について判定し、外部境界がある場合は直接境界、隣接1 block、関連2 blocks、System／E2E、利用者受入のどこまで確認するかを固定する。
4. 各Local Itemで対象／境界、外部境界の段階、事前状態／入力、操作／刺激、観測と期待結果、終了後条件および実行形態を固定する。
5. 型、Formatter、Lintを通してから、原因層の試験と直接境界ITを実行する。
6. 関連1〜2 blockまで段階的に結合し、そこで初めて増える不確実性を確認する。
7. 必要な公開CapabilityだけST／E2Eで確認する。
8. Evidenceを固定し、独立確認後に現在の品質状態を更新する。

## 5. 根拠と完了の境界

- Test Definitionと実行結果を分ける。実行結果はCHGまたはRelease Evidenceが所有する。
- 過去のPassと現在の対象改訂版のPassを混ぜない。
- 未確認、失敗、確認不能、一部成立を全体Passへ含めない。
- 自動化できない品質を検証対象から削除しない。人間の理解、アクセシビリティ、決定権限はManual／Hybridで扱う。
- 独立レビュー、統合、署名、Releaseは別の判断である。
