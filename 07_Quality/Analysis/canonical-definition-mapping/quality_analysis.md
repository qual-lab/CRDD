# 全Canonical DefinitionのQuality分析

成果物種別: Quality分析
分析単位: 全工程のCanonical Definitionと検証目標の対応
状態: Canonical
維持責任者: Qual-Lab

## 1. 確認する理由

上流工程がそれぞれ所有する異なる種類の成立条件を、既存SourceやTestから逆算せず、検証義務と検証目標へ接続する。個別処置はID別文書の作成ではなく、Canonical集合の全IDを次のMappingで一行以上処置したことを意味する。

```text
REQ／UX／IA／UI／SPEC／ARCH
        │ 全Canonical IDを一行以上処置
        ▼
Quality Analysis Mapping
        ↓
Verification Obligation
        │ Same／New／Merge
        ▼
Verification Objective
        ↓
Test Design／Evidence
```

## 2. 正式入力と分母

| 工程 | Canonical Definition数 | Qualityで確認する主な正しさ |
|---|---:|---|
| REQ | 36 | 課題を解決し、要求した結果が成立するか |
| UX | 32 | 利用者成果と重要な失敗時の体験が成立するか |
| IA | 22 | 必要な情報を理解・識別・追跡できるか |
| UI | 20 | 認識・操作・Feedbackが成立するか |
| SPEC | 29 | 正常・境界・失敗・副作用の振る舞い契約が成立するか |
| ARCH | 18 | 構造・境界・故障・回復が成立するか |
| **合計** | **157** | 全件をMappingで処置する |

分母は、正規ID名のDirectoryと工程所定のDefinition実体が両方存在する集合から導出する。空Directory、Template IDまたは本文中の参照IDを分母へ含めない。

## 5. 試験段階と種別の判断

試験段階は上流工程へ固定対応させない。各行は検証対象の実際の観測境界からLevelを割り当てた。同じSource IDに複数Levelがある場合、それぞれが別の不確実性を減らすかを検証定義で具体化する。

- RTは独立した試験段階ではなく、変更した意味と利用側に応じて既存の検証を再実行する選択とする。
- PT／LTは必要な性能・長時間・資源条件をDefinitionで設計できるが、人間が対象、環境、上限、費用／Credit、中止条件およびcleanupを明示しない限り実行しない。
- Rights Review、利用目的への適合および人間の決定権限は、無理に自動テストへ変換しない。
