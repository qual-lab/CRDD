## 2. 引き継ぐUI契約

鍵の発行・独立失効・交換は固定administrator専用で、Role設定のON／OFF対象にしない。通常鍵操作は同一Process Workbench backendだけ。MCPには鍵操作の一覧・Schema・登録・dispatchを公開しない。通常Host鍵回復はログイン済みローカル操作者を信頼する対話CLIで交換2操作のみを扱い、追加認証・専用資格・承認コード・OS管理者昇格なし、既存Root／Path検証を維持する。

| 管理操作 | developer | manager | administrator |
|---|---|---|---|
| ユーザー登録・表示名変更 | 不許可 | 許可 | 許可 |
| developer／managerの割当て・変更 | 不許可 | 許可 | 許可 |
| administratorの付与・解除・降格を含むRole変更 | 不許可 | 不許可 | 許可 |
| developer／managerの詳細権限設定 | 不許可 | 許可 | 許可 |
| administratorの詳細権限設定 | 不許可 | 不許可 | 許可 |
| 鍵の発行・独立失効・交換 | 不許可 | 不許可 | 許可 |
| Repository登録・登録解除 | 不許可 | 許可 | 許可 |
| Repository公開範囲設定 | 不許可 | 許可 | 許可 |

固定管理能力は現行Roleと上表から判定し、Role詳細の内容設定から派生させない。UIは管理可否と内容閲覧可否を別に示し、管理者にも内容を自動付与しない。manager自身の内容範囲変更も、変更前の現在管理認可→明示的なRole内容設定／Exposure更新→次要求で現行Role・Exposure・実アクセス再評価の順を認識可能にし、更新受理を取得成立と表示しない。

| 対象 | Architectureへ保持する認識・操作・Feedback |
|---|---|
| 利用・自身表示 | 自身の表示名と安定userId、現行Role権限、Repository公開範囲と実アクセスを別に認識する。利用5区分と部分成立を区別する |
| 最小ユーザー管理 | 安定userId（UUID）・管理用表示専用名・一つのRoleを分ける。新規登録は予定Role、既存Role変更は対象ID・前後Role、表示名変更は対象ID・新表示名を示す。managerのadministrator表示名変更は許可し、管理者Roleの付与・解除・降格は提供しない。表示名変更でID・Role・Credentialを変えず、資格発行と分離する。名前を本人性・Authorityにしない |
| Role内容設定 | 対象Roleと変更内容を示す。managerはdeveloper／manager、administratorは三Roleの内容設定を扱う。固定管理操作の設定委譲やユーザー・資格の個別追加権限を示さない |
| Repository管理 | manager／administratorへ対象Repository ID・現在の登録／公開状態・変更内容と結果を示す。登録解除は同じ受理操作・採用改訂で登録と対応Exposureを除去し、両方の読戻し確認後に完了表示する。対象外の登録・ExposureとRepository／Product Dataを保持する。登録≠公開、公開≠実アクセス、解除完了≠開始済み処理の取消完了を区別する |
| 資格 | Credential ID→userIdと現在のRoleを区別し、古い権限固定を避ける。有効／失効／不明を表示し、永続resetting／rotation状態を増やさない |
| 指定ユーザー交換 | 対象の全旧有効資格失効と同じ既存userIdへの発行、他ユーザーの鍵保持を認識する |
| 全員交換 | 操作中管理者自身を含む全旧有効資格の失効、指定既存administratorへの発行、他ユーザーの通常再発行・再配布待ちを認識する |
| 新規発行 | Workbenchの固定administratorが既存userIdへ発行し、操作administratorの画面へ新Secretを一度だけ提示する。追加受領ボタンなし。対象本人への引渡し・受領は製品外で観測しない。旧失効・交換再入場なし |
| 独立失効 | Workbenchの固定administrator操作の対象、失効結果、以後の要求拒否を示す。新発行・Secret・交換再入場なし。結果不明は既知状態と確認先を示し、開始済み操作の取消とは扱わない |
| 2入口 | 通常管理とHost回復は入口・Authorityの別軸。全4組で対象ID・表示名・失効範囲・既存発行先・保持情報を事前表示し、Host入口または全員交換だけ明示確認する |
| 情報保持 | 鍵交換でuserId・表示名・Role・詳細権限・Repository登録・Product Dataを保持する |
| 発行・記録不明 | Credential IDとは別の元発行Identityと既知事実・確認先を示す。交換由来なら元のexact Recoveryへ戻し、通常発行へ交換Recoveryや新しい交換を付けない |
| 発行・記録確定後の受け渡し不明 | 「発行済み・受け渡し未確認」と示し、対象本人の受領は観測外であり、未受領と断定しない。Secretを再保存・再表示・自動再発行しない。現在administratorが既存交換を別操作として明示選択できる。指定ユーザー交換は先発行鍵を含む対象の全旧有効鍵、全員交換は全旧有効鍵を失効する。別交換成功を旧Secret受領・rollback・取消完了と表示しない。遅れた旧応答で失効鍵を利用可能と案内しない |
| 現在administrator非接続 | 鍵処置のための現在administrator認証が成立しない場合は既存Host交換入口だけを案内する。任意の認可失敗からHostへ迂回させない |
| 可視性・秘密 | 自身表示可、非認証User情報0、現在他ユーザー参照を許可されていない主体の他User一覧・存在・件数0。非開示Repositoryも理由で漏らさない。新Secretは発行／交換後だけ一度表示、保存・再表示しない |
| 通常管理の停止 | 対象・変更前の現在管理認可・操作に必要な状態を安全に確認不能、または認可設定破損では新Effect前停止を認識できる。manager許可の通常管理へadministrator存在条件を追加しない |
| 鍵処置の停止 | 発行の既存userId、独立失効のCredentialとuserIdの結合、交換の対象・必要資格集合・全員交換の指定既存administrator等が不明・不成立なら新鍵Effect前停止を認識できる。通常入口の固定administratorとHostのログイン済み操作者を別に扱い、Hostへ追加資格認証を要求しない |
| 単体利用 | Repository単体利用は資格不要。初回設定を単体利用の前提にしない |
| 初回Host設定 | ログイン済みHost操作者が明示開始し、管理用表示名を入力する。最初のadministratorユーザーをUUIDで作成し、同じuserIdの鍵をHost端末へ一度表示する。表示名は識別補助で、本人性・Authorityではない。既存Root／Path検証を維持し、追加認証・専用資格・承認コード・OS昇格、MCP公開・自動起動を追加しない |
| 初回の4状態 | 管理状態と進行中初期化記録の双方が未初期化と確定した場合だけ新作成へ進む。既存、確認済み途中、観測不能を未初期化と区別して表示する。単一Fileの不在、別Root、読取不能、破損、Lock使用中、未解決回復を未初期化と案内しない |
| 初回の部分結果 | UUID作成・発行・記録後、Host一度提示→exact同鍵の初回確認用限定接続成功→確認の保存・読戻し・短命材料清掃とLock終了→初回完了・通常管理の順を示す。どの必要条件も未確認・失敗・観測不能なら完了表示と通常利用可能表示は0。追加受領操作は設けない |
| 初回の中断後 | 確認済み元初期化試行の非秘密相関と既知事実を示す。発行／結果記録が不明なら元試行の再観測だけとし、新交換・再初期化・自動再発行を案内しない。発行と結果記録が確定しHost提示または同鍵の初回接続確認だけ不明なら、作成済みadministratorへの既存Host指定ユーザー交換を別の明示操作として案内する。初期化試行自体は交換Recoveryにしない |

初回開始前に確認済み試行やUUIDがない場合は、それらを推定しない。正規の未試行で双方未初期化を確認できた場合の明示新作成は拒否しない。既存状態や通常の鍵喪失は初期化せず既存Host交換へ戻す。初回設定からRepository登録・Exposure・内容権限を自動付与せず、Product Dataを変更しない。非認証RemoteへのUser情報0と、信頼されたHost操作者への初回結果表示を混同しない。

重要な不足・不明・制限を詳細へ隠さず、色だけで識別させない。対象確認・判断・戻り先はキーボードと文字表示でも理解できるようにする。Workbench／Host CLIの入口分担は採用済み。具体表示・案内、Layout、CMP、Schemaは未確定事項を維持する。

## 3. Architecture観点の評価

| 観点 | 評価・引き渡し |
|---|---|
| 責務・Component | [ARCH-000013](../../Definitions/ARCH-000013/architecture_definition.md)へ同じ対象・境界を渡す。認証認可とユーザー／Role／資格状態はAccess Management、認可済みContext集約はDomain Modelへ分ける候補 |
| Interface・Authority | UIはAuthority・Effectを発行しない。公開入口は現行認可を維持し、通常Remote利用からHost実行能力を生成しない。初回設定のAuthorityはログイン済みHost操作者の明示操作であり、通常の既存ユーザー／administrator認証条件を初回開始へ適用しない |
| 状態・データ | 名前、ID、Role権限、資格、公開範囲、取得可能性、回復の結果を独立軸で搬送する。表示専用Storeを新設しない。ユーザー成立前の初期化状態・非秘密試行相関・個別事実は既存Access Managementの管理能力が所有し、成立後にUUIDと資格へ結ぶ |
| Failure・Recovery | 元処理の発行／記録不明の再観測、確定後の別明示交換、現在administrator非接続時の既存Hostを分ける。各交換内のexact相関を保持し、別操作と混同しない。結果表示を取消・rollback保証にしない。初回途中は元試行再観測、発行・記録確定後の提示・引渡し（初回は同鍵接続確認）だけ不明は別の既存Host指定交換へ分け、後者の交換内部だけexact Recoveryを維持する |
| Security・品質 | 三可視境界、秘密一度表示・非保存、管理と内容閲覧の分離、部分成立と不明の保持を利用側でも反証する |
| 検証意図 | 固定8操作の各Role許可／拒否、操作別対象、managerのadministrator名前のみ変更、自己範囲変更の時間順、管理≠内容、登録≠公開、解除≠削除を対象にする。developer管理拒否を自身表示・許可内利用の拒否へ広げない。2操作×2入口、独立失効、同名／改名、三可視境界、処置前停止、処置後不明も保持する。初回では双方未初期化確認と明示開始、既存拒否、確認済み途中、観測不能の表示と戻り先、二重UUID／追加鍵／Secret保存・再表示0、自動登録・公開・内容付与0、部分成立≠全体完了を対象にする。試験ID・実測結果はQualityで定める |

## 4. 処置と未確認事項

検証意図には、登録だけ除去・Exposure残存／観測不能、両除去後の開始済み終了未観測、対象外変更、通常発行不明からの新交換、確定発行の不明化、別交換成功による旧受領推定、遅延した失効鍵の利用案内を含める。UIの表示と次行動を確認し、結果の保存方式や試験IDをこの分析で定めない。

既存ARCH-000013を更新する。新ARCH-IDや新しい一般IAM責務を作らない。管理の具体的な操作対象は追加されるが、メール・Password・本人確認・自己登録／自己編集・SSO・複数Role・個別追加権限は追加しない。

| 継承事項 | 判断者・再評価契機 | 未確認時の扱い |
|---|---|---|
| 自身表示名と安定ID、現行範囲・利用不能理由の理解、接続負担と失敗後の選択 | 代表利用者・Qual-Lab。実利用／前提変更時 | 定量条件や具体導線を確定しない |
| 対象識別と確認負担、採用済みWorkbench／Host CLIの具体表示・案内 | 管理者・Host運用者・Qual-Lab。Pilot／回復実測時 | 画面・配布手順を先取りしない |

現在の追加採用判断は不要。上記の未確認を解消済みと扱わない。意味・開示・必要な操作に不足や競合があればUIへ戻し、UIが示す来歴Ownerへの再開を判断する。

## 5. 統合時の確認

対応SPEC-000012とは、UI操作／表示とSystemの契機／結果を後段で照合する。反対観点のAuthorityをこの分析へ暗黙に取り込まない。通常×指定ユーザー交換へ追加の確認Gateを作らない。
