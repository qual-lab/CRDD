# REQ-000031の利用者体験分析

成果物種別: UX Analysis

状態: UX再統合済み・独立再レビュー待ち
分析対象: [REQ-000031 人の理解順と構造を両立する成果物](../../../01_Discovery/Definitions/REQ-000031/requirement.md)

## 1. REQの一次分析

```text
Checklist順の表と専門語を解読しないと、問題・目的・判断が分からない
        ↓
解決策を先に固定せず、人の仕事として読み替える
        ↓
UXとして必要
課題と判断の物語から構造化詳細へ進む
```

この要求で解くのは機能の有無だけではない。CRDD成果物を読む人・書く人が「情報量を失わず短時間で意味と次の行動を理解できる」状態へ進めないことを問題として扱う。具体的な画面、データ構造、API、Componentまたは数値閾値はここで確定しない。

| 観点 | 内容 |
|---|---|
| 解決する問題 | Checklist順の表と専門語を解読しないと、問題・目的・判断が分からない |
| UX Need | 課題と判断の物語から構造化詳細へ進む |
| 対象範囲 | CRDD文書を読む人、次工程の担当者が、「Checklist順の表と専門語を解読しないと、問題・目的・判断が分からない」状態から「物語から問題と目的を理解し、構造化情報で条件・責務・根拠を確認できる」状態へ移る場面 |
| 対象外 | 具体的な画面、データ構造、実装方式および数値閾値の確定 |

## 3. 利用者に起きる変化

```text
Before
────────────────
- Checklist順の表と専門語を解読しないと、問題・目的・判断が分からない
        │
        │ 人の理解順と構造を両立する成果物が変える体験
        ▼
After
────────────────
- 物語から問題と目的を理解し、構造化情報で条件・責務・根拠を確認できる
```

人の理解順と構造を両立する成果物は、単に内部方式を成立させる要求ではない。「Checklist順の表と専門語を解読しないと、問題・目的・判断が分からない」状態から、「物語から問題と目的を理解し、構造化情報で条件・責務・根拠を確認できる」状態へ変わり、利用者が次の判断へ進めることまでを体験として扱う。

この変化で守るのは操作手順ではない。CRDD成果物を読む人・書く人が課題と判断の物語から構造化詳細へ進むことで、情報量を失わず短時間で意味と次の行動を理解できるようになることを守る。

## 4. UX成果への統合

```text
REQ-000031
   │
   └─ New  → UX-000027 物語と構造から文書の意味を理解する
```

| UX成果 | 処置 | 判断理由 | この要求が補う内容 |
|---|---|---|---|
| 物語と構造から文書の意味を理解する | `New → UX-000027` | 本要求が「課題と判断の物語を理解してから、表・図で条件と関係を確認し、次の行動へ進める」という独立した利用者成果を最初に定義する。 | 結論・物語・図・表・詳細の順で辿ることが、この要求固有の成立条件になる |

Same／Newは技術用語の近さや件数目標では決めない。「利用者は、どの状況で、何をするためにSystemと関わり、何ができるようになるか」が同じかを比較する。Capability、Information、Quality、Validationまたは下流の実現要素は、独立UXへ分割せず対応する成果の成立条件として保持する。

## 5. 重要な体験

### このREQのJourney

```text
工程成果物を初めて読む時
        ↓
結論・物語・図・表・詳細の順で辿る
        │
        ├─ ★ Critical: 判断理由と条件を結び付ける場面
        ├─ ⚠ Failure:  Checklist順と専門語だけで文書を埋める
        └─ ✓ Quality:  StoryとStructured Contextを両立する
        ↓
情報量を失わず短時間で意味と次の行動を理解できる
```

### Service Blueprintの処置

処置: `作成`

```text
[U: CRDD成果物を読む人・書く人（CRDD作成者・保守者）]
        │ 利用者行動: 課題と判断の物語から構造化詳細へ進む
        ▼
[T: 工程成果物を初めて読む時]
        │
        ├─ 時間差: 文書作成と人間レビューは別だが、読解中の非同期回復状態は持たない
        ├─ 完了時: 課題と判断の物語、構造化詳細、未確認事項、次の行動
        └─ 失敗時: 理解できない用語・順序・欠落Contextをレビュー担当から成果物作成者へ返す
                     │
                     ▼
             [R: 成果物作成者（CRDD作成者・保守者）]
                     │ 返却された事実と判断不能範囲を確認
                     └─ 次の行動: 物語または構造を直し、再レビューする

---------------- 可視境界 ----------------
                     │ 時間関係: 文書作成と人間レビューは別だが、読解中の非同期回復状態は持たない
                     ▼
[S: 成果物作成者]
        └─ 提供責務: 読者の理解順に物語と構造を組み立てる
```

この図は、利用者行動、利用者が観測する接点、提供責務および失敗時の引き渡しを示す。内部Componentの構造やProtocolは下流工程で具体化する。

### 横断Synthesisへの接続

- Journeyの横断統合先: [標準を変更・検証・公開する](../../03_Experience_Map.md#標準を変更検証公開する)
- Service Blueprintの横断統合先: [共同Service Blueprint](../../04_Service_Blueprint.md#1-共同service-blueprint)
- 横断成果物はこの個別分析から共通パターンを合成する。このREQのJourney、責任境界または品質の代替にはしない。

### このREQでの責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| 成果物作成者 | 読者の理解順に物語と構造を組み立てる | Checklist順に項目を埋めただけの文書にしない |
| 利用者 | 短時間で意味と次の行動を理解し必要な詳細へ進む | 専門語の連鎖参照を強制されない |
| レビュー担当 | 情報量ではなく伝達された意味と不足を確認する | 形式充足だけで人間可読性をPassにしない |

### 補足する品質

- 結果または状態を最初に受け取る時: 情報量を削って可読性を装わない。（避ける失敗: Checklist順の表と専門語を解読しないと、問題・目的・判断が分からない）
- 結果を判断または引き継ぐ時: 一段落へ複数の意味を詰めない。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 失敗・不足から次の行動を選ぶ時: 構造表をNarrativeの代替にしない。（避ける失敗: 成立不能の理由や回復先が分からないまま作業が止まる）


## 6. 下流への引き渡し

```text
このREQで確定した利用者成果
        │
        ├─→ IA: 必要な情報・関係・見つけ方
        ├─→ UI: 誤認させない表示・操作意図
        ├─→ SPEC: 振る舞い・失敗・体験品質の条件
        └─→ Verification: 仮説を破る反例と観測
```

### 妥当性確認と未確認事項

| 確認する仮説 | 観測方法 | 現在未確認の範囲 |
|---|---|---|
| 物語から問題と目的を理解し、構造化情報で条件・責務・根拠を確認できることで、Checklist順の表と専門語を解読しないと、問題・目的・判断が分からないという負担または誤認を減らせる。 | 代表シナリオの利用者確認、UX専門Review、および品質期待を破る反例による下流検証 | CRDD作成者・保守者が「課題と判断の物語から構造化詳細へ進む」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |

### 工程別の引き渡し

| 引き渡し先 | 具体化する義務 |
|---|---|
| 下流工程 | DocumentationはNarrative-firstとStructured-firstを両立し、各工程は読者理解と機械追跡を確認する。 |

Discoveryへ戻す条件は、想定した利用者、問題または「課題と判断の物語から構造化詳細へ進む」という必要性が誤っていると分かった場合である。下流は実現方式を具体化してよいが、「情報量を失わず短時間で意味と次の行動を理解できる」という成果を無断で弱めない。
