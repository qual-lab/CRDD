# REQ-000037の利用者体験分析

成果物種別: UX分析

状態: UX再統合済み・独立再レビュー待ち
分析対象: [REQ-000037 任意期限を使った日程リスク分析](../../../01_Discovery/Definitions/REQ-000037/requirement.md)

## 1. 要求の一次分析

```text
期限を確認したか分からない
        ↓
未設定と確認漏れを区別できない
        ↓
日程リスクを過小評価する
        ↓
設定済み期限または意図的な未設定を理解して判断する
```

利用者に必要なのは日付入力そのものではない。期限を設定するか選び、設定済みなら残る仕事と日程を合わせて理解し、未設定なら日程リスクを評価できないことを理解したうえでScopeや次の判断へ進むことである。

| 観点 | 内容 |
|---|---|
| 解決する問題 | 期限の未設定と確認漏れを区別できず、日程リスクを過小評価し得る |
| 利用者に必要なこと | 期限の設定状態と残る仕事を合わせて理解し、評価可能範囲を踏まえて判断する |
| 対象範囲 | Version期限とRoadmap項目期限の設定確認、日程リスク理解、人間判断への接続 |
| 対象外 | 期限の強制、見積方式の固定、AIによるScope・Release判断 |

## 2. 利用者・目標・成果

```text
プロジェクト運営者／PM
        │ VersionまたはRoadmap項目を開始・見直す
        ▼
期限の設定状態と残る仕事を確認する
        │
        ▼
日程リスクを過小評価せず次の判断を選べる
```

| 項目 | 内容 |
|---|---|
| 主な想定利用者 | プロジェクト運営者／PM |
| 関係する利用者 | Scope、期限、リスク受容またはReleaseを判断する人 |
| 利用場面 | VersionまたはRoadmap項目の開始時と、残るScope・依存・判断待ちが変わった時 |
| 目的 | 期限の有無と残る仕事を踏まえて日程リスクを理解する |
| 得られる結果 | 期限未設定を安全と誤認せず、Scope維持・分離・期限変更・リスク受容を人間が判断できる |
| この要求に固有の差 | Version期限と項目期限を独立して任意設定し、未設定を日程リスク未評価として扱う |
| 根拠・確信度 | REQ-000037から導いた採用済み要求。表示段階、確認負担および再計算方式は後続確認が必要 |

## 3. 利用者に起きる変化

```text
変更前
────────────────
期限がない理由や確認有無が分からず
日程リスクを感覚で補う
        │
        ▼
変更後
────────────────
期限の設定状態と残る仕事を合わせて確認し
評価できる範囲と人間が決めることを理解する
```

期限を設定しない選択は許容するが、日程を評価できない状態を「問題なし」へ変換しない。期限だけで品質Gateや必要な検証を省略せず、日程はプロジェクトの現在地を判断する一つの条件として扱う。

### Same判断の比較

#### プロジェクトの現在地を根拠と不完全性付きで理解する

比較対象: `UX-000009`

| 比較軸 | 既存UX | 現在の要求 | 差と統合判断 |
|---|---|---|---|
| 担い手 | プロジェクト運営者／PM | プロジェクト運営者／PMと期限判断者 | 判断者が加わるが、現在地を判断する中心成果は同じ |
| 利用のきっかけ | プロジェクト状況を確認する時 | Version・項目の開始時または日程条件の変化時 | 日程に焦点を当てた同じ状況確認である |
| 得られる結果 | 不完全性を踏まえて次の判断を選べる | 日程評価可能範囲を踏まえてScope等を判断できる | 日程は不完全性の一種であり独立成果を作らない |
| 避ける失敗 | 欠測を完全な現在値と誤認する | 期限未設定をリスクなしと誤認する | 同じ誤った完全性判断である |

統合理由: 期限設定は現在地理解を成立させる情報と判断条件であり、それ自体を別のUX-IDへしない。

## 5. 重要な体験

### この要求での利用の流れ

```text
VersionまたはRoadmap項目を開始・見直す
        ↓
期限の設定有無と残る仕事を確認する
        │
        ├─ ★ 重要場面: 日程リスクを説明しScopeを判断する直前
        ├─ ⚠ 失敗: 未設定をリスクなし、期限ありを達成可能と誤認する
        └─ ✓ 守る品質: 設定状態、根拠、残る仕事、未評価範囲を同時に示す
        ↓
人間がScope・期限・リスク受容を判断する
```

### サービス提供の流れの処置

処置: `作成`

```text
【利用者・責任者】プロジェクト運営者／PM
        │ 利用者行動: 期限を設定するか選び、日程リスクを確認する
        ▼
【利用者接点】VersionまたはRoadmap項目の開始・見直し
        │
        ├─ 時間差: 開始時の設定後、Scopeや依存の変化に応じて再評価する
        ├─ 完了時: 設定値または未設定、根拠、現在の日程リスク、判断候補
        └─ 失敗時: 評価不能な理由と不足情報を判断者へ返す
                     │
                     ▼
             【回復・判断する人】Scope・期限・リスク受容の決定権限者
                     └─ 次の行動: 維持、分離、期限変更または明示的な保留を選ぶ

---------------- 可視境界 ----------------
                     ▼
【提供側】Project Contextを提供するシステム／AI
        └─ 提供責務: 期限だけで達成可能性を断定せず、未設定と未評価を保持する
```

### 製品全体の整理への接続

- 利用の流れの統合先: [プロジェクトの現在地を判断する](../../03_Experience_Map.md#プロジェクトの現在地を判断する)
- サービス提供の流れの統合先: [共同のサービス提供の流れ](../../04_Service_Blueprint.md#1-共同のサービス提供の流れ)

### この要求での責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| プロジェクト運営者／PM | 期限の設定状態と日程リスクを確認する | 根拠のない期限を作ることを要求されない |
| 決定権限者 | Scope、期限変更、リスク受容またはReleaseを判断する | AIへリスク受容を委ねない |
| 提供システム／AI | 設定状態、残る仕事、未評価範囲および候補を説明する | 期限だけで達成可能性やRelease可否を確定しない |

### 補足する品質

- Version期限と項目期限を別々に扱う。
- 未設定と確認漏れを区別する。
- 期限変更では理由と現在判断への影響を失わない。

## 6. 下流への引き渡し

| 接続先 | この要求から保持する意味 |
|---|---|
| IA（直後工程への正式な引き渡し） | Version期限、項目期限、設定状態、設定者、根拠、残るScope・依存・判断待ち、日程リスク、未評価範囲の意味と関係 |
| Quality Analysis / UX（伴走） | 未設定、片方だけ設定、変更、期限超過、残る仕事との不整合を誤認しない義務 |
| UI（後続Contract Relation） | 設定・未設定・未評価と人間判断を区別して認識できること |
| SPEC（後続Contract Relation） | 二つの任意期限を独立して扱い、AIが推定・受容・Release判断しないこと |

### 妥当性確認と未確認事項

- 確認する観測: 期限が両方、一方だけ、両方未設定の各場合に、利用者が評価可能範囲と次の判断を説明できる。
- 未確認事項: 期限確認の負担、表示段階および再評価頻度。
- 現在判定: 後続確認が必要。UX-000009への統合を止める事項ではない。
- 確認事項: 実際のProject運営で、期限入力と日程分析が判断改善に寄与するか。
- 判断者: プロジェクト運営者／PMとQual-Lab。
- 未確認時の影響: 表示方式や再計算方式を確定しない。
- Discoveryへ戻す条件: 期限確認が負担だけを増やす、または日程判断に寄与しない場合。
