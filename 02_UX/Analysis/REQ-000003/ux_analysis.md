# REQ-000003の利用者体験分析

成果物種別: UX分析

状態: UX再統合済み・独立再レビュー待ち
分析対象: [REQ-000003 目的から統合までのプロジェクトの開始から完了・再開までの状態](../../../01_Discovery/Definitions/REQ-000003/requirement.md)

## 1. 要求の一次分析

```text
タスク数、Agent log、個別結果から進捗を組み立て直す／内部処理の節目ごとに再指示する
        ↓
解決策を先に固定せず、人の仕事として読み替える
        ↓
利用者に必要なこと
目的と受入条件で節目を委ねる
```

プロジェクト運営者／PMが「内部タスクを追わず統合済みの完成を判断できる」状態へ進めないことを問題として扱う。

| 観点 | 内容 |
|---|---|
| 解決する問題 | タスク数、Agent log、個別結果から進捗を組み立て直す／内部処理の節目ごとに再指示する |
| 利用者に必要なこと | 目的と受入条件で節目を委ねる |
| 対象範囲 | プロジェクト運営者、目的の決定権限者が、「タスク数、Agent log、個別結果から進捗を組み立て直す」状態から「節目の成立状態、判断待ち、統合結果をプロジェクトの仕事として理解する」状態へ移る場面 |
| 対象外 | 具体的な画面、データ構造、実装方式および数値閾値の確定 |

## 3. 利用者に起きる変化

```text
変更前
────────────────
- タスク数、Agent log、個別結果から進捗を組み立て直す
- 内部処理の節目ごとに再指示する
        │
        │ 目的から統合までのプロジェクトの開始から完了・再開までの状態が変える体験
        ▼
変更後
────────────────
- 節目の成立状態、判断待ち、統合結果をプロジェクトの仕事として理解する
- 許可済みの目標範囲では進行を委ね、判断が必要な時だけ戻される
```

人間が内部タスクを一つずつ起動・監視しても、プロジェクトの目的が成立したかは分からない。利用者が委ねたいのはタスク実行ではなく、目的を受け入れ可能な結果へ進める一連の仕事である。

プロジェクト運営者／PMが目的と受入条件で節目を委ねることで、内部タスクを追わず統合済みの完成を判断できるようになることを守る。

| 利用のきっかけ | 複数AIへ仕事を委ねる時 | プロジェクトの成果をまとめて任せる時 | 既存UXの「複数AIへ仕事を委ねる時」に対して現在要求は「プロジェクトの成果をまとめて任せる時」を具体化するが、同じ「委任範囲と権限を理解して任せる」が必要になる開始条件の差であり、独立した成果境界ではない |

統合理由: 目的・受入条件・判断点は同じ委任成果を節目単位で成立させる条件であり、別の利用者成果ではない

#### 委任中の状態と判断要否を理解する

比較対象: `UX-000003`

比較元: `REQ-000002`の正式なDiscovery定義と、このUXを最初に`New`とした同要求分析。担い手、利用のきっかけ、避ける失敗は正式入力と要求固有分析から、得られる結果はUX固有の`New`行から直接導いた。後から統合したUX定義は比較元にしない。

| 比較軸 | 既存UX | 現在の要求 | 差と統合判断 |
|---|---|---|---|
| 担い手 | プロジェクト運営者／PM | プロジェクト運営者／PM | 既存UXと現在要求はいずれも「プロジェクト運営者／PM」であり、利用者の違いはない |
| 利用のきっかけ | 複数AIへ仕事を委ねる時 | プロジェクトの成果をまとめて任せる時 | 現在要求は複数AIへの委任を節目全体の委任へ具体化するが、どちらも委任中の状態と判断要否を理解する同じ開始条件である |
| 得られる結果 | 内部ログを読まず、実行中・待機・停止と現在必要な判断を理解できる | 節目委任中に統合状態と判断待ちを理解し、内部タスクを追わず現在必要な判断を選べる | 最初のNew分析で定義された固有成果に対し、現在要求はその成果を「節目委任中に統合状態と判断待ちを理解し、内部タスクを追わず現在必要な判断を選べる」の場面へ具体化する。利用者が達成する中心成果は同じである |
| 避ける失敗 | 誰が何を実行し、停止後に何が残ったかを個別Logから推測する | 個別タスクの進行だけが見え、節目全体の統合状態と現在必要な判断が分からない | REQ-000002の問題に対し、現在要求は個別タスクだけでは節目全体の状態と判断要否が分からない発生形を具体化する。中心成果を妨げる同じ失敗として扱える |

統合理由: 節目状態は同じ状態理解成果の上位集約であり、独立した目的／得られる結果を追加しない

`Same`／`New`は技術用語の近さや件数目標では決めない。「利用者は、どの状況で、何をするためにシステムと関わり、何ができるようになるか」が同じかを比較する。提供能力、必要情報、品質、妥当性確認または下流の実現要素は、独立UXへ分割せず対応する成果の成立条件として保持する。

## 5. 重要な体験

### この要求での利用の流れ

```text
プロジェクトの成果をまとめて任せる時
        ↓
目的・受入条件・判断点を渡す
        │
        ├─ ★ 重要場面: タスク成功と節目完成を区別する
        ├─ ⚠ 失敗:  タスク件数を完成と誤認する
        └─ ✓ 守る品質:  統合・品質・判断待ちを分けて示す
        ↓
内部タスクを追わず統合済みの完成を判断できる
```

### サービス提供の流れの処置

処置: `作成`

```text
【利用者・責任者】プロジェクト運営者／PM
        │ 利用者行動: 目的・受入条件・判断点を渡し、節目の採否を判断する
        ▼
【利用者接点】プロジェクトの成果をまとめて任せる時
        │
        ├─ 時間差: タスク群の実行後に統合と品質確認が続き、節目判断まで時間差がある
        ├─ 完了時: 統合結果、受入条件の充足、未充足条件
        └─ 失敗時: 部分成功、未充足条件、保持された成果を品質確認者へ返す
                     │
                     ▼
             【回復・判断する人】品質確認者
                     │ 返却された事実と判断不能範囲を確認
                     └─ 次の行動: 再試行、回復、同じ節目への再開、追加タスク、再統合または節目採否を選ぶ

---------------- 可視境界 ----------------
                     │ 時間関係: タスク群の実行後に統合と品質確認が続き、節目判断まで時間差がある
                     ▼
【提供側】提供システム／AI
        └─ 提供責務: 内部タスクを編成し、統合状態と判断待ちを返す
```

### 製品全体の整理への接続

- 利用の流れの統合先: [プロジェクトの現在地を判断する](../../03_Experience_Map.md#プロジェクトの現在地を判断する)
- サービス提供の流れの統合先: [共同のサービス提供の流れ](../../04_Service_Blueprint.md#1-共同のサービス提供の流れ)

### この要求での責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| プロジェクト運営者／PM | 目的・受入条件・判断点を渡し、節目の採否を判断する | タスク件数だけから完成を推定しない |
| 提供システム／AI | 内部タスクを編成し、統合状態と判断待ちを返す | 部分成功を節目完成へ畳まない |
| 品質確認者 | 受入・統合・品質の成立を反証する | 未確認範囲を便宜的に完了へ変えない |

### 補足する品質

- 結果または状態を最初に受け取る時: 依頼時に目的、受入条件および委ねる範囲を理解できる。（避ける失敗: タスク数、Agent log、個別結果から進捗を組み立て直す）
- 結果を判断または引き継ぐ時: 進行中は内部タスクを読まなくても、現在地と次の判断要否が分かる。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 結果を判断または引き継ぐ時: 部分タスク成功を節目完成と表示しない。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 失敗・不足から次の行動を選ぶ時: 現在状態から、同じ処理をやり直す再試行、残存状態を解消する回復、同じ目的・節目・判断点へ戻る再開を区別する。（避ける失敗: 成立不能の理由や回復先が分からないまま作業が止まる）

## 6. 下流への引き渡し

本節では、IAへの直後工程の引き渡し、UX工程に伴走する品質分析、およびIA完了後にUI／SPECが保持する契約を区別する。UXの完了だけを根拠にIAを飛び越えてUIまたはSPECを開始しない。

| 接続先 | この要求から保持する意味 |
|---|---|
| IA（直後工程への正式な引き渡し） | 必要な情報、理解すべき差、関係、現行性および利用者成果 |
| Quality Analysis / UX（伴走） | 得られる結果、重要場面、失敗、品質期待および検証意図 |
| UI（後続Contract Relation） | IA完了後にUX定義とIA定義の双方から分析する認識・操作・判断の意図 |
| SPEC（後続Contract Relation） | IA完了後にUX定義とIA定義の双方から分析する成立条件・失敗・利用者成果 |

```text
この要求で確定した利用者成果
├─→ IA                         直後工程への正式な引き渡し
├─→ Quality Analysis / UX      UX工程に伴走する検証義務分析
└─→ UI / SPEC                  IA完了後に保持するContract Relation
```

### 妥当性確認と未確認事項

| 確認する仮説 | 観測方法 | 現在未確認の範囲 |
|---|---|---|
| 節目の成立状態、判断待ち、統合結果をプロジェクトの仕事として理解する／許可済みの目標範囲では進行を委ね、判断が必要な時だけ戻されることで、タスク数、Agent log、個別結果から進捗を組み立て直すという負担または誤認を減らせる。 | 代表シナリオの利用者確認、利用者体験の専門レビュー、および品質期待を破る反例による下流検証 | プロジェクト運営者／PMが「目的と受入条件で節目を委ねる」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |

人間への確認:
- 現在判定: 後続の実利用確認が必要。UX工程の構造整理を止める判断事項ではない。
- 確認事項: プロジェクト運営者／PMが「目的と受入条件で節目を委ねる」を行う際の判断基準、許容負担、利用環境および失敗後の選択
- 判断者: [製品全体の利用者像](../../02_Personas.md)の「プロジェクト運営者／PM」を代表する利用者とQual-Lab。
- 未確認時の影響: 利用者成果と品質期待は仮説として保持し、負担、閾値、UIまたは実装方式を確定しない。

Discoveryへ戻す条件は、想定した利用者、問題または「目的と受入条件で節目を委ねる」という必要性が誤っていると分かった場合である。IA以降は実現方式を具体化してよいが、利用者成果を無断で弱めない。
