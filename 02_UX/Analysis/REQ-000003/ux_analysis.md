## 1. 要求の一次分析

```text
タスク数、Agent log、個別結果から進捗を組み立て直す／内部処理の節目ごとに再指示する
        ↓
解決策を先に固定せず、人の仕事として読み替える
        ↓
利用者に必要なこと
目的と受入条件で節目を委ねる
```

この要求で解くのは機能の有無だけではない。プロジェクト運営者／PMが「内部タスクを追わず統合済みの完成を判断できる」状態へ進めないことを問題として扱う。具体的な画面、データ構造、API、構成要素または数値閾値はここで確定しない。

| 観点 | 内容 |
|---|---|
| 解決する問題 | タスク数、Agent log、個別結果から進捗を組み立て直す／内部処理の節目ごとに再指示する |
| 利用者に必要なこと | 目的と受入条件で節目を委ねる |
| 対象範囲 | プロジェクト運営者、目的の決定権限者が、「タスク数、Agent log、個別結果から進捗を組み立て直す」状態から「節目の成立状態、判断待ち、統合結果をプロジェクトの仕事として理解する」状態へ移る場面 |
| 対象外 | 具体的な画面、データ構造、実装方式および数値閾値の確定 |

## 3. 利用者に起きる変化

```text
変更前
────────────────
- タスク数、Agent log、個別結果から進捗を組み立て直す
- 内部処理の節目ごとに再指示する
        │
        │ 目的から統合までのプロジェクトの開始から完了・再開までの状態が変える体験
        ▼
変更後
────────────────
- 節目の成立状態、判断待ち、統合結果をプロジェクトの仕事として理解する
- 許可済みの目標範囲では進行を委ね、判断が必要な時だけ戻される
```

人間が内部タスクを一つずつ起動・監視しても、プロジェクトの目的が成立したかは分からない。利用者が委ねたいのはタスク実行ではなく、目的を受け入れ可能な結果へ進める一連の仕事である。

この変化で守るのは操作手順ではない。プロジェクト運営者／PMが目的と受入条件で節目を委ねることで、内部タスクを追わず統合済みの完成を判断できるようになることを守る。

## 5. 重要な体験

### この要求での利用の流れ

```text
プロジェクトの成果をまとめて任せる時
        ↓
目的・受入条件・判断点を渡す
        │
        ├─ ★ 重要場面: タスク成功と節目完成を区別する
        ├─ ⚠ 失敗:  タスク件数を完成と誤認する
        └─ ✓ 守る品質:  統合・品質・判断待ちを分けて示す
        ↓
内部タスクを追わず統合済みの完成を判断できる
```

### サービス提供の流れの処置

処置: `作成`

```text
【利用者・責任者】プロジェクト運営者／PM
        │ 利用者行動: 目的・受入条件・判断点を渡し、節目の採否を判断する
        ▼
【利用者接点】プロジェクトの成果をまとめて任せる時
        │
        ├─ 時間差: タスク群の実行後に統合と品質確認が続き、節目判断まで時間差がある
        ├─ 完了時: 統合結果、受入条件の充足、未充足条件
        └─ 失敗時: 部分成功、未充足条件、保持された成果を品質確認者へ返す
                     │
                     ▼
             【回復・判断する人】品質確認者
                     │ 返却された事実と判断不能範囲を確認
                     └─ 次の行動: 追加タスク、再統合、回復または節目採否を選ぶ

---------------- 可視境界 ----------------
                     │ 時間関係: タスク群の実行後に統合と品質確認が続き、節目判断まで時間差がある
                     ▼
【提供側】提供システム／AI
        └─ 提供責務: 内部タスクを編成し、統合状態と判断待ちを返す
```

この図は、利用者行動、利用者が観測する接点、提供責務および失敗時の引き渡しを示す。内部構成要素の構造やプロトコルは下流工程で具体化する。

### 製品全体の整理への接続

- 利用の流れの統合先: [プロジェクトの現在地を判断する](../../03_Experience_Map.md#プロジェクトの現在地を判断する)
- サービス提供の流れの統合先: [共同のサービス提供の流れ](../../04_Service_Blueprint.md#1-共同のサービス提供の流れ)
- 横断成果物はこの個別分析から共通パターンを合成する。この要求での利用の流れ、責任境界または品質の代替にはしない。

### この要求での責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| プロジェクト運営者／PM | 目的・受入条件・判断点を渡し、節目の採否を判断する | タスク件数だけから完成を推定しない |
| 提供システム／AI | 内部タスクを編成し、統合状態と判断待ちを返す | 部分成功を節目完成へ畳まない |
| 品質確認者 | 受入・統合・品質の成立を反証する | 未確認範囲を便宜的に完了へ変えない |

### 補足する品質

- 結果または状態を最初に受け取る時: 依頼時に目的、受入条件および委ねる範囲を理解できる。（避ける失敗: タスク数、Agent log、個別結果から進捗を組み立て直す）
- 結果を判断または引き継ぐ時: 進行中は内部タスクを読まなくても、現在地と次の判断要否が分かる。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 結果を判断または引き継ぐ時: 部分タスク成功を節目完成と表示しない。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 失敗・不足から次の行動を選ぶ時: 失敗時は、失われた仕事、保持された結果、再開条件を区別する。（避ける失敗: 成立不能の理由や回復先が分からないまま作業が止まる）


## 6. 下流への引き渡し

```text
この要求で確定した利用者成果
        │
        ├─→ IA: 必要な情報・関係・見つけ方
        ├─→ UI: 誤認させない表示・操作意図
        ├─→ SPEC: 振る舞い・失敗・体験品質の条件
        └─→ Verification: 仮説を破る反例と観測
```

### 妥当性確認と未確認事項

| 確認する仮説 | 観測方法 | 現在未確認の範囲 |
|---|---|---|
| 節目の成立状態、判断待ち、統合結果をプロジェクトの仕事として理解する／許可済みの目標範囲では進行を委ね、判断が必要な時だけ戻されることで、タスク数、Agent log、個別結果から進捗を組み立て直すという負担または誤認を減らせる。 | 代表シナリオの利用者確認、利用者体験の専門レビュー、および品質期待を破る反例による下流検証 | プロジェクト運営者／PMが「目的と受入条件で節目を委ねる」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |

### 工程別の引き渡し

| 引き渡し先 | 具体化する義務 |
|---|---|
| 下流工程 | IAは目的、節目、タスク、統合状態、品質および判断の関係を分ける。SPECとArchitectureは各状態の成立条件と再開契約を具体化し、総合試験はタスク数でなく一連の委任体験を確認する。 |

Discoveryへ戻す条件は、想定した利用者、問題または「目的と受入条件で節目を委ねる」という必要性が誤っていると分かった場合である。下流は実現方式を具体化してよいが、「内部タスクを追わず統合済みの完成を判断できる」という成果を無断で弱めない。
