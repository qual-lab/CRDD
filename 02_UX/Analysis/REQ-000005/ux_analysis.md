# REQ-000005の利用者体験分析

成果物種別: UX分析

状態: UX再統合済み・独立再レビュー待ち
分析対象: [REQ-000005 実行基盤責務と依存方向の分離](../../../01_Discovery/Definitions/REQ-000005/requirement.md)

## 1. 要求の一次分析

```text
一つの構成要素変更が無関係な入口や操作を壊し、原因を利用者が切り分ける
        ↓
解決策を先に固定せず、人の仕事として読み替える
        ↓
利用者に必要なこと
責務分離後も成立済み機能を使う
```

実行基盤保守者・利用者が「内部変更の影響範囲を限定して更新できる」状態へ進めないことを問題として扱う。

| 観点 | 内容 |
|---|---|
| 解決する問題 | 一つの構成要素変更が無関係な入口や操作を壊し、原因を利用者が切り分ける |
| 利用者に必要なこと | 責務分離後も成立済み機能を使う |
| 対象範囲 | CRDD ツールを利用する人、保守する人が、「一つの構成要素変更が無関係な入口や操作を壊し、原因を利用者が切り分ける」状態から「責務の違いを意識せず同じ入口を使え、故障時は影響する範囲を正確に知れる」状態へ移る場面 |
| 対象外 | 具体的な画面、データ構造、実装方式および数値閾値の確定 |

## 2. 利用者・目標・成果

```text
実行基盤保守者・利用者
        │
        │ 望んでいる
        ▼
責務分離後も成立済み機能を使う
        │
        │ その結果として
        ▼
内部変更の影響範囲を限定して更新できる
```

| 項目 | 内容 |
|---|---|
| 主な想定利用者 | [製品全体の利用者像](../../02_Personas.md)の「実行環境の導入・運用者」 |
| 利用場面 | 実行環境の構成要素を置換する時 |
| 目的 | 責務分離後も成立済み機能を使う |
| 得られる結果 | 内部変更の影響範囲を限定して更新できる |
| この要求に固有の差 | 公開契約と置換後の責任者を照合することが、この要求固有の成立条件になる |
| 根拠・確信度 | 同じREQのDiscovery定義から導いた仮説。実行環境の導入・運用者が「責務分離後も成立済み機能を使う」を判断する場面で、公開契約と置換後の責任者を照合することが実際に成果へ影響するかは未確認。 |

## 3. 利用者に起きる変化

```text
変更前
────────────────
- 一つの構成要素変更が無関係な入口や操作を壊し、原因を利用者が切り分ける
        │
        │ 実行基盤責務と依存方向の分離が変える体験
        ▼
変更後
────────────────
- 責務の違いを意識せず同じ入口を使え、故障時は影響する範囲を正確に知れる
```

実行基盤責務と依存方向の分離は、単に内部方式を成立させる要求ではない。「一つの構成要素変更が無関係な入口や操作を壊し、原因を利用者が切り分ける」状態から、「責務の違いを意識せず同じ入口を使え、故障時は影響する範囲を正確に知れる」状態へ変わり、利用者が次の判断へ進めることまでを体験として扱う。

実行基盤保守者・利用者が責務分離後も成立済み機能を使うことで、内部変更の影響範囲を限定して更新できるようになることを守る。

## 4. 利用者成果への統合

```text
REQ-000005
   │
   └─ New  → UX-000007 内部変更後も成立済み能力を安全に使う
```

| 利用者成果 | 処置 | 判断理由 | この要求が補う内容 |
|---|---|---|---|
| 内部変更後も成立済み能力を安全に使う | `New → UX-000007` | 本要求が「責務・契約・接続部の変更後も、維持・変更・廃止された能力を理解し、取り残しのない結果を安全に利用・公開できる」という独立した利用者成果を最初に定義する。 | 公開契約と置換後の責任者を照合することが、この要求固有の成立条件になる |

`Same`／`New`は技術用語の近さや件数目標では決めない。「利用者は、どの状況で、何をするためにシステムと関わり、何ができるようになるか」が同じかを比較する。提供能力、必要情報、品質、妥当性確認または下流の実現要素は、独立UXへ分割せず対応する成果の成立条件として保持する。

## 5. 重要な体験

### この要求での利用の流れ

```text
実行環境の構成要素を置換する時
        ↓
公開契約と置換後の責任者を照合する
        │
        ├─ ★ 重要場面: 利用者向け機能の継続
        ├─ ⚠ 失敗:  内部パス変更で公開入口が壊れる
        └─ ✓ 守る品質:  公開結果と成立済み能力を維持する
        ↓
内部変更の影響範囲を限定して更新できる
```

### サービス提供の流れの処置

処置: `作成`

```text
【利用者・責任者】実行基盤保守者・利用者（実行環境の導入・運用者）
        │ 利用者行動: 責務分離後も成立済み機能を使う
        ▼
【利用者接点】実行環境の構成要素を置換する時
        │
        ├─ 時間差: 実装完了後に独立確認が行われ、前版能力との比較まで時間差がある
        ├─ 完了時: 置換責任者、利用側一覧、維持・変更・廃止した能力
        └─ 失敗時: 未接続利用側と不足根拠を独立確認者から変更担当へ返す
                     │
                     ▼
             【回復・判断する人】変更担当（実行基盤保守者・利用者）
                     │ 返却された事実と判断不能範囲を確認
                     └─ 次の行動: 移行を補完するか、廃止判断を人間へ戻す

---------------- 可視境界 ----------------
                     │ 時間関係: 実装完了後に独立確認が行われ、前版能力との比較まで時間差がある
                     ▼
【提供側】実装担当
        └─ 提供責務: 新責任者と全利用側を接続し、移行結果を提示する
```

### 製品全体の整理への接続

- 利用の流れの統合先: [実行基盤を導入・更新・回復する](../../03_Experience_Map.md#実行基盤を導入更新回復する)
- サービス提供の流れの統合先: [共同のサービス提供の流れ](../../04_Service_Blueprint.md#1-共同のサービス提供の流れ)

### この要求での責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| CRDD作成者・保守者 | 変更目的と維持・変更・廃止する能力を明示する | 置換根拠なしに旧処理を不要と決めない |
| 実装担当 | 新責任者と全利用側を接続し、移行結果を提示する | 内部配置だけの変更を完成と表示しない |
| 独立確認者 | 前版根拠と公開入口から成立済み能力を反証する | 実装者の自己申告を成立根拠にしない |

### 補足する品質

- 結果または状態を最初に受け取る時: 内部配置を利用手順へ露出しない。（避ける失敗: 一つの構成要素変更が無関係な入口や操作を壊し、原因を利用者が切り分ける）
- 結果を判断または引き継ぐ時: 一部故障を全体成功に見せない。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 失敗・不足から次の行動を選ぶ時: 置換後も成立済み機能を失わない。（避ける失敗: 成立不能の理由や回復先が分からないまま作業が止まる）

## 6. 下流への引き渡し

本節では、IAへの直後工程の引き渡し、UX工程に伴走する品質分析、およびIA完了後にUI／SPECが保持する契約を区別する。UXの完了だけを根拠にIAを飛び越えてUIまたはSPECを開始しない。

| 接続先 | この要求から保持する意味 |
|---|---|
| IA（直後工程への正式な引き渡し） | 必要な情報、理解すべき差、関係、現行性および利用者成果 |
| Quality Analysis / UX（伴走） | 得られる結果、重要場面、失敗、品質期待および検証意図 |
| UI（後続Contract Relation） | IA完了後にUX定義とIA定義の双方から分析する認識・操作・判断の意図 |
| SPEC（後続Contract Relation） | IA完了後にUX定義とIA定義の双方から分析する成立条件・失敗・利用者成果 |

```text
この要求で確定した利用者成果
├─→ IA                         直後工程への正式な引き渡し
├─→ Quality Analysis / UX      UX工程に伴走する検証義務分析
└─→ UI / SPEC                  IA完了後に保持するContract Relation
```

### 妥当性確認と未確認事項

| 確認する仮説 | 観測方法 | 現在未確認の範囲 |
|---|---|---|
| 責務の違いを意識せず同じ入口を使え、故障時は影響する範囲を正確に知れることで、一つの構成要素変更が無関係な入口や操作を壊し、原因を利用者が切り分けるという負担または誤認を減らせる。 | 代表シナリオの利用者確認、利用者体験の専門レビュー、および品質期待を破る反例による下流検証 | 実行環境の導入・運用者が「責務分離後も成立済み機能を使う」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |

人間への確認:
- 現在判定: 後続の実利用確認が必要。UX工程の構造整理を止める判断事項ではない。
- 確認事項: 実行環境の導入・運用者が「責務分離後も成立済み機能を使う」を行う際の判断基準、許容負担、利用環境および失敗後の選択
- 判断者: [製品全体の利用者像](../../02_Personas.md)の「実行環境の導入・運用者」を代表する利用者とQual-Lab。
- 未確認時の影響: 利用者成果と品質期待は仮説として保持し、負担、閾値、UIまたは実装方式を確定しない。

Discoveryへ戻す条件は、想定した利用者、問題または「責務分離後も成立済み機能を使う」という必要性が誤っていると分かった場合である。IA以降は実現方式を具体化してよいが、利用者成果を無断で弱めない。
