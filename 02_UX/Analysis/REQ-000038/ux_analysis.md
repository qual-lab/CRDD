# REQ-000038の利用者体験分析

成果物種別: UX分析

状態: UX再統合済み・独立再レビュー待ち
分析対象: [REQ-000038 Consumerに依存しない標準Project Context](../../../01_Discovery/Definitions/REQ-000038/requirement.md)

## 1. 要求の一次分析

```text
利用者やAIが複数の正本を都度探索する
        ↓
入口ごとに回答範囲、根拠、不完全性、分析が変わる
        ↓
何を信じ、次に何を判断するかを毎回組み立て直す
        ↓
共通の現在投影から同じ意味を理解する
```

利用者に必要なのはWorkbenchという画面ではない。Repositoryが責任を持てる範囲から、現在地、リスク、判断待ち、理由、次の一手を同じ意味で理解し、Ownerへ戻り、入口を変えても判断を続けられることである。

| 観点 | 内容 |
|---|---|
| 解決する問題 | 利用者やConsumerごとに探索範囲、回答、不完全性および分析品質が変わる |
| 利用者に必要なこと | Repositoryが責任を持つ同じProject Contextから現在状態と次の判断を理解する |
| 対象範囲 | Repository単位のCurrent Projectionと、人間・AI・MCP・Workbench候補による利用 |
| 対象外 | Workbench採否、Live監視、項目別権限、内部Modelおよび複数Repository統合方式の確定 |

## 2. 利用者・目標・成果

```text
開発者／プロジェクト運営者／PM／管理層
        │ Projectの状況と次の判断を知りたい
        ▼
共通の現在事実と共有分析を確認する
        │
        ▼
入口の違いを意識せず、根拠へ戻って次へ進める
```

| 項目 | 内容 |
|---|---|
| 主な想定利用者 | 開発者、プロジェクト運営者／PM、経営・管理層 |
| 関係する利用者 | Project Contextを更新・訂正するOwnerと、Federationを利用する人 |
| 利用場面 | 「今どうなっているか」を確認し、リスク・判断・理由・次の一手をまとめて理解する時 |
| 目的 | 同じRepository状態を入口ごとに再解釈せず理解する |
| 得られる結果 | 現在事実、共有分析、追加推論を区別し、根拠と不完全性を保って次の判断へ進める |
| この要求に固有の差 | Repository Role内だけをMarkdownで投影し、同一Repository内の項目別権限やLive状態を持たない |
| 根拠・確信度 | REQ-000038として採用済み。五場面は人間確認済みだが、実利用頻度・負担・入口比較は未確認 |

## 3. 利用者に起きる変化

```text
変更前
────────────────
入口ごとに正本を探索し
回答範囲と分析差を自分で埋める
        │
        ▼
変更後
────────────────
共通の現在投影から五場面をまとめて理解し
必要なOwnerへ戻り、入口を変えても判断を続ける
```

Project Contextは新しい業務正本ではない。結論と必要最小限の理由を示し、詳細と履歴はOwner Artifactへ戻す。範囲外ContextやLive状態を推測しないことも、利用者へ誤った完全性を与えないための体験条件である。

## 4. 利用者成果への統合

```text
REQ-000038
    ├─ Same → UX-000009  プロジェクトの現在地を根拠と不完全性付きで理解する
    └─ Same → UX-000012  入口を変えても同じ仕事を続ける
```

| 利用者成果 | 処置 | 判断理由 | この要求が補う内容 |
|---|---|---|---|
| プロジェクトの現在地を根拠と不完全性付きで理解する | `Same → UX-000009` | 五場面は現在地理解と次の判断を一つにまとめる具体条件であり、中心成果は同じ | Repository内の標準Markdown、共有分析、Owner Relation、Role外非開示、Live状態対象外 |
| 入口を変えても同じ仕事を続ける | `Same → UX-000012` | 人間・複数AI・MCP・Workbench候補で同じ意味を使うことは、入口差を読み替えない既存成果と同じ | 共通Project Context、事実・共有分析・追加推論の区別、Consumer固有Store禁止 |

### Same判断の比較

#### プロジェクトの現在地を根拠と不完全性付きで理解する

比較対象: `UX-000009`

| 比較軸 | 既存UX | 現在の要求 | 差と統合判断 |
|---|---|---|---|
| 担い手 | プロジェクト運営者／PM | 開発者、PM、管理層 | 利用者範囲は広がるが同じProject理解を得る |
| 利用のきっかけ | プロジェクト状況を確認する時 | 五場面をまとめて確認する時 | 五場面は既存の状況確認を具体化する |
| 得られる結果 | 根拠と不完全性付きで現在地を理解する | 事実・共有分析・推論を分けて根拠へ戻る | 共有分析を加えるが中心成果は同じ |
| 避ける失敗 | 欠測等を完全な現在値と誤認する | Role外や未反映を正常・不存在へ畳む | 同じ不完全性誤認である |

統合理由: Project ContextはUX-000009を複数Consumerで再現するための情報契約であり、新しい最終成果ではない。

#### 入口を変えても同じ仕事を続ける

比較対象: `UX-000012`

| 比較軸 | 既存UX | 現在の要求 | 差と統合判断 |
|---|---|---|---|
| 担い手 | 開発者とProject利用者 | 人間、複数AI、MCP、Workbench利用者 | Consumerは増えるが同じ仕事を継続する主体である |
| 利用のきっかけ | 接続方式や入口を選ぶ時 | Projectの状況を任意の入口で確認する時 | 入口選択の具体場面である |
| 得られる結果 | 同じ入力・状態・結果で続けられる | 同じ範囲・事実・分析・不完全性で続けられる | Project理解の意味を具体化する |
| 避ける失敗 | 入口ごとに意味や結果が変わる | Consumerごとに別Store・再推論・回答差が生じる | 同じ入口間不一致である |

統合理由: 固定Markdown契約は入口同値性の実現条件であり、別の利用者成果ではない。

## 5. 重要な体験

### この要求での利用の流れ

```text
「今どうなっているか」を確認する
        ↓
現在地・Risk・判断待ち・理由・次候補をまとめて確認する
        │
        ├─ ★ 重要場面: 要約を信じて次の判断へ進む直前
        ├─ ⚠ 失敗: Role外、欠測、未反映、AI推論を確認済み事実として扱う
        └─ ✓ 守る品質: 事実・共有分析・追加推論とOwner Relationを区別する
        ↓
必要なOwnerへ戻るか、人間の判断または次の作業を選ぶ
```

### サービス提供の流れの処置

処置: `作成`

```text
【利用者・責任者】Projectを理解・判断する人
        │ 利用者行動: 五場面をまとめて確認する
        ▼
【利用者接点】Markdown、AI、MCPまたはWorkbench候補
        │
        ├─ 時間差: Owner変更後、Gateを閉じる前に意味影響を評価して再投影する
        ├─ 完了時: 現在事実、共有分析、不完全性、Owner Relation、保存済み次候補
        └─ 失敗時: 競合、未反映または不明な範囲とOwnerへの導線を返す
                     │
                     ▼
             【回復・判断する人】Project ContextのOwnerまたは利用者
                     └─ 次の行動: 再投影、Owner確認、判断保留または利用可能範囲での判断

---------------- 可視境界 ----------------
                     ▼
【提供側】Project Contextを投影・利用するシステム／AI
        └─ 提供責務: Repository Role内の正本から同じ意味を返し、追加推論を分ける
```

### 製品全体の整理への接続

- 利用の流れの統合先: [プロジェクトの現在地を判断する](../../03_Experience_Map.md#プロジェクトの現在地を判断する)
- サービス提供の流れの統合先: [共同のサービス提供の流れ](../../04_Service_Blueprint.md#1-共同のサービス提供の流れ)

### この要求での責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| 利用者 | 状況、根拠、不完全性と次候補を確認し、必要な判断を行う | 表示されないContextを不存在と推定しない |
| Owner | 正本を更新し、Project Contextの意味影響を評価する | Project ContextへOwnerの履歴と詳細を複製しない |
| 提供システム／AI | 五場面を同じ意味で返し、事実・共有分析・追加推論を分ける | Role外やLive状態を推測せず、人間判断を自動昇格しない |

### 補足する品質

- 五場面を一度に理解でき、各結論からOwnerへ戻れる。
- Project Context固有IDを追加しない。
- 同一Repository内の項目別権限を作らず、範囲外Contextの存在を漏らさない。
- `Observed At`やDeploy先のLive状態を持たず、Ownerの変更未反映を競合として扱う。

## 6. 下流への引き渡し

| 接続先 | この要求から保持する意味 |
|---|---|
| IA（直後工程への正式な引き渡し） | Project／Repository Identity、Role、五場面、現在事実、共有分析、Owner Relation、不完全性、保存済み次候補の意味と関係 |
| Quality Analysis / UX（伴走） | Consumer間同値性、Role外非開示、第二正本禁止、競合・未反映・不明の保持、追加推論の分離 |
| UI（後続Contract Relation） | 五場面の結論を先に理解し、詳細・根拠・判断へ進めること |
| SPEC（後続Contract Relation） | Owner優先、意味変化時の再投影、Role内限定、Live状態対象外、追加推論の非昇格 |

### 妥当性確認と未確認事項

- 確認する観測: 同じRepository状態から、人間と複数Consumerが五場面について同じ意味を説明し、Ownerへ戻れる。
- 未確認事項: 実利用頻度、再探索時間、見落とし、更新負担、入口比較。
- 現在判定: Project ContextのUX統合は可能。Workbenchその他の入口採用は未確認。
- 確認事項: 最小Markdownが実際の判断を十分支え、第二正本化しないか。
- 判断者: 各利用者を代表する人とQual-Lab。
- 未確認時の影響: Workbench、内部Model、生成方式および表示詳細を確定しない。
- Discoveryへ戻す条件: Consumer間で意味が分かれる、更新負担が探索負担を上回る、または必要なOwnerへ戻れない場合。
