# REQ-000004の利用者体験分析

成果物種別: UX分析

状態: UX再統合済み・独立再レビュー待ち
分析対象: [REQ-000004 実行事実の再利用可能な記録](../../../01_Discovery/Definitions/REQ-000004/requirement.md)

## 1. 要求の一次分析

```text
実行基盤ごとに異なるLogを読み、事実と推定を混ぜて比較する
        ↓
解決策を先に固定せず、人の仕事として読み替える
        ↓
利用者に必要なこと
├ 記録する側: 同じ実行を重複させず安全に記録し、結果を確かめる
└ 振り返る側: 実行事実を出所と観測時点付きで比較する
```

この要求で解くのは機能の有無だけではない。実行基盤運用者・改善担当が「推測と事実を混ぜず改善候補を判断できる」状態へ進めないことを問題として扱う。具体的な画面、データ構造、API、構成要素または数値閾値はここで確定しない。

| 観点 | 内容 |
|---|---|
| 解決する問題 | 実行基盤ごとに異なるLogを読み、事実と推定を混ぜて比較する |
| 利用者に必要なこと | 作成側は同じ実行を重複させず記録して結果を確かめ、振り返る側は実行事実を出所と観測時点付きで比較する |
| 対象範囲 | 実行基盤・アプリの組込み担当者が観測事実を記録する場面と、運用・改善担当が記録を振り返る場面 |
| 対象外 | 具体的な画面、データ構造、実装方式および数値閾値の確定 |

## 2. 利用者・目標・成果

```text
実行基盤運用者・改善担当
        │
        │ 望んでいる
        ▼
実行事実を出所と観測時点付きで比較する
        │
        │ その結果として
        ▼
推測と事実を混ぜず改善候補を判断できる
```

| 項目 | 内容 |
|---|---|
| 主な想定利用者 | [製品全体の利用者像](../../02_Personas.md)の「実行環境の導入・運用者」 |
| 利用場面 | 実行結果を振り返る時 |
| 目的 | 実行事実を出所と観測時点付きで比較する |
| 得られる結果 | 推測と事実を混ぜず改善候補を判断できる |
| この要求に固有の差 | 観測事実・評価・改善候補を分けて読むことが、この要求固有の成立条件になる |
| 根拠・確信度 | 同じREQのDiscovery定義から導いた仮説。実行環境の導入・運用者が「実行事実を出所と観測時点付きで比較する」を判断する場面で、観測事実・評価・改善候補を分けて読むことが実際に成果へ影響するかは未確認。 |

記録を作る側には、振り返る側とは別の成果がある。

| 項目 | 内容 |
|---|---|
| 主な想定利用者 | 実行基盤・TypeScriptアプリの組込み担当者 |
| 利用場面 | 観測可能な実行段階が確定し、事実を共有可能にする時 |
| 目的 | 同じ意味で取得できる記録を安全に一度だけ公開する |
| 得られる結果 | 記録済み・未記録・結果不明を見分け、重複や上書きなく次の処置を選べる |
| この要求に固有の差 | 複数作成側、再送、並行書込み、途中失敗、情報最小化およびEffect不明時の再観測が成立条件になる |

## 3. 利用者に起きる変化

```text
変更前
────────────────
- 実行基盤ごとに異なるLogを読み、事実と推定を混ぜて比較する
        │
        │ 実行事実の再利用可能な記録が変える体験
        ▼
変更後
────────────────
- 実行主体が違っても同じ意味の事実を確認し、評価や改善候補と区別できる
```

実行事実の再利用可能な記録は、単に内部方式を成立させる要求ではない。「実行基盤ごとに異なるLogを読み、事実と推定を混ぜて比較する」状態から、「実行主体が違っても同じ意味の事実を確認し、評価や改善候補と区別できる」状態へ変わり、利用者が次の判断へ進めることまでを体験として扱う。

この変化で守るのは操作手順ではない。実行基盤運用者・改善担当が実行事実を出所と観測時点付きで比較することで、推測と事実を混ぜず改善候補を判断できるようになることを守る。

## 4. 利用者成果への統合

```text
REQ-000004
   │
   ├─ New  → UX-000006 実行事実を根拠付きで振り返る
   └─ New  → UX-000032 実行事実を安全に記録して結果を確かめる
```

| 利用者成果 | 処置 | 判断理由 | この要求が補う内容 |
|---|---|---|---|
| 実行事実を根拠付きで振り返る | `New → UX-000006` | 本要求が「実行主体が異なっても、観測事実・未観測・評価・改善候補を出所と時点付きで区別して振り返れる」という独立した利用者成果を最初に定義する。 | 観測事実・評価・改善候補を分けて読むことが、この要求固有の成立条件になる |
| 実行事実を安全に記録して結果を確かめる | `New → UX-000032` | 記録を発行する側は、後から読む側と異なる操作、Authority、Effect、失敗および回復判断を持つ。 | 記録済み・未記録・結果不明を分け、再送・並行書込み・途中失敗・許可外情報を安全に扱う |

`Same`／`New`は技術用語の近さや件数目標では決めない。「利用者は、どの状況で、何をするためにシステムと関わり、何ができるようになるか」が同じかを比較する。提供能力、必要情報、品質、妥当性確認または下流の実現要素は、独立UXへ分割せず対応する成果の成立条件として保持する。

## 5. 重要な体験

### この要求での利用の流れ

```text
実行結果を振り返る時
        ↓
観測事実・評価・改善候補を分けて読む
        │
        ├─ ★ 重要場面: 未観測値を含む実行事実の取得
        ├─ ⚠ 失敗:  未観測を0や正常へ畳む
        └─ ✓ 守る品質:  出所・時点・観測状態を保持する
        ↓
推測と事実を混ぜず改善候補を判断できる
```

```text
観測した実行事実を共有可能にする時
        ↓
実行・情報源・観測・許可範囲を確認
        ↓
一度だけ記録を依頼
        │
        ├─ ★ 重要場面: 保存要求後に結果確認が途切れる
        ├─ ⚠ 失敗:  未記録と推定して再発行する
        └─ ✓ 守る品質: 同じExecutionとAttemptで再観測する
        ↓
記録済み／未記録／結果不明に応じて次へ進む
```

### サービス提供の流れの処置

処置: `作成`

```text
【利用者・責任者】実行環境の導入・運用者
        │ 利用者行動: 事実と評価を区別して比較し改善要否を判断する
        ▼
【利用者接点】実行結果を振り返る時
        │
        ├─ 時間差: 実行観測の確定後に評価が行われ、未観測値は後から補完しない
        ├─ 完了時: 観測事実、観測時点、出所、未観測項目
        └─ 失敗時: 欠測した観測と評価不能範囲を評価担当へ返す
                     │
                     ▼
             【回復・判断する人】評価担当／AI
                     │ 返却された事実と判断不能範囲を確認
                     └─ 次の行動: 追加観測の要否を決め、事実と評価を分けて改善判断する

---------------- 可視境界 ----------------
                     │ 時間関係: 実行観測の確定後に評価が行われ、未観測値は後から補完しない
                     ▼
【提供側】実行基盤／ツール
        └─ 提供責務: 実行事実と未観測状態を出所・時点付きで残す
```

この図は、利用者行動、利用者が観測する接点、提供責務および失敗時の引き渡しを示す。内部構成要素の構造やプロトコルは下流工程で具体化する。

### 製品全体の整理への接続

- 利用の流れの統合先: [実行基盤を導入・更新・回復する](../../03_Experience_Map.md#実行基盤を導入更新回復する)
- サービス提供の流れの統合先: [共同のサービス提供の流れ](../../04_Service_Blueprint.md#1-共同のサービス提供の流れ)
- 横断成果物はこの個別分析から共通パターンを合成する。この要求での利用の流れ、責任境界または品質の代替にはしない。

### この要求での責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| 実行基盤／ツール | 実行事実と未観測状態を出所・時点付きで残す | 未観測を0または正常として記録しない |
| 実行環境の導入・運用者 | 事実と評価を区別して比較し改善要否を判断する | 評価を観測事実として扱わない |
| 評価担当／AI | 記録された事実から評価と改善候補を別に提示する | 推定を実測値へ昇格しない |
| 実行基盤・アプリの組込み担当者 | 許可された最小事実をCanonicalな識別情報とともに一度記録する | 結果不明を未記録と推定して再発行しない |
| 記録System | Effect前検査、不変公開、衝突再読取り、結果返却、資源回収 | 記録AuthorityをTask実行や評価採用へ流用しない |

### 補足する品質

- 結果または状態を最初に受け取る時: 記録時点と出典が分かる。（避ける失敗: 実行基盤ごとに異なるLogを読み、事実と推定を混ぜて比較する）
- 結果を判断または引き継ぐ時: 未観測値をゼロとして見せない。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 失敗・不足から次の行動を選ぶ時: 推定・評価・改善候補を実行事実と見分けられる。（避ける失敗: 成立不能の理由や回復先が分からないまま作業が止まる）


## 6. 下流への引き渡し

```text
この要求で確定した利用者成果
        │
        ├─→ IA: 必要な情報・関係・見つけ方
        ├─→ UI: 誤認させない表示・操作意図
        ├─→ SPEC: 振る舞い・失敗・体験品質の条件
        └─→ Verification: 仮説を破る反例と観測
```

### 妥当性確認と未確認事項

| 確認する仮説 | 観測方法 | 現在未確認の範囲 |
|---|---|---|
| 実行主体が違っても同じ意味の事実を確認し、評価や改善候補と区別できることで、実行基盤ごとに異なるLogを読み、事実と推定を混ぜて比較するという負担または誤認を減らせる。 | 代表シナリオの利用者確認、利用者体験の専門レビュー、および品質期待を破る反例による下流検証 | 実行環境の導入・運用者が「実行事実を出所と観測時点付きで比較する」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |

### 工程別の引き渡し

| 引き渡し先 | 具体化する義務 |
|---|---|
| 下流工程 | IAはExecution、Observation、Assessmentを分け、Verificationは複数実行基盤間で意味が保存されることを確認する。 |
| 下流工程 | IAは記録作成側のExecution、Source、Observation、Record Attempt、Publication Resultを分け、UI／SPECは記録Effectと結果不明時の再観測を読取り責務から分離する。 |

Discoveryへ戻す条件は、想定した利用者、問題または「実行事実を出所と観測時点付きで比較する」という必要性が誤っていると分かった場合である。下流は実現方式を具体化してよいが、「推測と事実を混ぜず改善候補を判断できる」という成果を無断で弱めない。
