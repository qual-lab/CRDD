# REQ-000001の利用者体験分析

成果物種別: UX分析

状態: UX再統合済み・独立再レビュー待ち
分析対象: [REQ-000001 決定論的なリポジトリ事前確認](../../../01_Discovery/Definitions/REQ-000001/requirement.md)

## 1. 要求の一次分析

```text
レビューへ渡してから形式不備が見つかり、意味確認と機械修正が混ざる
        ↓
解決策を先に固定せず、人の仕事として読み替える
        ↓
利用者に必要なこと
意味レビュー前に機械判定できる不備を落とす
```

CRDD成果物の作成者・確認者が「人が意味と判断へ集中できる」状態へ進めないことを問題として扱う。

| 観点 | 内容 |
|---|---|
| 解決する問題 | レビューへ渡してから形式不備が見つかり、意味確認と機械修正が混ざる |
| 利用者に必要なこと | 意味レビュー前に機械判定できる不備を落とす |
| 対象範囲 | CRDD成果物を作成・確認する人が、「レビューへ渡してから形式不備が見つかり、意味確認と機械修正が混ざる」状態から「意味レビューの前に直せる不備と、なお人が判断する事項を区別して把握できる」状態へ移る場面 |
| 対象外 | 具体的な画面、データ構造、実装方式および数値閾値の確定 |

## 2. 利用者・目標・成果

```text
CRDD成果物の作成者・確認者
        │
        │ 望んでいる
        ▼
意味レビュー前に機械判定できる不備を落とす
        │
        │ その結果として
        ▼
人が意味と判断へ集中できる
```

| 項目 | 内容 |
|---|---|
| 主な想定利用者 | [製品全体の利用者像](../../02_Personas.md)の「CRDD作成者・保守者」 |
| 利用場面 | 成果物をレビューへ渡す前 |
| 目的 | 意味レビュー前に機械判定できる不備を落とす |
| 得られる結果 | 人が意味と判断へ集中できる |
| この要求に固有の差 | 同じ対象を決定論的に確認することが、この要求固有の成立条件になる |
| 根拠・確信度 | 同じREQのDiscovery定義から導いた仮説。CRDD作成者・保守者が「意味レビュー前に機械判定できる不備を落とす」を判断する場面で、同じ対象を決定論的に確認することが実際に成果へ影響するかは未確認。 |

## 3. 利用者に起きる変化

```text
変更前
────────────────
- レビューへ渡してから形式不備が見つかり、意味確認と機械修正が混ざる
        │
        │ 決定論的なリポジトリ事前確認が変える体験
        ▼
変更後
────────────────
- 意味レビューの前に直せる不備と、なお人が判断する事項を区別して把握できる
```

決定論的なリポジトリ事前確認は、単に内部方式を成立させる要求ではない。「レビューへ渡してから形式不備が見つかり、意味確認と機械修正が混ざる」状態から、「意味レビューの前に直せる不備と、なお人が判断する事項を区別して把握できる」状態へ変わり、利用者が次の判断へ進めることまでを体験として扱う。

CRDD成果物の作成者・確認者が意味レビュー前に機械判定できる不備を落とすことで、人が意味と判断へ集中できるようになることを守る。

## 4. 利用者成果への統合

```text
REQ-000001
   │
   └─ New  → UX-000001 意味レビューへ集中できる事前確認
```

| 利用者成果 | 処置 | 判断理由 | この要求が補う内容 |
|---|---|---|---|
| 意味レビューへ集中できる事前確認 | `New → UX-000001` | 本要求が「同じ対象と条件なら機械的不備と修正箇所を先に理解し、意味レビューへ集中できる」という独立した利用者成果を最初に定義する。 | 同じ対象を決定論的に確認することが、この要求固有の成立条件になる |

`Same`／`New`は技術用語の近さや件数目標では決めない。「利用者は、どの状況で、何をするためにシステムと関わり、何ができるようになるか」が同じかを比較する。提供能力、必要情報、品質、妥当性確認または下流の実現要素は、独立UXへ分割せず対応する成果の成立条件として保持する。

## 5. 重要な体験

### この要求での利用の流れ

```text
成果物をレビューへ渡す前
        ↓
同じ対象を決定論的に確認する
        │
        ├─ ★ 重要場面: 機械指摘と意味判断を分ける
        ├─ ⚠ 失敗:  検査範囲や理由が分からない
        └─ ✓ 守る品質:  同じ入力へ同じ指摘と修正可能な場所を返す
        ↓
人が意味と判断へ集中できる
```

### サービス提供の流れの処置

処置: `作成`

```text
【利用者・責任者】CRDD作成者・保守者
        │ 利用者行動: 同じ対象と条件を固定し機械的不備を是正する
        ▼
【利用者接点】成果物をレビューへ渡す前
        │
        ├─ 時間差: 機械検査は同じ入力へ即時に返り、意味レビューは不備是正後に始まる
        ├─ 完了時: 検査対象、違反規則、対象箇所
        └─ 失敗時: 未判定の規則と修正箇所を意味レビュー担当へ返す
                     │
                     ▼
             【回復・判断する人】意味レビュー担当
                     │ 返却された事実と判断不能範囲を確認
                     └─ 次の行動: 機械的不備を直すか、意味判断としてレビューへ送る

---------------- 可視境界 ----------------
                     │ 時間関係: 機械検査は同じ入力へ即時に返り、意味レビューは不備是正後に始まる
                     ▼
【提供側】機械Checker
        └─ 提供責務: 決定論的に判定できる不備・場所・理由を返す
```

### 製品全体の整理への接続

- 利用の流れの統合先: [標準を変更・検証・公開する](../../03_Experience_Map.md#標準を変更検証公開する)
- サービス提供の流れの統合先: [共同のサービス提供の流れ](../../04_Service_Blueprint.md#1-共同のサービス提供の流れ)

### この要求での責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| CRDD作成者・保守者 | 同じ対象と条件を固定し機械的不備を是正する | Checker結果を意味レビューのPassへ読み替えない |
| 機械Checker | 決定論的に判定できる不備・場所・理由を返す | 意味品質や人間判断を代行しない |
| 意味レビュー担当 | 機械確認済み範囲と未確認範囲を理解して意味を判断する | 機械的不備の再探索へレビュー時間を費やさない |

### 補足する品質

- 結果または状態を最初に受け取る時: 同じ入力には同じ指摘が返る。（避ける失敗: レビューへ渡してから形式不備が見つかり、意味確認と機械修正が混ざる）
- 結果を判断または引き継ぐ時: 指摘は対象パスと修正可能な理由を示す。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 失敗・不足から次の行動を選ぶ時: Checker合格を意味品質の合格と誤認させない。（避ける失敗: 成立不能の理由や回復先が分からないまま作業が止まる）

## 6. 下流への引き渡し

本節では、IAへの直後工程の引き渡し、UX工程に伴走する品質分析、およびIA完了後にUI／SPECが保持する契約を区別する。UXの完了だけを根拠にIAを飛び越えてUIまたはSPECを開始しない。

| 接続先 | この要求から保持する意味 |
|---|---|
| IA（直後工程への正式な引き渡し） | 必要な情報、理解すべき差、関係、現行性および利用者成果 |
| Quality Analysis / UX（伴走） | 得られる結果、重要場面、失敗、品質期待および検証意図 |
| UI（後続Contract Relation） | IA完了後にUX定義とIA定義の双方から分析する認識・操作・判断の意図 |
| SPEC（後続Contract Relation） | IA完了後にUX定義とIA定義の双方から分析する成立条件・失敗・利用者成果 |

```text
この要求で確定した利用者成果
├─→ IA                         直後工程への正式な引き渡し
├─→ Quality Analysis / UX      UX工程に伴走する検証義務分析
└─→ UI / SPEC                  IA完了後に保持するContract Relation
```

### 妥当性確認と未確認事項

| 確認する仮説 | 観測方法 | 現在未確認の範囲 |
|---|---|---|
| 意味レビューの前に直せる不備と、なお人が判断する事項を区別して把握できることで、レビューへ渡してから形式不備が見つかり、意味確認と機械修正が混ざるという負担または誤認を減らせる。 | 代表シナリオの利用者確認、利用者体験の専門レビュー、および品質期待を破る反例による下流検証 | CRDD作成者・保守者が「意味レビュー前に機械判定できる不備を落とす」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |

人間への確認:
- 現在判定: 後続の実利用確認が必要。UX工程の構造整理を止める判断事項ではない。
- 確認事項: CRDD作成者・保守者が「意味レビュー前に機械判定できる不備を落とす」を行う際の判断基準、許容負担、利用環境および失敗後の選択
- 判断者: [製品全体の利用者像](../../02_Personas.md)の「CRDD作成者・保守者」を代表する利用者とQual-Lab。
- 未確認時の影響: 利用者成果と品質期待は仮説として保持し、負担、閾値、UIまたは実装方式を確定しない。

Discoveryへ戻す条件は、想定した利用者、問題または「意味レビュー前に機械判定できる不備を落とす」という必要性が誤っていると分かった場合である。IA以降は実現方式を具体化してよいが、利用者成果を無断で弱めない。
