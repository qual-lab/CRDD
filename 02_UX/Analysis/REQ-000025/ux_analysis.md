分析対象: [REQ-000025 導入責任者が所有する信頼方針](../../../01_Discovery/Definitions/REQ-000025/requirement.md)

## 1. 要求の一次分析

```text
Qual-Lab署名の有無だけで実行可否が固定され、派生版や組織Buildを安全に使えない
        ↓
解決策を先に固定せず、人の仕事として読み替える
        ↓
利用者に必要なこと
信頼する配布者と手元例外を自分で定める
```

導入責任者が「OSS派生版や組織Buildも方針に従って利用できる」状態へ進めないことを問題として扱う。

| 観点 | 内容 |
|---|---|
| 解決する問題 | Qual-Lab署名の有無だけで実行可否が固定され、派生版や組織Buildを安全に使えない |
| 利用者に必要なこと | 信頼する配布者と手元例外を自分で定める |
| 対象範囲 | 導入責任者、組織の実行基盤管理者が、「Qual-Lab署名の有無だけで実行可否が固定され、派生版や組織Buildを安全に使えない」状態から「公式版・組織版・手元版の信頼条件を所有し、更新・失効・移行を管理できる」状態へ移る場面 |
| 対象外 | 具体的な画面、データ構造、実装方式および数値閾値の確定 |

## 3. 利用者に起きる変化

```text
変更前
────────────────
- Qual-Lab署名の有無だけで実行可否が固定され、派生版や組織Buildを安全に使えない
        │
        │ 導入責任者が所有する信頼方針が変える体験
        ▼
変更後
────────────────
- 公式版・組織版・手元版の信頼条件を所有し、更新・失効・移行を管理できる
```

導入責任者が所有する信頼方針は、単に内部方式を成立させる要求ではない。「Qual-Lab署名の有無だけで実行可否が固定され、派生版や組織Buildを安全に使えない」状態から、「公式版・組織版・手元版の信頼条件を所有し、更新・失効・移行を管理できる」状態へ変わり、利用者が次の判断へ進めることまでを体験として扱う。

導入責任者が信頼する配布者と手元例外を自分で定めることで、OSS派生版や組織Buildも方針に従って利用できるようになることを守る。

### Same判断の比較

#### 利用環境の信頼方針で実行基盤を選ぶ

比較対象: `UX-000020`

比較元: `REQ-000018`でこのUXを最初に`New`とした固有記載。得られる結果は同分析のUX固有行、他の軸は同分析と初版Definitionの一致を確認して固定した。

| 比較軸 | 既存UX | 現在の要求 | 差と統合判断 |
|---|---|---|---|
| 担い手 | 実行環境の導入・運用者 | 実行環境の導入・運用者 | 既存UXと現在要求はいずれも「実行環境の導入・運用者」であり、利用者の違いはない |
| 利用のきっかけ | 実行基盤を導入または更新する時 | 実行基盤 Artifactを実行候補にする時 | 既存UXの「実行基盤を導入または更新する時」に対して現在要求は「実行基盤 Artifactを実行候補にする時」を具体化するが、同じ「利用環境の信頼方針で実行基盤を選ぶ」が必要になる開始条件の差であり、独立した成果境界ではない |
| 得られる結果 | 準拠、改ざん有無、配布者、公式表示および実行許可を区別し、自分の環境の方針で公式版・派生版・組織版を選べる | 導入責任者が自身の信頼方針でQual-Lab公式版・派生版・組織Buildの実行可否を選べる | 最初のNew分析で定義された固有成果に対し、現在要求はその成果を「導入責任者が自身の信頼方針でQual-Lab公式版・派生版・組織Buildの実行可否を選べる」の場面へ具体化する。利用者が達成する中心成果は同じである |
| 避ける失敗 | 一つの署名表示を全保証と誤認する | Qual-Lab署名だけを唯一の実行資格とし、派生版や組織Buildを方針に従って評価できない | 最初のNew分析で確認された失敗に対し、現在要求は「Qual-Lab署名だけを唯一の実行資格とし、派生版や組織Buildを方針に従って評価できない」へ具体化するが、中心成果を妨げる同じ失敗として扱える |

統合理由: 信頼方針は同じ実行基盤選択成果を実行時に成立させる決定条件である

`Same`／`New`は技術用語の近さや件数目標では決めない。「利用者は、どの状況で、何をするためにシステムと関わり、何ができるようになるか」が同じかを比較する。提供能力、必要情報、品質、妥当性確認または下流の実現要素は、独立UXへ分割せず対応する成果の成立条件として保持する。

## 5. 重要な体験

### この要求での利用の流れ

```text
実行基盤 Artifactを実行候補にする時
        ↓
Artifactの改ざん有無と利用者所有信頼方針を照合する
        │
        ├─ ★ 重要場面: 実行環境へ権限を与える直前
        ├─ ⚠ 失敗:  Qual-Lab署名だけを唯一の実行資格にする
        └─ ✓ 守る品質:  発行元への信頼と実行許可を利用環境が所有する
        ↓
OSS派生版や組織Buildも方針に従って利用できる
```

### サービス提供の流れの処置

処置: `作成`

```text
【利用者・責任者】導入責任者（実行環境の導入・運用者）
        │ 利用者行動: 信頼する配布者と手元例外を自分で定める
        ▼
【利用者接点】実行基盤 Artifactを実行候補にする時
        │
        ├─ 時間差: Artifact公開後、導入責任者が導入時に自身の方針を適用する
        ├─ 完了時: 配布者、改ざん有無、準拠結果、適用方針、実行可否
        └─ 失敗時: 方針不一致と不足する検証を導入責任者へ返す
                     │
                     ▼
             【回復・判断する人】導入責任者（信頼方針適用の判断役割へ切替）
                     │ 返却された事実と判断不能範囲を確認
                     └─ 次の行動: Artifactを採用、拒否または追加検証する

---------------- 可視境界 ----------------
                     │ 時間関係: Artifact公開後、導入責任者が導入時に自身の方針を適用する
                     ▼
【提供側】提供システム
        └─ 提供責務: 現在方針に従って実行候補を評価する
```

### この要求での責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| 実行基盤の配布者 | 自身が発行したArtifactと保証範囲を示す | 利用者環境の信頼判断を代行しない |
| 導入責任者 | 信頼する配布者と限定例外を所有する | 秘密情報や方針をリポジトリへ平文保存しない |
| 提供システム | 現在方針に従って実行候補を評価する | Qual-Lab署名だけを唯一の実行資格にしない |

### 補足する品質

- 結果または状態を最初に受け取る時: 既定拒否と手元開発例外を区別する。（避ける失敗: Qual-Lab署名の有無だけで実行可否が固定され、派生版や組織Buildを安全に使えない）
- 結果を判断または引き継ぐ時: 配布者変更を無言で受け入れない。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 失敗・不足から次の行動を選ぶ時: 管理者権限と内容の利用権限を混ぜない。（避ける失敗: 成立不能の理由や回復先が分からないまま作業が止まる）

## 6. 下流への引き渡し

本節では、IAへの直後工程の引き渡し、UX工程に伴走する品質分析、およびIA完了後にUI／SPECが保持する契約を区別する。UXの完了だけを根拠にIAを飛び越えてUIまたはSPECを開始しない。

| 接続先 | この要求から保持する意味 |
|---|---|
| IA（直後工程への正式な引き渡し） | 必要な情報、理解すべき差、関係、現行性および利用者成果 |
| Quality Analysis / UX（伴走） | 得られる結果、重要場面、失敗、品質期待および検証意図 |
| UI（後続Contract Relation） | IA完了後にUX定義とIA定義の双方から分析する認識・操作・判断の意図 |
| SPEC（後続Contract Relation） | IA完了後にUX定義とIA定義の双方から分析する成立条件・失敗・利用者成果 |

```text
この要求で確定した利用者成果
├─→ IA                         直後工程への正式な引き渡し
├─→ Quality Analysis / UX      UX工程に伴走する検証義務分析
└─→ UI / SPEC                  IA完了後に保持するContract Relation
```

### 妥当性確認と未確認事項

| 確認する仮説 | 観測方法 | 現在未確認の範囲 |
|---|---|---|
| 公式版・組織版・手元版の信頼条件を所有し、更新・失効・移行を管理できることで、Qual-Lab署名の有無だけで実行可否が固定され、派生版や組織Buildを安全に使えないという負担または誤認を減らせる。 | 代表シナリオの利用者確認、利用者体験の専門レビュー、および品質期待を破る反例による下流検証 | 実行環境の導入・運用者が「信頼する配布者と手元例外を自分で定める」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |

人間への確認:
- 現在判定: 後続の実利用確認が必要。UX工程の構造整理を止める判断事項ではない。
- 確認事項: 実行環境の導入・運用者が「信頼する配布者と手元例外を自分で定める」を行う際の判断基準、許容負担、利用環境および失敗後の選択
- 判断者: [製品全体の利用者像](../../02_Personas.md)の「実行環境の導入・運用者」を代表する利用者とQual-Lab。
- 未確認時の影響: 利用者成果と品質期待は仮説として保持し、負担、閾値、UIまたは実装方式を確定しない。

Discoveryへ戻す条件は、想定した利用者、問題または「信頼する配布者と手元例外を自分で定める」という必要性が誤っていると分かった場合である。IA以降は実現方式を具体化してよいが、利用者成果を無断で弱めない。
