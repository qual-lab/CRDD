# REQ-000036の利用者体験分析

## 1. 要求の一次分析

```text
未Commitでは処理できない、Git内部差でツール全体が壊れる等の制約を利用者が背負う
        ↓
解決策を先に固定せず、人の仕事として読み替える
        ↓
利用者に必要なこと
日常作業をCommit SHAや特定Git実装から切り離す
```

この要求で解くのは機能の有無だけではない。開発者／実行基盤保守者が「未Commit状態でも作業し将来履歴管理を差し替えられる」状態へ進めないことを問題として扱う。具体的な画面、データ構造、API、構成要素または数値閾値はここで確定しない。

| 観点 | 内容 |
|---|---|
| 解決する問題 | 未Commitでは処理できない、Git内部差でツール全体が壊れる等の制約を利用者が背負う |
| 利用者に必要なこと | 日常作業をCommit SHAや特定Git実装から切り離す |
| 対象範囲 | CRDD ツールを使う人、ツール保守者が、「未Commitでは処理できない、Git内部差でツール全体が壊れる等の制約を利用者が背負う」状態から「通常の読取り・編集は作業状態にかかわらず成立し、履歴機能が必要な時だけ履歴管理能力を使う」状態へ移る場面 |
| 対象外 | 具体的な画面、データ構造、実装方式および数値閾値の確定 |

## 3. 利用者に起きる変化

```text
変更前
────────────────
- 未Commitでは処理できない、Git内部差でツール全体が壊れる等の制約を利用者が背負う
        │
        │ 差し替え可能な履歴管理境界が変える体験
        ▼
変更後
────────────────
- 通常の読取り・編集は作業状態にかかわらず成立し、履歴機能が必要な時だけ履歴管理能力を使う
```

差し替え可能な履歴管理境界は、単に内部方式を成立させる要求ではない。「未Commitでは処理できない、Git内部差でツール全体が壊れる等の制約を利用者が背負う」状態から、「通常の読取り・編集は作業状態にかかわらず成立し、履歴機能が必要な時だけ履歴管理能力を使う」状態へ変わり、利用者が次の判断へ進めることまでを体験として扱う。

この変化で守るのは操作手順ではない。開発者／実行基盤保守者が日常作業をCommit SHAや特定Git実装から切り離すことで、未Commit状態でも作業し将来履歴管理を差し替えられるようになることを守る。

### Same判断の比較

#### リポジトリ単独で日常作業を続ける

比較対象: `UX-000010`

| 比較軸 | 既存UX | 現在の要求 | 差と統合判断 |
|---|---|---|---|
| 担い手 | 開発者 | 開発者 | 既存UXと現在要求はいずれも「開発者」であり、利用者の違いはない |
| 利用のきっかけ | リポジトリで作業を始める時 | リポジトリを読み書きし履歴機能を使う時 | 既存UXの「リポジトリで作業を始める時」に対して現在要求は「リポジトリを読み書きし履歴機能を使う時」を具体化するが、同じ「リポジトリ単独で日常作業を続ける」が必要になる開始条件の差であり、独立した成果境界ではない |
| 得られる結果 | 横断機能、Commit済み状態または特定の履歴実装を前提にせず、現在リポジトリで日常作業を開始・継続できる | 未Commit状態または履歴管理の接続部障害時も、履歴機能と無関係なリポジトリ作業を続けられる | 現在要求は「リポジトリ単独で日常作業を続ける」をこの要求の場面で成立させる得られる結果を具体化しており、要求全体の中心となる利用者成果や別のUX成果へ置き換えていない |
| 避ける失敗 | Commit済み状態または特定の履歴実装を前提にし、通常の読取り・編集を継続できない | 未Commitであることや履歴管理の接続部の故障だけで無関係な日常作業まで停止する | 現在要求は履歴管理境界を原因として特定するが、現在リポジトリで日常作業を続けられない失敗は同じである |

統合理由: 差し替え可能な履歴境界は同じ手元作業成果を守るアーキテクチャ上の条件である

`Same`／`New`は技術用語の近さや件数目標では決めない。「利用者は、どの状況で、何をするためにシステムと関わり、何ができるようになるか」が同じかを比較する。提供能力、必要情報、品質、妥当性確認または下流の実現要素は、独立UXへ分割せず対応する成果の成立条件として保持する。

## 5. 重要な体験

### この要求での利用の流れ

```text
リポジトリを読み書きし履歴機能を使う時
        ↓
通常操作と履歴管理 機能を分ける
        │
        ├─ ★ 重要場面: 履歴識別情報が本当に必要な場面
        ├─ ⚠ 失敗:  Commitされていないだけで通常作業が成立しない
        └─ ✓ 守る品質:  外部境界接続部越しに必要時だけ履歴を使う
        ↓
未Commit状態でも作業し将来履歴管理を差し替えられる
```

### サービス提供の流れの処置

処置: `非該当`

この要求が変えるのは、開発者の通常作業を履歴管理の状態や実装から切り離すことであり、利用者が観測する新しい引き渡しを追加することではない。通常作業と履歴機能の責任差は利用の流れと責任境界で保持でき、別主体への時間差のある責任移送や回復受け渡しは成果の成立条件にならないため非該当とする。履歴管理操作そのものを別Serviceへ委任し、その失敗・回復が利用者体験を左右する場合は再評価する。

### 製品全体の整理への接続

- 利用の流れの統合先: [リポジトリで日常作業を進める](../../03_Experience_Map.md#リポジトリで日常作業を進める)
- サービス提供の流れの統合先: [共同のサービス提供の流れ](../../04_Service_Blueprint.md#1-共同のサービス提供の流れ)
- 横断成果物はこの個別分析から共通パターンを合成する。この要求での利用の流れ、責任境界または品質の代替にはしない。

### この要求での責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| 利用者（開発者／実行基盤保守者） | 日常作業をCommit SHAや特定Git実装から切り離すために、提示された状態と根拠から次の行動を判断する | 不足情報や内部状態を推測で補うことを要求されない |
| 提供システム／AI | 通常操作と履歴管理 機能を分けるための状態、根拠および選択肢を示す | Commitされていないだけで通常作業が成立しない状態を成功・完了として表示しない |
| 運用・確認者 | 「外部境界接続部越しに必要時だけ履歴を使う」ことと、未Commit状態でも作業し将来履歴管理を差し替えられる状態へ到達できることを反証する | 未確認範囲や人間の判断を便宜的に上書きしない |

### 補足する品質

- 結果または状態を最初に受け取る時: Commit SHAを通常Objectの識別情報にしない。（避ける失敗: 未Commitでは処理できない、Git内部差でツール全体が壊れる等の制約を利用者が背負う）
- 結果を判断または引き継ぐ時: Git不在とリポジトリ不正を区別する。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 失敗・不足から次の行動を選ぶ時: 接続部故障時に無関係な操作まで止めない。（避ける失敗: 成立不能の理由や回復先が分からないまま作業が止まる）


Discoveryへ戻す条件は、想定した利用者、問題または「日常作業をCommit SHAや特定Git実装から切り離す」という必要性が誤っていると分かった場合である。下流は実現方式を具体化してよいが、「未Commit状態でも作業し将来履歴管理を差し替えられる」という成果を無断で弱めない。
