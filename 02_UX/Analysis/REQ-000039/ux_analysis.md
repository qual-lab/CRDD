# REQ-000039の利用者体験分析

成果物種別: UX分析

状態: UX再統合済み・独立再レビュー待ち
分析対象: [REQ-000039 TopicとMeetingの共通操作](../../../01_Discovery/Definitions/REQ-000039/requirement.md)

## 1. 要求の一次分析

```text
入口ごとにTopic／Meetingの扱い方が異なる
        ↓
同じ記録でも状態・関係・履歴・削除結果が揃わない
        ↓
利用者に必要なこと
論点と会議記録を、経緯を壊さず日常的に維持する
```

本要求は、登録・編集・削除等の機能一覧を作ること自体を目的にしない。Project運営者やMeeting参加者が、入口やファイル構造を意識せず、継続論点と時点記録を正しい性質のまま扱い続けられる体験を対象とする。

| 観点 | 内容 |
|---|---|
| 解決する問題 | 入口ごとにファイル探索、編集、関係処置および削除判断が分かれ、同じTopic／Meetingの意味と結果が揃わない |
| 利用者に必要なこと | 論点と会議記録を作成・発見・更新し、誤登録だけを安全に削除しながら経緯を保つ |
| 対象範囲 | Topic／Meetingの日常的な登録、一覧、取得、編集、終了・訂正および誤登録の物理削除 |
| 対象外 | 具体的な画面、MCP Tool名、保存形式、Transaction方式および実装技術の決定 |

## 2. 利用者・目標・成果

```text
Project運営者／Meeting参加者／Topic責任者
        │ 論点や会議記録を残し、後の仕事へつなぐ時
        ▼
論点と会議記録を経緯ごと維持する
        │
        ▼
入口を変えても同じ記録を扱い、誤登録だけを影響確認後に除ける
```

| 項目 | 内容 |
|---|---|
| 主な想定利用者 | [製品全体の利用者像](../../02_Personas.md)の「プロジェクト運営者／PM」 |
| 関係する利用者 | Meeting参加者、Topic責任者、Front AI |
| 利用場面 | 論点や会議記録を登録・確認・更新する時、誤登録を見つけた時 |
| 目的 | 論点と会議記録を、現在状態と当時記録の違いを保って維持する |
| 得られる結果 | 入口を変えても同じ記録と経緯へ到達し、正当な履歴を失わず誤登録だけを安全に除ける |
| この要求に固有の差 | Topicの継続状態とMeetingの時点記録、終了・訂正と物理削除を区別する |
| 根拠・確信度 | REQ-000039で人間確認済みの要求。具体的な入力負担、一覧粒度および削除確認の理解しやすさはDogfoodで確認する |

## 3. 利用者に起きる変化

```text
変更前
────────────────
- 入口ごとにファイル、書式、関係、削除方法を解釈する
- 誤登録を残すか、関係や履歴ごと危険に消す
        │
        ▼
変更後
────────────────
- どの入口でも同じTopic／Meetingを一通り扱う
- 正当な履歴は終了・訂正として残し、誤登録は影響を理解して除く
```

利用者は、記録方式の違いを調停する作業から離れ、論点や会議の意味、関係、次の判断へ集中できる。削除は便利な操作ではなく、失われる内容と関係への処置を理解したうえで誤登録だけを除く重要場面として扱う。

## 4. 利用者成果への統合

```text
REQ-000039
   ├─ New  → UX-000033 論点と会議記録を安全に維持する
   ├─ Same → UX-000012 入口を変えても同じ仕事を続ける
   └─ Same → UX-000014 Meeting内容を候補化し採否を判断する
```

| 利用者成果 | 処置 | 判断理由 | この要求が補う内容 |
|---|---|---|---|
| 論点と会議記録を安全に維持する | `New → UX-000033` | 作成・発見・更新・終了・訂正・誤登録削除を通じて経緯を保つことは、独立して利用・変更・確認できる成果である | TopicとMeetingの性質差、削除前の影響理解、正当な履歴の保持 |
| 入口を変えても同じ仕事を続ける | `Same → UX-000012` | 入口間で同じ正本・状態・結果へ到達する成果は既存UXと同じである | Topic／Meeting操作にも入口一貫性を適用する |
| Meeting内容を候補化し採否を判断する | `Same → UX-000014` | Meetingから候補を正本へつなぐ成果は既存UXと同じである | Meeting記録の維持と候補反映の境界を接続する |

### Same判断の比較

#### 入口を変えても同じ仕事を続ける

比較対象: `UX-000012`

| 比較軸 | 既存UX | 現在の要求 | 差と統合判断 |
|---|---|---|---|
| 担い手 | 開発者と各入口の利用者 | Project運営者、Meeting参加者、Front AI | 担い手は増えるが入口一貫性という成果は同じ |
| 利用のきっかけ | 接続方式やProject理解の入口を選ぶ時 | Topic／Meetingを異なる入口から扱う時 | 対象領域の追加であり独立成果ではない |
| 得られる結果 | 同じ入力・権限・状態・結果で仕事を続ける | 同じ記録・Lifecycle・削除結果へ到達する | UX-000012の具体的な成立条件として統合する |
| 避ける失敗 | 入口ごとの第二正本や結果差 | 入口ごとのTopic／Meeting状態や関係差 | 同じ失敗類型である |

統合理由: Topic／Meeting固有の維持成果はUX-000033へ分ける一方、入口が変わっても意味を変えない成果はUX-000012のまま保持できる。

#### Meeting内容を候補化し採否を判断する

比較対象: `UX-000014`

| 比較軸 | 既存UX | 現在の要求 | 差と統合判断 |
|---|---|---|---|
| 担い手 | Project運営者／Meeting参加者 | Project運営者／Meeting参加者／Topic責任者 | 同じ判断主体を含む |
| 利用のきっかけ | Meeting後に内容を整理する時 | Meeting記録から候補を後続へつなぐ時 | 同じ場面である |
| 得られる結果 | 会話と採用判断を混同せず正本へつなぐ | Meeting記録を維持し候補を比較後に反映する | 候補化の成果は同じ |
| 避ける失敗 | Meeting記録の自動正本化 | 現在状態による当時記録の上書き、自動反映 | 本要求固有の履歴保持を追加するが独立UXにはしない |

統合理由: 本要求はMeeting記録の維持契約を補うが、候補を人間判断後に正本へ戻す利用者成果は既存UX-000014と同じである。

## 5. 重要な体験

### この要求での利用の流れ

```text
論点または会議記録を扱う
        ↓
登録・検索・確認・更新を行う
        │
        ├─ 通常: 経緯と関係を保って継続・終了・訂正する
        └─ 誤登録: 失われる内容と関係への処置を確認する
                         │
                         ├─ ★ 重要場面: 物理削除を確定する直前
                         ├─ ⚠ 失敗: 正当な履歴または関連対象まで失う
                         └─ ✓ 守る品質: 対象・影響・復旧可能性を示し明示確認する
        ↓
正当な経緯を保ったまま次の判断・Actionへ進む
```

### サービス提供の流れの処置

処置: `作成`

```text
【利用者・責任者】Project運営者／Meeting参加者／Topic責任者
        │ 利用者行動: 記録を扱い、削除時は影響を確認する
        ▼
【利用者接点】Topic／Meetingの登録・一覧・取得・編集・削除
        │
        ├─ 時間差: Meetingの当時記録と後続のTopic更新を別時点の事実として保つ
        ├─ 完了時: 同じ正本、状態、関係および反映結果を返す
        └─ 失敗時: 競合、権限不足、部分成功、残る関係と回復先を返す
                     │
                     ▼
             【回復・判断する人】操作した利用者またはOwner
                     └─ 次の行動: 再取得、訂正、終了、削除取消または回復を選ぶ

---------------- 可視境界 ----------------
                     ▼
【提供側】共通Application Capability
        └─ 提供責務: Topic／Meeting固有の意味と削除境界を入口間で一致させる
```

### 製品全体の整理への接続

- 利用の流れの統合先: [プロジェクトの現在地を判断する](../../03_Experience_Map.md#プロジェクトの現在地を判断する)
- サービス提供の流れの統合先: [共同のサービス提供の流れ](../../04_Service_Blueprint.md#1-共同のサービス提供の流れ)

### この要求での責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| 利用者／Owner | 記録の意味、終了・訂正・削除の判断、削除前確認 | 読取り可能性を削除権限とみなさない |
| Front AI／入口 | 同じ能力を呼び出し、事実・候補・確認待ちを区別する | 影響確認や人間判断を代行しない |
| 共通Application Capability | Identity、状態、関係、競合、削除処置を一貫させる | 別成果物を連鎖削除せず、部分成功を完了にしない |

### 補足する品質

- Meetingの当時記録とTopicの現在状態を無言で同一化しない。
- 誤登録の削除と、正当な履歴の終了・撤回・訂正を区別する。
- 削除対象以外を連鎖削除せず、無効な関係を残さない。

## 6. 下流への引き渡し

| 接続先 | この要求から保持する意味 |
|---|---|
| IA（直後工程への正式な引き渡し） | Topic、Meeting、状態、時点、関係、候補、削除影響、復旧可能性およびOwner |
| Quality Analysis / UX（伴走） | 入口一貫性、履歴保持、削除前確認、非連鎖削除、関係整合および部分失敗 |
| UI（後続Contract Relation） | 発見・編集・終了・訂正・削除確認に必要な認識と判断 |
| SPEC（後続Contract Relation） | 操作結果、競合、Authority、候補、削除、部分成功および回復の成立条件 |

### 妥当性確認と未確認事項

| 確認する仮説 | 観測方法 | 現在未確認の範囲 |
|---|---|---|
| 共通操作により直接編集より負担を増やさず、関係と履歴の誤破壊を減らせる | Workbench／MCP Dogfood、削除反例、入口間結果比較 | 登録必須項目、一覧粒度、削除確認の理解しやすさ |

- 現在判定: 後続の実利用確認が必要。UX定義を進めることは妨げない。
- 確認事項: 登録必須項目、一覧粒度および削除確認が、直接編集より過剰な負担にならず誤操作を減らすか。
- 判断者: Project運営者、Meeting参加者およびQual-Lab。
- 未確認時の影響: 具体的な入力、画面、確認回数および実装方式を固定しない。
- Discoveryへ戻す条件: 共通操作が直接編集より負担を増やす、関係影響を安全に説明できない、または正当な履歴を誤削除する場合。
