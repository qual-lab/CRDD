# REQ-000026の利用者体験分析

成果物種別: UX分析

状態: UX再統合済み・独立再レビュー待ち
分析対象: [REQ-000026 判断・監査・是正の収束可能な閉包](../../../01_Discovery/Definitions/REQ-000026/requirement.md)

## 1. 要求の一次分析

```text
指摘が小出しになり、何が合意済みで何が未処置か分からない
        ↓
解決策を先に固定せず、人の仕事として読み替える
        ↓
利用者に必要なこと
監査合意から是正・反証までを一つの改訂版で閉じる
```

CRDD保守者・判断する人が「小出しの指摘と局所PatchのLoopを減らせる」状態へ進めないことを問題として扱う。

| 観点 | 内容 |
|---|---|
| 解決する問題 | 指摘が小出しになり、何が合意済みで何が未処置か分からない |
| 利用者に必要なこと | 監査合意から是正・反証までを一つの改訂版で閉じる |
| 対象範囲 | 変更担当者、確認者、決定権限者が、「指摘が小出しになり、何が合意済みで何が未処置か分からない」状態から「対象範囲、全指摘、是正対応、反証結果、今決める事項を一つの閉包として把握できる」状態へ移る場面 |
| 対象外 | 具体的な画面、データ構造、実装方式および数値閾値の確定 |

## 2. 利用者・目標・成果

```text
CRDD保守者・判断する人
        │
        │ 望んでいる
        ▼
監査合意から是正・反証までを一つの改訂版で閉じる
        │
        │ その結果として
        ▼
小出しの指摘と局所PatchのLoopを減らせる
```

| 項目 | 内容 |
|---|---|
| 主な想定利用者 | [製品全体の利用者像](../../02_Personas.md)の「CRDD作成者・保守者」 |
| 利用場面 | 複数指摘を是正する時 |
| 目的 | 監査合意から是正・反証までを一つの改訂版で閉じる |
| 得られる結果 | 小出しの指摘と局所PatchのLoopを減らせる |
| この要求に固有の差 | 全条件・適用先・禁止範囲・試験を対応付けることが、この要求固有の成立条件になる |
| 根拠・確信度 | 同じREQのDiscovery定義から導いた仮説。CRDD作成者・保守者が「監査合意から是正・反証までを一つの改訂版で閉じる」を判断する場面で、全条件・適用先・禁止範囲・試験を対応付けることが実際に成果へ影響するかは未確認。 |

## 3. 利用者に起きる変化

```text
変更前
────────────────
- 指摘が小出しになり、何が合意済みで何が未処置か分からない
        │
        │ 判断・監査・是正の収束可能な閉包が変える体験
        ▼
変更後
────────────────
- 対象範囲、全指摘、是正対応、反証結果、今決める事項を一つの閉包として把握できる
```

判断・監査・是正の収束可能な閉包は、単に内部方式を成立させる要求ではない。「指摘が小出しになり、何が合意済みで何が未処置か分からない」状態から、「対象範囲、全指摘、是正対応、反証結果、今決める事項を一つの閉包として把握できる」状態へ変わり、利用者が次の判断へ進めることまでを体験として扱う。

CRDD保守者・判断する人が監査合意から是正・反証までを一つの改訂版で閉じることで、小出しの指摘と局所PatchのLoopを減らせるようになることを守る。

## 4. 利用者成果への統合

```text
REQ-000026
   │
   └─ New  → UX-000023 監査・是正・判断を一つの改訂版で閉じる
```

| 利用者成果 | 処置 | 判断理由 | この要求が補う内容 |
|---|---|---|---|
| 監査・是正・判断を一つの改訂版で閉じる | `New → UX-000023` | 本要求が「合意した条件、適用先、反証、未処置および現在必要な人間判断を一つの改訂版で理解して収束できる」という独立した利用者成果を最初に定義する。 | 全条件・適用先・禁止範囲・試験を対応付けることが、この要求固有の成立条件になる |

`Same`／`New`は技術用語の近さや件数目標では決めない。「利用者は、どの状況で、何をするためにシステムと関わり、何ができるようになるか」が同じかを比較する。提供能力、必要情報、品質、妥当性確認または下流の実現要素は、独立UXへ分割せず対応する成果の成立条件として保持する。

## 5. 重要な体験

### この要求での利用の流れ

```text
複数指摘を是正する時
        ↓
全条件・適用先・禁止範囲・試験を対応付ける
        │
        ├─ ★ 重要場面: 再レビューへ固定候補を渡す直前
        ├─ ⚠ 失敗:  一部是正や監査回数を完成と誤認する
        └─ ✓ 守る品質:  合意事項と試験を全数対応させる
        ↓
小出しの指摘と局所PatchのLoopを減らせる
```

### サービス提供の流れの処置

処置: `作成`

```text
【利用者・責任者】CRDD作成者・保守者
        │ 利用者行動: 全指摘と編集・試験を対応付けて一つの候補へ反映する
        ▼
【利用者接点】複数指摘を是正する時
        │
        ├─ 時間差: 監査、統合方針、是正、再レビューは同じ固定改訂版を介して順に行う
        ├─ 完了時: 全指摘、原因、修正案、変更禁止範囲、反証、残る判断
        └─ 失敗時: 未解消指摘と現在必要な判断だけを人間の決定権限者へ返す
                     │
                     ▼
             【回復・判断する人】人間の決定権限者
                     │ 返却された事実と判断不能範囲を確認
                     └─ 次の行動: 追加是正、リスク判断、保留または工程移行を選ぶ

---------------- 可視境界 ----------------
                     │ 時間関係: 監査、統合方針、是正、再レビューは同じ固定改訂版を介して順に行う
                     ▼
【提供側】独立監査者
        └─ 提供責務: 原因・期待状態・変更禁止範囲・確認方法を一括提示し再評価する
```

### 製品全体の整理への接続

- 利用の流れの統合先: [標準を変更・検証・公開する](../../03_Experience_Map.md#標準を変更検証公開する)
- サービス提供の流れの統合先: [共同のサービス提供の流れ](../../04_Service_Blueprint.md#1-共同のサービス提供の流れ)

### この要求での責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| 独立監査者 | 原因・期待状態・変更禁止範囲・確認方法を一括提示し再評価する | 指摘を小出しにして別改訂版へ混在させない |
| CRDD作成者・保守者 | 全指摘と編集・試験を対応付けて一つの候補へ反映する | 一部是正や監査回数を完成と表示しない |
| 人間の決定権限者 | 是正後にも残る判断と影響だけを判断する | 解消済み事項を重ねて承認しない |

### 補足する品質

- 結果または状態を最初に受け取る時: 監査回数を進捗と見なさない。（避ける失敗: 指摘が小出しになり、何が合意済みで何が未処置か分からない）
- 結果を判断または引き継ぐ時: 合意事項と試験ケースの対応漏れを示す。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 失敗・不足から次の行動を選ぶ時: 解消済み事項を人間判断へ再提示しない。（避ける失敗: 成立不能の理由や回復先が分からないまま作業が止まる）

## 6. 下流への引き渡し

本節では、IAへの直後工程の引き渡し、UX工程に伴走する品質分析、およびIA完了後にUI／SPECが保持する契約を区別する。UXの完了だけを根拠にIAを飛び越えてUIまたはSPECを開始しない。

| 接続先 | この要求から保持する意味 |
|---|---|
| IA（直後工程への正式な引き渡し） | 必要な情報、理解すべき差、関係、現行性および利用者成果 |
| Quality Analysis / UX（伴走） | 得られる結果、重要場面、失敗、品質期待および検証意図 |
| UI（後続Contract Relation） | IA完了後にUX定義とIA定義の双方から分析する認識・操作・判断の意図 |
| SPEC（後続Contract Relation） | IA完了後にUX定義とIA定義の双方から分析する成立条件・失敗・利用者成果 |

```text
この要求で確定した利用者成果
├─→ IA                         直後工程への正式な引き渡し
├─→ Quality Analysis / UX      UX工程に伴走する検証義務分析
└─→ UI / SPEC                  IA完了後に保持するContract Relation
```

### 妥当性確認と未確認事項

| 確認する仮説 | 観測方法 | 現在未確認の範囲 |
|---|---|---|
| 対象範囲、全指摘、是正対応、反証結果、今決める事項を一つの閉包として把握できることで、指摘が小出しになり、何が合意済みで何が未処置か分からないという負担または誤認を減らせる。 | 代表シナリオの利用者確認、利用者体験の専門レビュー、および品質期待を破る反例による下流検証 | CRDD作成者・保守者が「監査合意から是正・反証までを一つの改訂版で閉じる」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |

人間への確認:
- 現在判定: 後続の実利用確認が必要。UX工程の構造整理を止める判断事項ではない。
- 確認事項: CRDD作成者・保守者が「監査合意から是正・反証までを一つの改訂版で閉じる」を行う際の判断基準、許容負担、利用環境および失敗後の選択
- 判断者: [製品全体の利用者像](../../02_Personas.md)の「CRDD作成者・保守者」を代表する利用者とQual-Lab。
- 未確認時の影響: 利用者成果と品質期待は仮説として保持し、負担、閾値、UIまたは実装方式を確定しない。

Discoveryへ戻す条件は、想定した利用者、問題または「監査合意から是正・反証までを一つの改訂版で閉じる」という必要性が誤っていると分かった場合である。IA以降は実現方式を具体化してよいが、利用者成果を無断で弱めない。
