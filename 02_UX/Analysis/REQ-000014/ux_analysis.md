# REQ-000014の利用者体験分析

成果物種別: UX分析

状態: UX再統合済み・独立再レビュー待ち
分析対象: [REQ-000014 リポジトリ ツール能力の明示登録一覧](../../../01_Discovery/Definitions/REQ-000014/requirement.md)

## 1. 要求の一次分析

```text
存在するファイルや名前から能力と実行許可を推測する
        ↓
解決策を先に固定せず、人の仕事として読み替える
        ↓
利用者に必要なこと
現在リポジトリで利用可能な機能を知る
```

この要求で解くのは機能の有無だけではない。リポジトリでツールを使う人が「名前やパスを推測せず適切な入口を選べる」状態へ進めないことを問題として扱う。具体的な画面、データ構造、API、構成要素または数値閾値はここで確定しない。

| 観点 | 内容 |
|---|---|
| 解決する問題 | 存在するファイルや名前から能力と実行許可を推測する |
| 利用者に必要なこと | 現在リポジトリで利用可能な機能を知る |
| 対象範囲 | リポジトリで作業する人、AI、外部ツールが、「存在するファイルや名前から能力と実行許可を推測する」状態から「登録済み能力、現在利用可能な能力、許可された操作を区別して選べる」状態へ移る場面 |
| 対象外 | 具体的な画面、データ構造、実装方式および数値閾値の確定 |

## 2. 利用者・目標・成果

```text
リポジトリでツールを使う人
        │
        │ 望んでいる
        ▼
現在リポジトリで利用可能な機能を知る
        │
        │ その結果として
        ▼
名前やパスを推測せず適切な入口を選べる
```

| 項目 | 内容 |
|---|---|
| 主な想定利用者 | [製品全体の利用者像](../../02_Personas.md)の「開発者」 |
| 利用場面 | ツールで処理を始める時 |
| 目的 | 現在リポジトリで利用可能な機能を知る |
| 得られる結果 | 名前やパスを推測せず適切な入口を選べる |
| この要求に固有の差 | リポジトリが公開する機能を確認することが、この要求固有の成立条件になる |
| 根拠・確信度 | 同じREQのDiscovery定義から導いた仮説。開発者が「現在リポジトリで利用可能な機能を知る」を判断する場面で、リポジトリが公開する機能を確認することが実際に成果へ影響するかは未確認。 |

## 3. 利用者に起きる変化

```text
変更前
────────────────
- 存在するファイルや名前から能力と実行許可を推測する
        │
        │ リポジトリ ツール能力の明示登録一覧が変える体験
        ▼
変更後
────────────────
- 登録済み能力、現在利用可能な能力、許可された操作を区別して選べる
```

リポジトリ ツール能力の明示登録一覧は、単に内部方式を成立させる要求ではない。「存在するファイルや名前から能力と実行許可を推測する」状態から、「登録済み能力、現在利用可能な能力、許可された操作を区別して選べる」状態へ変わり、利用者が次の判断へ進めることまでを体験として扱う。

この変化で守るのは操作手順ではない。リポジトリでツールを使う人が現在リポジトリで利用可能な機能を知ることで、名前やパスを推測せず適切な入口を選べるようになることを守る。

## 4. 利用者成果への統合

```text
REQ-000014
   │
   └─ New  → UX-000016 仕事に必要な標準ツールを迷わず選ぶ
```

| 利用者成果 | 処置 | 判断理由 | この要求が補う内容 |
|---|---|---|---|
| 仕事に必要な標準ツールを迷わず選ぶ | `New → UX-000016` | 本要求が「現在リポジトリと目的に対応する標準ツールを見つけ、利用可能性・外部作用（Effect）権限・開発実行・公式実行を区別して選べる」という独立した利用者成果を最初に定義する。 | リポジトリが公開する機能を確認することが、この要求固有の成立条件になる |

`Same`／`New`は技術用語の近さや件数目標では決めない。「利用者は、どの状況で、何をするためにシステムと関わり、何ができるようになるか」が同じかを比較する。提供能力、必要情報、品質、妥当性確認または下流の実現要素は、独立UXへ分割せず対応する成果の成立条件として保持する。

## 5. 重要な体験

### この要求での利用の流れ

```text
ツールで処理を始める時
        ↓
リポジトリが公開する機能を確認する
        │
        ├─ ★ 重要場面: 実行入口を選択する場面
        ├─ ⚠ 失敗:  存在するファイルを利用可能機能と誤認する
        └─ ✓ 守る品質:  能力・入口・制約・現在状態を明示する
        ↓
名前やパスを推測せず適切な入口を選べる
```

### サービス提供の流れの処置

処置: `作成`

```text
【利用者・責任者】開発者
        │ 利用者行動: 目的と必要外部作用（Effect）に合うツールを選ぶ
        ▼
【利用者接点】ツールで処理を始める時
        │
        ├─ 時間差: 機能登録後の利用可能性確認はツール起動時に行う
        ├─ 完了時: 登録機能、現在の利用可能性、必要外部作用（Effect）権限、実行Mode
        └─ 失敗時: 未登録または利用不能な機能と理由をリポジトリ／ツールの責任者へ返す
                     │
                     ▼
             【回復・判断する人】リポジトリ／ツールの責任者
                     │ 返却された事実と判断不能範囲を確認
                     └─ 次の行動: 別ツールを選ぶか、登録一覧更新を依頼する

---------------- 可視境界 ----------------
                     │ 時間関係: 機能登録後の利用可能性確認はツール起動時に行う
                     ▼
【提供側】提供システム
        └─ 提供責務: 登録済み機能と現在の利用可能性を返す
```

この図は、利用者行動、利用者が観測する接点、提供責務および失敗時の引き渡しを示す。内部構成要素の構造やプロトコルは下流工程で具体化する。

### 製品全体の整理への接続

- 利用の流れの統合先: [リポジトリで日常作業を進める](../../03_Experience_Map.md#リポジトリで日常作業を進める)
- サービス提供の流れの統合先: [共同のサービス提供の流れ](../../04_Service_Blueprint.md#1-共同のサービス提供の流れ)
- 横断成果物はこの個別分析から共通パターンを合成する。この要求での利用の流れ、責任境界または品質の代替にはしない。

### この要求での責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| リポジトリ／ツールの責任者 | リポジトリに対応する機能と正式入口を宣言する | 存在するFileだけを利用可能機能と表示しない |
| 開発者 | 目的と必要外部作用（Effect）に合うツールを選ぶ | ツールの表示を実行決定権限とみなさない |
| 提供システム | 登録済み機能と現在の利用可能性を返す | 未登録ツールを推測で起動しない |

### 補足する品質

- 結果または状態を最初に受け取る時: 未登録能力を推測表示しない。（避ける失敗: 存在するファイルや名前から能力と実行許可を推測する）
- 結果を判断または引き継ぐ時: 利用不能理由を登録欠落と権限拒否で分ける。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 失敗・不足から次の行動を選ぶ時: 一覧表示だけで外部変更の決定権限を与えない。（避ける失敗: 成立不能の理由や回復先が分からないまま作業が止まる）


## 6. 下流への引き渡し

```text
この要求で確定した利用者成果
        │
        ├─→ IA: 必要な情報・関係・見つけ方
        ├─→ UI: 誤認させない表示・操作意図
        ├─→ SPEC: 振る舞い・失敗・体験品質の条件
        └─→ Verification: 仮説を破る反例と観測
```

### 妥当性確認と未確認事項

| 確認する仮説 | 観測方法 | 現在未確認の範囲 |
|---|---|---|
| 登録済み能力、現在利用可能な能力、許可された操作を区別して選べることで、存在するファイルや名前から能力と実行許可を推測するという負担または誤認を減らせる。 | 代表シナリオの利用者確認、利用者体験の専門レビュー、および品質期待を破る反例による下流検証 | 開発者が「現在リポジトリで利用可能な機能を知る」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |

### 工程別の引き渡し

| 引き渡し先 | 具体化する義務 |
|---|---|
| 下流工程 | IAは機能、利用可否、決定権限を分け、UI／MCPとVerificationは同じ登録一覧投影を利用する。 |

Discoveryへ戻す条件は、想定した利用者、問題または「現在リポジトリで利用可能な機能を知る」という必要性が誤っていると分かった場合である。下流は実現方式を具体化してよいが、「名前やパスを推測せず適切な入口を選べる」という成果を無断で弱めない。
