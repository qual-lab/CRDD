# REQ-000006の利用者体験分析

成果物種別: UX分析

状態: UX再統合済み・独立再レビュー待ち
分析対象: [REQ-000006 ローカルMCP 通信方式間の意味統一](../../../01_Discovery/Definitions/REQ-000006/requirement.md)

## 1. 要求の一次分析

```text
通信方式ごとに結果、状態、エラー、許可の意味が変わる
        ↓
解決策を先に固定せず、人の仕事として読み替える
        ↓
利用者に必要なこと
stdioとHTTPで同じ意味の操作を行う
```

MCP（AIやツールが機能を呼び出す共通接続方式）／ツール利用者・統合者が「通信方式を変えても結果を読み替えなくてよい」状態へ進めないことを問題として扱う。

| 観点 | 内容 |
|---|---|
| 解決する問題 | 通信方式ごとに結果、状態、エラー、許可の意味が変わる |
| 利用者に必要なこと | stdioとHTTPで同じ意味の操作を行う |
| 対象範囲 | ローカルMCPを標準入出力（stdio）またはこのPC内の通信（localhost HTTP）で使う人・ツールが、「通信方式ごとに結果、状態、エラー、許可の意味が変わる」状態から「利用する接続方法を変えても同じ依頼が同じ意味の結果と停止理由を返す」状態へ移る場面 |
| 対象外 | 具体的な画面、データ構造、実装方式および数値閾値の確定 |

## 3. 利用者に起きる変化

```text
変更前
────────────────
- 通信方式ごとに結果、状態、エラー、許可の意味が変わる
        │
        │ ローカルMCP 通信方式間の意味統一が変える体験
        ▼
変更後
────────────────
- 利用する接続方法を変えても同じ依頼が同じ意味の結果と停止理由を返す
```

ローカルMCP 通信方式間の意味統一は、単に内部方式を成立させる要求ではない。「通信方式ごとに結果、状態、エラー、許可の意味が変わる」状態から、「利用する接続方法を変えても同じ依頼が同じ意味の結果と停止理由を返す」状態へ変わり、利用者が次の判断へ進めることまでを体験として扱う。

MCP／ツール利用者・統合者がstdioとHTTPで同じ意味の操作を行うことで、通信方式を変えても結果を読み替えなくてよいようになることを守る。

## 4. 利用者成果への統合

```text
REQ-000006
   │
   └─ New  → UX-000012 入口を変えても同じ仕事を続ける
```

| 利用者成果 | 処置 | 判断理由 | この要求が補う内容 |
|---|---|---|---|
| 入口を変えても同じ仕事を続ける | `New → UX-000012` | 本要求が「stdio MCPとlocalhost HTTPのどちらでも、同じ入力・権限・状態・結果で仕事を続けられる」という独立した利用者成果を最初に定義する。 | 同じ公開契約へ要求を渡すことが、この要求固有の成立条件になる |

### Same判断の比較

`Same`／`New`は技術用語の近さや件数目標では決めない。「利用者は、どの状況で、何をするためにシステムと関わり、何ができるようになるか」が同じかを比較する。提供能力、必要情報、品質、妥当性確認または下流の実現要素は、独立UXへ分割せず対応する成果の成立条件として保持する。

## 5. 重要な体験

### この要求での利用の流れ

```text
利用する接続方式を選ぶ時
        ↓
同じ公開契約へ要求を渡す
        │
        ├─ ★ 重要場面: 通信方式境界を越えた意味同値
        ├─ ⚠ 失敗:  接続方式ごとに状態や結果が変わる
        └─ ✓ 守る品質:  入力・認可・結果の意味を共通化する
        ↓
通信方式を変えても結果を読み替えなくてよい
```

### サービス提供の流れの処置

処置: `作成`

```text
【利用者・責任者】開発者
        │ 利用者行動: 利用環境に合う接続方式を選び、同じ意図の仕事を依頼する
        ▼
【利用者接点】利用する接続方式を選ぶ時
        │
        ├─ 時間差: 各通信方式の要求と応答は一回の利用内で比較し、長期の回復状態は持たない
        ├─ 完了時: 同じ意味の結果
        └─ 失敗時: 失敗した通信方式と外部作用（Effect）の発行有無を運用・確認者へ返す
                     │
                     ▼
             【回復・判断する人】運用・確認者
                     │ 返却された事実と判断不能範囲を確認
                     └─ 次の行動: 正常な入口を選ぶか、不一致を修正対象として止める

---------------- 可視境界 ----------------
                     │ 時間関係: 各通信方式の要求と応答は一回の利用内で比較し、長期の回復状態は持たない
                     ▼
【提供側】提供システム
        └─ 提供責務: 接続方式にかかわらず同じ意味の入力・権限・結果を保つ
```

### 製品全体の整理への接続

- 利用の流れの統合先: [リポジトリで日常作業を進める](../../03_Experience_Map.md#リポジトリで日常作業を進める)
- サービス提供の流れの統合先: [共同のサービス提供の流れ](../../04_Service_Blueprint.md#1-共同のサービス提供の流れ)

### この要求での責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| 開発者 | 利用環境に合う接続方式を選び、同じ意図の仕事を依頼する | 接続方式ごとの内部契約を覚えることを要求されない |
| 提供システム | 接続方式にかかわらず同じ意味の入力・権限・結果を保つ | 通信方式固有の都合を業務結果へ混入しない |
| 運用・確認者 | 両経路の成功・失敗・結果搬送が意味同値であることを確認する | 一方の単発成功から他方を推定しない |

### 補足する品質

- 結果または状態を最初に受け取る時: 通信方式差を業務状態として見せない。（避ける失敗: 通信方式ごとに結果、状態、エラー、許可の意味が変わる）
- 結果を判断または引き継ぐ時: 同じ入力・権限なら同じ意味になる。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 失敗・不足から次の行動を選ぶ時: どの通信方式で失敗したかと、外部作用が発行されたかを区別し、入口変更や再処置を判断できる。（避ける失敗: 成立不能の理由や回復先が分からないまま作業が止まる）

## 6. 下流への引き渡し

本節では、IAへの直後工程の引き渡し、UX工程に伴走する品質分析、およびIA完了後にUI／SPECが保持する契約を区別する。UXの完了だけを根拠にIAを飛び越えてUIまたはSPECを開始しない。

| 接続先 | この要求から保持する意味 |
|---|---|
| IA（直後工程への正式な引き渡し） | 必要な情報、理解すべき差、関係、現行性および利用者成果 |
| Quality Analysis / UX（伴走） | 得られる結果、重要場面、失敗、品質期待および検証意図 |
| UI（後続Contract Relation） | IA完了後にUX定義とIA定義の双方から分析する認識・操作・判断の意図 |
| SPEC（後続Contract Relation） | IA完了後にUX定義とIA定義の双方から分析する成立条件・失敗・利用者成果 |

```text
この要求で確定した利用者成果
├─→ IA                         直後工程への正式な引き渡し
├─→ Quality Analysis / UX      UX工程に伴走する検証義務分析
└─→ UI / SPEC                  IA完了後に保持するContract Relation
```

### 妥当性確認と未確認事項

| 確認する仮説 | 観測方法 | 現在未確認の範囲 |
|---|---|---|
| 利用する接続方法を変えても同じ依頼が同じ意味の結果と停止理由を返すことで、通信方式ごとに結果、状態、エラー、許可の意味が変わるという負担または誤認を減らせる。 | 代表シナリオの利用者確認、利用者体験の専門レビュー、および品質期待を破る反例による下流検証 | 開発者が「stdioとHTTPで同じ意味の操作を行う」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |

人間への確認:
- 現在判定: 後続の実利用確認が必要。UX工程の構造整理を止める判断事項ではない。
- 確認事項: 開発者が「stdioとHTTPで同じ意味の操作を行う」を行う際の判断基準、許容負担、利用環境および失敗後の選択
- 判断者: [製品全体の利用者像](../../02_Personas.md)の「開発者」を代表する利用者とQual-Lab。
- 未確認時の影響: 利用者成果と品質期待は仮説として保持し、負担、閾値、UIまたは実装方式を確定しない。

Discoveryへ戻す条件は、想定した利用者、問題または「stdioとHTTPで同じ意味の操作を行う」という必要性が誤っていると分かった場合である。IA以降は実現方式を具体化してよいが、利用者成果を無断で弱めない。
