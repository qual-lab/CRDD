# REQ-000006の利用者体験分析

成果物種別: UX分析

状態: UX再統合済み・独立再レビュー待ち
分析対象: [REQ-000006 ローカルMCP 通信方式間の意味統一](../../../01_Discovery/Definitions/REQ-000006/requirement.md)

## 1. 要求の一次分析

```text
通信方式ごとに結果、状態、エラー、許可の意味が変わる
        ↓
解決策を先に固定せず、人の仕事として読み替える
        ↓
利用者に必要なこと
stdioとHTTPで同じ意味の操作を行う
```

この要求で解くのは機能の有無だけではない。MCP／ツール利用者・統合者が「通信方式を変えても結果を読み替えなくてよい」状態へ進めないことを問題として扱う。具体的な画面、データ構造、API、構成要素または数値閾値はここで確定しない。

| 観点 | 内容 |
|---|---|
| 解決する問題 | 通信方式ごとに結果、状態、エラー、許可の意味が変わる |
| 利用者に必要なこと | stdioとHTTPで同じ意味の操作を行う |
| 対象範囲 | ローカルMCPをstdioまたはHTTPで使う人・ツールが、「通信方式ごとに結果、状態、エラー、許可の意味が変わる」状態から「利用する接続方法を変えても同じ依頼が同じ意味の結果と停止理由を返す」状態へ移る場面 |
| 対象外 | 具体的な画面、データ構造、実装方式および数値閾値の確定 |

## 3. 利用者に起きる変化

```text
変更前
────────────────
- 通信方式ごとに結果、状態、エラー、許可の意味が変わる
        │
        │ ローカルMCP 通信方式間の意味統一が変える体験
        ▼
変更後
────────────────
- 利用する接続方法を変えても同じ依頼が同じ意味の結果と停止理由を返す
```

ローカルMCP 通信方式間の意味統一は、単に内部方式を成立させる要求ではない。「通信方式ごとに結果、状態、エラー、許可の意味が変わる」状態から、「利用する接続方法を変えても同じ依頼が同じ意味の結果と停止理由を返す」状態へ変わり、利用者が次の判断へ進めることまでを体験として扱う。

この変化で守るのは操作手順ではない。MCP／ツール利用者・統合者がstdioとHTTPで同じ意味の操作を行うことで、通信方式を変えても結果を読み替えなくてよいようになることを守る。

## 5. 重要な体験

### この要求での利用の流れ

```text
利用する接続方式を選ぶ時
        ↓
同じ公開契約へ要求を渡す
        │
        ├─ ★ 重要場面: 通信方式境界を越えた意味同値
        ├─ ⚠ 失敗:  接続方式ごとに状態や結果が変わる
        └─ ✓ 守る品質:  入力・認可・結果の意味を共通化する
        ↓
通信方式を変えても結果を読み替えなくてよい
```

### サービス提供の流れの処置

処置: `作成`

```text
【利用者・責任者】開発者
        │ 利用者行動: 利用環境に合う接続方式を選び、同じ意図の仕事を依頼する
        ▼
【利用者接点】利用する接続方式を選ぶ時
        │
        ├─ 時間差: 各通信方式の要求と応答は一回の利用内で比較し、長期の回復状態は持たない
        ├─ 完了時: 接続・処理・結果搬送の各成否と同じ意味の結果
        └─ 失敗時: 意味差が生じた通信方式と影響する操作だけを運用・確認者へ返す
                     │
                     ▼
             【回復・判断する人】運用・確認者
                     │ 返却された事実と判断不能範囲を確認
                     └─ 次の行動: 正常な入口を選ぶか、不一致を修正対象として止める

---------------- 可視境界 ----------------
                     │ 時間関係: 各通信方式の要求と応答は一回の利用内で比較し、長期の回復状態は持たない
                     ▼
【提供側】提供システム
        └─ 提供責務: 接続方式にかかわらず同じ意味の入力・権限・結果を保つ
```

この図は、利用者行動、利用者が観測する接点、提供責務および失敗時の引き渡しを示す。内部構成要素の構造やプロトコルは下流工程で具体化する。

### 製品全体の整理への接続

- 利用の流れの統合先: [リポジトリで日常作業を進める](../../03_Experience_Map.md#リポジトリで日常作業を進める)
- サービス提供の流れの統合先: [共同のサービス提供の流れ](../../04_Service_Blueprint.md#1-共同のサービス提供の流れ)
- 横断成果物はこの個別分析から共通パターンを合成する。この要求での利用の流れ、責任境界または品質の代替にはしない。

### この要求での責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| 開発者 | 利用環境に合う接続方式を選び、同じ意図の仕事を依頼する | 接続方式ごとの内部契約を覚えることを要求されない |
| 提供システム | 接続方式にかかわらず同じ意味の入力・権限・結果を保つ | 通信方式固有の都合を業務結果へ混入しない |
| 運用・確認者 | 両経路の成功・失敗・結果搬送が意味同値であることを確認する | 一方の単発成功から他方を推定しない |

### 補足する品質

- 結果または状態を最初に受け取る時: 通信方式差を業務状態として見せない。（避ける失敗: 通信方式ごとに結果、状態、エラー、許可の意味が変わる）
- 結果を判断または引き継ぐ時: 同じ入力・権限なら同じ意味になる。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 失敗・不足から次の行動を選ぶ時: 接続失敗と実行基盤失敗を区別できる。（避ける失敗: 成立不能の理由や回復先が分からないまま作業が止まる）


## 6. 下流への引き渡し

```text
この要求で確定した利用者成果
        │
        ├─→ IA: 必要な情報・関係・見つけ方
        ├─→ UI: 誤認させない表示・操作意図
        ├─→ SPEC: 振る舞い・失敗・体験品質の条件
        └─→ Verification: 仮説を破る反例と観測
```

### 妥当性確認と未確認事項

| 確認する仮説 | 観測方法 | 現在未確認の範囲 |
|---|---|---|
| 利用する接続方法を変えても同じ依頼が同じ意味の結果と停止理由を返すことで、通信方式ごとに結果、状態、エラー、許可の意味が変わるという負担または誤認を減らせる。 | 代表シナリオの利用者確認、利用者体験の専門レビュー、および品質期待を破る反例による下流検証 | 開発者が「stdioとHTTPで同じ意味の操作を行う」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |

### 工程別の引き渡し

| 引き渡し先 | 具体化する義務 |
|---|---|
| 下流工程 | SPECは公開結果と通信方式 errorを分け、ArchitectureとVerificationは両入口の意味同値性を保証する。 |

Discoveryへ戻す条件は、想定した利用者、問題または「stdioとHTTPで同じ意味の操作を行う」という必要性が誤っていると分かった場合である。下流は実現方式を具体化してよいが、「通信方式を変えても結果を読み替えなくてよい」という成果を無断で弱めない。
