## 1. REQの一次分析

```text
過去の議事録を探して論点の経緯を再構成する／会議内容の転記か自動反映の二択になる
        ↓
解決策を先に固定せず、人の仕事として読み替える
        ↓
UXとして必要
会議の内容を候補として整理し正本へつなぐ
```

この要求で解くのは機能の有無だけではない。Project Operator／Meeting参加者が「会話と採用判断を混同せず仕事を継続できる」状態へ進めないことを問題として扱う。具体的な画面、データ構造、API、Componentまたは数値閾値はここで確定しない。

| 観点 | 内容 |
|---|---|
| 解決する問題 | 過去の議事録を探して論点の経緯を再構成する／会議内容の転記か自動反映の二択になる |
| UX Need | 会議の内容を候補として整理し正本へつなぐ |
| 対象範囲 | 会議参加者、Topic・判断の所有者が、「過去の議事録を探して論点の経緯を再構成する」状態から「Topicから関連Meeting、調査、Decision、CHGを時間順に辿る」状態へ移る場面 |
| 対象外 | 具体的な画面、データ構造、実装方式および数値閾値の確定 |

## 3. 利用者に起きる変化

```text
Before
────────────────
- 過去の議事録を探して論点の経緯を再構成する
- 会議内容の転記か自動反映の二択になる
        │
        │ Meetingから候補を経た正本更新が変える体験
        ▼
After
────────────────
- Topicから関連Meeting、調査、Decision、CHGを時間順に辿る
- 更新候補を比較し、所有正本の決定権限へ戻す
```

会議で生まれた決定や論点が議事録に閉じると、後の仕事へ届かない。反対に、AIが会話から正本を直接更新すると、候補と採用判断が混ざる。

この変化で守るのは操作手順ではない。Project Operator／Meeting参加者が会議の内容を候補として整理し正本へつなぐことで、会話と採用判断を混同せず仕事を継続できるようになることを守る。


Same／Newは技術用語の近さや件数目標では決めない。「利用者は、どの状況で、何をするためにSystemと関わり、何ができるようになるか」が同じかを比較する。Capability、Information、Quality、Validationまたは下流の実現要素は、独立UXへ分割せず対応する成果の成立条件として保持する。

## 5. 重要な体験

### このREQのJourney

```text
Meeting後に決定・Topic・Actionを整理する時
        ↓
候補化し所有正本の判断へ渡す
        │
        ├─ ★ Critical: 候補を採用または却下する場面
        ├─ ⚠ Failure:  会議記録が自動的に正本へ昇格する
        └─ ✓ Quality:  候補・判断・反映結果を区別する
        ↓
会話と採用判断を混同せず仕事を継続できる
```

### Service Blueprintの処置

処置: `作成`

```text
[U: 会議参加者（Project Operator／PMを含む）]
        │ 利用者行動: 会議の内容を候補として整理し正本へつなぐ
        ▼
[T: Meeting後に決定・Topic・Actionを整理する時]
        │
        ├─ 時間差: Meeting終了、候補生成、人間の採否、正本更新は別の判断時点を持つ
        ├─ 完了時: 発言の出所、候補種別、既存Topicとの関係、採否待ち
        └─ 失敗時: 根拠不足または競合する候補をProject Operator／正本Ownerへ返す
                     │
                     ▼
             [R: Project Operator／正本Owner（候補採否の判断役割）]
                     │ 返却された事実と判断不能範囲を確認
                     └─ 次の行動: 候補を採用、修正、統合、分割または却下する

---------------- 可視境界 ----------------
                     │ 時間関係: Meeting終了、候補生成、人間の採否、正本更新は別の判断時点を持つ
                     ▼
[S: 提供System／AI]
        └─ 提供責務: 内容を候補化し既存Contextとの関係を示す
```

この図は、利用者行動、利用者が観測する接点、提供責務および失敗時の引き渡しを示す。内部Componentの構造やProtocolは下流工程で具体化する。

### 横断Synthesisへの接続

- 横断成果物はこの個別分析から共通パターンを合成する。このREQのJourney、責任境界または品質の代替にはしない。

### このREQでの責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| 会議参加者 | 事実・意見・候補を区別できる材料として残す | 発言だけで採用済み決定を確定しない |
| 提供System／AI | 内容を候補化し既存Contextとの関係を示す | 候補を正本へ自動昇格しない |
| Project Operator／正本Owner | 候補の採否と反映先を決める | 所有しない正本の判断を代行しない |

### 補足する品質

- 結果または状態を最初に受け取る時: 生Transcript、観察、仮説、決定候補、採用済み判断を区別する。（避ける失敗: 過去の議事録を探して論点の経緯を再構成する）
- 結果を判断または引き継ぐ時: 既存TopicとのSame／Newを判断できる根拠を示す。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 結果を判断または引き継ぐ時: 候補の採用先、変更内容、決定権限者が分かる。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 失敗・不足から次の行動を選ぶ時: 利用不能なMeeting内容を推測して経緯を埋めない。（避ける失敗: 成立不能の理由や回復先が分からないまま作業が止まる）


## 6. 下流への引き渡し

```text
このREQで確定した利用者成果
        │
        ├─→ IA: 必要な情報・関係・見つけ方
        ├─→ UI: 誤認させない表示・操作意図
        ├─→ SPEC: 振る舞い・失敗・体験品質の条件
        └─→ Verification: 仮説を破る反例と観測
```

### 妥当性確認と未確認事項

| 確認する仮説 | 観測方法 | 現在未確認の範囲 |
|---|---|---|
| Topicから関連Meeting、調査、Decision、CHGを時間順に辿る／更新候補を比較し、所有正本の決定権限へ戻すことで、過去の議事録を探して論点の経緯を再構成するという負担または誤認を減らせる。 | 代表シナリオの利用者確認、UX専門Review、および品質期待を破る反例による下流検証 | Project Operator／PMが「会議の内容を候補として整理し正本へつなぐ」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |

### 工程別の引き渡し

| 引き渡し先 | 具体化する義務 |
|---|---|
| 下流工程 | IAはMeeting、Topic、Candidate、DecisionおよびSource Relationを分ける。Communicationは外部表現への昇格を別判断とし、UI／SPECは候補比較と採用を別操作にする。 |

Discoveryへ戻す条件は、想定した利用者、問題または「会議の内容を候補として整理し正本へつなぐ」という必要性が誤っていると分かった場合である。下流は実現方式を具体化してよいが、「会話と採用判断を混同せず仕事を継続できる」という成果を無断で弱めない。
