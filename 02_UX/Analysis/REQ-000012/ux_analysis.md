# REQ-000012の利用者体験分析

成果物種別: UX分析

状態: UX再統合済み・独立再レビュー待ち
分析対象: [REQ-000012 Meetingから候補を経た正本更新](../../../01_Discovery/Definitions/REQ-000012/requirement.md)

## 1. 要求の一次分析

```text
過去の議事録を探して論点の経緯を再構成する／会議内容の転記か自動反映の二択になる
        ↓
解決策を先に固定せず、人の仕事として読み替える
        ↓
利用者に必要なこと
会議の内容を候補として整理し正本へつなぐ
```

この要求で解くのは機能の有無だけではない。プロジェクト運営者／Meeting参加者が「会話と採用判断を混同せず仕事を継続できる」状態へ進めないことを問題として扱う。具体的な画面、データ構造、API、構成要素または数値閾値はここで確定しない。

| 観点 | 内容 |
|---|---|
| 解決する問題 | 過去の議事録を探して論点の経緯を再構成する／会議内容の転記か自動反映の二択になる |
| 利用者に必要なこと | 会議の内容を候補として整理し正本へつなぐ |
| 対象範囲 | 会議参加者、Topic・判断の所有者が、「過去の議事録を探して論点の経緯を再構成する」状態から「Topicから関連Meeting、調査、判断、CHGを時間順に辿る」状態へ移る場面 |
| 対象外 | 具体的な画面、データ構造、実装方式および数値閾値の確定 |

## 3. 利用者に起きる変化

```text
変更前
────────────────
- 過去の議事録を探して論点の経緯を再構成する
- 会議内容の転記か自動反映の二択になる
        │
        │ Meetingから候補を経た正本更新が変える体験
        ▼
変更後
────────────────
- Topicから関連Meeting、調査、判断、CHGを時間順に辿る
- 更新候補を比較し、所有正本の決定権限へ戻す
```

会議で生まれた決定や論点が議事録に閉じると、後の仕事へ届かない。反対に、AIが会話から正本を直接更新すると、候補と採用判断が混ざる。

この変化で守るのは操作手順ではない。プロジェクト運営者／Meeting参加者が会議の内容を候補として整理し正本へつなぐことで、会話と採用判断を混同せず仕事を継続できるようになることを守る。

## 4. 利用者成果への統合

```text
REQ-000012
   │
   └─ New  → UX-000014 Meeting内容を候補化し採否を判断する
```

| 利用者成果 | 処置 | 判断理由 | この要求が補う内容 |
|---|---|---|---|
| Meeting内容を候補化し採否を判断する | `New → UX-000014` | 本要求が「会話・観察・仮説・候補・決定を区別し、既存Topicとの関係を根拠付きで判断して所有正本へ戻せる」という独立した利用者成果を最初に定義する。 | 候補化し所有正本の判断へ渡すことが、この要求固有の成立条件になる |

`Same`／`New`は技術用語の近さや件数目標では決めない。「利用者は、どの状況で、何をするためにシステムと関わり、何ができるようになるか」が同じかを比較する。提供能力、必要情報、品質、妥当性確認または下流の実現要素は、独立UXへ分割せず対応する成果の成立条件として保持する。

## 5. 重要な体験

### この要求での利用の流れ

```text
Meeting後に決定・Topic・Actionを整理する時
        ↓
候補化し所有正本の判断へ渡す
        │
        ├─ ★ 重要場面: 候補を採用または却下する場面
        ├─ ⚠ 失敗:  会議記録が自動的に正本へ昇格する
        └─ ✓ 守る品質:  候補・判断・反映結果を区別する
        ↓
会話と採用判断を混同せず仕事を継続できる
```

### サービス提供の流れの処置

処置: `作成`

```text
【利用者・責任者】会議参加者（プロジェクト運営者／PMを含む）
        │ 利用者行動: 会議の内容を候補として整理し正本へつなぐ
        ▼
【利用者接点】Meeting後に決定・Topic・Actionを整理する時
        │
        ├─ 時間差: Meeting終了、候補生成、人間の採否、正本更新は別の判断時点を持つ
        ├─ 完了時: 発言の出所、候補種別、既存Topicとの関係、採否待ち
        └─ 失敗時: 根拠不足または競合する候補をプロジェクト運営者／正本責任者へ返す
                     │
                     ▼
             【回復・判断する人】プロジェクト運営者／正本責任者（候補採否の判断役割）
                     │ 返却された事実と判断不能範囲を確認
                     └─ 次の行動: 候補を採用、修正、統合、分割または却下する

---------------- 可視境界 ----------------
                     │ 時間関係: Meeting終了、候補生成、人間の採否、正本更新は別の判断時点を持つ
                     ▼
【提供側】提供システム／AI
        └─ 提供責務: 内容を候補化し既存情報との関係を示す
```

この図は、利用者行動、利用者が観測する接点、提供責務および失敗時の引き渡しを示す。内部構成要素の構造やプロトコルは下流工程で具体化する。

### 製品全体の整理への接続

- 利用の流れの統合先: [プロジェクトの現在地を判断する](../../03_Experience_Map.md#プロジェクトの現在地を判断する)
- サービス提供の流れの統合先: [共同のサービス提供の流れ](../../04_Service_Blueprint.md#1-共同のサービス提供の流れ)
- 横断成果物はこの個別分析から共通パターンを合成する。この要求での利用の流れ、責任境界または品質の代替にはしない。

### この要求での責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| 会議参加者 | 事実・意見・候補を区別できる材料として残す | 発言だけで採用済み決定を確定しない |
| 提供システム／AI | 内容を候補化し既存情報との関係を示す | 候補を正本へ自動昇格しない |
| プロジェクト運営者／正本責任者 | 候補の採否と反映先を決める | 所有しない正本の判断を代行しない |

### 補足する品質

- 結果または状態を最初に受け取る時: 生Transcript、観察、仮説、決定候補、採用済み判断を区別する。（避ける失敗: 過去の議事録を探して論点の経緯を再構成する）
- 結果を判断または引き継ぐ時: 既存TopicとのSame／Newを判断できる根拠を示す。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 結果を判断または引き継ぐ時: 候補の採用先、変更内容、決定権限者が分かる。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 失敗・不足から次の行動を選ぶ時: 利用不能なMeeting内容を推測して経緯を埋めない。（避ける失敗: 成立不能の理由や回復先が分からないまま作業が止まる）


## 6. 下流への引き渡し

```text
この要求で確定した利用者成果
        │
        ├─→ IA: 必要な情報・関係・見つけ方
        ├─→ UI: 誤認させない表示・操作意図
        ├─→ SPEC: 振る舞い・失敗・体験品質の条件
        └─→ Verification: 仮説を破る反例と観測
```

### 妥当性確認と未確認事項

| 確認する仮説 | 観測方法 | 現在未確認の範囲 |
|---|---|---|
| Topicから関連Meeting、調査、判断、CHGを時間順に辿る／更新候補を比較し、所有正本の決定権限へ戻すことで、過去の議事録を探して論点の経緯を再構成するという負担または誤認を減らせる。 | 代表シナリオの利用者確認、利用者体験の専門レビュー、および品質期待を破る反例による下流検証 | プロジェクト運営者／PMが「会議の内容を候補として整理し正本へつなぐ」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |

### 工程別の引き渡し

| 引き渡し先 | 具体化する義務 |
|---|---|
| 下流工程 | IAはMeeting、Topic、候補、判断および情報源同士の関係を分ける。Communicationは外部表現への昇格を別判断とし、UI／SPECは候補比較と採用を別操作にする。 |

Discoveryへ戻す条件は、想定した利用者、問題または「会議の内容を候補として整理し正本へつなぐ」という必要性が誤っていると分かった場合である。下流は実現方式を具体化してよいが、「会話と採用判断を混同せず仕事を継続できる」という成果を無断で弱めない。
