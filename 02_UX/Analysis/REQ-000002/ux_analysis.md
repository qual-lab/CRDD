## 1. 要求の一次分析

```text
誰が何を実行し、停止後に何が残ったかを個別Logから推測する
        ↓
解決策を先に固定せず、人の仕事として読み替える
        ↓
利用者に必要なこと
複数AIへ任せる範囲と権限を理解する
```

この要求で解くのは機能の有無だけではない。仕事を委ねる人が「停止や失敗後も主導権を失わず結果を受け取れる」状態へ進めないことを問題として扱う。具体的な画面、データ構造、API、構成要素または数値閾値はここで確定しない。

| 観点 | 内容 |
|---|---|
| 解決する問題 | 誰が何を実行し、停止後に何が残ったかを個別Logから推測する |
| 利用者に必要なこと | 複数AIへ任せる範囲と権限を理解する |
| 対象範囲 | AIへ仕事を委ねる人、結果を確認する人が、「誰が何を実行し、停止後に何が残ったかを個別Logから推測する」状態から「委ねた範囲、現在の実行者、確認者、結果、取消・清掃・回復を一つの仕事として追える」状態へ移る場面 |
| 対象外 | 具体的な画面、データ構造、実装方式および数値閾値の確定 |

## 3. 利用者に起きる変化

```text
変更前
────────────────
- 誰が何を実行し、停止後に何が残ったかを個別Logから推測する
        │
        │ 複数AI実行の範囲・権限・回復が変える体験
        ▼
変更後
────────────────
- 委ねた範囲、現在の実行者、確認者、結果、取消・清掃・回復を一つの仕事として追える
```

複数AI実行の範囲・権限・回復は、単に内部方式を成立させる要求ではない。「誰が何を実行し、停止後に何が残ったかを個別Logから推測する」状態から、「委ねた範囲、現在の実行者、確認者、結果、取消・清掃・回復を一つの仕事として追える」状態へ変わり、利用者が次の判断へ進めることまでを体験として扱う。

この変化で守るのは操作手順ではない。仕事を委ねる人が複数AIへ任せる範囲と権限を理解することで、停止や失敗後も主導権を失わず結果を受け取れるようになることを守る。

## 4. 利用者成果への統合

```text

   ├─ New  → UX-000003 委任中の状態と判断要否を理解する
   └─ New  → UX-000004 失敗後の再試行・回復を選ぶ
```

| 利用者成果 | 処置 | 判断理由 | この要求が補う内容 |
|---|---|---|---|
| 委任範囲と権限を理解して任せる | `New → UX-000002` | 本要求が「実行前に誰へ何をどこまで任せるかを理解し、暗黙の範囲拡張なく仕事を委ねられる」という独立した利用者成果を最初に定義する。 | 範囲・権限・実行者を確認して依頼することが、この要求固有の成立条件になる |
| 委任中の状態と判断要否を理解する | `New → UX-000003` | 本要求が「内部ログを読まず、実行中・待機・停止と現在必要な判断を理解できる」という独立した利用者成果を最初に定義する。 | 範囲・権限・実行者を確認して依頼することが、この要求固有の成立条件になる |
| 失敗後の再試行・回復を選ぶ | `New → UX-000004` | 本要求が「失敗後に状態確認、再試行、回復および清掃を取り違えず、二重外部への変更を避けて次の行動を選べる」という独立した利用者成果を最初に定義する。 | 範囲・権限・実行者を確認して依頼することが、この要求固有の成立条件になる |

`Same`／`New`は技術用語の近さや件数目標では決めない。「利用者は、どの状況で、何をするためにシステムと関わり、何ができるようになるか」が同じかを比較する。提供能力、必要情報、品質、妥当性確認または下流の実現要素は、独立UXへ分割せず対応する成果の成立条件として保持する。

## 5. 重要な体験

### この要求での利用の流れ

```text
複数AIへ仕事を委ねる時
        ↓
範囲・権限・実行者を確認して依頼する
        │
        ├─ ★ 重要場面: 外部への変更の前の委任境界
        ├─ ⚠ 失敗:  暗黙の範囲拡張や回復不能
        └─ ✓ 守る品質:  委任状態・停止理由・回復先を行動可能に示す
        ↓
停止や失敗後も主導権を失わず結果を受け取れる
```

### サービス提供の流れの処置

処置: `作成`

```text
【利用者・責任者】プロジェクト運営者／PM
        │ 利用者行動: 目的・範囲・停止条件を提示し、返された状態から次の行動を判断する
        ▼
【利用者接点】複数AIへ仕事を委ねる時
        │
        ├─ 時間差: 複数AIの実行・取消・回復は非同期で、判断待ちを挟み得る
        ├─ 完了時: 実行主体、委任範囲、現在状態、判断要否
        └─ 失敗時: 停止したタスク、発生済み外部への変更、残る回復義務を人間の決定権限者へ返す
                     │
                     ▼
             【回復・判断する人】人間の決定権限者
                     │ 返却された事実と判断不能範囲を確認
                     └─ 次の行動: 状態確認、取消、再試行、回復または追加判断を選ぶ

---------------- 可視境界 ----------------
                     │ 時間関係: 複数AIの実行・取消・回復は非同期で、判断待ちを挟み得る
                     ▼
【提供側】提供システム／AI
        └─ 提供責務: 許可範囲内で実行し、状態・結果・回復選択を同じ依頼へ返す
```

この図は、利用者行動、利用者が観測する接点、提供責務および失敗時の引き渡しを示す。内部構成要素の構造やプロトコルは下流工程で具体化する。

### 製品全体の整理への接続

- 利用の流れの統合先: [対話と構築を往復する](../../03_Experience_Map.md#対話と構築を往復する)
- サービス提供の流れの統合先: [共同のサービス提供の流れ](../../04_Service_Blueprint.md#1-共同のサービス提供の流れ)
- 横断成果物はこの個別分析から共通パターンを合成する。この要求での利用の流れ、責任境界または品質の代替にはしない。

### この要求での責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| プロジェクト運営者／PM | 目的・範囲・停止条件を提示し、返された状態から次の行動を判断する | 内部決定権限や未提示外部への変更を推測しない |
| 人間の決定権限者 | 委任可能な範囲と追加判断条件を確定する | 未承認の範囲を黙示的に許可しない |
| 提供システム／AI | 許可範囲内で実行し、状態・結果・回復選択を同じ依頼へ返す | 停止・失敗を成功として表示しない |

### 補足する品質

- 結果または状態を最初に受け取る時: 委任前に範囲と権限が理解できる。（避ける失敗: 誰が何を実行し、停止後に何が残ったかを個別Logから推測する）
- 結果を判断または引き継ぐ時: 実行中と停止中を区別できる。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 失敗・不足から次の行動を選ぶ時: 失敗時に再実行と回復を取り違えない。（避ける失敗: 成立不能の理由や回復先が分からないまま作業が止まる）

```text

        │
        ├─→ IA: 必要な情報・関係・見つけ方

        ├─→ SPEC: 振る舞い・失敗・体験品質の条件

```
