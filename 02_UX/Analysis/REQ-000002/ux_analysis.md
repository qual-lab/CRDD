# REQ-000002の利用者体験分析

成果物種別: UX分析

状態: UX再統合済み・独立再レビュー待ち
分析対象: [REQ-000002 複数AI実行の範囲・権限・回復](../../../01_Discovery/Definitions/REQ-000002/requirement.md)

## 1. 要求の一次分析

```text
誰が何を実行し、停止後に何が残ったかを個別Logから推測する
        ↓
解決策を先に固定せず、人の仕事として読み替える
        ↓
利用者に必要なこと
複数AIへ任せる範囲と権限を理解する
```

仕事を委ねる人が「停止や失敗後も主導権を失わず結果を受け取れる」状態へ進めないことを問題として扱う。

| 観点 | 内容 |
|---|---|
| 解決する問題 | 誰が何を実行し、停止後に何が残ったかを個別Logから推測する |
| 利用者に必要なこと | 複数AIへ任せる範囲と権限を理解する |
| 対象範囲 | AIへ仕事を委ねる人、結果を確認する人が、「誰が何を実行し、停止後に何が残ったかを個別Logから推測する」状態から「委ねた範囲、現在の実行者、確認者、結果、取消・清掃・回復を一つの仕事として追える」状態へ移る場面 |
| 対象外 | 具体的な画面、データ構造、実装方式および数値閾値の確定 |

## 3. 利用者に起きる変化

```text
変更前
────────────────
- 誰が何を実行し、停止後に何が残ったかを個別Logから推測する
        │
        │ 複数AI実行の範囲・権限・回復が変える体験
        ▼
変更後
────────────────
- 委ねた範囲、現在の実行者、確認者、結果、取消・清掃・回復を一つの仕事として追える
```

複数AI実行の範囲・権限・回復は、単に内部方式を成立させる要求ではない。「誰が何を実行し、停止後に何が残ったかを個別Logから推測する」状態から、「委ねた範囲、現在の実行者、確認者、結果、取消・清掃・回復を一つの仕事として追える」状態へ変わり、利用者が次の判断へ進めることまでを体験として扱う。

仕事を委ねる人が複数AIへ任せる範囲と権限を理解することで、停止や失敗後も主導権を失わず結果を受け取れるようになることを守る。

## 4. 利用者成果への統合

```text
REQ-000002
   │
   ├─ New  → UX-000002 委任範囲と権限を理解して任せる
   ├─ New  → UX-000003 委任中の状態と判断要否を理解する
   └─ New  → UX-000004 失敗後の再試行・回復を選ぶ
```

| 利用者成果 | 処置 | 判断理由 | この要求が補う内容 |
|---|---|---|---|
| 委任範囲と権限を理解して任せる | `New → UX-000002` | 本要求が「実行前に誰へ何をどこまで任せるかを理解し、暗黙の範囲拡張なく仕事を委ねられる」という独立した利用者成果を最初に定義する。 | 範囲・権限・実行者を確認して依頼することが、この要求固有の成立条件になる |
| 委任中の状態と判断要否を理解する | `New → UX-000003` | 本要求が「内部ログを読まず、実行中・待機・停止と現在必要な判断を理解できる」という独立した利用者成果を最初に定義する。 | 範囲・権限・実行者を確認して依頼することが、この要求固有の成立条件になる |
| 失敗後の再試行・回復を選ぶ | `New → UX-000004` | 本要求が「失敗後に状態確認、再試行、回復および清掃を取り違えず、外部作用（Effect）の二重実行を避けて次の行動を選べる」という独立した利用者成果を最初に定義する。 | 範囲・権限・実行者を確認して依頼することが、この要求固有の成立条件になる |

`Same`／`New`は技術用語の近さや件数目標では決めない。「利用者は、どの状況で、何をするためにシステムと関わり、何ができるようになるか」が同じかを比較する。提供能力、必要情報、品質、妥当性確認または下流の実現要素は、独立UXへ分割せず対応する成果の成立条件として保持する。

## 5. 重要な体験

### この要求での利用の流れ

```text
複数AIへ仕事を委ねる時
        ↓
範囲・権限・実行者を確認して依頼する
        │
        ├─ ★ 重要場面: 外部作用（Effect）の前の委任境界
        ├─ ⚠ 失敗:  暗黙の範囲拡張や回復不能
        └─ ✓ 守る品質:  委任状態・停止理由・回復先を行動可能に示す
        ↓
停止や失敗後も主導権を失わず結果を受け取れる
```

### サービス提供の流れの処置

処置: `作成`

```text
【利用者・責任者】プロジェクト運営者／PM
        │ 利用者行動: 目的・範囲・停止条件を提示し、返された状態から次の行動を判断する
        ▼
【利用者接点】複数AIへ仕事を委ねる時
        │
        ├─ 時間差: 複数AIの実行・取消・回復は非同期で、判断待ちを挟み得る
        ├─ 完了時: 実行主体、委任範囲、現在状態、判断要否
        └─ 失敗時: 停止したタスク、発生済み外部作用（Effect）、残る回復義務を人間の決定権限者へ返す
                     │
                     ▼
             【回復・判断する人】人間の決定権限者
                     │ 返却された事実と判断不能範囲を確認
                     └─ 次の行動: 状態確認、取消、再試行、回復または追加判断を選ぶ

---------------- 可視境界 ----------------
                     │ 時間関係: 複数AIの実行・取消・回復は非同期で、判断待ちを挟み得る
                     ▼
【提供側】提供システム／AI
        └─ 提供責務: 許可範囲内で実行し、状態・結果・回復選択を同じ依頼へ返す
```

- 利用の流れの統合先: [対話と構築を往復する](../../03_Experience_Map.md#対話と構築を往復する)
- サービス提供の流れの統合先: [共同のサービス提供の流れ](../../04_Service_Blueprint.md#1-共同のサービス提供の流れ)

### この要求での責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| プロジェクト運営者／PM | 目的・範囲・停止条件を提示し、返された状態から次の行動を判断する | 内部決定権限や未提示外部作用（Effect）を推測しない |
| 人間の決定権限者 | 委任可能な範囲と追加判断条件を確定する | 未承認の範囲を黙示的に許可しない |
| 提供システム／AI | 許可範囲内で実行し、状態・結果・回復選択を同じ依頼へ返す | 停止・失敗を成功として表示しない |

### 補足する品質

- 結果または状態を最初に受け取る時: 委任前に範囲と権限が理解できる。（避ける失敗: 誰が何を実行し、停止後に何が残ったかを個別Logから推測する）
- 結果を判断または引き継ぐ時: 実行中と停止中を区別できる。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 失敗・不足から次の行動を選ぶ時: 失敗時に再実行と回復を取り違えない。（避ける失敗: 成立不能の理由や回復先が分からないまま作業が止まる）

## 6. 下流への引き渡し

本節では、IAへの直後工程の引き渡し、UX工程に伴走する品質分析、およびIA完了後にUI／SPECが保持する契約を区別する。UXの完了だけを根拠にIAを飛び越えてUIまたはSPECを開始しない。

| 接続先 | この要求から保持する意味 |
|---|---|
| IA（直後工程への正式な引き渡し） | 必要な情報、理解すべき差、関係、現行性および利用者成果 |
| Quality Analysis / UX（伴走） | 得られる結果、重要場面、失敗、品質期待および検証意図 |
| UI（後続Contract Relation） | IA完了後にUX定義とIA定義の双方から分析する認識・操作・判断の意図 |
| SPEC（後続Contract Relation） | IA完了後にUX定義とIA定義の双方から分析する成立条件・失敗・利用者成果 |

```text
この要求で確定した利用者成果
├─→ IA                         直後工程への正式な引き渡し
├─→ Quality Analysis / UX      UX工程に伴走する検証義務分析
└─→ UI / SPEC                  IA完了後に保持するContract Relation
```

### 妥当性確認と未確認事項

| 確認する仮説 | 観測方法 | 現在未確認の範囲 |
|---|---|---|
| 委ねた範囲、現在の実行者、確認者、結果、取消・清掃・回復を一つの仕事として追えることで、誰が何を実行し、停止後に何が残ったかを個別Logから推測するという負担または誤認を減らせる。 | 代表シナリオの利用者確認、利用者体験の専門レビュー、および品質期待を破る反例による下流検証 | プロジェクト運営者／PMが「複数AIへ任せる範囲と権限を理解する」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |

人間への確認:
- 現在判定: 後続の実利用確認が必要。UX工程の構造整理を止める判断事項ではない。
- 確認事項: プロジェクト運営者／PMが「複数AIへ任せる範囲と権限を理解する」を行う際の判断基準、許容負担、利用環境および失敗後の選択
- 判断者: [製品全体の利用者像](../../02_Personas.md)の「プロジェクト運営者／PM」を代表する利用者とQual-Lab。
- 未確認時の影響: 利用者成果と品質期待は仮説として保持し、負担、閾値、UIまたは実装方式を確定しない。

Discoveryへ戻す条件は、想定した利用者、問題または「複数AIへ任せる範囲と権限を理解する」という必要性が誤っていると分かった場合である。IA以降は実現方式を具体化してよいが、利用者成果を無断で弱めない。
