## 1. 要求の一次分析

```text
責務移動後に珍しい入口だけ旧契約へ残り、リリース時に初めて壊れる
        ↓
解決策を先に固定せず、人の仕事として読み替える
        ↓
利用者に必要なこと
責務移動後の全利用側を閉じる
```

契約を変更する保守者・確認者が「稀な署名・リリース・回復経路の取り残しを防ぐ」状態へ進めないことを問題として扱う。

| 観点 | 内容 |
|---|---|
| 解決する問題 | 責務移動後に珍しい入口だけ旧契約へ残り、リリース時に初めて壊れる |
| 利用者に必要なこと | 責務移動後の全利用側を閉じる |
| 対象範囲 | CRDDを更新する人、リリースを受け取る人が、「責務移動後に珍しい入口だけ旧契約へ残り、リリース時に初めて壊れる」状態から「変更対象の全利用経路が移行済みか確認でき、未移行範囲を残したまま完成表示されない」状態へ移る場面 |
| 対象外 | 具体的な画面、データ構造、実装方式および数値閾値の確定 |

## 3. 利用者に起きる変化

```text
変更前
────────────────
- 責務移動後に珍しい入口だけ旧契約へ残り、リリース時に初めて壊れる
        │
        │ 契約移行時の利用側閉包が変える体験
        ▼
変更後
────────────────
- 変更対象の全利用経路が移行済みか確認でき、未移行範囲を残したまま完成表示されない
```

契約移行時の利用側閉包は、単に内部方式を成立させる要求ではない。「責務移動後に珍しい入口だけ旧契約へ残り、リリース時に初めて壊れる」状態から、「変更対象の全利用経路が移行済みか確認でき、未移行範囲を残したまま完成表示されない」状態へ変わり、利用者が次の判断へ進めることまでを体験として扱う。

契約を変更する保守者・確認者が責務移動後の全利用側を閉じることで、稀な署名・リリース・回復経路の取り残しを防ぐようになることを守る。

### Same判断の比較

#### 内部変更後も成立済み能力を安全に使う

比較対象: `UX-000007`

比較元: `REQ-000005`の正式なDiscovery定義と、このUXを最初に`New`とした同要求分析。担い手、利用のきっかけ、避ける失敗は正式入力と要求固有分析から、得られる結果はUX固有の`New`行から直接導いた。後から統合したUX定義は比較元にしない。

| 比較軸 | 既存UX | 現在の要求 | 差と統合判断 |
|---|---|---|---|
| 担い手 | 実行環境の導入・運用者 | CRDD作成者・保守者 | 現在要求は契約移行を担う保守者へ役割を具体化するが、いずれも責務変更後の成立済み能力を安全に使える状態へ戻す当事者である |
| 利用のきっかけ | 実行環境の構成要素を置換する時 | 正式な契約や責任者を変更する時 | 現在要求は構成要素の置換を正式契約の移行へ具体化しており、独立した成果境界ではない |
| 得られる結果 | 責務・契約・接続部の変更後も、維持・変更・廃止された能力を理解し、取り残しのない結果を安全に利用・公開できる | 契約移行後に署名・リリース・回復を含む全利用側が接続された能力を安全に利用・公開できる | 最初のNew分析で定義された固有成果に対し、現在要求はその成果を「契約移行後に署名・リリース・回復を含む全利用側が接続された能力を安全に利用・公開できる」の場面へ具体化する。利用者が達成する中心成果は同じである |
| 避ける失敗 | 一つの構成要素変更が無関係な入口や操作を壊し、原因を利用者が切り分ける | 主経路だけを更新し署名・リリース・回復等の利用側が旧契約に残る | REQ-000005の問題に対し、現在要求は未移行の副次利用側が無関係な入口や操作を壊す発生形を具体化する。中心成果を妨げる同じ失敗である |

統合理由: 利用側閉包は既存成果を保証するArchitecture／Validation条件であり、独立した利用者目的ではない

`Same`／`New`は技術用語の近さや件数目標では決めない。「利用者は、どの状況で、何をするためにシステムと関わり、何ができるようになるか」が同じかを比較する。提供能力、必要情報、品質、妥当性確認または下流の実現要素は、独立UXへ分割せず対応する成果の成立条件として保持する。

## 5. 重要な体験

### この要求での利用の流れ

```text
正式な契約や責任者を変更する時
        ↓
作成側・利用側・派生物・公開経路を照合する
        │
        ├─ ★ 重要場面: 移行完了を表示する直前
        ├─ ⚠ 失敗:  代表利用側だけ更新して完了扱いする
        └─ ✓ 守る品質:  自動導出集合と契約試験で閉包を確認する
        ↓
稀な署名・リリース・回復経路の取り残しを防ぐ
```

### サービス提供の流れの処置

処置: `作成`

```text
【利用者・責任者】CRDD作成者・保守者
        │ 利用者行動: 変更した意味と維持する利用側を明示する
        ▼
【利用者接点】正式な契約や責任者を変更する時
        │
        ├─ 時間差: 契約変更後に利用側導出と独立確認を行い、閉包まで時間差がある
        ├─ 完了時: 作成側、全利用側、派生物、公開・署名・リリース経路の接続状態
        └─ 失敗時: 未接続利用側と旧契約残存を独立確認者から変更担当へ返す
                     │
                     ▼
             【回復・判断する人】変更担当（CRDD作成者・保守者）
                     │ 返却された事実と判断不能範囲を確認
                     └─ 次の行動: 不足利用側を移行するか、意図した廃止として判断を得る

---------------- 可視境界 ----------------
                     │ 時間関係: 契約変更後に利用側導出と独立確認を行い、閉包まで時間差がある
                     ▼
【提供側】提供システム
        └─ 提供責務: 宣言と実際のソースから利用側集合と差分を提示する
```

### 製品全体の整理への接続

- 利用の流れの統合先: [標準を変更・検証・公開する](../../03_Experience_Map.md#標準を変更検証公開する)
- サービス提供の流れの統合先: [共同のサービス提供の流れ](../../04_Service_Blueprint.md#1-共同のサービス提供の流れ)

### この要求での責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| CRDD作成者・保守者 | 変更した意味と維持する利用側を明示する | 代表利用側だけで移行完了としない |
| 提供システム | 宣言と実際のソースから利用側集合と差分を提示する | 登録一覧だけを完全な正本とみなさない |
| 独立確認者 | 稀な署名・リリース・回復経路まで閉じたか確認する | 試験件数だけで利用側閉包を推定しない |

### 補足する品質

- 結果または状態を最初に受け取る時: 主要経路だけで完了としない。（避ける失敗: 責務移動後に珍しい入口だけ旧契約へ残り、リリース時に初めて壊れる）
- 結果を判断または引き継ぐ時: 署名・回復・リリース等の副次経路を含める。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 失敗・不足から次の行動を選ぶ時: 旧契約残存を検出可能にする。（避ける失敗: 成立不能の理由や回復先が分からないまま作業が止まる）

## 6. 下流への引き渡し

本節では、IAへの直後工程の引き渡し、UX工程に伴走する品質分析、およびIA完了後にUI／SPECが保持する契約を区別する。UXの完了だけを根拠にIAを飛び越えてUIまたはSPECを開始しない。

| 接続先 | この要求から保持する意味 |
|---|---|
| IA（直後工程への正式な引き渡し） | 必要な情報、理解すべき差、関係、現行性および利用者成果 |
| Quality Analysis / UX（伴走） | 得られる結果、重要場面、失敗、品質期待および検証意図 |
| UI（後続Contract Relation） | IA完了後にUX定義とIA定義の双方から分析する認識・操作・判断の意図 |
| SPEC（後続Contract Relation） | IA完了後にUX定義とIA定義の双方から分析する成立条件・失敗・利用者成果 |

```text
この要求で確定した利用者成果
├─→ IA                         直後工程への正式な引き渡し
├─→ Quality Analysis / UX      UX工程に伴走する検証義務分析
└─→ UI / SPEC                  IA完了後に保持するContract Relation
```

### 妥当性確認と未確認事項

| 確認する仮説 | 観測方法 | 現在未確認の範囲 |
|---|---|---|
| 変更対象の全利用経路が移行済みか確認でき、未移行範囲を残したまま完成表示されないことで、責務移動後に珍しい入口だけ旧契約へ残り、リリース時に初めて壊れるという負担または誤認を減らせる。 | 代表シナリオの利用者確認、利用者体験の専門レビュー、および品質期待を破る反例による下流検証 | CRDD作成者・保守者が「責務移動後の全利用側を閉じる」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |

人間への確認:
- 現在判定: 後続の実利用確認が必要。UX工程の構造整理を止める判断事項ではない。
- 確認事項: CRDD作成者・保守者が「責務移動後の全利用側を閉じる」を行う際の判断基準、許容負担、利用環境および失敗後の選択
- 判断者: [製品全体の利用者像](../../02_Personas.md)の「CRDD作成者・保守者」を代表する利用者とQual-Lab。
- 未確認時の影響: 利用者成果と品質期待は仮説として保持し、負担、閾値、UIまたは実装方式を確定しない。

Discoveryへ戻す条件は、想定した利用者、問題または「責務移動後の全利用側を閉じる」という必要性が誤っていると分かった場合である。IA以降は実現方式を具体化してよいが、利用者成果を無断で弱めない。
