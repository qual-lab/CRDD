分析対象: [REQ-000015 実行時データの基点フォルダの所有と用途](../../../01_Discovery/Definitions/REQ-000015/requirement.md)

## 1. 要求の一次分析

```text
.crddやOS領域に用途不明のFileが増え、消してよいか判断できない
        ↓
解決策を先に固定せず、人の仕事として読み替える
        ↓
利用者に必要なこと
実行時データの所有場所と一連の状態変化を理解する
```

実行基盤運用者・保守者が「残存・清掃・回復を別リポジトリへ波及させず扱える」状態へ進めないことを問題として扱う。

| 観点 | 内容 |
|---|---|
| 解決する問題 | .crddやOS領域に用途不明のFileが増え、消してよいか判断できない |
| 利用者に必要なこと | 実行時データの所有場所と一連の状態変化を理解する |
| 対象範囲 | リポジトリ所有者、実行基盤運用者が、「`.crdd`やOS領域に用途不明のFileが増え、消してよいか判断できない」状態から「リポジトリ固有データと横断実行基盤データを区別し、責任者、保持、Git管理、清掃条件を確認できる」状態へ移る場面 |
| 対象外 | 具体的な画面、データ構造、実装方式および数値閾値の確定 |

## 3. 利用者に起きる変化

```text
変更前
────────────────
- `.crdd`やOS領域に用途不明のFileが増え、消してよいか判断できない
        │
        │ 実行時データの基点フォルダの所有と用途が変える体験
        ▼
変更後
────────────────
- リポジトリ固有データと横断実行基盤データを区別し、責任者、保持、Git管理、清掃条件を確認できる
```

実行時データの基点フォルダの所有と用途は、単に内部方式を成立させる要求ではない。「`.crdd`やOS領域に用途不明のFileが増え、消してよいか判断できない」状態から、「リポジトリ固有データと横断実行基盤データを区別し、責任者、保持、Git管理、清掃条件を確認できる」状態へ変わり、利用者が次の判断へ進めることまでを体験として扱う。

実行基盤運用者・保守者が実行時データの所有場所と一連の状態変化を理解することで、残存・清掃・回復を別リポジトリへ波及させず扱えるようになることを守る。

`Same`／`New`は技術用語の近さや件数目標では決めない。「利用者は、どの状況で、何をするためにシステムと関わり、何ができるようになるか」が同じかを比較する。提供能力、必要情報、品質、妥当性確認または下流の実現要素は、独立UXへ分割せず対応する成果の成立条件として保持する。

## 5. 重要な体験

### この要求での利用の流れ

```text
実行時データを作成または清掃する時
        ↓
検証済み基点フォルダ・責任者・保持条件を確認する
        │
        ├─ ★ 重要場面: 永続化または削除の直前
        ├─ ⚠ 失敗:  subdirectoryや別基点フォルダへ同名データを作る
        └─ ✓ 守る品質:  用途別領域とcleanup条件を明示する
        ↓
残存・清掃・回復を別リポジトリへ波及させず扱える
```

### サービス提供の流れの処置

処置: `作成`

```text
【利用者・責任者】実行環境の導入・運用者
        │ 利用者行動: 保持すべき状態と一時物を理解して処置する
        ▼
【利用者接点】実行時データを作成または清掃する時
        │
        ├─ 時間差: 書込み前に基点フォルダを確認し、終了・清掃時に残存を再観測する
        ├─ 完了時: データの責任者、用途、Durability、cleanup条件、終了後の存在状態
        └─ 失敗時: 由来不明または観測不能なDataを実行環境の導入・運用者へ返す
                     │
                     ▼
             【回復・判断する人】実行環境の導入・運用者
                     │ 返却された事実と判断不能範囲を確認
                     └─ 次の行動: 保持、再観測、回復または安全な清掃を選ぶ

---------------- 可視境界 ----------------
                     │ 時間関係: 書込み前に基点フォルダを確認し、終了・清掃時に残存を再観測する
                     ▼
【提供側】実行基盤／ツール
        └─ 提供責務: 検証済み基点フォルダと用途別領域へDataを作成する
```

### 製品全体の整理への接続

- 利用の流れの統合先: [実行基盤を導入・更新・回復する](../../03_Experience_Map.md#実行基盤を導入更新回復する)
- サービス提供の流れの統合先: [共同のサービス提供の流れ](../../04_Service_Blueprint.md#1-共同のサービス提供の流れ)

### この要求での責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| 実行基盤／ツール | 検証済み基点フォルダと用途別領域へDataを作成する | subdirectoryや別リポジトリへ同名領域を作らない |
| 実行環境の導入・運用者 | 保持すべき状態と一時物を理解して処置する | 由来不明物を名前だけで削除しない |
| 提供システム | 責任者・一連の状態変化・cleanup条件を示して処置結果を返す | 観測不能を不存在として表示しない |

### 補足する品質

- 結果または状態を最初に受け取る時: 用途不明の直下Fileを作らない。（避ける失敗: .crddやOS領域に用途不明のFileが増え、消してよいか判断できない）
- 結果を判断または引き継ぐ時: DurableとTemporaryを名前だけで混同しない。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 失敗・不足から次の行動を選ぶ時: 別リポジトリやOS領域への書込みを隠さない。（避ける失敗: 成立不能の理由や回復先が分からないまま作業が止まる）

## 6. 下流への引き渡し

本節では、IAへの直後工程の引き渡し、UX工程に伴走する品質分析、およびIA完了後にUI／SPECが保持する契約を区別する。UXの完了だけを根拠にIAを飛び越えてUIまたはSPECを開始しない。

| 接続先 | この要求から保持する意味 |
|---|---|
| IA（直後工程への正式な引き渡し） | 必要な情報、理解すべき差、関係、現行性および利用者成果 |
| Quality Analysis / UX（伴走） | 得られる結果、重要場面、失敗、品質期待および検証意図 |
| UI（後続Contract Relation） | IA完了後にUX定義とIA定義の双方から分析する認識・操作・判断の意図 |
| SPEC（後続Contract Relation） | IA完了後にUX定義とIA定義の双方から分析する成立条件・失敗・利用者成果 |

```text
この要求で確定した利用者成果
├─→ IA                         直後工程への正式な引き渡し
├─→ Quality Analysis / UX      UX工程に伴走する検証義務分析
└─→ UI / SPEC                  IA完了後に保持するContract Relation
```

### 妥当性確認と未確認事項

| 確認する仮説 | 観測方法 | 現在未確認の範囲 |
|---|---|---|
| リポジトリ固有データと横断実行基盤データを区別し、責任者、保持、Git管理、清掃条件を確認できることで、.crddやOS領域に用途不明のFileが増え、消してよいか判断できないという負担または誤認を減らせる。 | 代表シナリオの利用者確認、利用者体験の専門レビュー、および品質期待を破る反例による下流検証 | 実行環境の導入・運用者が「実行時データの所有場所と一連の状態変化を理解する」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |

人間への確認:
- 現在判定: 後続の実利用確認が必要。UX工程の構造整理を止める判断事項ではない。
- 確認事項: 実行環境の導入・運用者が「実行時データの所有場所と一連の状態変化を理解する」を行う際の判断基準、許容負担、利用環境および失敗後の選択
- 判断者: [製品全体の利用者像](../../02_Personas.md)の「実行環境の導入・運用者」を代表する利用者とQual-Lab。
- 未確認時の影響: 利用者成果と品質期待は仮説として保持し、負担、閾値、UIまたは実装方式を確定しない。

Discoveryへ戻す条件は、想定した利用者、問題または「実行時データの所有場所と一連の状態変化を理解する」という必要性が誤っていると分かった場合である。IA以降は実現方式を具体化してよいが、利用者成果を無断で弱めない。
