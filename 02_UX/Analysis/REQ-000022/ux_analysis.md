# REQ-000022の利用者体験分析

成果物種別: UX分析

状態: UX再統合済み・独立再レビュー待ち
分析対象: [REQ-000022 実行時データの保持・清掃・回復](../../../01_Discovery/Definitions/REQ-000022/requirement.md)

## 1. 要求の一次分析

```text
残存物を消してよいか分からず蓄積するか、名前だけで削除して回復情報を失う
        ↓
解決策を先に固定せず、人の仕事として読み替える
        ↓
利用者に必要なこと
残存資源の由来・保持・清掃・回復を理解する
```

実行基盤運用者が「必要な根拠を残し不要物を安全に片付けられる」状態へ進めないことを問題として扱う。

| 観点 | 内容 |
|---|---|
| 解決する問題 | 残存物を消してよいか分からず蓄積するか、名前だけで削除して回復情報を失う |
| 利用者に必要なこと | 残存資源の由来・保持・清掃・回復を理解する |
| 対象範囲 | 実行基盤運用者、リポジトリ所有者が、「残存物を消してよいか分からず蓄積するか、名前だけで削除して回復情報を失う」状態から「保持理由、回復要否、清掃可能条件、終了後状態を確認して安全に処置できる」状態へ移る場面 |
| 対象外 | 具体的な画面、データ構造、実装方式および数値閾値の確定 |

## 3. 利用者に起きる変化

```text
変更前
────────────────
- 残存物を消してよいか分からず蓄積するか、名前だけで削除して回復情報を失う
        │
        │ 実行時データの保持・清掃・回復が変える体験
        ▼

────────────────
- 保持理由、回復要否、清掃可能条件、終了後状態を確認して安全に処置できる
```

実行時データの保持・清掃・回復は、単に内部方式を成立させる要求ではない。「残存物を消してよいか分からず蓄積するか、名前だけで削除して回復情報を失う」状態から、「保持理由、回復要否、清掃可能条件、終了後状態を確認して安全に処置できる」状態へ変わり、利用者が次の判断へ進めることまでを体験として扱う。

実行基盤運用者が残存資源の由来・保持・清掃・回復を理解することで、必要な根拠を残し不要物を安全に片付けられるようになることを守る。

### Same判断の比較

#### 実行時データを安全に保持・清掃する

比較対象: `UX-000017`

比較元: `REQ-000015`でこのUXを最初に`New`とした固有記載。得られる結果は同分析のUX固有行、他の軸は同分析と初版Definitionの一致を確認して固定した。

| 比較軸 | 既存UX | 現在の要求 | 差と統合判断 |
|---|---|---|---|
| 担い手 | 実行環境の導入・運用者 | 実行環境の導入・運用者 | 既存UXと現在要求はいずれも「実行環境の導入・運用者」であり、利用者の違いはない |
| 利用のきっかけ | 実行時データを作成または清掃する時 | 失敗後または保守時に残存を見つけた時 | 既存UXの「実行時データを作成または清掃する時」に対して現在要求は「失敗後または保守時に残存を見つけた時」を具体化するが、同じ「実行時データを安全に保持・清掃する」が必要になる開始条件の差であり、独立した成果境界ではない |
| 得られる結果 | 保存場所の内部構造を推測せず、保持すべき状態と一時物を区別して安全に作業を継続・終了できる | 失敗後の残存について由来・参照・回復義務を確認し、保持すべき根拠と一時物を区別して安全に清掃できる | 最初のNew分析で定義された固有成果に対し、現在要求はその成果を「失敗後の残存について由来・参照・回復義務を確認し、保持すべき根拠と一時物を区別して安全に清掃できる」の場面へ具体化する。利用者が達成する中心成果は同じである |
| 避ける失敗 | 子フォルダや別の基点フォルダへ同名データを作る | 由来・参照・回復義務を確認せず残存を削除または無期限保持する | 最初のNew分析で確認された失敗に対し、現在要求は「由来・参照・回復義務を確認せず残存を削除または無期限保持する」へ具体化するが、中心成果を妨げる同じ失敗として扱える |

統合理由: 正確な識別情報とcleanup条件は同じ実行時データ成果を成立させる情報・回復条件である

`Same`／`New`は技術用語の近さや件数目標では決めない。「利用者は、どの状況で、何をするためにシステムと関わり、何ができるようになるか」が同じかを比較する。提供能力、必要情報、品質、妥当性確認または下流の実現要素は、独立UXへ分割せず対応する成果の成立条件として保持する。

## 5. 重要な体験

### この要求での利用の流れ

```text
失敗後または保守時に残存を見つけた時
        ↓
正確な識別情報・参照中か・cleanup条件を確認する
        │
        ├─ ★ 重要場面: 削除または回復を選ぶ場面
        ├─ ⚠ 失敗:  名前や経過時間だけで由来不明物を削除する
        └─ ✓ 守る品質:  残存・観測不能・不存在を区別する
        ↓
必要な根拠を残し不要物を安全に片付けられる
```

### サービス提供の流れの処置

処置: `作成`

```text
【利用者・責任者】実行環境の導入・運用者
        │ 利用者行動: 残存の由来と影響を確認し処置を依頼する
        ▼
【利用者接点】失敗後または保守時に残存を見つけた時
        │
        ├─ 時間差: 失敗発生、残存観測、人間判断、清掃後の不存在確認は別時点になる
        ├─ 完了時: 残存の由来、参照、回復義務、削除条件、不存在根拠
        └─ 失敗時: 削除可否を断定できない残存と影響を人間の決定権限者へ返す
                     │
                     ▼
             【回復・判断する人】人間の決定権限者
                     │ 返却された事実と判断不能範囲を確認
                     └─ 次の行動: 保持、追加調査、回復または削除を選ぶ

---------------- 可視境界 ----------------
                     │ 時間関係: 失敗発生、残存観測、人間判断、清掃後の不存在確認は別時点になる
                     ▼
【提供側】提供システム
        └─ 提供責務: 正確な識別情報で処置し、終了後状態または回復義務を返す
```

### 製品全体の整理への接続

- 利用の流れの統合先: [実行基盤を導入・更新・回復する](../../03_Experience_Map.md#実行基盤を導入更新回復する)
- サービス提供の流れの統合先: [共同のサービス提供の流れ](../../04_Service_Blueprint.md#1-共同のサービス提供の流れ)

### この要求での責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| 実行環境の導入・運用者 | 残存の由来と影響を確認し処置を依頼する | 名前や経過時間だけで削除しない |
| 人間の決定権限者 | 不明点と残存リスクを踏まえ保持・回復・清掃を選ぶ | 観測不能を不存在として受容しない |
| 提供システム | 正確な識別情報で処置し、終了後状態または回復義務を返す | cleanup要求の発行だけを完了と表示しない |

### 補足する品質

- 結果または状態を最初に受け取る時: 由来不明と不要を同一視しない。（避ける失敗: 残存物を消してよいか分からず蓄積するか、名前だけで削除して回復情報を失う）
- 結果を判断または引き継ぐ時: 清掃不能時にexactな再入場情報を示す。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 失敗・不足から次の行動を選ぶ時: 成功後は物理残存がないことを確認できる。（避ける失敗: 成立不能の理由や回復先が分からないまま作業が止まる）

## 6. 下流への引き渡し

本節では、IAへの直後工程の引き渡し、UX工程に伴走する品質分析、およびIA完了後にUI／SPECが保持する契約を区別する。UXの完了だけを根拠にIAを飛び越えてUIまたはSPECを開始しない。

| 接続先 | この要求から保持する意味 |
|---|---|
| IA（直後工程への正式な引き渡し） | 必要な情報、理解すべき差、関係、現行性および利用者成果 |
| Quality Analysis / UX（伴走） | 得られる結果、重要場面、失敗、品質期待および検証意図 |
| UI（後続Contract Relation） | IA完了後にUX定義とIA定義の双方から分析する認識・操作・判断の意図 |
| SPEC（後続Contract Relation） | IA完了後にUX定義とIA定義の双方から分析する成立条件・失敗・利用者成果 |

```text
この要求で確定した利用者成果
├─→ IA                         直後工程への正式な引き渡し
├─→ Quality Analysis / UX      UX工程に伴走する検証義務分析
└─→ UI / SPEC                  IA完了後に保持するContract Relation
```

### 妥当性確認と未確認事項

| 確認する仮説 | 観測方法 | 現在未確認の範囲 |
|---|---|---|
| 保持理由、回復要否、清掃可能条件、終了後状態を確認して安全に処置できることで、残存物を消してよいか分からず蓄積するか、名前だけで削除して回復情報を失うという負担または誤認を減らせる。 | 代表シナリオの利用者確認、利用者体験の専門レビュー、および品質期待を破る反例による下流検証 | 実行環境の導入・運用者が「残存資源の由来・保持・清掃・回復を理解する」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |

人間への確認:
- 現在判定: 後続の実利用確認が必要。UX工程の構造整理を止める判断事項ではない。
- 確認事項: 実行環境の導入・運用者が「残存資源の由来・保持・清掃・回復を理解する」を行う際の判断基準、許容負担、利用環境および失敗後の選択
- 判断者: [製品全体の利用者像](../../02_Personas.md)の「実行環境の導入・運用者」を代表する利用者とQual-Lab。
- 未確認時の影響: 利用者成果と品質期待は仮説として保持し、負担、閾値、UIまたは実装方式を確定しない。

Discoveryへ戻す条件は、想定した利用者、問題または「残存資源の由来・保持・清掃・回復を理解する」という必要性が誤っていると分かった場合である。IA以降は実現方式を具体化してよいが、利用者成果を無断で弱めない。
