# REQ-000035の利用者体験分析

成果物種別: UX分析

状態: UX再統合済み・独立再レビュー待ち
分析対象: [REQ-000035 公式視覚素材の権利・用途・追跡](../../../01_Discovery/Definitions/REQ-000035/requirement.md)

## 1. 要求の一次分析

```text
見た目が公式であることと、品質保証・信頼・権利許諾を同じ意味に扱う
        ↓
解決策を先に固定せず、人の仕事として読み替える
        ↓
利用者に必要なこと
視覚素材の出所・権利・用途を確認する
```

この要求で解くのは素材の有無だけではない。閲覧者が公式入口を見分けつつ表示だけを保証と誤認せず、保守者が権利・原本・派生関係を確認して収載・再利用できる状態へ進めないことを問題として扱う。具体的な画面、素材形式または配布方式はここで確定しない。

| 観点 | 内容 |
|---|---|
| 解決する問題 | 見た目が公式であることと、品質保証・信頼・権利許諾を同じ意味に扱う |
| 利用者に必要なこと | 視覚素材の出所・権利・用途を確認する |
| 対象範囲 | CRDDを識別・紹介・再配布する人が、「見た目が公式であることと、品質保証・信頼・権利許諾を同じ意味に扱う」状態から「公式の識別用途、素材の出所、利用条件、派生関係を確認して適切に使える」状態へ移る場面 |
| 対象外 | 具体的な画面、データ構造、実装方式および数値閾値の確定 |

## 2. 利用者・目標・成果

```text
閲覧者／公式素材を管理・再利用する人
        │
        │ 望んでいる
        ▼
公式識別と保証を分け、素材の出所・権利・用途を確認する
        │
        │ その結果として
        ▼
公式入口を誤認なく選び、素材を安心して収載・派生利用できる
```

| 項目 | 内容 |
|---|---|
| 主な想定利用者 | [製品全体の利用者像](../../02_Personas.md)の「CRDD閲覧者」／「CRDD作成者・保守者」 |
| 利用場面 | 公式らしい入口を選ぶ時／ブランド素材を追加・再利用する時 |
| 目的 | 公式識別と保証を分け、素材の出所・権利・用途を確認する |
| 得られる結果 | 公式入口を誤認なく選び、素材を安心して収載・派生利用できる |
| この要求に固有の差 | 閲覧者の識別判断と、保守者の権利・原本・派生物管理は別の独立成果になる |
| 根拠・確信度 | 採用要求から導いた仮説。識別表示が閲覧者の入口選択を助けつつ信頼誤認を増やさないかは未確認。 |

## 3. 利用者に起きる変化

```text
変更前
────────────────
- 見た目が公式であることと、品質保証・信頼・権利許諾を同じ意味に扱う
        │
        │ 公式視覚素材の権利・用途・追跡が変える体験
        ▼
変更後
────────────────
- 公式の識別用途、素材の出所、利用条件、派生関係を確認して適切に使える
```

公式視覚素材の権利・用途・追跡は、単に内部方式を成立させる要求ではない。「見た目が公式であることと、品質保証・信頼・権利許諾を同じ意味に扱う」状態から、「公式の識別用途、素材の出所、利用条件、派生関係を確認して適切に使える」状態へ変わり、利用者が次の判断へ進めることまでを体験として扱う。

この変化で守るのは一つの見た目ではない。閲覧者が公式識別と保証根拠を分けて入口を選べることと、保守者が視覚素材の出所・権利・用途を確認して安心して収載・派生利用できることを守る。

## 4. 利用者成果への統合

```text
REQ-000035
   │
   ├─ New  → UX-000030 公式素材を権利と用途を確認して使う
   └─ New  → UX-000031 公式の識別と保証を混同せず見分ける
```

| 利用者成果 | 処置 | 判断理由 | この要求が補う内容 |
|---|---|---|---|
| 公式素材を権利と用途を確認して使う | `New → UX-000030` | 本要求が「公式素材の出所・原本・派生物・利用条件を確認し、許可された用途で安心して収載・再利用できる」という独立した利用者成果を最初に定義する。 | 原本・生成経緯・許可・派生関係を確認することが、この要求固有の成立条件になる |
| 公式の識別と保証を混同せず見分ける | `New → UX-000031` | 本要求が、閲覧者が公式入口を識別しつつ、その表示だけを署名・準拠・品質・発行元への信頼の証明と誤認しない独立成果を最初に定義する。 | 識別表示と検証可能な保証根拠を別に確認できることが成立条件になる |

`Same`／`New`は技術用語の近さや件数目標では決めない。「利用者は、どの状況で、何をするためにシステムと関わり、何ができるようになるか」が同じかを比較する。提供能力、必要情報、品質、妥当性確認または下流の実現要素は、独立UXへ分割せず対応する成果の成立条件として保持する。

## 5. 重要な体験

### この要求での利用の流れ

#### 閲覧者

```text
公式らしい入口や視覚素材を見つけた時
        ↓
識別表示と保証の根拠を分けて確認する
        │
        ├─ ★ 重要場面: 公式表示を信頼判断へ用いる直前
        ├─ ⚠ 失敗:  アイコンや見た目を署名・準拠・品質保証と誤認する
        └─ ✓ 守る品質:  識別表示と検証可能な信頼根拠を別に示す
        ↓
見た目だけを信頼根拠にせず適切な入口を選べる
```

#### 保守者

```text
ブランド素材を追加または利用する時
        ↓
原本・生成経緯・許可・派生関係を確認する
        │
        ├─ ★ 重要場面: 公式用途へ採用する直前
        ├─ ⚠ 失敗:  見た目だけで権利や信頼保証を推定する
        └─ ✓ 守る品質:  由来・権利・用途を追跡する
        ↓
公式識別へ安心して収載・派生利用できる
```

### サービス提供の流れの処置

処置: `作成`

```text
【利用者・責任者】CRDD作成者・保守者
        │ 利用者行動: 公式用途とライセンス条件を照合して候補化する
        ▼
【利用者接点】ブランド素材を追加または利用する時
        │
        ├─ 時間差: 素材生成・権利確認・リポジトリ収載は別の判断時点を持つ
        ├─ 完了時: 原本、生成経緯、権利確認、用途、再配布許可
        └─ 失敗時: 権利または用途が未確認の素材を人間の決定権限者へ返す
                     │
                     ▼
             【回復・判断する人】人間の決定権限者
                     │ 返却された事実と判断不能範囲を確認
                     └─ 次の行動: 追加確認、用途制限、却下または収載を選ぶ

---------------- 可視境界 ----------------
                     │ 時間関係: 素材生成・権利確認・リポジトリ収載は別の判断時点を持つ
                     ▼
【提供側】素材作成者／権利確認者
        └─ 提供責務: 出所・生成経緯・権利・再配布許可を提示する
```

この図は、利用者行動、利用者が観測する接点、提供責務および失敗時の引き渡しを示す。内部構成要素の構造やプロトコルは下流工程で具体化する。

### 製品全体の整理への接続

- 利用の流れの統合先: [標準を変更・検証・公開する](../../03_Experience_Map.md#標準を変更検証公開する)／[公式入口と素材を扱う](../../03_Experience_Map.md#公式入口と素材を扱う)
- サービス提供の流れの統合先: [共同のサービス提供の流れ](../../04_Service_Blueprint.md#1-共同のサービス提供の流れ)
- 横断成果物はこの個別分析から共通パターンを合成する。この要求での利用の流れ、責任境界または品質の代替にはしない。

### この要求での責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| 素材作成者／権利確認者 | 出所・生成経緯・権利・再配布許可を提示する | 見た目だけから権利を保証しない |
| CRDD作成者・保守者 | 公式用途とライセンス条件を照合して候補化する | 権利確認を信頼保証へ拡張しない |
| 閲覧者 | 識別表示と別の保証根拠を確認して入口を選ぶ | 見た目だけを署名・準拠・品質の証明とみなさない |
| 人間の決定権限者 | 採用・用途制限・不採用を根拠付きで決める | 不明な権利を黙示受容しない |

### 補足する品質

- 結果または状態を最初に受け取る時: ブランド表示を実行基盤保証に使わない。（避ける失敗: 見た目が公式であることと、品質保証・信頼・権利許諾を同じ意味に扱う）
- 結果を判断または引き継ぐ時: 権利確認のない素材を収載しない。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 失敗・不足から次の行動を選ぶ時: 原本と派生物を追跡できる。（避ける失敗: 成立不能の理由や回復先が分からないまま作業が止まる）


## 6. 下流への引き渡し

```text
この要求で確定した利用者成果
        │
        ├─→ IA: 必要な情報・関係・見つけ方
        ├─→ UI: 誤認させない表示・操作意図
        ├─→ SPEC: 振る舞い・失敗・体験品質の条件
        └─→ Verification: 仮説を破る反例と観測
```

### 妥当性確認と未確認事項

| 確認する仮説 | 観測方法 | 現在未確認の範囲 |
|---|---|---|
| 閲覧者が公式識別と保証根拠を分け、保守者が素材の出所・権利・派生関係を確認できることで、見た目・信頼・権利を同じ意味に扱う誤認を減らせる。 | 閲覧者の公式／非公式入口選択と、保守者の収載・派生利用シナリオを分けて確認する | 識別表示が入口発見を助けながら信頼誤認を増やさないか、権利情報の許容確認負担 |

### 工程別の引き渡し

| 引き渡し先 | 具体化する義務 |
|---|---|
| 下流工程 | Communicationは識別用途と表示を、Releaseは権利・原本・派生物の追跡を具体化する。 |

Discoveryへ戻す条件は、想定した利用者、問題または「視覚素材の出所・権利・用途を確認する」という必要性が誤っていると分かった場合である。下流は実現方式を具体化してよいが、「公式識別へ安心して収載・派生利用できる」という成果を無断で弱めない。
