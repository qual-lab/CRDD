# REQ-000021の利用者体験分析

成果物種別: UX分析

状態: UX再統合済み・独立再レビュー待ち
分析対象: [REQ-000021 リモート要求結果の同一識別情報再取得](../../../01_Discovery/Definitions/REQ-000021/requirement.md)

## 1. 要求の一次分析

```text
Timeout後に同じ依頼を新規実行する／応答喪失と処理失敗を同一視する
        ↓
解決策を先に固定せず、人の仕事として読み替える
        ↓
利用者に必要なこと
切断後に同じ依頼へ戻る
```

この要求で解くのは機能の有無だけではない。リモート要求を行う人が「二重実行せず状態・結果・回復義務を取得できる」状態へ進めないことを問題として扱う。具体的な画面、データ構造、API、構成要素または数値閾値はここで確定しない。

| 観点 | 内容 |
|---|---|
| 解決する問題 | Timeout後に同じ依頼を新規実行する／応答喪失と処理失敗を同一視する |
| 利用者に必要なこと | 切断後に同じ依頼へ戻る |
| 対象範囲 | リモート要求を行う人、運用者が、「Timeout後に同じ依頼を新規実行する」状態から「同じ依頼の識別情報から状態、結果、回復義務を再取得する」状態へ移る場面 |
| 対象外 | 具体的な画面、データ構造、実装方式および数値閾値の確定 |

```text
        │
        │ その結果として
        ▼

```

## 3. 利用者に起きる変化

```text
変更前
────────────────
- Timeout後に同じ依頼を新規実行する
- 応答喪失と処理失敗を同一視する
        │
        │ リモート要求結果の同一識別情報再取得が変える体験
        ▼
変更後
────────────────
- 同じ依頼の識別情報から状態、結果、回復義務を再取得する
- 外部への変更の成立、結果搬送、観測不能を区別する
```

リモート要求の応答が消えた時、同じ操作を再実行すると二重外部への変更の危険がある。利用者は「失敗した」と推測するのでなく、元の要求へ戻って現在状態を確認できる必要がある。

この変化で守るのは操作手順ではない。リモート要求を行う人が切断後に同じ依頼へ戻ることで、二重実行せず状態・結果・回復義務を取得できるようになることを守る。

## 4. 利用者成果への統合

```text
REQ-000021
   │
   ├─ Same → UX-000004 失敗後の再試行・回復を選ぶ
   └─ New  → UX-000021 切断後も同じ依頼へ戻る
```

| 利用者成果 | 処置 | 判断理由 | この要求が補う内容 |
|---|---|---|---|
| 失敗後の再試行・回復を選ぶ | `Same → UX-000004` | 既存UXの利用者: プロジェクト運営者／PM<br>現在要求の利用者: プロジェクト運営者／PM<br>利用者の差: 既存UXと現在要求はいずれも「プロジェクト運営者／PM」であり、利用者の違いはない<br>既存UXの利用のきっかけ: 複数AIへ仕事を委ねる時<br>現在要求の利用のきっかけ: 応答喪失後に再接続する時<br>利用のきっかけの差: 既存UXの「複数AIへ仕事を委ねる時」に対して現在要求は「応答喪失後に再接続する時」を具体化するが、同じ「失敗後の再試行・回復を選ぶ」が必要になる開始条件の差であり、独立した成果境界ではない<br>既存UXで得られる結果: 失敗後に状態確認、再試行、回復および清掃を取り違えず、二重外部への変更を避けて次の行動を選べる<br>現在要求で得られる結果: 応答喪失時に既存依頼の状態を先に確認し、新規実行・再試行・回復を取り違えず選べる<br>得られる結果の差: 現在要求は「失敗後の再試行・回復を選ぶ」をこの要求の場面で成立させる得られる結果を具体化しており、要求全体の中心となる利用者成果や別のUX成果へ置き換えていない<br>既存UXでの失敗: 失敗後に状態確認・再試行・回復・清掃を取り違え、二重外部への変更を起こす<br>現在要求での失敗: Timeoutを未実行とみなし、同じ依頼を確認せず新規外部への変更を開始する<br>失敗の差: 現在要求は応答喪失という具体的な失敗契機を追加するが、誤った再試行選択による二重外部への変更は同じである<br>同じ利用者成果へ統合できる理由: 依頼再取得は同じ回復選択成果の成立条件であり、別の利用者成果ではない | 依頼の識別情報と現在利用権限を再確認することが、この要求固有の成立条件になる |
| 切断後も同じ依頼へ戻る | `New → UX-000021` | 本要求が「応答喪失後に新規実行せず、現在の利用権限で同じ依頼の状態・結果・回復義務へ戻れる」という独立した利用者成果を最初に定義する。 | 依頼の識別情報と現在利用権限を再確認することが、この要求固有の成立条件になる |

`Same`／`New`は技術用語の近さや件数目標では決めない。「利用者は、どの状況で、何をするためにシステムと関わり、何ができるようになるか」が同じかを比較する。提供能力、必要情報、品質、妥当性確認または下流の実現要素は、独立UXへ分割せず対応する成果の成立条件として保持する。

## 5. 重要な体験

### この要求での利用の流れ

```text
応答喪失後に再接続する時
        ↓
依頼の識別情報と現在利用権限を再確認する
        │
        ├─ ★ 重要場面: 再実行するか判断する直前
        ├─ ⚠ 失敗:  Timeoutを未実行とみなし新規外部への変更を起こす
        └─ ✓ 守る品質:  同一識別情報の照会を再実行より先に示す
        ↓
二重実行せず状態・結果・回復義務を取得できる
```

### サービス提供の流れの処置

処置: `作成`

```text
【利用者・責任者】プロジェクト運営者／PM
        │ 利用者行動: 既存依頼を指定して再接続し、次の処置を判断する
        ▼
【利用者接点】応答喪失後に再接続する時
        │
        ├─ 時間差: 応答喪失から再接続まで時間差があり、元依頼は継続し得る
        ├─ 完了時: 同じ依頼の状態、結果、外部への変更状態、回復義務
        └─ 失敗時: 依頼不一致または状態不明を運用・確認者へ返す
                     │
                     ▼
             【回復・判断する人】運用・確認者
                     │ 返却された事実と判断不能範囲を確認
                     └─ 次の行動: 状態再観測、結果取得、回復または明示的な新規実行を選ぶ

---------------- 可視境界 ----------------
                     │ 時間関係: 応答喪失から再接続まで時間差があり、元依頼は継続し得る
                     ▼
【提供側】提供システム
        └─ 提供責務: 同じ識別情報の状態・結果・回復義務を保持し現在利用権限で返す
```

この図は、利用者行動、利用者が観測する接点、提供責務および失敗時の引き渡しを示す。内部構成要素の構造やプロトコルは下流工程で具体化する。

### 製品全体の整理への接続

- 利用の流れの統合先: [リモートで情報と結果へ戻る](../../03_Experience_Map.md#リモートで情報と結果へ戻る)
- サービス提供の流れの統合先: [共同のサービス提供の流れ](../../04_Service_Blueprint.md#1-共同のサービス提供の流れ)
- 横断成果物はこの個別分析から共通パターンを合成する。この要求での利用の流れ、責任境界または品質の代替にはしない。

### この要求での責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| プロジェクト運営者／PM | 既存依頼を指定して再接続し、次の処置を判断する | Timeoutだけで未実行と決めて新規外部への変更を起こさない |
| 提供システム | 同じ識別情報の状態・結果・回復義務を保持し現在利用権限で返す | 古い接続単位の権限や不明な結果を成功へ畳まない |
| 運用・確認者 | 切断前後の識別情報、外部への変更、再取得を反証する | 再接続成功だけから二重外部への変更不存在を推定しない |

### 補足する品質

- 結果または状態を最初に受け取る時: 切断後も依頼の識別情報を失わない。（避ける失敗: Timeout後に同じ依頼を新規実行する）
- 結果を判断または引き継ぐ時: 状態不明を失敗や未実行へ畳まない。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 結果を判断または引き継ぐ時: 再接続時に別・拡大決定権限を生成しない。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 失敗・不足から次の行動を選ぶ時: 回復が必要なら対象と次の操作を一意に示す。（避ける失敗: 成立不能の理由や回復先が分からないまま作業が止まる）


## 6. 下流への引き渡し

```text
この要求で確定した利用者成果
        │
        ├─→ IA: 必要な情報・関係・見つけ方
        ├─→ UI: 誤認させない表示・操作意図
        ├─→ SPEC: 振る舞い・失敗・体験品質の条件
        └─→ Verification: 仮説を破る反例と観測
```

### 妥当性確認と未確認事項

| 確認する仮説 | 観測方法 | 現在未確認の範囲 |
|---|---|---|
| 同じ依頼の識別情報から状態、結果、回復義務を再取得する／外部への変更の成立、結果搬送、観測不能を区別することで、Timeout後に同じ依頼を新規実行するという負担または誤認を減らせる。 | 代表シナリオの利用者確認、利用者体験の専門レビュー、および品質期待を破る反例による下流検証 | プロジェクト運営者／PMが「切断後に同じ依頼へ戻る」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |

### 工程別の引き渡し

| 引き渡し先 | 具体化する義務 |
|---|---|
| 下流工程 | IAは依頼、試行、結果、結果の受け渡しおよび回復を関連付ける。SPEC／Architectureは冪等な照会と再入場を分け、総合試験は切断を含む一連の状態変化全体を確認する。 |

Discoveryへ戻す条件は、想定した利用者、問題または「切断後に同じ依頼へ戻る」という必要性が誤っていると分かった場合である。下流は実現方式を具体化してよいが、「二重実行せず状態・結果・回復義務を取得できる」という成果を無断で弱めない。
