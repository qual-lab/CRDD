# REQ-000016の利用者体験分析

成果物種別: UX分析

状態: UX再統合済み・独立再レビュー待ち
分析対象: [REQ-000016 AIモデル設定内容の検証可能な外部構成](../../../01_Discovery/Definitions/REQ-000016/requirement.md)

## 1. 要求の一次分析

```text
新モデルやCLI配置の変更ごとに中核改修を待ち、何が選ばれたか分からない
        ↓
解決策を先に固定せず、人の仕事として読み替える
        ↓
利用者に必要なこと
AIモデル選択を検証可能な構成として更新する
```

実行基盤構成管理者が「新モデルへ追随してもコード改修を繰り返さずに済む」状態へ進めないことを問題として扱う。

| 観点 | 内容 |
|---|---|
| 解決する問題 | 新モデルやCLI配置の変更ごとに中核改修を待ち、何が選ばれたか分からない |
| 利用者に必要なこと | AIモデル選択を検証可能な構成として更新する |
| 対象範囲 | AIを選択・運用する人が、「新モデルやCLI配置の変更ごとに中核改修を待ち、何が選ばれたか分からない」状態から「互換範囲の変更は検証済み設定で反映でき、実際に選ばれた設定内容と理由を確認できる」状態へ移る場面 |
| 対象外 | 具体的な画面、データ構造、実装方式および数値閾値の確定 |

実行基盤構成管理者

        │
        │ その結果として
        ▼

| 得られる結果 | 新モデルへ追随してもコード改修を繰り返さずに済む |
| この要求に固有の差 | 構成の出所・互換性・選択結果を確認することが、この要求固有の成立条件になる |
| 根拠・確信度 | 同じREQのDiscovery定義から導いた仮説。実行環境の導入・運用者が「AIモデル選択を検証可能な構成として更新する」を判断する場面で、構成の出所・互換性・選択結果を確認することが実際に成果へ影響するかは未確認。 |

## 3. 利用者に起きる変化

```text
変更前
────────────────
- 新モデルやCLI配置の変更ごとに中核改修を待ち、何が選ばれたか分からない
        │
        │ AIモデル設定内容の検証可能な外部構成が変える体験
        ▼
変更後
────────────────
- 互換範囲の変更は検証済み設定で反映でき、実際に選ばれた設定内容と理由を確認できる
```

AIモデル設定内容の検証可能な外部構成は、単に内部方式を成立させる要求ではない。「新モデルやCLI配置の変更ごとに中核改修を待ち、何が選ばれたか分からない」状態から、「互換範囲の変更は検証済み設定で反映でき、実際に選ばれた設定内容と理由を確認できる」状態へ変わり、利用者が次の判断へ進めることまでを体験として扱う。

実行基盤構成管理者がAIモデル選択を検証可能な構成として更新することで、新モデルへ追随してもコード改修を繰り返さずに済むようになることを守る。

## 4. 利用者成果への統合

```text
REQ-000016
   │
   └─ New  → UX-000018 AIモデル構成を安全に更新・選択する
```

| 利用者成果 | 処置 | 判断理由 | この要求が補う内容 |
|---|---|---|---|
| AIモデル構成を安全に更新・選択する | `New → UX-000018` | 本要求が「新しいモデルへ追随するとき、コード改修を待たず検証済み構成を更新し、実効選択と再選定理由を理解できる」という独立した利用者成果を最初に定義する。 | 構成の出所・互換性・選択結果を確認することが、この要求固有の成立条件になる |

`Same`／`New`は技術用語の近さや件数目標では決めない。「利用者は、どの状況で、何をするためにシステムと関わり、何ができるようになるか」が同じかを比較する。提供能力、必要情報、品質、妥当性確認または下流の実現要素は、独立UXへ分割せず対応する成果の成立条件として保持する。

## 5. 重要な体験

### この要求での利用の流れ

```text
利用モデルやAI提供元条件を変更する時
        ↓
構成の出所・互換性・選択結果を確認する
        │
        ├─ ★ 重要場面: AI提供元で実行する前のモデル確定
        ├─ ⚠ 失敗:  未知または非対応のモデルを実行可能と表示する
        └─ ✓ 守る品質:  構成変更を検証し実効選択を観測可能にする
        ↓
新モデルへ追随してもコード改修を繰り返さずに済む
```

### サービス提供の流れの処置

処置: `作成`

```text
【利用者・責任者】実行環境の導入・運用者
        │ 利用者行動: 利用目的に合う設定内容を構成し選択結果を確認する
        ▼
【利用者接点】利用モデルやAI提供元条件を変更する時
        │
        ├─ 時間差: 構成更新後にAI提供元能力を検証し、その後の選択へ反映する
        ├─ 完了時: 設定内容、検証結果、実効モデル、選択理由、再選定条件
        └─ 失敗時: 未知・非対応の構成項目をModel構成責任者へ返す
                     │
                     ▼
             【回復・判断する人】Model構成責任者
                     │ 返却された事実と判断不能範囲を確認
                     └─ 次の行動: 設定内容を修正するか、検証済み代替を選ぶ

---------------- 可視境界 ----------------
                     │ 時間関係: 構成更新後にAI提供元能力を検証し、その後の選択へ反映する
                     ▼
【提供側】提供システム
        └─ 提供責務: 構成と現在機能を照合し選択・再選定理由を返す
```

### 製品全体の整理への接続

- 利用の流れの統合先: [実行基盤を導入・更新・回復する](../../03_Experience_Map.md#実行基盤を導入更新回復する)
- サービス提供の流れの統合先: [共同のサービス提供の流れ](../../04_Service_Blueprint.md#1-共同のサービス提供の流れ)

### この要求での責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| 実行環境の導入・運用者 | 利用目的に合う設定内容を構成し選択結果を確認する | 未知設定の黙示Fallbackを期待しない |
| Model構成責任者 | 対応Model・機能・制約を更新する | 設定可能性を実行可能性として保証しない |
| 提供システム | 構成と現在機能を照合し選択・再選定理由を返す | 非対応Modelを実行可能として表示しない |

### 補足する品質

- 結果または状態を最初に受け取る時: 未知の設定を黙って代替しない。（避ける失敗: 新モデルやCLI配置の変更ごとに中核改修を待ち、何が選ばれたか分からない）
- 結果を判断または引き継ぐ時: 設定変更と接続部変更を区別する。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 失敗・不足から次の行動を選ぶ時: 利用不能時は再選定条件を示す。（避ける失敗: 成立不能の理由や回復先が分からないまま作業が止まる）

## 6. 下流への引き渡し

本節では、IAへの直後工程の引き渡し、UX工程に伴走する品質分析、およびIA完了後にUI／SPECが保持する契約を区別する。UXの完了だけを根拠にIAを飛び越えてUIまたはSPECを開始しない。

| 接続先 | この要求から保持する意味 |
|---|---|
| IA（直後工程への正式な引き渡し） | 必要な情報、理解すべき差、関係、現行性および利用者成果 |
| Quality Analysis / UX（伴走） | 得られる結果、重要場面、失敗、品質期待および検証意図 |
| UI（後続Contract Relation） | IA完了後にUX定義とIA定義の双方から分析する認識・操作・判断の意図 |
| SPEC（後続Contract Relation） | IA完了後にUX定義とIA定義の双方から分析する成立条件・失敗・利用者成果 |

```text
この要求で確定した利用者成果
├─→ IA                         直後工程への正式な引き渡し
├─→ Quality Analysis / UX      UX工程に伴走する検証義務分析
└─→ UI / SPEC                  IA完了後に保持するContract Relation
```

### 妥当性確認と未確認事項

| 確認する仮説 | 観測方法 | 現在未確認の範囲 |
|---|---|---|
| 互換範囲の変更は検証済み設定で反映でき、実際に選ばれた設定内容と理由を確認できることで、新モデルやCLI配置の変更ごとに中核改修を待ち、何が選ばれたか分からないという負担または誤認を減らせる。 | 代表シナリオの利用者確認、利用者体験の専門レビュー、および品質期待を破る反例による下流検証 | 実行環境の導入・運用者が「AIモデル選択を検証可能な構成として更新する」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |

人間への確認:
- 現在判定: 後続の実利用確認が必要。UX工程の構造整理を止める判断事項ではない。
- 確認事項: 実行環境の導入・運用者が「AIモデル選択を検証可能な構成として更新する」を行う際の判断基準、許容負担、利用環境および失敗後の選択
- 判断者: [製品全体の利用者像](../../02_Personas.md)の「実行環境の導入・運用者」を代表する利用者とQual-Lab。
- 未確認時の影響: 利用者成果と品質期待は仮説として保持し、負担、閾値、UIまたは実装方式を確定しない。

Discoveryへ戻す条件は、想定した利用者、問題または「AIモデル選択を検証可能な構成として更新する」という必要性が誤っていると分かった場合である。IA以降は実現方式を具体化してよいが、利用者成果を無断で弱めない。
