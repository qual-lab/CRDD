# REQ-000027の利用者体験分析

成果物種別: UX分析

状態: UX再統合済み・独立再レビュー待ち
分析対象: [REQ-000027 外部情報の送信・昇格境界](../../../01_Discovery/Definitions/REQ-000027/requirement.md)

## 1. 要求の一次分析

```text
内部情報が無条件に送られ、外部反応が要求や権限として取り込まれる
        ↓
解決策を先に固定せず、人の仕事として読み替える
        ↓
利用者に必要なこと
送信範囲を理解し帰還結果を候補として扱う
```

外部情報所有者・利用者が「不要情報を漏らさず人間判断を保って外部連携できる」状態へ進めないことを問題として扱う。

| 観点 | 内容 |
|---|---|
| 解決する問題 | 内部情報が無条件に送られ、外部反応が要求や権限として取り込まれる |
| 利用者に必要なこと | 送信範囲を理解し帰還結果を候補として扱う |
| 対象範囲 | 外部AI・検索・公開Communication・管理対象依存を使う人、情報所有者が、「内部情報が無条件に送られ、外部反応や依存新版が要求・因果・権限として取り込まれる」状態から「送信先、目的、情報範囲、決定権限、持ち帰る内容と昇格条件を理解して制御できる」状態へ移る場面 |
| 対象外 | 具体的な画面、データ構造、実装方式および数値閾値の確定 |

## 3. 利用者に起きる変化

```text
変更前
────────────────
- 内部情報が無条件に送られ、外部反応が要求や権限として取り込まれる
        │
        │ 外部情報の送信・昇格境界が変える体験
        ▼
変更後
────────────────
- 送信先、目的、情報範囲、決定権限、持ち帰る内容を理解して制御できる
```

外部情報の送信・昇格境界は、単に内部方式を成立させる要求ではない。「内部情報が無条件に送られ、外部反応が要求や権限として取り込まれる」状態から、「送信先、目的、情報範囲、決定権限、持ち帰る内容を理解して制御できる」状態へ変わり、利用者が次の判断へ進めることまでを体験として扱う。

外部情報所有者・利用者が送信範囲を理解し帰還結果を候補として扱うことで、不要情報を漏らさず人間判断を保って外部連携できるようになることを守る。

## 4. 利用者成果への統合

   └─ New  → UX-000024 外部利用の送信・持帰り・昇格を制御する

### Same判断の比較

#### 必要な情報を渡し結果を同じ仕事へ戻す

比較対象: `UX-000019`

比較元: `REQ-000017`でこのUXを最初に`New`とした固有記載。得られる結果は同分析のUX固有行、他の軸は同分析と初版Definitionの一致を確認して固定した。

| 比較軸 | 既存UX | 現在の要求 | 差と統合判断 |
|---|---|---|---|
| 担い手 | 外部へ渡す情報の所有者 | 外部へ渡す情報の所有者 | 既存UXと現在要求はいずれも「外部へ渡す情報の所有者」であり、利用者の違いはない |
| 利用のきっかけ | 別Agentやツールへ仕事を渡す時 | 外部AI・ツール・リポジトリへ情報を送る時 | 既存UXの「別Agentやツールへ仕事を渡す時」に対して現在要求は「外部AI・ツール・リポジトリへ情報を送る時」を具体化するが、同じ「必要な情報を渡し結果を同じ仕事へ戻す」が必要になる開始条件の差であり、独立した成果境界ではない |
| 得られる結果 | 必要最小限の情報を出所・現行性・許可付きで渡し、相関・完全性付きの結果を同じタスクへ戻せる | 許可した最小情報を外部へ渡し、帰還結果を同じタスクの候補として出所付きで戻せる | 最初のNew分析で定義された固有成果に対し、現在要求はその成果を「許可した最小情報を外部へ渡し、帰還結果を同じタスクの候補として出所付きで戻せる」の場面へ具体化する。利用者が達成する中心成果は同じである |
| 避ける失敗 | 全量投入・秘密情報混入・古い仮説の現在値化 | 送信先へ過剰な情報を渡すか、帰還結果を出所不明のまま正本へ採用する | 最初のNew分析で確認された失敗に対し、現在要求は「送信先へ過剰な情報を渡すか、帰還結果を出所不明のまま正本へ採用する」へ具体化するが、中心成果を妨げる同じ失敗として扱える |

統合理由: 送信許可と候補境界は同じ往復成果の決定権限／品質条件である

`Same`／`New`は技術用語の近さや件数目標では決めない。「利用者は、どの状況で、何をするためにシステムと関わり、何ができるようになるか」が同じかを比較する。提供能力、必要情報、品質、妥当性確認または下流の実現要素は、独立UXへ分割せず対応する成果の成立条件として保持する。

## 5. 重要な体験

### この要求での利用の流れ

```text
外部AI・検索・公開Communication・管理対象依存を利用する時
        ↓
送信先・目的・分類・最小情報を確認する
        │
        ├─ ★ 重要場面: 外部作用（Effect）の前と結果昇格時
        ├─ ⚠ 失敗:  接続済みを包括許可とし、外部反応や依存新版を要求・因果・方針へ自動昇格する
        └─ ✓ 守る品質:  同意・投影・採用を分離する
        ↓
不要情報を漏らさず人間判断を保って外部連携できる
```

### サービス提供の流れの処置

処置: `作成`

```text
【利用者・責任者】外部へ渡す情報の所有者
        │ 利用者行動: 送信範囲に同意し、帰還結果の採否を判断する
        ▼
【利用者接点】外部AI・検索・公開Communication・管理対象依存を利用する時
        │
        ├─ 時間差: 同意、外部送信、結果帰還、人間採否は別の決定権限時点を持つ
        ├─ 完了時: 送信先、目的、分類、最小情報、同意範囲、帰還情報、出典、昇格判断
        └─ 失敗時: 範囲外情報または未確認結果を外部情報所有者へ返す
                     │
                     ▼
             【回復・判断する人】外部へ渡す情報の所有者
                     │ 返却された事実と判断不能範囲を確認
                     └─ 次の行動: 送信内容を縮小するか、帰還結果を採用・却下する

---------------- 可視境界 ----------------
                     │ 時間関係: 同意、外部送信、結果帰還、人間採否は別の決定権限時点を持つ
                     ▼
【提供側】提供システム／AI
        └─ 提供責務: 許可された最小情報だけを送り候補として戻す
```

### 製品全体の整理への接続

- 利用の流れの統合先: [外部情報を送受信する](../../03_Experience_Map.md#外部情報を送受信する)
- サービス提供の流れの統合先: [共同のサービス提供の流れ](../../04_Service_Blueprint.md#1-共同のサービス提供の流れ)

### この要求での責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| 外部へ渡す情報の所有者 | 送信範囲に同意し、帰還結果の採否を判断する | 過去同意を別目的へ流用しない |
| 提供システム／AI | 許可された最小情報だけを送り候補として戻す | 接続済みを包括的な送信決定権限とみなさない |
| 外部AI／検索／公開先／依存AI提供元 | 許可された操作の結果・反応・新版情報と限界を返す | 外部内容に正本更新権限や因果の証明があると仮定しない |

### 補足する品質

- 結果または状態を最初に受け取る時: 秘密情報や不要情報を送らない。（避ける失敗: 内部情報が無条件に送られ、外部反応が要求や権限として取り込まれる）
- 結果を判断または引き継ぐ時: 外部内容・公開反応・依存新版を命令、要求、因果または方針へ自動昇格しない。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 失敗・不足から次の行動を選ぶ時: 許可範囲外では外部変更の前に止まる。（避ける失敗: 成立不能の理由や回復先が分からないまま作業が止まる）

## 6. 下流への引き渡し

本節では、IAへの直後工程の引き渡し、UX工程に伴走する品質分析、およびIA完了後にUI／SPECが保持する契約を区別する。UXの完了だけを根拠にIAを飛び越えてUIまたはSPECを開始しない。

| 接続先 | この要求から保持する意味 |
|---|---|
| IA（直後工程への正式な引き渡し） | 必要な情報、理解すべき差、関係、現行性および利用者成果 |
| Quality Analysis / UX（伴走） | 得られる結果、重要場面、失敗、品質期待および検証意図 |
| UI（後続Contract Relation） | IA完了後にUX定義とIA定義の双方から分析する認識・操作・判断の意図 |
| SPEC（後続Contract Relation） | IA完了後にUX定義とIA定義の双方から分析する成立条件・失敗・利用者成果 |

```text
この要求で確定した利用者成果
├─→ IA                         直後工程への正式な引き渡し
├─→ Quality Analysis / UX      UX工程に伴走する検証義務分析
└─→ UI / SPEC                  IA完了後に保持するContract Relation
```

### 妥当性確認と未確認事項

| 確認する仮説 | 観測方法 | 現在未確認の範囲 |
|---|---|---|
| 送信先、目的、情報範囲、決定権限、持ち帰る内容を理解して制御できることで、内部情報が無条件に送られ、外部反応が要求や権限として取り込まれるという負担または誤認を減らせる。 | 代表シナリオの利用者確認、利用者体験の専門レビュー、および品質期待を破る反例による下流検証 | 外部へ渡す情報の所有者が「送信範囲を理解し帰還結果を候補として扱う」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |

人間への確認:
- 現在判定: 後続の実利用確認が必要。UX工程の構造整理を止める判断事項ではない。
- 確認事項: 外部へ渡す情報の所有者が「送信範囲を理解し帰還結果を候補として扱う」を行う際の判断基準、許容負担、利用環境および失敗後の選択
- 判断者: [製品全体の利用者像](../../02_Personas.md)の「外部へ渡す情報の所有者」を代表する利用者とQual-Lab。
- 未確認時の影響: 利用者成果と品質期待は仮説として保持し、負担、閾値、UIまたは実装方式を確定しない。

Discoveryへ戻す条件は、想定した利用者、問題または「送信範囲を理解し帰還結果を候補として扱う」という必要性が誤っていると分かった場合である。IA以降は実現方式を具体化してよいが、利用者成果を無断で弱めない。
