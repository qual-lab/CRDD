# REQ-000030の利用者体験分析

成果物種別: UX分析

状態: UX再統合済み・独立再レビュー待ち
分析対象: [REQ-000030 段階的実境界試験と回帰選択](../../../01_Discovery/Definitions/REQ-000030/requirement.md)

## 1. 要求の一次分析

```text
UT・IT・E2Eを区別せず繰り返し、失敗原因と残る不確実性が分からない
        ↓
解決策を先に固定せず、人の仕事として読み替える
        ↓
利用者に必要なこと
試験層ごとの保証と未確認範囲を理解する
```

実装者・品質確認者が「最終E2E前に外部境界の問題を局所化できる」状態へ進めないことを問題として扱う。

| 観点 | 内容 |
|---|---|
| 解決する問題 | UT・IT・E2Eを区別せず繰り返し、失敗原因と残る不確実性が分からない |
| 利用者に必要なこと | 試験層ごとの保証と未確認範囲を理解する |
| 対象範囲 | 変更担当者、リリース判断者が、「UT・IT・E2Eを区別せず繰り返し、失敗原因と残る不確実性が分からない」状態から「どの成立条件をどの試験で確認し、何が未確認か理解して次の検証を選べる」状態へ移る場面 |
| 対象外 | 具体的な画面、データ構造、実装方式および数値閾値の確定 |

## 3. 利用者に起きる変化

```text
変更前
────────────────
- UT・IT・E2Eを区別せず繰り返し、失敗原因と残る不確実性が分からない
        │
        │ 段階的実境界試験と回帰選択が変える体験
        ▼
変更後
────────────────
- どの成立条件をどの試験で確認し、何が未確認か理解して次の検証を選べる
```

段階的実境界試験と回帰選択は、単に内部方式を成立させる要求ではない。「UT・IT・E2Eを区別せず繰り返し、失敗原因と残る不確実性が分からない」状態から、「どの成立条件をどの試験で確認し、何が未確認か理解して次の検証を選べる」状態へ変わり、利用者が次の判断へ進めることまでを体験として扱う。

実装者・品質確認者が試験層ごとの保証と未確認範囲を理解することで、最終E2E前に外部境界の問題を局所化できるようになることを守る。

## 4. 利用者成果への統合

```text
REQ-000030
   │
   └─ New  → UX-000026 試験層と現在の保証範囲を理解して選ぶ
```

| 利用者成果 | 処置 | 判断理由 | この要求が補う内容 |
|---|---|---|---|
| 試験層と現在の保証範囲を理解して選ぶ | `New → UX-000026` | 本要求が「各試験層が確認したこと・未確認範囲・時間や費用を理解し、必要な検証と高負荷試験の実行有無を選べる」という独立した利用者成果を最初に定義する。 | UTからRTまでの対象と回帰選択を組み立てることが、この要求固有の成立条件になる |

`Same`／`New`は技術用語の近さや件数目標では決めない。「利用者は、どの状況で、何をするためにシステムと関わり、何ができるようになるか」が同じかを比較する。提供能力、必要情報、品質、妥当性確認または下流の実現要素は、独立UXへ分割せず対応する成果の成立条件として保持する。

## 5. 重要な体験

### この要求での利用の流れ

```text
変更の検証計画を作る時
        ↓
UTからRTまでの対象と回帰選択を組み立てる
        │
        ├─ ★ 重要場面: 外部境界を結合する各段階
        ├─ ⚠ 失敗:  単発成功や試験件数から一連の状態変化全体を保証する
        └─ ✓ 守る品質:  開始から清掃まで段階的に反証する
        ↓
最終E2E前に外部境界の問題を局所化できる
```

### サービス提供の流れの処置

処置: `作成`

```text
【利用者・責任者】CRDD作成者・保守者
        │ 利用者行動: 変更意味と確認したい保証を示す
        ▼
【利用者接点】変更の検証計画を作る時
        │
        ├─ 時間差: 各試験層は段階的に実行され、上位試験前に下位境界の結果を得る
        ├─ 完了時: 試験層、確認済み保証、未確認範囲、費用、実行決定権限
        └─ 失敗時: 未確認の外部境界と高負荷試験の実行判断を人間の決定権限者へ返す
                     │
                     ▼
             【回復・判断する人】人間の決定権限者
                     │ 返却された事実と判断不能範囲を確認
                     └─ 次の行動: 不足試験を追加するか、未実行を明示して次完了条件を判断する

---------------- 可視境界 ----------------
                     │ 時間関係: 各試験層は段階的に実行され、上位試験前に下位境界の結果を得る
                     ▼
【提供側】品質確認者
        └─ 提供責務: 外部境界一連の状態変化を段階的に結合し保証範囲を示す
```

- 利用の流れの統合先: [標準を変更・検証・公開する](../../03_Experience_Map.md#標準を変更検証公開する)
- サービス提供の流れの統合先: [共同のサービス提供の流れ](../../04_Service_Blueprint.md#1-共同のサービス提供の流れ)

### この要求での責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| CRDD作成者・保守者 | 変更意味と確認したい保証を示す | 試験件数だけで検証完了を主張しない |
| 品質確認者 | 外部境界一連の状態変化を段階的に結合し保証範囲を示す | 単発成功を一連の状態変化全体へ一般化しない |
| 人間の決定権限者 | 高負荷試験の費用・時間・代替根拠を踏まえ実行有無を決める | 未指示のPT／LTを自動実行しない |

### 補足する品質

- 結果または状態を最初に受け取る時: 試験件数だけで品質を表示しない。（避ける失敗: UT・IT・E2Eを区別せず繰り返し、失敗原因と残る不確実性が分からない）
- 結果を判断または引き継ぐ時: 外部境界は開始から清掃・回復まで確認する。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 失敗・不足から次の行動を選ぶ時: PT／LTを明示指示なしに実行しない。（避ける失敗: 成立不能の理由や回復先が分からないまま作業が止まる）

## 6. 下流への引き渡し

本節では、IAへの直後工程の引き渡し、UX工程に伴走する品質分析、およびIA完了後にUI／SPECが保持する契約を区別する。UXの完了だけを根拠にIAを飛び越えてUIまたはSPECを開始しない。

| 接続先 | この要求から保持する意味 |
|---|---|
| IA（直後工程への正式な引き渡し） | 必要な情報、理解すべき差、関係、現行性および利用者成果 |
| Quality Analysis / UX（伴走） | 得られる結果、重要場面、失敗、品質期待および検証意図 |
| UI（後続Contract Relation） | IA完了後にUX定義とIA定義の双方から分析する認識・操作・判断の意図 |
| SPEC（後続Contract Relation） | IA完了後にUX定義とIA定義の双方から分析する成立条件・失敗・利用者成果 |

```text
この要求で確定した利用者成果
├─→ IA                         直後工程への正式な引き渡し
├─→ Quality Analysis / UX      UX工程に伴走する検証義務分析
└─→ UI / SPEC                  IA完了後に保持するContract Relation
```

### 妥当性確認と未確認事項

| 確認する仮説 | 観測方法 | 現在未確認の範囲 |
|---|---|---|
| どの成立条件をどの試験で確認し、何が未確認か理解して次の検証を選べることで、UT・IT・E2Eを区別せず繰り返し、失敗原因と残る不確実性が分からないという負担または誤認を減らせる。 | 代表シナリオの利用者確認、利用者体験の専門レビュー、および品質期待を破る反例による下流検証 | CRDD作成者・保守者が「試験層ごとの保証と未確認範囲を理解する」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |

人間への確認:
- 現在判定: 後続の実利用確認が必要。UX工程の構造整理を止める判断事項ではない。
- 確認事項: CRDD作成者・保守者が「試験層ごとの保証と未確認範囲を理解する」を行う際の判断基準、許容負担、利用環境および失敗後の選択
- 判断者: [製品全体の利用者像](../../02_Personas.md)の「CRDD作成者・保守者」を代表する利用者とQual-Lab。
- 未確認時の影響: 利用者成果と品質期待は仮説として保持し、負担、閾値、UIまたは実装方式を確定しない。

Discoveryへ戻す条件は、想定した利用者、問題または「試験層ごとの保証と未確認範囲を理解する」という必要性が誤っていると分かった場合である。IA以降は実現方式を具体化してよいが、利用者成果を無断で弱めない。
