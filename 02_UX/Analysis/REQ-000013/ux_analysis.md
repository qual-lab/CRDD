# REQ-000013の利用者体験分析

成果物種別: UX分析

状態: UX再統合済み・独立再レビュー待ち
分析対象: [REQ-000013 根拠と不完全性を保つ複数プロジェクトの一覧](../../../01_Discovery/Definitions/REQ-000013/requirement.md)

## 1. 要求の一次分析

```text
プロジェクトごとの資料を開いて比較表を手で作る／集計結果を根拠不明のまま受け取る
        ↓
解決策を先に固定せず、人の仕事として読み替える
        ↓
利用者に必要なこと
複数プロジェクトを根拠付きで比較する
```

この要求で解くのは機能の有無だけではない。経営・管理層／複数プロジェクトの一覧利用者が「重要差分から必要なプロジェクトだけを掘り下げられる」状態へ進めないことを問題として扱う。具体的な画面、データ構造、API、構成要素または数値閾値はここで確定しない。

| 観点 | 内容 |
|---|---|
| 解決する問題 | プロジェクトごとの資料を開いて比較表を手で作る／集計結果を根拠不明のまま受け取る |
| 利用者に必要なこと | 複数プロジェクトを根拠付きで比較する |
| 対象範囲 | 複数プロジェクトを比較するPM、経営・管理層が、「プロジェクトごとの資料を開いて比較表を手で作る」状態から「許可されたプロジェクトの要点を同じ観点で比較する」状態へ移る場面 |
| 対象外 | 具体的な画面、データ構造、実装方式および数値閾値の確定 |

## 2. 利用者・目標・成果

```text

        │
        │ 望んでいる
        ▼
複数プロジェクトを根拠付きで比較する
        │
        │ その結果として
        ▼

```

| 項目 | 内容 |

| 目的 | 複数プロジェクトを根拠付きで比較する |

## 3. 利用者に起きる変化

```text
変更前
────────────────
- プロジェクトごとの資料を開いて比較表を手で作る
- 集計結果を根拠不明のまま受け取る
        │
        │ 根拠と不完全性を保つ複数プロジェクトの一覧が変える体験
        ▼
変更後
────────────────
- 許可されたプロジェクトの要点を同じ観点で比較する
- 注意事項からプロジェクト、情報源、観測時点へ段階的に辿る
```

複数プロジェクトを比較する人には要約が必要だが、単一Scoreや色だけでは、なぜ注意が必要か、どの情報が欠けているかを判断できない。

この変化で守るのは操作手順ではない。経営・管理層／複数プロジェクトの一覧利用者が複数プロジェクトを根拠付きで比較することで、重要差分から必要なプロジェクトだけを掘り下げられるようになることを守る。

## 4. 利用者成果への統合

```text
REQ-000013
   │
   └─ New  → UX-000015 複数プロジェクトを根拠付きで比較する
```

| 利用者成果 | 処置 | 判断理由 | この要求が補う内容 |
|---|---|---|---|
| 複数プロジェクトを根拠付きで比較する | `New → UX-000015` | 本要求が「許可されたプロジェクトの重要差を比較し、網羅範囲と根拠を保ったまま必要なプロジェクトだけを掘り下げられる」という独立した利用者成果を最初に定義する。 | 許可されたプロジェクトの状態と網羅範囲を比較することが、この要求固有の成立条件になる |

`Same`／`New`は技術用語の近さや件数目標では決めない。「利用者は、どの状況で、何をするためにシステムと関わり、何ができるようになるか」が同じかを比較する。提供能力、必要情報、品質、妥当性確認または下流の実現要素は、独立UXへ分割せず対応する成果の成立条件として保持する。

## 5. 重要な体験

### この要求での利用の流れ

```text
複数プロジェクトの一覧の優先度を判断する時
        ↓
許可されたプロジェクトの状態と網羅範囲を比較する
        │
        ├─ ★ 重要場面: 要約から優先判断へ進む直前
        ├─ ⚠ 失敗:  単一Scoreや欠測した集計で健全性を断定する
        └─ ✓ 守る品質:  比較値から根拠・古さ・不足へ戻れる
        ↓
重要差分から必要なプロジェクトだけを掘り下げられる
```

### サービス提供の流れの処置

処置: `作成`

```text
【利用者・責任者】経営・管理層
        │ 利用者行動: 網羅範囲差を踏まえて優先判断と掘り下げ先を選ぶ
        ▼
【利用者接点】複数プロジェクトの一覧の優先度を判断する時
        │
        ├─ 時間差: プロジェクトごとの観測時点が異なり、複数プロジェクトの一覧比較まで更新差が生じる
        ├─ 完了時: プロジェクト別網羅範囲、観測時点、重要差、開示不能範囲
        └─ 失敗時: 比較不能なプロジェクトと不足情報源を各プロジェクトの正本責任者へ返す
                     │
                     ▼
             【回復・判断する人】各プロジェクトの正本責任者
                     │ 返却された事実と判断不能範囲を確認
                     └─ 次の行動: 比較範囲を狭めるか、対象プロジェクトを掘り下げる

---------------- 可視境界 ----------------
                     │ 時間関係: プロジェクトごとの観測時点が異なり、複数プロジェクトの一覧比較まで更新差が生じる
                     ▼
【提供側】提供システム
        └─ 提供責務: 許可範囲だけを比較し根拠へ戻れるようにする
```

この図は、利用者行動、利用者が観測する接点、提供責務および失敗時の引き渡しを示す。内部構成要素の構造やプロトコルは下流工程で具体化する。

### 製品全体の整理への接続

- 利用の流れの統合先: [複数プロジェクトを比較する](../../03_Experience_Map.md#複数プロジェクトを比較する)
- サービス提供の流れの統合先: [共同のサービス提供の流れ](../../04_Service_Blueprint.md#1-共同のサービス提供の流れ)
- 横断成果物はこの個別分析から共通パターンを合成する。この要求での利用の流れ、責任境界または品質の代替にはしない。

### この要求での責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| 各プロジェクトの正本責任者 | 開示可能な状態と根拠を現行性付きで提供する | 他プロジェクトの状態を代理して確定しない |
| 経営・管理層 | 網羅範囲差を踏まえて優先判断と掘り下げ先を選ぶ | 単一Scoreや欠測した集計だけで健全性を断定しない |
| 提供システム | 許可範囲だけを比較し根拠へ戻れるようにする | 非開示プロジェクトの存在または内容を漏らさない |

### 補足する品質

- 結果または状態を最初に受け取る時: 非開示プロジェクトの存在や件数を漏らさない。（避ける失敗: プロジェクトごとの資料を開いて比較表を手で作る）
- 結果を判断または引き継ぐ時: プロジェクトごとの観測時点と網羅範囲差を比較時に保持する。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 結果を判断または引き継ぐ時: 単一Scoreだけで健全性や優先順位を確定しない。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 失敗・不足から次の行動を選ぶ時: 要約から判断根拠へ戻れる。（避ける失敗: 成立不能の理由や回復先が分からないまま作業が止まる）


## 6. 下流への引き渡し

```text
この要求で確定した利用者成果
        │
        ├─→ IA: 必要な情報・関係・見つけ方
        ├─→ UI: 誤認させない表示・操作意図
        ├─→ SPEC: 振る舞い・失敗・体験品質の条件
        └─→ Verification: 仮説を破る反例と観測
```

### 妥当性確認と未確認事項

| 確認する仮説 | 観測方法 | 現在未確認の範囲 |
|---|---|---|
| 許可されたプロジェクトの要点を同じ観点で比較する／注意事項からプロジェクト、情報源、観測時点へ段階的に辿ることで、プロジェクトごとの資料を開いて比較表を手で作るという負担または誤認を減らせる。 | 代表シナリオの利用者確認、利用者体験の専門レビュー、および品質期待を破る反例による下流検証 | 経営・管理層が「複数プロジェクトを根拠付きで比較する」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |

### 工程別の引き渡し

| 引き渡し先 | 具体化する義務 |
|---|---|
| 下流工程 | IAはプロジェクト比較軸、情報源の網羅範囲、情報の新しさおよび根拠導線をモデル化する。Verificationは不完全なプロジェクト集合を完全複数プロジェクトの一覧として表示しないことを確認する。 |

Discoveryへ戻す条件は、想定した利用者、問題または「複数プロジェクトを根拠付きで比較する」という必要性が誤っていると分かった場合である。下流は実現方式を具体化してよいが、「重要差分から必要なプロジェクトだけを掘り下げられる」という成果を無断で弱めない。
