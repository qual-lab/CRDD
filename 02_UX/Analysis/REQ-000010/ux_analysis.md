# REQ-000010の利用者体験分析

成果物種別: UX分析

状態: UX再統合済み・独立再レビュー待ち
分析対象: [REQ-000010 Workbench・MCP・CLIの公開契約共有](../../../01_Discovery/Definitions/REQ-000010/requirement.md)

## 1. 要求の一次分析

```text
UI、AI、CLIで状態名や操作結果が違う／UIだけが持つ直接更新を信頼する
        ↓
解決策を先に固定せず、人の仕事として読み替える
        ↓
利用者に必要なこと
入口が違っても同じプロジェクト操作を行う
```

この要求で解くのは機能の有無だけではない。Workbench・MCP・CLI利用者が「入口固有の状態や意味を覚えず使い分けられる」状態へ進めないことを問題として扱う。具体的な画面、データ構造、API、構成要素または数値閾値はここで確定しない。

| 観点 | 内容 |
|---|---|
| 解決する問題 | UI、AI、CLIで状態名や操作結果が違う／UIだけが持つ直接更新を信頼する |
| 利用者に必要なこと | 入口が違っても同じプロジェクト操作を行う |
| 対象範囲 | Workbench、MCPまたはCLIからCRDDを使う人が、「UI、AI、CLIで状態名や操作結果が違う」状態から「入口が違っても同じ状態、判断境界、結果へ到達する」状態へ移る場面 |
| 対象外 | 具体的な画面、データ構造、実装方式および数値閾値の確定 |

## 3. 利用者に起きる変化

```text
変更前
────────────────
- UI、AI、CLIで状態名や操作結果が違う
- UIだけが持つ直接更新を信頼する
        │
        │ Workbench・MCP・CLIの公開契約共有が変える体験
        ▼
変更後
────────────────
- 入口が違っても同じ状態、判断境界、結果へ到達する
- 所有正本のCommandまたは候補を通じて反映する
```

同じプロジェクト状態が入口ごとに違う意味や結果を返すと、利用者は入口固有のルールを覚え、どれを信じるか判断しなければならない。Workbenchは別の業務実装ではなく、人向けの薄い入口である必要がある。

この変化で守るのは操作手順ではない。Workbench・MCP・CLI利用者が入口が違っても同じプロジェクト操作を行うことで、入口固有の状態や意味を覚えず使い分けられるようになることを守る。

## 4. 利用者成果への統合

```text

   └─ Same → UX-000012 入口を変えても同じ仕事を続ける
```

| 利用者成果 | 処置 | 判断理由 | この要求が補う内容 |
|---|---|---|---|
| 入口を変えても同じ仕事を続ける | `Same → UX-000012` | 既存UXの利用者: 開発者<br>現在要求の利用者: プロジェクト運営者／PM<br>利用者の差: 既存UXの「開発者」に対して現在要求は「プロジェクト運営者／PM」だが、両者とも「入口を変えても同じ仕事を続ける」を利用・確認する当事者であり、役割差だけでは別の利用者成果にならない<br>既存UXの利用のきっかけ: 利用する接続方式を選ぶ時<br>現在要求の利用のきっかけ: 利用場面に合う入口を選ぶ時<br>利用のきっかけの差: 既存UXの「利用する接続方式を選ぶ時」に対して現在要求は「利用場面に合う入口を選ぶ時」を具体化するが、同じ「入口を変えても同じ仕事を続ける」が必要になる開始条件の差であり、独立した成果境界ではない<br>既存UXで得られる結果: Workbench、MCP、CLIまたはAIの入口を変えても、同じ入力・権限・状態・結果を用いて仕事を続けられる<br>現在要求で得られる結果: Workbench・MCP・CLIの入口を変えても、同じ入力・権限・状態・結果でプロジェクト操作を続けられる<br>得られる結果の差: 現在要求は「入口を変えても同じ仕事を続ける」をこの要求の場面で成立させる得られる結果を具体化しており、要求全体の中心となる利用者成果や別のUX成果へ置き換えていない<br>既存UXでの失敗: Workbench・MCP・CLIで状態や結果の意味が変わり、入口ごとに仕事を読み替える<br>現在要求での失敗: 入口ごとに別の業務ロジックまたは結果契約が動き、同じプロジェクト操作を継続できない<br>失敗の差: 現在要求は公開契約共有という成立手段を具体化するが、入口変更で仕事が途切れる失敗は同じである<br>同じ利用者成果へ統合できる理由: 公開契約共有は同じ仕事を継続するための機能上の条件であり、別の利用者成果ではない | 共通の公開アプリケーション契約へ要求することが、この要求固有の成立条件になる |

`Same`／`New`は技術用語の近さや件数目標では決めない。「利用者は、どの状況で、何をするためにシステムと関わり、何ができるようになるか」が同じかを比較する。提供能力、必要情報、品質、妥当性確認または下流の実現要素は、独立UXへ分割せず対応する成果の成立条件として保持する。

## 5. 重要な体験

### この要求での利用の流れ

```text
利用場面に合う入口を選ぶ時
        ↓
共通の公開アプリケーション契約へ要求する
        │
        ├─ ★ 重要場面: 候補・採用・外部への変更を選ぶ時
        ├─ ⚠ 失敗:  入口ごとに別の業務ロジックが動く
        └─ ✓ 守る品質:  同じ入力・権限へ同じ構造結果を返す
        ↓
入口固有の状態や意味を覚えず使い分けられる
```

### サービス提供の流れの処置

処置: `作成`

```text
【利用者・責任者】プロジェクトを操作する人（プロジェクト運営者／PM）
        │ 利用者行動: 入口が違っても同じプロジェクト操作を行う
        ▼
【利用者接点】利用場面に合う入口を選ぶ時
        │
        ├─ 時間差: 入口ごとの要求・応答内で同値性を確認し、独立した回復一連の状態変化は持たない
        ├─ 完了時: 同じ入力・権限・状態・結果と入口固有表現
        └─ 失敗時: 意味が一致しない入口と差分項目を運用・確認者へ返す
                     │
                     ▼
             【回復・判断する人】運用・確認者
                     │ 返却された事実と判断不能範囲を確認
                     └─ 次の行動: 別入口で同じ仕事を続けるか、不一致を修正対象にする

---------------- 可視境界 ----------------
                     │ 時間関係: 入口ごとの要求・応答内で同値性を確認し、独立した回復一連の状態変化は持たない
                     ▼
【提供側】提供システム
        └─ 提供責務: 入口間で入力・決定権限・状態・結果の意味を保つ
```

この図は、利用者行動、利用者が観測する接点、提供責務および失敗時の引き渡しを示す。内部構成要素の構造やプロトコルは下流工程で具体化する。

### 製品全体の整理への接続

- 利用の流れの統合先: [リポジトリで日常作業を進める](../../03_Experience_Map.md#リポジトリで日常作業を進める)
- サービス提供の流れの統合先: [共同のサービス提供の流れ](../../04_Service_Blueprint.md#1-共同のサービス提供の流れ)
- 横断成果物はこの個別分析から共通パターンを合成する。この要求での利用の流れ、責任境界または品質の代替にはしない。

### この要求での責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| 利用者 | 場面に合う入口を選び、同じプロジェクト操作を続ける | 入口ごとの内部状態や別手順を覚えることを要求されない |
| 提供システム | 入口間で入力・決定権限・状態・結果の意味を保つ | 入口固有の第二正本を作らない |
| 運用・確認者 | 各入口の同値性と失敗時の差を確認する | 表示の類似だけで意味同値と判定しない |

### 補足する品質

- 結果または状態を最初に受け取る時: 接続成功と、内容取得、候補作成、採用、外部への変更許可を区別する。（避ける失敗: UI、AI、CLIで状態名や操作結果が違う）
- 結果を判断または引き継ぐ時: Workbench内部に第二の正本や独自決定権限判断を持たない。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 結果を判断または引き継ぐ時: Structured 結果を画面・自然言語・CLIで矛盾なく表現する。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 失敗・不足から次の行動を選ぶ時: Surface障害後も所有正本から状態を再取得できる。（避ける失敗: 成立不能の理由や回復先が分からないまま作業が止まる）


## 6. 下流への引き渡し

```text
この要求で確定した利用者成果
        │
        ├─→ IA: 必要な情報・関係・見つけ方
        ├─→ UI: 誤認させない表示・操作意図
        ├─→ SPEC: 振る舞い・失敗・体験品質の条件
        └─→ Verification: 仮説を破る反例と観測
```

### 妥当性確認と未確認事項

| 確認する仮説 | 観測方法 | 現在未確認の範囲 |
|---|---|---|
| 入口が違っても同じ状態、判断境界、結果へ到達する／所有正本のCommandまたは候補を通じて反映することで、UI、AI、CLIで状態名や操作結果が違うという負担または誤認を減らせる。 | 代表シナリオの利用者確認、利用者体験の専門レビュー、および品質期待を破る反例による下流検証 | プロジェクト運営者／PMが「入口が違っても同じプロジェクト操作を行う」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |

### 工程別の引き渡し

| 引き渡し先 | 具体化する義務 |
|---|---|
| 下流工程 | IAは公開結果と表示状態を分ける。UI／SPECは同じ正式な状態から表示と操作可否を導き、Architectureは公開アプリケーション契約を唯一の意味境界にする。 |

Discoveryへ戻す条件は、想定した利用者、問題または「入口が違っても同じプロジェクト操作を行う」という必要性が誤っていると分かった場合である。下流は実現方式を具体化してよいが、「入口固有の状態や意味を覚えず使い分けられる」という成果を無断で弱めない。
