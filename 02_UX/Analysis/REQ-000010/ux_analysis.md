# REQ-000010の利用者体験分析

成果物種別: UX分析

状態: UX再統合済み・独立再レビュー待ち
分析対象: [REQ-000010 Workbench・MCP・CLIの公開契約共有](../../../01_Discovery/Definitions/REQ-000010/requirement.md)

## 1. 要求の一次分析

```text
UI、AI、CLIで状態名や操作結果が違う／UIだけが持つ直接更新を信頼する
        ↓
解決策を先に固定せず、人の仕事として読み替える
        ↓
利用者に必要なこと
入口が違っても同じプロジェクト操作を行う
```

Workbench・MCP・CLI利用者が「入口固有の状態や意味を覚えず使い分けられる」状態へ進めないことを問題として扱う。

| 観点 | 内容 |
|---|---|
| 解決する問題 | UI、AI、CLIで状態名や操作結果が違う／UIだけが持つ直接更新を信頼する |
| 利用者に必要なこと | 入口が違っても同じプロジェクト操作を行う |
| 対象範囲 | Workbench、MCPまたはCLIからCRDDを使う人が、「UI、AI、CLIで状態名や操作結果が違う」状態から「入口が違っても同じ状態、判断境界、結果へ到達する」状態へ移る場面 |
| 対象外 | 具体的な画面、データ構造、実装方式および数値閾値の確定 |

## 3. 利用者に起きる変化

```text
変更前
────────────────
- UI、AI、CLIで状態名や操作結果が違う
- UIだけが持つ直接更新を信頼する
        │
        │ Workbench・MCP・CLIの公開契約共有が変える体験
        ▼
変更後
────────────────
- 入口が違っても同じ状態、判断境界、結果へ到達する
- 所有正本のCommandまたは候補を通じて反映する
```

同じプロジェクト状態が入口ごとに違う意味や結果を返すと、利用者は入口固有のルールを覚え、どれを信じるか判断しなければならない。Workbenchは別の業務実装ではなく、人向けの薄い入口である必要がある。

Workbench・MCP・CLI利用者が入口が違っても同じプロジェクト操作を行うことで、入口固有の状態や意味を覚えず使い分けられるようになることを守る。

## 4. 利用者成果への統合

```text
REQ-000010
   │
   └─ Same → UX-000012 入口を変えても同じ仕事を続ける
```

| 利用者成果 | 処置 | 判断理由 | この要求が補う内容 |
|---|---|---|---|
| 入口を変えても同じ仕事を続ける | `Same → UX-000012` | 4軸比較で同じ利用者成果と判断した。詳細は次の比較を参照。 | 共通の公開アプリケーション契約へ要求することが、この要求固有の成立条件になる |

### Same判断の比較

#### 入口を変えても同じ仕事を続ける

比較対象: `UX-000012`

比較元: `REQ-000006`でこのUXを最初に`New`とした固有記載。得られる結果は同分析のUX固有行、他の軸は同分析と初版Definitionの一致を確認して固定した。

| 比較軸 | 既存UX | 現在の要求 | 差と統合判断 |
|---|---|---|---|
| 担い手 | 開発者 | プロジェクト運営者／PM | 既存UXの「開発者」に対して現在要求は「プロジェクト運営者／PM」だが、両者とも「入口を変えても同じ仕事を続ける」を利用・確認する当事者であり、役割差だけでは別の利用者成果にならない |
| 利用のきっかけ | 利用する接続方式を選ぶ時 | 利用場面に合う入口を選ぶ時 | 既存UXの「利用する接続方式を選ぶ時」に対して現在要求は「利用場面に合う入口を選ぶ時」を具体化するが、同じ「入口を変えても同じ仕事を続ける」が必要になる開始条件の差であり、独立した成果境界ではない |
| 得られる結果 | stdio MCPとlocalhost HTTPのどちらでも、同じ入力・権限・状態・結果で仕事を続けられる | Workbench・MCP・CLIの入口を変えても、同じ入力・権限・状態・結果でプロジェクト操作を続けられる | 現在要求は通信方式間の同値性をWorkbench・MCP・CLIへ広げるが、入口差を読み替えず同じ仕事を続ける中心成果は同じである |
| 避ける失敗 | 接続方式ごとに状態や結果が変わる | 入口ごとに別の業務ロジックまたは結果契約が動き、同じプロジェクト操作を継続できない | 最初のNew分析で確認された失敗に対し、現在要求は「入口ごとに別の業務ロジックまたは結果契約が動き、同じプロジェクト操作を継続できない」へ具体化するが、中心成果を妨げる同じ失敗として扱える |

統合理由: 公開契約共有は同じ仕事を継続するための機能上の条件であり、別の利用者成果ではない

`Same`／`New`は技術用語の近さや件数目標では決めない。「利用者は、どの状況で、何をするためにシステムと関わり、何ができるようになるか」が同じかを比較する。提供能力、必要情報、品質、妥当性確認または下流の実現要素は、独立UXへ分割せず対応する成果の成立条件として保持する。

## 5. 重要な体験

### この要求での利用の流れ

```text
利用場面に合う入口を選ぶ時
        ↓
共通の公開アプリケーション契約へ要求する
        │
        ├─ ★ 重要場面: 候補・採用・外部作用（Effect）を選ぶ時
        ├─ ⚠ 失敗:  入口ごとに別の業務ロジックが動く
        └─ ✓ 守る品質:  同じ入力・権限へ同じ構造結果を返す
        ↓
入口固有の状態や意味を覚えず使い分けられる
```

### サービス提供の流れの処置

処置: `作成`

```text
【利用者・責任者】プロジェクトを操作する人（プロジェクト運営者／PM）
        │ 利用者行動: 入口が違っても同じプロジェクト操作を行う
        ▼
【利用者接点】利用場面に合う入口を選ぶ時
        │
        ├─ 時間差: 入口ごとの要求・応答内で同値性を確認し、独立した回復一連の状態変化は持たない
        ├─ 完了時: 同じ入力・権限・状態・結果と入口固有表現
        └─ 失敗時: 意味が一致しない入口と差分項目を運用・確認者へ返す
                     │
                     ▼
             【回復・判断する人】運用・確認者
                     │ 返却された事実と判断不能範囲を確認
                     └─ 次の行動: 別入口で同じ仕事を続けるか、不一致を修正対象にする

---------------- 可視境界 ----------------
                     │ 時間関係: 入口ごとの要求・応答内で同値性を確認し、独立した回復一連の状態変化は持たない
                     ▼
【提供側】提供システム
        └─ 提供責務: 入口間で入力・決定権限・状態・結果の意味を保つ
```

### 製品全体の整理への接続

- 利用の流れの統合先: [リポジトリで日常作業を進める](../../03_Experience_Map.md#リポジトリで日常作業を進める)
- サービス提供の流れの統合先: [共同のサービス提供の流れ](../../04_Service_Blueprint.md#1-共同のサービス提供の流れ)

### この要求での責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| 利用者 | 場面に合う入口を選び、同じプロジェクト操作を続ける | 入口ごとの内部状態や別手順を覚えることを要求されない |
| 提供システム | 入口間で入力・決定権限・状態・結果の意味を保つ | 入口固有の第二正本を作らない |
| 運用・確認者 | 各入口の同値性と失敗時の差を確認する | 表示の類似だけで意味同値と判定しない |

### 補足する品質

- 結果または状態を最初に受け取る時: 接続成功と、内容取得、候補作成、採用、外部作用（Effect）許可を区別する。（避ける失敗: UI、AI、CLIで状態名や操作結果が違う）
- 結果を判断または引き継ぐ時: Workbench内部に第二の正本や独自決定権限判断を持たない。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 結果を判断または引き継ぐ時: Structured 結果を画面・自然言語・CLIで矛盾なく表現する。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 失敗・不足から次の行動を選ぶ時: Surface障害後も所有正本から状態を再取得できる。（避ける失敗: 成立不能の理由や回復先が分からないまま作業が止まる）

## 6. 下流への引き渡し

本節では、IAへの直後工程の引き渡し、UX工程に伴走する品質分析、およびIA完了後にUI／SPECが保持する契約を区別する。UXの完了だけを根拠にIAを飛び越えてUIまたはSPECを開始しない。

| 接続先 | この要求から保持する意味 |
|---|---|
| IA（直後工程への正式な引き渡し） | 必要な情報、理解すべき差、関係、現行性および利用者成果 |
| Quality Analysis / UX（伴走） | 得られる結果、重要場面、失敗、品質期待および検証意図 |
| UI（後続Contract Relation） | IA完了後にUX定義とIA定義の双方から分析する認識・操作・判断の意図 |
| SPEC（後続Contract Relation） | IA完了後にUX定義とIA定義の双方から分析する成立条件・失敗・利用者成果 |

```text
この要求で確定した利用者成果
├─→ IA                         直後工程への正式な引き渡し
├─→ Quality Analysis / UX      UX工程に伴走する検証義務分析
└─→ UI / SPEC                  IA完了後に保持するContract Relation
```

### 妥当性確認と未確認事項

| 確認する仮説 | 観測方法 | 現在未確認の範囲 |
|---|---|---|
| 入口が違っても同じ状態、判断境界、結果へ到達する／所有正本のCommandまたは候補を通じて反映することで、UI、AI、CLIで状態名や操作結果が違うという負担または誤認を減らせる。 | 代表シナリオの利用者確認、利用者体験の専門レビュー、および品質期待を破る反例による下流検証 | プロジェクト運営者／PMが「入口が違っても同じプロジェクト操作を行う」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |

人間への確認:
- 現在判定: 後続の実利用確認が必要。UX工程の構造整理を止める判断事項ではない。
- 確認事項: プロジェクト運営者／PMが「入口が違っても同じプロジェクト操作を行う」を行う際の判断基準、許容負担、利用環境および失敗後の選択
- 判断者: [製品全体の利用者像](../../02_Personas.md)の「プロジェクト運営者／PM」を代表する利用者とQual-Lab。
- 未確認時の影響: 利用者成果と品質期待は仮説として保持し、負担、閾値、UIまたは実装方式を確定しない。

Discoveryへ戻す条件は、想定した利用者、問題または「入口が違っても同じプロジェクト操作を行う」という必要性が誤っていると分かった場合である。IA以降は実現方式を具体化してよいが、利用者成果を無断で弱めない。
