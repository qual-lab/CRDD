# REQ-000033の利用者体験分析

成果物種別: UX分析

状態: UX再統合済み・独立再レビュー待ち
分析対象: [REQ-000033 作業の一連の流れと根拠所有の分離](../../../01_Discovery/Definitions/REQ-000033/requirement.md)

## 1. 要求の一次分析

```text
Roadmap、CHG、根拠、品質の置場と役割が重なり、現在状態と履歴を探し回る
        ↓
解決策を先に固定せず、人の仕事として読み替える
        ↓
利用者に必要なこと
作業・変更・根拠・品質を役割別に辿る
```

この要求で解くのは機能の有無だけではない。CRDD保守者・監査者が「変更理由と全影響パスを重複なく確認できる」状態へ進めないことを問題として扱う。具体的な画面、データ構造、API、構成要素または数値閾値はここで確定しない。

| 観点 | 内容 |
|---|---|
| 解決する問題 | Roadmap、CHG、根拠、品質の置場と役割が重なり、現在状態と履歴を探し回る |
| 利用者に必要なこと | 作業・変更・根拠・品質を役割別に辿る |
| 対象範囲 | 変更を追う人、リリース・品質を判断する人が、「Roadmap、CHG、根拠、品質の置場と役割が重なり、現在状態と履歴を探し回る」状態から「何が未完了か、何を変えたか、何が成立を証明するか、現在品質は何かを役割別に辿れる」状態へ移る場面 |
| 対象外 | 具体的な画面、データ構造、実装方式および数値閾値の確定 |

## 3. 利用者に起きる変化

```text
変更前
────────────────
- Roadmap、CHG、根拠、品質の置場と役割が重なり、現在状態と履歴を探し回る
        │
        │ 作業の一連の流れと根拠所有の分離が変える体験
        ▼
変更後
────────────────
- 何が未完了か、何を変えたか、何が成立を証明するか、現在品質は何かを役割別に辿れる
```

作業の一連の流れと根拠所有の分離は、単に内部方式を成立させる要求ではない。「Roadmap、CHG、根拠、品質の置場と役割が重なり、現在状態と履歴を探し回る」状態から、「何が未完了か、何を変えたか、何が成立を証明するか、現在品質は何かを役割別に辿れる」状態へ変わり、利用者が次の判断へ進めることまでを体験として扱う。

この変化で守るのは操作手順ではない。CRDD保守者・監査者が作業・変更・根拠・品質を役割別に辿ることで、変更理由と全影響パスを重複なく確認できるようになることを守る。

## 4. 利用者成果への統合

```text
REQ-000033
   │
   └─ New  → UX-000029 作業・変更・根拠・品質を迷わず辿る
```

| 利用者成果 | 処置 | 判断理由 | この要求が補う内容 |
|---|---|---|---|
| 作業・変更・根拠・品質を迷わず辿る | `New → UX-000029` | 本要求が「未完了、変更理由、全影響パス、成立根拠および現在品質を役割の違いとともに辿れる」という独立した利用者成果を最初に定義する。 | 各責任者から状態・差分・根拠を接続することが、この要求固有の成立条件になる |

`Same`／`New`は技術用語の近さや件数目標では決めない。「利用者は、どの状況で、何をするためにシステムと関わり、何ができるようになるか」が同じかを比較する。提供能力、必要情報、品質、妥当性確認または下流の実現要素は、独立UXへ分割せず対応する成果の成立条件として保持する。

## 5. 重要な体験

### この要求での利用の流れ

```text
変更の現在地や根拠を調べる時
        ↓
各責任者から状態・差分・根拠を接続する
        │
        ├─ ★ 重要場面: 変更の影響漏れを確認する場面
        ├─ ⚠ 失敗:  同じ説明を複製し代表ファイルだけで済ませる
        └─ ✓ 守る品質:  正本を分け全影響ファイルを列挙する
        ↓
変更理由と全影響パスを重複なく確認できる
```

### サービス提供の流れの処置

処置: `作成`

```text
【利用者・責任者】CRDD作成者・保守者
        │ 利用者行動: 目的に応じて未完了・変更理由・根拠・品質を辿る
        ▼
【利用者接点】変更の現在地や根拠を調べる時
        │
        ├─ 時間差: 各責任者の成果物更新後にChange 表示が再投影される
        ├─ 完了時: Work、Change、全影響パス、根拠、現在品質への参照
        └─ 失敗時: 所有先不明または参照切れの情報を該当成果物責任者へ返す
                     │
                     ▼
             【回復・判断する人】各成果物責任者
                     │ 返却された事実と判断不能範囲を確認
                     └─ 次の行動: 正本を修正するか、現在状態と未完了を明示する

---------------- 可視境界 ----------------
                     │ 時間関係: 各責任者の成果物更新後にChange 表示が再投影される
                     ▼
【提供側】提供システム
        └─ 提供責務: 責任者間のRelationと全影響パスを提示する
```

この図は、利用者行動、利用者が観測する接点、提供責務および失敗時の引き渡しを示す。内部構成要素の構造やプロトコルは下流工程で具体化する。

### 製品全体の整理への接続

- 利用の流れの統合先: [標準を変更・検証・公開する](../../03_Experience_Map.md#標準を変更検証公開する)
- サービス提供の流れの統合先: [共同のサービス提供の流れ](../../04_Service_Blueprint.md#1-共同のサービス提供の流れ)
- 横断成果物はこの個別分析から共通パターンを合成する。この要求での利用の流れ、責任境界または品質の代替にはしない。

### この要求での責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| CRDD作成者・保守者 | 目的に応じて未完了・変更理由・根拠・品質を辿る | 一つの成果物を全情報の正本とみなさない |
| 各成果物責任者 | 担当する状態・差分・根拠を現在の正本として保つ | 他責任者の説明を複製して上書きしない |
| 提供システム | 責任者間のRelationと全影響パスを提示する | 代表ファイルだけで影響範囲を省略しない |

### 補足する品質

- 結果または状態を最初に受け取る時: 同じ説明を複数正本へ複製しない。（避ける失敗: Roadmap、CHG、根拠、品質の置場と役割が重なり、現在状態と履歴を探し回る）
- 結果を判断または引き継ぐ時: CHGから全影響パスを確認できる。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 失敗・不足から次の行動を選ぶ時: 過去根拠を現在状態で上書きしない。（避ける失敗: 成立不能の理由や回復先が分からないまま作業が止まる）


## 6. 下流への引き渡し

```text
この要求で確定した利用者成果
        │
        ├─→ IA: 必要な情報・関係・見つけ方
        ├─→ UI: 誤認させない表示・操作意図
        ├─→ SPEC: 振る舞い・失敗・体験品質の条件
        └─→ Verification: 仮説を破る反例と観測
```

### 妥当性確認と未確認事項

| 確認する仮説 | 観測方法 | 現在未確認の範囲 |
|---|---|---|
| 何が未完了か、何を変えたか、何が成立を証明するか、現在品質は何かを役割別に辿れることで、Roadmap、CHG、根拠、品質の置場と役割が重なり、現在状態と履歴を探し回るという負担または誤認を減らせる。 | 代表シナリオの利用者確認、利用者体験の専門レビュー、および品質期待を破る反例による下流検証 | CRDD作成者・保守者が「作業・変更・根拠・品質を役割別に辿る」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |

### 工程別の引き渡し

| 引き渡し先 | 具体化する義務 |
|---|---|
| 下流工程 | IAは作業の一連の流れのNavigationとEntity関係を分け、Release・Quality Assurance・Checkerは各責任者境界を維持する。 |

Discoveryへ戻す条件は、想定した利用者、問題または「作業・変更・根拠・品質を役割別に辿る」という必要性が誤っていると分かった場合である。下流は実現方式を具体化してよいが、「変更理由と全影響パスを重複なく確認できる」という成果を無断で弱めない。
