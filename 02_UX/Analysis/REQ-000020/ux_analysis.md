## 1. 要求の一次分析

```text
リポジトリごとの状態を手で合成し、不足を見落とす／最新値らしい一つを選んでしまう
        ↓
解決策を先に固定せず、人の仕事として読み替える
        ↓
利用者に必要なこと
複数リポジトリを不完全性付きで一つのプロジェクトとして見る
```

この要求で解くのは機能の有無だけではない。プロジェクト運営者／CROS利用者が「欠測・制限・競合を保ったまま横断判断できる」状態へ進めないことを問題として扱う。具体的な画面、データ構造、API、構成要素または数値閾値はここで確定しない。

| 観点 | 内容 |
|---|---|
| 解決する問題 | リポジトリごとの状態を手で合成し、不足を見落とす／最新値らしい一つを選んでしまう |
| 利用者に必要なこと | 複数リポジトリを不完全性付きで一つのプロジェクトとして見る |
| 対象範囲 | 複数リポジトリを横断するプロジェクト運営者が、「リポジトリごとの状態を手で合成し、不足を見落とす」状態から「一つのプロジェクト全体の表示で、取得済み・欠測・競合を同時に確認する」状態へ移る場面 |
| 対象外 | 具体的な画面、データ構造、実装方式および数値閾値の確定 |

## 3. 利用者に起きる変化

```text
変更前
────────────────
- リポジトリごとの状態を手で合成し、不足を見落とす
- 最新値らしい一つを選んでしまう
        │
        │ 欠測・競合を保つリポジトリ横断統合が変える体験
        ▼
変更後
────────────────
- 一つのプロジェクト全体の表示で、取得済み・欠測・競合を同時に確認する
- 情報源ごとの値と統合不能理由を理解する
```

複数リポジトリを束ねると、一部の取得失敗や値の競合を一つの正常値へ丸めたくなる。しかし利用者が必要なのは、見栄えのよい統合結果より、判断に使える正確な全体像である。

この変化で守るのは操作手順ではない。プロジェクト運営者／CROS利用者が複数リポジトリを不完全性付きで一つのプロジェクトとして見ることで、欠測・制限・競合を保ったまま横断判断できるようになることを守る。

## 5. 重要な体験

### この要求での利用の流れ

```text
複数リポジトリを束ねたProjectを開く時
        ↓
各リポジトリの識別情報・情報源状態・網羅範囲を解決する
        │
        ├─ ★ 重要場面: 複数の情報源を統合する場面
        ├─ ⚠ 失敗:  読めない情報源を推測補完し完全表示する
        └─ ✓ 守る品質:  partial・restricted・stale・conflictingを保持する
        ↓
欠測・制限・競合を保ったまま横断判断できる
```

### サービス提供の流れの処置

処置: `作成`

```text
【利用者・責任者】プロジェクト運営者／PM
        │ 利用者行動: 網羅範囲を確認して横断判断または掘り下げを選ぶ
        ▼
【利用者接点】複数リポジトリを束ねたProjectを開く時
        │
        ├─ 時間差: リポジトリごとの観測後に横断統合を合成するため、情報源間に時点差がある
        ├─ 完了時: リポジトリ別情報源状態、網羅範囲、欠測・制限・競合
        └─ 失敗時: 読めないリポジトリと競合項目を各正本責任者へ返す
                     │
                     ▼
             【回復・判断する人】リポジトリごとの正本責任者
                     │ 返却された事実と判断不能範囲を確認
                     └─ 次の行動: 部分表示で判断するか、情報源解決を依頼する

---------------- 可視境界 ----------------
                     │ 時間関係: リポジトリごとの観測後に横断統合を合成するため、情報源間に時点差がある
                     ▼
【提供側】提供システム
        └─ 提供責務: 利用可能な情報源だけを統合し不完全性を保持する
```

この図は、利用者行動、利用者が観測する接点、提供責務および失敗時の引き渡しを示す。内部構成要素の構造やプロトコルは下流工程で具体化する。

### 製品全体の整理への接続

- 利用の流れの統合先: [プロジェクトの現在地を判断する](../../03_Experience_Map.md#プロジェクトの現在地を判断する)
- サービス提供の流れの統合先: [共同のサービス提供の流れ](../../04_Service_Blueprint.md#1-共同のサービス提供の流れ)
- 横断成果物はこの個別分析から共通パターンを合成する。この要求での利用の流れ、責任境界または品質の代替にはしない。

### この要求での責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| プロジェクト運営者／PM | 網羅範囲を確認して横断判断または掘り下げを選ぶ | 読めない情報を推測で補わない |
| リポジトリごとの正本責任者 | 担当情報と現在の開示可否を提供する | 他リポジトリの状態を複製して正本化しない |
| 提供システム | 利用可能な情報源だけを統合し不完全性を保持する | 非開示情報源の存在や内容を漏らさない |

### 補足する品質

- 結果または状態を最初に受け取る時: 情報源ごとの取得状態と観測時点を保持する。（避ける失敗: リポジトリごとの状態を手で合成し、不足を見落とす）
- 結果を判断または引き継ぐ時: `missing`と`restricted`と`unavailable`を混同しない。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 結果を判断または引き継ぐ時: 競合値をAIが勝手に一つへ統合しない。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 失敗・不足から次の行動を選ぶ時: 一部だけの結果でも分かる範囲と判断できない範囲を示す。（避ける失敗: 成立不能の理由や回復先が分からないまま作業が止まる）


## 6. 下流への引き渡し

```text
この要求で確定した利用者成果
        │
        ├─→ IA: 必要な情報・関係・見つけ方
        ├─→ UI: 誤認させない表示・操作意図
        ├─→ SPEC: 振る舞い・失敗・体験品質の条件
        └─→ Verification: 仮説を破る反例と観測
```

### 妥当性確認と未確認事項

| 確認する仮説 | 観測方法 | 現在未確認の範囲 |
|---|---|---|
| 一つのプロジェクト全体の表示で、取得済み・欠測・競合を同時に確認する／情報源ごとの値と統合不能理由を理解することで、リポジトリごとの状態を手で合成し、不足を見落とすという負担または誤認を減らせる。 | 代表シナリオの利用者確認、利用者体験の専門レビュー、および品質期待を破る反例による下流検証 | プロジェクト運営者／PMが「複数リポジトリを不完全性付きで一つのプロジェクトとして見る」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |

### 工程別の引き渡し

| 引き渡し先 | 具体化する義務 |
|---|---|
| 下流工程 | IAは項目単位の情報源・由来（Provenance）と網羅範囲を持つ。SPECは統合決定表と情報の新しさ条件を定め、Architectureは情報源との接続部の失敗をプロジェクト全体成功へ隠さない。 |

Discoveryへ戻す条件は、想定した利用者、問題または「複数リポジトリを不完全性付きで一つのプロジェクトとして見る」という必要性が誤っていると分かった場合である。下流は実現方式を具体化してよいが、「欠測・制限・競合を保ったまま横断判断できる」という成果を無断で弱めない。
