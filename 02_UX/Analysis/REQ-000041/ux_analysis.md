# REQ-000041の利用者体験分析

成果物種別: UX分析

状態: UX再統合中（初回Host設定の候補伝播・契約／品質限定独立レビュー済み・残指摘0。IA以降は初回設定未伝播）
分析対象: [REQ-000041 最小ユーザー識別とRole権限によるRemote CROS利用](../../../01_Discovery/Definitions/REQ-000041/requirement.md)

## 1. 要求の一次分析

鍵の発行・独立失効・交換はadministrator専用固定でON／OFF設定なし。通常は同一Process Workbench、MCPに鍵操作は非公開。Host回復はログイン済みローカル操作者の対話CLIで交換2操作だけを行い、追加認証・専用資格・承認コード・OS管理者昇格を要求しない。既存Root／Path検証を維持し、全4組で対象・影響を事前表示、Hostまたは全員交換の3組だけ明示確認する。

managerとadministratorはユーザー登録・表示名変更、developer／managerの割当て・詳細権限、Repository登録・登録解除・公開範囲を管理する。administratorの付与・解除・降格を含むRole変更、administrator詳細権限と鍵3操作はadministratorだけが管理し、設定からdeveloperへ管理操作やmanagerへ管理者専用操作を委譲しない。

manager自身の内容範囲も、変更前の現在権限による管理操作の認可とRole詳細権限・公開範囲の明示更新を経て変更できる。更新後は既存実アクセスを含めて次要求から評価し、管理能力だけで内容を自動付与しない。Repository登録だけで公開せず、登録解除は登録と対応する公開設定を同時に解除し、CROSから対象へ以後アクセスできなくする。他Repositoryの登録・公開設定と対象Repository／Product Dataは保持する。

```text
Remote CROSでは利用範囲を分けたい
        ↓
誰向けの資格か分からないが、一般的なアカウント管理は重い
        ↓
利用者に必要なこと
Remote利用者は自身と許可範囲を理解する
manager／administratorはユーザー・業務RoleとRepository登録・公開範囲を用意する
administratorだけが管理者Role・詳細権限と鍵を管理する
Host操作者は指定ユーザーの鍵交換、または全員失効＋指定既存administratorへの再発行で接続を回復する
```

本要求には二つの独立した利用者成果がある。Remote利用者は一度受け取った接続資格で許可範囲だけを継続利用したい。managerとadministratorは安定ユーザーIDと表示名で対象を識別し、業務上の利用範囲を維持したい。administratorは資格を維持・回復したい。同じAccess維持の成果を担当者ごとに分担する。表示名は本人確認や権限ではない。Repository単体利用へCROS認証を持ち込まないことは両成果の共通制約である。

| 観点 | 内容 |
|---|---|
| 解決する問題 | 共有資格だけでは対象を識別しにくいが、一般アカウント管理まで持つと導入・申請・本人確認等が現在目的に対して重い |
| 利用者に必要なこと | Remote利用者は現在の許可範囲だけを利用し、manager／administratorはユーザーと業務の利用範囲を用意する。administratorは管理者Role・詳細権限と鍵を管理し、Host操作者は鍵交換だけで接続を回復する |
| 対象範囲 | 最小ユーザー識別と表示名、developer／managerのRole割当て・詳細権限、Repository登録・登録解除・公開範囲はmanager／administrator。administratorのRole割当て・詳細権限と鍵3操作はadministrator専用。通常Host回復は交換2操作だけ |
| 対象外 | 最小情報を超えるアカウント管理、メール・Password・本人確認・自己登録・自己編集・申請、SSO、Multi-tenant IAM、Repository単体利用への認証強制 |

## 2. 利用者・目標・成果

```text
Remote利用者 → 現在の許可範囲だけを使い、再接続できる
業務管理のmanager／administrator → 対象ユーザー・業務Role・Repository登録と公開範囲を維持する
administrator → 管理者Role・詳細権限と鍵を維持し、資格漏洩・喪失後も通常管理へ戻る
ログイン済みHost操作者 → 既存ユーザーとRoleを保持した鍵交換2操作だけを行う
```

| 項目 | 内容 |
|---|---|
| 主な想定利用者 | Remote CROS利用者、業務管理のmanager／administrator、管理者資格・鍵のadministrator |
| 関係する利用者 | Server Hostへログイン済みの操作者、Credentialを安全な別経路で受け取る利用者 |
| 利用場面 | ユーザー登録・表示名／Role変更、Repository登録・登録解除・公開範囲変更、初回設定・再接続、鍵発行・独立失効・交換、既存administratorの有効Credential全喪失 |
| 目的 | 最小ユーザー管理でRemote利用範囲を分け、管理不能時もProduct Dataを失わず復旧する |
| 得られる結果 | 利用者は許可範囲だけを使い、manager／administratorは業務アクセスを維持できる。administratorは管理者資格と鍵を維持し、Host回復でも既存Roleを保って通常管理へ戻れる |
| この要求に固有の差 | Credentialはユーザーの安定IDへ紐づき、詳細権限はRoleが所有し、Administrator能力と内容閲覧を分け、緊急復旧をRemote認証から切り離す |
| 根拠・確信度 | REQ-000041で人間確認済み。対象識別とCredentialリセットの実操作負担はPilotで確認する |

## 3. 利用者に起きる変化

```text
変更前
個人別登録・申請を作るか、Server接続者へ広すぎる範囲を与える
        ↓
変更後
manager／administratorが対象ユーザー・業務Role・Repository登録と公開範囲を明示的に管理する
```

Repositoryを直接利用できる人は従来どおりFilesystem／Git Accessの範囲で作業する。CROS Roleは同一Repository内のファイルを隠す仕組みにしない。

### Same判断の比較

#### 許可された作業領域だけをリモート利用する

比較対象: `UX-000013`

| 比較軸 | 既存UX | 現在の要求 | 差と統合判断 |
|---|---|---|---|
| 担い手 | Remote利用者 | `developer`／`manager`等のRoleで接続するRemote利用者 | 成果の主体は同じ |
| 利用のきっかけ | Remote接続・再接続 | ユーザーCredentialの初回設定・再接続 | Credential方式の具体化である |
| 目的 | 許可範囲の情報と作業を安全に利用する | 現行Roleの許可範囲の情報と作業を安全に利用する | 同じ利用目的である |
| 得られる結果 | 許可された範囲だけを利用できる | Roleが許すRepository Contextだけを利用できる | 同じ利用者成果である |
| 避ける失敗 | 非開示対象の存在・内容漏えい | Role外Repositoryの存在漏えい、Administratorからの内容権限推定 | 同じ失敗類型を補強する |

#### 軽量なユーザー管理でRemote Accessを維持・回復する

比較対象: `UX-000035`

比較の基準は変更前の利用者成果である。

| 比較軸 | 変更前の成果 | 現在の要求 | 差と統合判断 |
|---|---|---|---|
| 担い手 | CROS管理者、Host運用者 | 業務管理のmanager／administrator、管理者資格・鍵のadministrator、ログイン済みHost操作者 | 既存管理担当の分担を具体化。職種からRoleを推定せず、Remote管理とHostを分ける |
| 利用のきっかけ | 資格の維持、漏洩・喪失・認可破損 | manager／administratorが業務の利用範囲を用意・変更し、administratorが資格を維持する。喪失時は鍵交換、認可設定破損は停止 | 軽量なAccess維持を担当者別に具体化し、認可設定修復は対象から外す |
| 目的 | 軽量な管理でRemote Accessを維持し、管理不能時に通常管理へ戻る | 最小ユーザー管理でRemote Accessを維持し、管理不能時に通常管理へ戻る | 管理対象の具体化であり、目的は同じ |
| 得られる結果 | 接続を維持し、Product Dataを保って通常管理へ再入場する | 業務設定と鍵管理を分担して接続を維持し、IDを保ったリセットと安全な再入場を行う | 目的・成果は同じ。新たな独立成果ではなく分担を具体化する |
| 避ける失敗 | 秘密漏えい、管理と内容権限の混同、Product Data削除 | 別ユーザー処置、名前のAuthority化、managerによる管理者資格・鍵境界の迂回、登録と公開／解除と削除の混同を防ぐ | 既存成果の安全な成立条件を補強する |

統合理由: `Same → UX-000035`として既存IDを維持する。Goalは軽量なAccess維持・回復、Outcomeは接続継続と通常管理への再入場のままである。Actorの分担と管理対象、Failureの管理者境界・登録公開誤認を具体化し、一般アカウント管理を新しい成果として追加しない。

## 5. 重要な体験

### この要求での利用の流れ

```text
managerまたはadministratorが対象ID・表示名・業務RoleとRepository公開範囲を用意する
        ↓
administratorが対象ユーザーを確認してCredentialを発行する
        ↓
利用者が秘密値を一度登録して接続する
        ↓
Role範囲だけを利用する
        │
        ├─ ★ 重要場面: 資格漏洩・全喪失を検出した時（認可設定破損は処置前停止）
        ├─ ⚠ 失敗: 別ユーザーをリセットする／名前を本人確認に使う／秘密値を記録する／Product Dataを消す
        └─ ✓ 守る品質: 通常失効とServer-local Recoveryを分け、安全な再入場を示す
        ↓
新Credentialを配布し通常管理へ戻る
```

```text
---------------- 可視境界 ----------------
                     │ 時間関係: Remote利用とHost RecoveryのAuthority・開始・完了を分ける

        └─ 操作別担当Roleを確認し、登録・公開・削除を区別する。Credentialをユーザーへ結び、生Secretを記録しない
```

| ログイン済みHost操作者 | 追加認証なしの対話CLIで鍵交換2操作だけを行う | 一般管理へ広げず、既存Root／Path維持、Product Data非削除、Secret非記録 |

### 補足する品質

- manager自身の内容範囲も、変更前の現在権限による管理操作の認可とRole詳細権限・公開範囲の明示更新を経て変更できる。更新後は既存実アクセスを含めて次要求から評価し、管理能力だけで内容を自動付与しない。Repository登録だけで公開せず、登録解除は登録と対応する公開設定を同時に解除し、CROSから対象へ以後アクセスできなくする。他Repositoryの登録・公開設定と対象Repository／Product Dataは保持する。
- developerの管理操作、managerによるadministrator付与・解除・降格・詳細権限変更・鍵操作と、設定による固定制限迂回を拒否する。表示名変更まで管理者資格変更と誤認して禁止しない。

- 指定ユーザー交換は、そのユーザーの旧有効資格すべての失効と新資格の一度発行。全員交換は全旧有効資格失効と指定既存administratorへの一度発行。他ユーザーは管理者から再発行・再配布を受けるまで接続できない。
- 両操作はユーザーID・表示名・Role・詳細権限・Repository登録・Product Dataを保持し、回復専用ユーザー・追加権限を作らない。通常管理とHost入口はAuthorityだけを分ける。
- 交換後の発行自体または結果記録が未確定となる発行失敗・応答喪失・Process喪失では既知失効と不明な発行結果を同じRecoveryに保持する。再入場時は現在状態を再観測し、再観測なしに完了・rollback・未失効・開始済み取消完了・Secret再表示を推定しない。

- Secretは発行時一度だけ表示し、ServerはDigestだけを保持する。
- 指定ユーザー／全員の鍵交換は共通の2操作とし、通常管理とHostは入口・Authorityだけを分ける。どちらもID・名前・Role・権限を保持し、旧資格の以後拒否と開始済み操作の取消を混同しない。
- 同名・改名からIDや権限の変化を推定しない。Role権限変更は次の認可へ反映し、自身表示と管理者の対象一覧を分ける。
- 認証済み利用者の自身表示を許可し、非認証入口へユーザー情報を開示せず、管理権限のない入口へ他ユーザー一覧・存在・件数を開示しない。
- Recoveryの対象、保持するProduct Data、結果および再入場方法を秘密値なしで追跡できる。

### 登録解除と鍵の受け渡し未確認の体験

| 場面 | 利用者が理解できる結果と次の行動 |
|---|---|
| Repository登録解除 | 登録と対応する公開設定を同時に解除し、CROSから対象へ以後アクセスできなくなる。他Repositoryの登録・公開設定、対象Repository本体・Product Dataは残る。開始済み操作の取消完了とは別である |
| 発行と結果記録が確定し、受け渡しだけ未確認 | 「発行済み・受け渡し未確認」と示す。確実な未受領とは言わず、Secretの保存・再表示・自動再発行はしない。現在認可されたadministratorが、既存の交換操作を明示的に新しく実行できる |
| 指定ユーザーへの新しい交換 | 未受領の可能性がある発行済み資格を含め、そのユーザーの旧有効資格すべてを失効し、同じ既存ユーザーへ新資格を発行する。他ユーザーの鍵は保持する |
| 全員への新しい交換 | 発行済み資格を含め全ユーザーの旧有効資格を失効し、指定した既存administratorへ新資格を発行する。他ユーザーは通常の再発行・再配布が必要となる |
| 発行自体または結果記録が不明 | 新交換を案内せず、元発行のIdentityと既知事実に相関した現在状態の再観測へ戻す。元処理が交換の場合だけ同じexact Recoveryを保持する。通常発行に交換用Recoveryを新設しない |
| 現在の管理者認証が使えない | 通常Workbenchの認可を迂回せず、既存のログイン済みHost操作者向け交換入口へ案内する |

新しい交換は旧処理の再試行・再開ではなく、別Operation／別Recoveryとして扱う。旧発行の既知事実を保持し、新交換の成功から旧Secretの受領・rollback・取消を推定しない。処置前には現在の資格・権限を再確認し、遅延した旧応答から失効済み鍵を利用可能と案内しない。新交換にも指定ユーザー／全員の範囲、4組の事前表示・3組の明示確認、ユーザー情報・Role・権限・Product Data保持を適用する。

### 初回設定で利用可能にする体験

未初期化を確定できるCROSで、ログイン済みHost操作者が明示的な初回設定を選び、管理用表示名を入力する。最初のadministratorをUUIDで識別し、そのユーザーに結び付く鍵を一度だけ受け取って通常管理へ入れる。初回設定は既存ユーザーの鍵回復とは別の開始場面であり、Remote Credential、追加認証、専用資格、承認コード、OS管理者昇格を要求しない。

| 重要場面 | 利用者が理解する状態・次の行動 |
|---|---|
| 正しいHost Rootで管理状態と初回処理の記録がともに未初期化と確定 | 表示名を入力し、最初のadministrator UUIDとその鍵を一度だけ受け取る。Repository登録・公開・内容アクセスは自動付与されない |
| 既存状態・管理者がある | 初回設定を繰り返さず通常管理へ進む。鍵を失った場合は既存ユーザーのHost交換へ進む |
| 読取不能・破損・対象不明・Lock競合・回収待ち | 未初期化と説明せず、新しいユーザー・鍵を作らない。判定不能理由と再確認先を示し、元試行の存在を推定しない |
| 確認できた開始済み初回試行 | 同じ試行の非秘密相関と既知事実を保持し、現在状態を再観測する。新しい初回設定へ戻さない |
| ユーザー作成・発行・結果記録の一部まで成立 | 最初からやり直したと説明しない。作成済みUUID、発行・記録・受け渡しの各事実を分け、別UUIDの作成やSecret再表示をしない |
| 発行・結果記録は確定し、受け渡しだけ未確認 | 初回設定を再実行せず、作成済みadministratorを指定する既存Host交換を明示的に選ぶ |
| 発行自体・結果記録が不明 | 新しい交換へ進まず、元試行の現在状態を再観測する。通常発行に交換用Recoveryを新設しない |

必要な情報は、正しいHost Root、未初期化／既存／途中／観測不能の区別、管理用表示名、作成済みuserId、発行・結果記録・受け渡しの各事実、元試行への非秘密の相関、内容アクセス非付与および次の行動である。具体Schema、CLI引数、保存方式、相関値の物理形式は下流で決める。

MCPや自動起動から初期化しない。表示名を認可の根拠にしない。既存ユーザーまたは管理状態があれば初期化を拒否する。

初回設定もUX-000035へSame統合する。利用者は同じCROS管理主体／Host操作者、成果は既存の「Remote利用範囲を用意・維持・回復する」であり、初回設定はその導入前条件を補う。Triggerは未初期化CROSの利用開始、Failureは二重作成・不明状態の初回扱い・Secret再表示で、同じユーザー／資格lifecycleに属する。一般Server導入、Repository配置や内容権限の自動設定まで成果を拡張する場合はSame／Newを再評価する。

```text
Hostで明示開始 → 未初期化を確認 → 表示名・最初の管理者UUID → 鍵一度受領 → 通常管理
                   └ 既存・途中・不明 → 新作成せず状態に応じた既存経路／元試行再観測
```

サービスの責任分担は、Host操作者が開始と表示名を決定し、管理機能が状態を確認してユーザー・資格の成立事実を区別し、操作者が鍵を一度受け取って通常管理へ進む。応答喪失時も発行・記録・受け渡しを一つの成功へ畳まない。利用者の確認操作から実際の保存成立を推定しない。

## 6. 下流への引き渡し

初回設定のIA正式入力には上記の状態・情報・責任・時間関係を渡す。Qualityには、未初期化確定時の一度作成・一度受領、既存／途中／不明からの新作成0、Secret再表示0、内容自動付与0を観測する意図を渡す。UI／SPECへの後続関係では初回設定と通常Host回復を別場面として保持し、発行・記録不明の再観測と確定発行後の受け渡し不明の既存交換を混同しない。IA以降は今回未伝播である。

各引渡し先は、上記の登録・公開設定同時解除と、発行／結果記録／受け渡しの区別を保持する。各交換操作内では同じexact Recoveryを保持する。元交換の未確定結果への再入場と、確定発行後に明示する別Operation／別Recoveryの新交換を区別し、通常発行へ交換用Recoveryを新設しない。

通常発行・独立失効・交換を分ける。通常発行はadministratorの同一Process Workbenchから新Secretを一度発行し、既存資格の失効を伴わない。独立失効は同じ入口と担当者で指定資格を失効し、新資格・Secretを発行しない。交換は定義済みのユーザー単位または全員の失効範囲と新Secretの一度発行、情報保持・同じRecoveryを組み合わせる。通常Host回復には交換2操作だけを渡す。Quality／UI／SPECへの引渡しもこの操作別結果を保持し、交換専用の回復条件を通常発行・独立失効へ転用しない。

各引渡し先は本文の最新鍵管理条件（固定administrator、Workbench通常入口、追加認証なしのHost交換2操作、既存Root／Path、MCP鍵操作非公開、全4組表示／3組確認）を保持する。採用済み担当Role、manager自身の明示範囲変更、登録／公開／削除の別を引き継ぐ。具体的画面・API・保存・権限語彙は後工程で決める。

| 接続先 | この要求から保持する意味 |
|---|---|
| IA（直後工程への正式な引き渡し） | ユーザーID・表示名・Role詳細権限・資格相関と三可視境界。指定ユーザー／全員の失効範囲と既存ユーザー発行先、通常／HostのAuthority差、ユーザー情報・Role・権限・Product Data保持、既知処置・発行不明・同じRecovery。最新鍵管理の固定条件と、業務管理／管理者専用境界・登録と公開の分離・解除と削除の分離を保持する。 |
| Quality Analysis / UX（伴走） | 2操作の範囲と同じ保持条件、全員交換の指定既存管理者発行と再配布、通常／HostのAuthority差、対象不明・破損停止、発行失敗・応答喪失・Process喪失後の既知処置保持・同じRecovery・再観測。名前非Authority、Secret非保存・単体非依存も保持。最新鍵管理の固定条件と、業務管理／管理者専用境界・登録と公開の分離・解除と削除の分離を保持する。 |

### 妥当性確認と未確認事項

通常発行の一度受領と既存資格不変、独立失効後の旧資格拒否と新資格非発行、交換の既知失効・新発行・保持条件を別々に観測する。鍵3操作のadministrator限定・同一Process Workbench・MCP非公開を共通に確認し、通常Host回復は交換だけとする。既存administrator不存在・Role／認可設定破損を鍵喪失と混同せず処置前停止する。

- 確認する観測: manager／administratorの業務管理分担、administratorだけの管理者資格・鍵管理、developer管理と設定迂回の拒否、manager自身の明示範囲変更と次要求の反映、登録≠公開・解除≠削除の理解。自身表示、対象識別、IDを維持した資格リセット、管理不能時のHost回復も維持する。
- 未確認事項: 対象識別とリセット確認の負担、採用済みWorkbench／Host CLI入口の具体的な表示・案内の負担。UUID版・表示名の構文／一意性・保存Schema・権限語彙は下流で決める。
- Host回復でも既存ユーザーIDへ資格を結び、ユーザー情報・Role・詳細権限・Repository登録・Product Dataを保持する。特別な回復ユーザー・権限を作らず、管理者不存在・対象不明・認可設定破損では処置前停止する。初回設定は採用済みのHost明示操作・表示名入力・最初のadministrator UUID作成・鍵一度受領を保持し、具体化は下流で行う。
- 現在判定: 後続確認が必要。UX定義を進めることは妨げない。
- 確認事項: 最小管理だけで対象と処置影響を理解できるか。
- 判断者: CROS管理者、Remote利用者およびQual-Lab。
- 未確認時の影響: 画面配置および配布手順を確定しない。
- Discoveryへ戻す条件: 本人確認・自己管理・申請、複数Role、個別追加権限または個人行動監査が必要な場合。
