# REQ-000041の利用者体験分析

成果物種別: UX分析

状態: Googleログイン・共有MCP認可への切替を反映。実サービスでの体験評価は未実施
分析対象: [REQ-000041 最小ユーザー識別とRole権限によるRemote CROS利用](../../../01_Discovery/Definitions/REQ-000041/requirement.md)

## 1. 要求の一次分析

| 観点 | 内容 |
|---|---|
| 解決する問題 | 長期の接続鍵は配布・交換が必要で、どの利用者と対象への許可なのかも分かりにくい |
| 利用者に必要なこと | 招待された既存の利用者として接続し、通常利用・管理・MCP認可・Gitホスト連携の違いを理解する |
| 対象範囲 | 共有の本人確認・招待・通常利用・管理書込み・管理者の再入場、およびGitホストとの結合が必要な共有登録 |
| 対象外 | 自己登録、接続鍵の手入力、単体への追加認証、Gitホストでのアカウント自動作成 |

## 2. 利用者・目標・成果

| 項目 | 内容 |
|---|---|
| 主な想定利用者 | 招待された共有利用者、業務上のアクセスを維持するmanager／administrator、最初の設定や管理者復旧を行うHost操作者 |
| 利用場面 | 初回の招待引受、通常の再ログイン、MCPクライアントへの利用許可、対象の登録・公開、管理不能からの再入場 |
| 目的 | 誰として何にアクセスするかを把握し、別対象に権限を付与せずに業務利用と管理を続ける |
| 得られる結果 | 利用者は現在の許可範囲だけを使い、管理担当者は利用者・対象・影響を明確にしたうえで管理を維持できる |
| 根拠と未確認範囲 | REQ-000041の現行判断に従う。実端末・外部ログイン・対象MCPクライアントでの操作負担は未評価 |

## 3. 利用者に起きる変化

```text

        ↓

   └─ Same → UX-000035 軽量なユーザー管理でRemote Accessを維持・回復する
```

|---|---|---|---|
| 許可された作業領域だけをリモート利用する | `Same → UX-000013` | 接続方式が変わっても、担い手・目的・利用できる範囲を理解する成果は同じ | 登録済み本人、利用入口別の許可、対象に対する本人の実効権限 |
| 軽量なユーザー管理でRemote Accessを維持・回復する | `Same → UX-000035` | 運用の継続と通常管理への再入場という成果は同じ | 招待による開始、短命の管理セッション、同じ管理者の再紐付け、他対象とデータの保持 |

### Same判断の比較

#### 許可された作業領域だけをリモート利用する

比較対象: `UX-000013`

| 比較軸 | 切替前 | 切替後 | 差と統合判断 |
|---|---|---|---|
| 担い手 | 共有利用者 | 登録済みの共有利用者 | 同じ利用者 |
| 利用のきっかけ | 接続・再接続 | 招待引受と再ログイン、またはMCP認可 | 本人確認の導線だけ変わる |
| 得られる結果 | 許可対象の利用 | 同じ本人の現在の許可対象の利用 | 成果は同じ |
| 避ける失敗 | 権限外の情報漏えい | 別主体・別入口・別対象の資格を使うこと | 同じ情報境界を補強する |

統合理由: ログインの手段が変わっても、業務で使える範囲を理解して利用する成果は変わらない。

#### 軽量なユーザー管理でRemote Accessを維持・回復する

比較対象: `UX-000035`

| 比較軸 | 切替前 | 切替後 | 差と統合判断 |
|---|---|---|---|
| 担い手 | 共有の管理担当者とHost操作者 | 同じ担当者 | 担当権限は維持 |
| 利用のきっかけ | 鍵の維持・喪失 | 共有の利用準備とログイン不能 | 手続きが変わる |
| 得られる結果 | 同じ利用者として通常管理に戻る | 現行の紐付けで同じ管理者として戻る | 再入場の成果は同じ |
| 避ける失敗 | 別対象への処置・設定喪失 | 別主体の紐付け・再初期化・設定喪失 | 同じ対象と設定を保持する |

統合理由: 招待や再紐付けは既存成果に必要な手段であり、独立した利用者成果を追加しない。

## 5. 重要な体験

### この要求での利用の流れ

```text
Hostで初回設定 → 管理担当者がWorkbenchへログイン → 短命の管理セッションを開始 → 招待を発行
                         └─ 既存管理者がログインできない → Hostで本人を確認して再紐付け
招待を受けた利用者 → Googleで本人確認 → 許可された範囲でWorkbenchを利用
外部クライアント → CRDDで本人確認し、MCP利用を別途許可 → 現在認可された操作を利用
共有の対象 → 対応Gitホストの本人アカウントを連携 → 本人が実際に読み書きできる範囲を利用
```

### サービス提供の流れの処置

処置: `作成`

```text
【利用者・責任者】管理担当者が対象を確かめて招待し、本人が引き受ける
  ↓
【利用者接点】Workbenchのログイン／管理確認、またはMCPクライアントへの利用許可
  ├─ 時間差: 招待の発行と本人の引受は別の時点
  ├─ 完了時: 許可された入口と対象を使える
  └─ 失敗時: 別主体・期限切れ・失効を許可に変えない
--- 可視境界 ---
【提供側】CRDDが紐付け・現在認可・対象を確認する
  ↓
【回復・判断する人】本人／管理担当者／Host操作者
  └─ 次の行動: 再ログイン、招待の再発行、または既存管理者の再紐付け
```

### この要求での責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| 共有利用者 | 招待を引き受け、本人としてログインし、外部クライアントへの操作許可を選ぶ | 自分で利用者を作らない。クライアントにログインしたアカウントだけでCRDDの権限を得ない |
| 管理担当者 | 短命の管理セッションで招待・ロール・登録を扱う。既存利用者への招待再発行はadministratorのみ | 対象ロールの固定境界を越えない。登録だけでは内容を許可せず、登録解除と削除を混同しない |
| Host操作者 | 未初期化時の初回設定または既存管理者の再紐付けを明示する | 状態不明や既存状態を再初期化しない。回復を理由に登録や内容権限を増やさない |
| CRDD | 入口に応じて現在認可を観測し、実行に影響する失効と処置結果を区別する | 別主体・別対象を露出しない。停止要求を終了や巻戻しと表示しない |

### 補足する品質

招待を受けた本人が通常のログインで引き受けられること、アクセス管理の書込みには管理セッションが必要なことを区別する。失敗時は、再ログインできる場合、管理者へ確認する場合、既存Hostから回復する場合、現在状態を再確認する場合を混同しない。認可不能によって別対象の存在を伝えない。

## 6. 下流への引き渡し

| 接続先 | この要求から保持する意味 |
|---|---|
| IA（直後工程への正式な引き渡し） | 本人、招待、通常と管理のセッション、MCP同意、Gitホストとの結合、対象と公開範囲を区別する。初回設定と既存管理者の再紐付けを分ける |
| Quality Analysis / UX（伴走） | 正常時の入口と、別主体・期限切れ・権限変更・途中結果・確認不能を区別できるか確認する。旧鍵の検証結果は流用しない |
| UI（後続Contract Relation） | 招待発行／引受、ログイン／追加の管理確認、クライアントの認可、Gitホスト連携、終了不明を区別する |
| SPEC（後続Contract Relation） | 公開入口と現在認可、処置前後の結果、他対象保持、同じ対象への再入場と失効時の停止を具体化する |

### 妥当性確認と未確認事項

- 現在判定: 既存の利用者成果へ統合。実サービスでの体験評価は未実施。
- 確認事項: 本人選択・招待・MCP同意・対象を利用者が取り違えないか。Host復旧時に対象と保持範囲が明確か。
- 判断者: 共有利用者、管理担当者、Host操作者およびQual-Lab。
- 未確認時の影響: 外部サービスでの実運用の成立を主張しない。
- Discoveryへ戻す条件: 自己登録、対応する外部本人確認の範囲、個人別権限、複数人を巻き込む回復を変更する場合。
