# REQ-000017の利用者体験分析

成果物種別: UX分析

状態: UX再統合済み・独立再レビュー待ち
分析対象: [REQ-000017 出所付き受け渡す情報一式の解決](../../../01_Discovery/Definitions/REQ-000017/requirement.md)

## 1. 要求の一次分析

```text
次のAgentへ必要そうな情報を手で貼り直す／Agentが何を参照したか推測する
        ↓
解決策を先に固定せず、人の仕事として読み替える
        ↓
利用者に必要なこと
必要な情報だけを出所付きで渡す
```

この要求で解くのは機能の有無だけではない。対話AI／コーディングAIの利用者が「何を使って判断・生成したか後から追跡できる」状態へ進めないことを問題として扱う。具体的な画面、データ構造、API、構成要素または数値閾値はここで確定しない。

| 観点 | 内容 |
|---|---|
| 解決する問題 | 次のAgentへ必要そうな情報を手で貼り直す／Agentが何を参照したか推測する |
| 利用者に必要なこと | 必要な情報だけを出所付きで渡す |
| 対象範囲 | 情報を利用する人・AI、情報所有者が、「次のAgentへ必要そうな情報を手で貼り直す」状態から「対象タスクに必要な情報が情報源と改訂版付きで解決される」状態へ移る場面 |
| 対象外 | 具体的な画面、データ構造、実装方式および数値閾値の確定 |

| 得られる結果 | 何を使って判断・生成したか後から追跡できる |

| 根拠・確信度 | 同じREQのDiscovery定義から導いた仮説。外部へ渡す情報の所有者が「必要な情報だけを出所付きで渡す」を判断する場面で、対象に必要な受け渡す情報一式を解決することが実際に成果へ影響するかは未確認。 |

## 3. 利用者に起きる変化

```text
変更前
────────────────
- 次のAgentへ必要そうな情報を手で貼り直す
- Agentが何を参照したか推測する
        │
        │ 出所付き受け渡す情報一式の解決が変える体験
        ▼
変更後
────────────────
- 対象タスクに必要な情報が情報源と改訂版付きで解決される
- 利用した情報集合と不足範囲を後から追跡する
```

対話AIとコーディングAIの間で人間が文書や会話を転記すると、出所、改訂版、選択理由が失われる。全情報の投入は過剰共有と認知負荷を増やす。

この変化で守るのは操作手順ではない。対話AI／コーディングAIの利用者が必要な情報だけを出所付きで渡すことで、何を使って判断・生成したか後から追跡できるようになることを守る。

## 4. 利用者成果への統合

```text
REQ-000017
   │
   └─ New  → UX-000019 必要な情報を渡し結果を同じ仕事へ戻す
```

| 利用者成果 | 処置 | 判断理由 | この要求が補う内容 |
|---|---|---|---|
| 必要な情報を渡し結果を同じ仕事へ戻す | `New → UX-000019` | 本要求が「必要最小限の情報を出所・現行性・許可付きで渡し、相関・完全性付きの結果を同じタスクへ戻せる」という独立した利用者成果を最初に定義する。 | 対象に必要な受け渡す情報一式を解決することが、この要求固有の成立条件になる |

`Same`／`New`は技術用語の近さや件数目標では決めない。「利用者は、どの状況で、何をするためにシステムと関わり、何ができるようになるか」が同じかを比較する。提供能力、必要情報、品質、妥当性確認または下流の実現要素は、独立UXへ分割せず対応する成果の成立条件として保持する。

## 5. 重要な体験

### この要求での利用の流れ

```text
別Agentやツールへ仕事を渡す時
        ↓
対象に必要な受け渡す情報一式を解決する
        │
        ├─ ★ 重要場面: 外部境界へ情報を出す直前
        ├─ ⚠ 失敗:  全量投入・秘密情報混入・古い仮説の現在値化
        └─ ✓ 守る品質:  情報源・改訂版・選択理由を保持する
        ↓
何を使って判断・生成したか後から追跡できる
```

### サービス提供の流れの処置

処置: `作成`

```text
【利用者・責任者】外部へ渡す情報の所有者
        │ 利用者行動: 送信目的と範囲を確認し、帰還結果の採否を判断する
        ▼
【利用者接点】別Agentやツールへ仕事を渡す時
        │
        ├─ 時間差: 情報準備、外部実行、結果帰還は別時点で成立する
        ├─ 完了時: 送信情報の出所・現行性・許可と帰還結果の相関
        └─ 失敗時: 不足情報、拒否された情報、未確認の結果を外部情報所有者へ返す
                     │
                     ▼
             【回復・判断する人】外部へ渡す情報の所有者
                     │ 返却された事実と判断不能範囲を確認
                     └─ 次の行動: 送信範囲を修正するか、結果を候補として採否判断する

---------------- 可視境界 ----------------
                     │ 時間関係: 情報準備、外部実行、結果帰還は別時点で成立する
                     ▼
【提供側】提供システム／AI
        └─ 提供責務: 必要最小限の情報を出所付きで搬送し候補として戻す
```

この図は、利用者行動、利用者が観測する接点、提供責務および失敗時の引き渡しを示す。内部構成要素の構造やプロトコルは下流工程で具体化する。

### 製品全体の整理への接続

- 利用の流れの統合先: [対話と構築を往復する](../../03_Experience_Map.md#対話と構築を往復する)／[外部情報を送受信する](../../03_Experience_Map.md#外部情報を送受信する)
- サービス提供の流れの統合先: [共同のサービス提供の流れ](../../04_Service_Blueprint.md#1-共同のサービス提供の流れ)
- 横断成果物はこの個別分析から共通パターンを合成する。この要求での利用の流れ、責任境界または品質の代替にはしない。

### この要求での責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| 外部へ渡す情報の所有者 | 送信目的と範囲を確認し、帰還結果の採否を判断する | 接続済みであることを包括許可とみなさない |
| 提供システム／AI | 必要最小限の情報を出所付きで搬送し候補として戻す | 秘密情報や無関係情報を黙示送信しない |
| 外部Agent／ツール | 許可された情報から結果と未確認範囲を返す | 結果へ正本採用権限があると仮定しない |

### 補足する品質

- 結果または状態を最初に受け取る時: 対象成果物（Artifact）、上位意図、制約判断、必要根拠、現在有効な仮説を選ぶ。（避ける失敗: 次のAgentへ必要そうな情報を手で貼り直す）
- 結果を判断または引き継ぐ時: 古い、競合する、利用不能な情報を暗黙に統合しない。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 結果を判断または引き継ぐ時: 秘密情報や許可外情報をPackageへ含めない。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 失敗・不足から次の行動を選ぶ時: 不足情報をAgentの推測で補完しない。（避ける失敗: 成立不能の理由や回復先が分からないまま作業が止まる）


## 6. 下流への引き渡し

```text
この要求で確定した利用者成果
        │
        ├─→ IA: 必要な情報・関係・見つけ方
        ├─→ UI: 誤認させない表示・操作意図
        ├─→ SPEC: 振る舞い・失敗・体験品質の条件
        └─→ Verification: 仮説を破る反例と観測
```

### 妥当性確認と未確認事項

| 確認する仮説 | 観測方法 | 現在未確認の範囲 |
|---|---|---|
| 対象タスクに必要な情報が情報源と改訂版付きで解決される／利用した情報集合と不足範囲を後から追跡することで、次のAgentへ必要そうな情報を手で貼り直すという負担または誤認を減らせる。 | 代表シナリオの利用者確認、利用者体験の専門レビュー、および品質期待を破る反例による下流検証 | 外部へ渡す情報の所有者が「必要な情報だけを出所付きで渡す」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |

### 工程別の引き渡し

| 引き渡し先 | 具体化する義務 |
|---|---|
| 下流工程 | IAは受け渡す情報一式、情報源、改訂版、選択理由およびタスク Relationを分ける。ArchitectureはResolverと通信方式を分離し、Verificationは出所喪失と過剰投入を反証する。 |

Discoveryへ戻す条件は、想定した利用者、問題または「必要な情報だけを出所付きで渡す」という必要性が誤っていると分かった場合である。下流は実現方式を具体化してよいが、「何を使って判断・生成したか後から追跡できる」という成果を無断で弱めない。
