# REQ-000009の利用者体験分析

成果物種別: UX分析

状態: UX再統合済み・独立再レビュー待ち
分析対象: [REQ-000009 プロジェクト・リポジトリ・基点フォルダの識別情報分離](../../../01_Discovery/Definitions/REQ-000009/requirement.md)

## 1. 要求の一次分析

```text
リポジトリ名や配置から論理プロジェクトを推測する／横断結果の操作対象が曖昧になる
        ↓
解決策を先に固定せず、人の仕事として読み替える
        ↓
利用者に必要なこと
プロジェクト・リポジトリ・基点フォルダを区別して対象を確認する
```

この要求で解くのは機能の有無だけではない。プロジェクト運営者／実行基盤利用者が「論理プロジェクトを一つに見ながら誤った場所へ作用しない」状態へ進めないことを問題として扱う。具体的な画面、データ構造、API、構成要素または数値閾値はここで確定しない。

| 観点 | 内容 |
|---|---|
| 解決する問題 | リポジトリ名や配置から論理プロジェクトを推測する／横断結果の操作対象が曖昧になる |
| 利用者に必要なこと | プロジェクト・リポジトリ・基点フォルダを区別して対象を確認する |
| 対象範囲 | プロジェクト運営者、リポジトリ管理者が、「リポジトリ名や配置から論理プロジェクトを推測する」状態から「一つのプロジェクトとして見ながら、必要時に各情報源へ辿る」状態へ移る場面 |
| 対象外 | 具体的な画面、データ構造、実装方式および数値閾値の確定 |

## 3. 利用者に起きる変化

```text
変更前
────────────────
- リポジトリ名や配置から論理プロジェクトを推測する
- 横断結果の操作対象が曖昧になる
        │
        │ プロジェクト・リポジトリ・基点フォルダの識別情報分離が変える体験
        ▼
変更後
────────────────
- 一つのプロジェクトとして見ながら、必要時に各情報源へ辿る
- プロジェクト、リポジトリ、検証済み基点フォルダを区別して確認できる
```

一つのプロジェクトが複数リポジトリに分かれても、利用者は物理配置から案件全体を再構成したくない。一方、異なるリポジトリや基点フォルダを同一視すると、根拠と操作対象を取り違える。

この変化で守るのは操作手順ではない。プロジェクト運営者／実行基盤利用者がプロジェクト・リポジトリ・基点フォルダを区別して対象を確認することで、論理プロジェクトを一つに見ながら誤った場所へ作用しないようになることを守る。

## 5. 重要な体験

### この要求での利用の流れ

```text
参照または操作対象を選ぶ時
        ↓
識別情報と検証済み基点フォルダを確認する
        │
        ├─ ★ 重要場面: 外部への変更対象を確定する直前
        ├─ ⚠ 失敗:  同名や近いパスを同じ対象と誤認する
        └─ ✓ 守る品質:  各識別情報と物理基点フォルダの結合を明示する
        ↓
論理プロジェクトを一つに見ながら誤った場所へ作用しない
```

### サービス提供の流れの処置

処置: `作成`

```text
【利用者・責任者】プロジェクト運営者／PM
        │ 利用者行動: 目的に合う対象候補を選び、確認結果から実行可否を判断する
        ▼
【利用者接点】参照または操作対象を選ぶ時
        │
        ├─ 時間差: 識別情報確認は参照・外部変更の前に完了し、曖昧ならその場で停止する
        ├─ 完了時: プロジェクト・リポジトリ・基点フォルダの識別情報とBinding
        └─ 失敗時: 一致しない識別情報と未検証基点フォルダを運用・確認者へ返す
                     │
                     ▼
             【回復・判断する人】運用・確認者
                     │ 返却された事実と判断不能範囲を確認
                     └─ 次の行動: 対象を選び直すか、Binding確認を依頼する

---------------- 可視境界 ----------------
                     │ 時間関係: 識別情報確認は参照・外部変更の前に完了し、曖昧ならその場で停止する
                     ▼
【提供側】提供システム
        └─ 提供責務: 識別情報と検証済み基点フォルダを照合し、exactな対象または拒否理由を返す
```

この図は、利用者行動、利用者が観測する接点、提供責務および失敗時の引き渡しを示す。内部構成要素の構造やプロトコルは下流工程で具体化する。

### 製品全体の整理への接続

- 利用の流れの統合先: [プロジェクトの現在地を判断する](../../03_Experience_Map.md#プロジェクトの現在地を判断する)
- サービス提供の流れの統合先: [共同のサービス提供の流れ](../../04_Service_Blueprint.md#1-共同のサービス提供の流れ)
- 横断成果物はこの個別分析から共通パターンを合成する。この要求での利用の流れ、責任境界または品質の代替にはしない。

### この要求での責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| プロジェクト運営者／PM | 目的に合う対象候補を選び、確認結果から実行可否を判断する | 名前やパスの類似だけで同一対象と決めない |
| 提供システム | 識別情報と検証済み基点フォルダを照合し、exactな対象または拒否理由を返す | 曖昧な対象へ外部への変更を発行しない |
| 運用・確認者 | 誤結合・基点フォルダ外・観測不能の反例を確認する | 読取り可能性を実行権限へ読み替えない |

### 補足する品質

- 結果または状態を最初に受け取る時: 同じプロジェクト IDを持つリポジトリを一つの表示で理解できる。（避ける失敗: リポジトリ名や配置から論理プロジェクトを推測する）
- 結果を判断または引き継ぐ時: 名前の一致だけでリポジトリや基点フォルダを同一とみなさない。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 結果を判断または引き継ぐ時: 変更操作前には対象リポジトリと決定権限を確認できる。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 失敗・不足から次の行動を選ぶ時: 利用できないリポジトリの内容を推測で補完しない。（避ける失敗: 成立不能の理由や回復先が分からないまま作業が止まる）


## 6. 下流への引き渡し

```text
この要求で確定した利用者成果
        │
        ├─→ IA: 必要な情報・関係・見つけ方
        ├─→ UI: 誤認させない表示・操作意図
        ├─→ SPEC: 振る舞い・失敗・体験品質の条件
        └─→ Verification: 仮説を破る反例と観測
```

### 妥当性確認と未確認事項

| 確認する仮説 | 観測方法 | 現在未確認の範囲 |
|---|---|---|
| 一つのプロジェクトとして見ながら、必要時に各情報源へ辿る／プロジェクト、リポジトリ、検証済み基点フォルダを区別して確認できることで、リポジトリ名や配置から論理プロジェクトを推測するという負担または誤認を減らせる。 | 代表シナリオの利用者確認、利用者体験の専門レビュー、および品質期待を破る反例による下流検証 | プロジェクト運営者／PMが「プロジェクト・リポジトリ・基点フォルダを区別して対象を確認する」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |

### 工程別の引き渡し

| 引き渡し先 | 具体化する義務 |
|---|---|
| 下流工程 | IAはプロジェクト、リポジトリ、基点フォルダおよびBindingを別Entityとして関連付ける。UIは通常表示と情報源詳細を分け、Architectureは検証済み識別情報を公開結果まで保持する。 |

Discoveryへ戻す条件は、想定した利用者、問題または「プロジェクト・リポジトリ・基点フォルダを区別して対象を確認する」という必要性が誤っていると分かった場合である。下流は実現方式を具体化してよいが、「論理プロジェクトを一つに見ながら誤った場所へ作用しない」という成果を無断で弱めない。
