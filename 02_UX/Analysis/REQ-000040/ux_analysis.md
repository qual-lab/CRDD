# REQ-000040の利用者体験分析

成果物種別: UX分析

状態: UX再統合済み・独立再レビュー待ち
分析対象: [REQ-000040 Project情報と作業ツリーをつなぐWorkbench](../../../01_Discovery/Definitions/REQ-000040/requirement.md)

## 1. 要求の一次分析

```text
Project情報、AI、Editor、Git Clientを行き来する
        ↓
利用者がProject上の意味と作業差分を頭の中で結ぶ
        ↓
利用者に必要なこと
今の状況、次の仕事、変更内容、共有対象を一続きで判断する
```

本要求はWorkbenchという画面を作ること自体を成果にしない。Project上の意味を理解して選んだ仕事と、実際の作業ツリーに生じた変更を、別々の道具から人手で再構成せず一続きで扱える体験を対象とする。

| 観点 | 内容 |
|---|---|
| 解決する問題 | Project情報と作業ツリーが別の入口に分かれ、利用者が意味、差分、共有対象を頭の中で結んでいる |
| 利用者に必要なこと | Projectの現在地から次の仕事を選び、変更を確認して安全に共有まで進む |
| 対象範囲 | Project情報の理解・詳細確認・定型操作と、Tree、Diff、Stage、Commit、通常Pushの接続 |
| 対象外 | フルIDE、高度なGit Client、具体的Screen／Component／Visual Directionの決定 |

## 2. 利用者・目標・成果

```text
開発者／Project運営者
        │ Projectの状況を見て作業し、変更を共有する時
        ▼
Projectの意味と作業差分を一つの流れで扱う
        │
        ▼
状況理解から次の仕事、差分確認、共有まで迷わず進める
```

| 項目 | 内容 |
|---|---|
| 主な想定利用者 | [製品全体の利用者像](../../02_Personas.md)の「開発者」と「プロジェクト運営者／PM」 |
| 関係する利用者 | 変更の確認者、Front AI |
| 利用場面 | Project状況を確認し、関連する作業を進め、変更を共有する時 |
| 目的 | Project上の判断とRepository上の変更を取り違えず一続きで扱う |
| 得られる結果 | 状況理解から次の仕事、差分確認、Commit、通常Pushまで進み、結論からOwnerへ戻れる |
| この要求に固有の差 | Project情報の横断投影と現在の作業ツリーを同じ判断の流れへ接続する |
| 根拠・確信度 | REQ-000040で人間確認済み。既存Tool併用より判断負担を減らせるかはWorkbench Dogfoodで検証する |

## 3. 利用者に起きる変化

```text
変更前
────────────────
- Project情報、AI、Editor、Git Clientを行き来する
- 作業の意味と差分を自分で対応付ける
        │
        ▼
変更後
────────────────
- Projectの現在地から詳細と次の仕事へ進む
- 同じ流れでTree、Diff、Stage、Commit、Push対象を確認する
- 必要ならAI、CLI、Editor、既存Git Clientへ戻る
```

Workbenchは既存入口を置き換えるのではなく、Project理解と現在の変更を接続する選択可能な入口になる。多くの情報を一画面に置くことではなく、利用者が判断に必要な意味と差分を取り違えず次へ進めることを成果とする。

## 4. 利用者成果への統合

```text
REQ-000040
   ├─ New  → UX-000034 Projectの意味と作業差分を一つの流れで扱う
   ├─ Same → UX-000009 Projectの現在地を根拠と不完全性付きで理解する
   ├─ Same → UX-000010 リポジトリ単独で日常作業を続ける
   └─ Same → UX-000012 入口を変えても同じ仕事を続ける
```

| 利用者成果 | 処置 | 判断理由 | この要求が補う内容 |
|---|---|---|---|
| Projectの意味と作業差分を一つの流れで扱う | `New → UX-000034` | Project上の判断から作業差分と共有対象までを一続きに扱うことは、既存の状況理解や単独作業だけでは表せない独立成果である | 横断情報、次の仕事、Tree／Diff／Stage／Commit／Pushの接続 |
| Projectの現在地を根拠と不完全性付きで理解する | `Same → UX-000009` | WorkbenchでもProjectの現在地を理解する成果自体は変わらない | 五場面から詳細・Owner・作業へ進む入口を追加する |
| リポジトリ単独で日常作業を続ける | `Same → UX-000010` | Workbenchがなくても作業でき、未Commitを正常状態とする成果は既存UXと同じである | Workbenchを任意の入口として追加し、Version Control実装を差し替え可能にする |
| 入口を変えても同じ仕事を続ける | `Same → UX-000012` | Workbench、MCP、AI、CLIで同じ正本・能力・状態・結果を使う成果は既存UXと同じである | Workbenchの情報・操作にも入口一貫性を適用する |

### Same判断の比較

#### Projectの現在地を根拠と不完全性付きで理解する

比較対象: `UX-000009`

| 比較軸 | 既存UX | 現在の要求 | 差と統合判断 |
|---|---|---|---|
| 担い手 | Project運営者／PM | 開発者／Project運営者／PM | 開発者を加えるが現在地理解は同じ成果 |
| 利用のきっかけ | Project状況を確認する時 | Workbenchから状況と作業を確認する時 | 入口が増えるだけで目的は同じ |
| 得られる結果 | 根拠と不完全性付きで現在地を理解する | 現在地から詳細と次の仕事へ進む | 後半はUX-000034へ分け、現在地理解は統合する |
| 避ける失敗 | 欠測・競合・古さの誤認 | 横断投影を完全な事実と誤認 | 同じ失敗類型である |

統合理由: Workbench固有の作業接続は新UXへ分けるが、Projectの現在地理解はUX-000009の成果を変えない。

#### リポジトリ単独で日常作業を続ける

比較対象: `UX-000010`

| 比較軸 | 既存UX | 現在の要求 | 差と統合判断 |
|---|---|---|---|
| 担い手 | 開発者 | 開発者／Project運営者 | 主な日常作業主体は共通する |
| 利用のきっかけ | Repositoryで作業を始める時 | Workbenchまたは既存Toolで作業する時 | 選択肢追加であり成果は同じ |
| 得られる結果 | 横断機能やCommitを前提にせず作業できる | Workbenchがなくても同じ正本と能力を利用できる | 既存成果の成立条件を補強する |
| 避ける失敗 | 横断機能やGit状態による無関係な停止 | Workbench強制、未Commit状態の拒否 | 同じ失敗類型である |

統合理由: Workbenchを追加しても単独Repository作業を守る成果はUX-000010へ統合できる。

#### 入口を変えても同じ仕事を続ける

比較対象: `UX-000012`

| 比較軸 | 既存UX | 現在の要求 | 差と統合判断 |
|---|---|---|---|
| 担い手 | 開発者と各入口の利用者 | 開発者、Project運営者、Front AI | 同じ入口選択者を含む |
| 利用のきっかけ | 接続方式または入口を選ぶ時 | Workbench、MCP、AI、CLIを選ぶ時 | Workbench追加であり独立成果ではない |
| 得られる結果 | 同じ正本・入力・状態・結果で続ける | 同じApplication Capabilityで続ける | 同じ成果である |
| 避ける失敗 | 入口ごとの第二正本や結果差 | Workbench固有Storeや状態差 | 同じ失敗類型である |

統合理由: Workbench固有価値はUX-000034へ分け、入口一貫性はUX-000012へ統合する。

## 5. 重要な体験

### この要求での利用の流れ

```text
Projectの状況を確認する
        ↓
根拠・不完全性・Attentionから次の仕事を選ぶ
        ↓
Owner情報または定型操作へ進む
        ↓
同じRepositoryのTreeとDiffを確認する
        ↓
Stage／Commit
        │
        ├─ ★ 重要場面: 外部へPushする直前
        ├─ ⚠ 失敗: 誤ったRemote・Branch・Commitを送る
        └─ ✓ 守る品質: 送信対象を示し人間の明示確認を得る
        ↓
通常Pushまたは別入口へ引き継ぐ
```

### サービス提供の流れの処置

処置: `作成`

```text
【利用者・責任者】開発者／Project運営者
        │ 利用者行動: 状況理解、仕事選択、差分確認、共有判断
        ▼
【利用者接点】WorkbenchのProject情報とVersion Control情報
        │
        ├─ 時間差: Project投影、作業ツリー観測、CommitおよびRemote反映の時点差を保つ
        ├─ 完了時: Owner Relation、現在差分、操作結果、次の行動を返す
        └─ 失敗時: 欠測、競合、権限不足、観測不能、Push拒否、終了後状態を返す
                     │
                     ▼
             【回復・判断する人】操作した利用者
                     └─ 次の行動: 再確認、操作取消、別入口、Credential処置または再試行を選ぶ

---------------- 可視境界 ----------------
                     ▼
【提供側】共通Application Capability＋Version Control Adapter
        └─ 提供責務: Ownerの意味を保ち、Git固有差を境界内へ閉じる
```

### 製品全体の整理への接続

- 利用の流れの統合先: [リポジトリで日常作業を進める](../../03_Experience_Map.md#リポジトリで日常作業を進める)、[プロジェクトの現在地を判断する](../../03_Experience_Map.md#プロジェクトの現在地を判断する)
- サービス提供の流れの統合先: [共同のサービス提供の流れ](../../04_Service_Blueprint.md#1-共同のサービス提供の流れ)

### この要求での責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| 利用者 | 次の仕事、変更内容、Commit、Push対象を判断する | 要約だけでOwner情報や差分確認を省略しない |
| Workbench／Front AI | 情報と操作を同じ能力へ接続し、事実・共有分析・推論を区別する | Project正本、Authority、Credentialを独自所有しない |
| Version Control Adapter | Tree、Diff、Stage、Commit、Push結果を現在環境から提供する | GitのIdentityや履歴を業務正本にしない |

### 補足する品質

- 多くの情報を並べるのではなく、結論、根拠、次の仕事、差分の順で理解できる。
- 横断ProjectionからOwner Relationへ戻れ、AI推論を保存済み事実として表示しない。
- Pushの要求発行、Remote受理および終了後状態を区別する。

## 6. 下流への引き渡し

| 接続先 | この要求から保持する意味 |
|---|---|
| IA（直後工程への正式な引き渡し） | Project Context、Owner情報、Attention、関係・経緯、次の仕事、Repository、Tree、差分、Stage、Commit、Remote、BranchおよびPush対象 |
| Quality Analysis / UX（伴走） | 状況理解、入口代替性、Owner到達、誤操作防止、Push前確認、欠測・競合・失敗後の行動 |
| UI（後続Contract Relation） | 情報量、段階的開示、作業の連続性、Diff／Stage／Pushの認識と確認 |
| SPEC（後続Contract Relation） | Projection、定型操作、Version Control結果、外部Effect、確認、失敗および回復の成立条件 |

### 妥当性確認と未確認事項

| 確認する仮説 | 観測方法 | 現在未確認の範囲 |
|---|---|---|
| Project情報と作業差分の接続が、既存Tool間の再探索と対応付け負担を減らす | Workbench Dogfood、Chat＋MCP／既存Git Clientとの比較、誤操作反例 | 役割別情報量、常時表示、部分Stage、Large Repository、認証失敗時の負担 |

- 現在判定: 後続の実利用確認が必要。UX定義を進めることは妨げない。
- 確認事項: Project情報と作業差分の接続が、既存Toolの併用より再探索と対応付け負担を減らし、誤操作を増やさないか。
- 判断者: 開発者、Project運営者およびQual-Lab。
- 未確認時の影響: Screen、Navigation、Visual、詳細なGit操作および性能条件を確定しない。
- Discoveryへ戻す条件: 既存入口より負担や誤操作が増える、Owner Relationを失う、または維持費が価値を上回る場合。
