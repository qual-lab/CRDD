# REQ-000007の利用者体験分析

成果物種別: UX分析

状態: UX再統合済み・独立再レビュー待ち
分析対象: [REQ-000007 出典と不完全性を保つプロジェクト全体の表示](../../../01_Discovery/Definitions/REQ-000007/requirement.md)

## 1. 要求の一次分析

```text
複数文書とログを辿り、現在地を自分で合成する／要約が完全かどうかを推測する
        ↓
解決策を先に固定せず、人の仕事として読み替える
        ↓
利用者に必要なこと
プロジェクトの現在地を根拠と不完全性付きで理解する
```

この要求で解くのは機能の有無だけではない。プロジェクト運営者／PMが「不足・競合・古さを踏まえて次の判断を選べる」状態へ進めないことを問題として扱う。具体的な画面、データ構造、API、構成要素または数値閾値はここで確定しない。

| 観点 | 内容 |
|---|---|
| 解決する問題 | 複数文書とログを辿り、現在地を自分で合成する／要約が完全かどうかを推測する |
| 利用者に必要なこと | プロジェクトの現在地を根拠と不完全性付きで理解する |
| 対象範囲 | プロジェクト運営者、PM、経営・管理層が、「複数文書とログを辿り、現在地を自分で合成する」状態から「プロジェクト全体の表示から現在地、根拠、観測時点および不足を同時に理解する」状態へ移る場面 |
| 対象外 | 具体的な画面、データ構造、実装方式および数値閾値の確定 |

## 3. 利用者に起きる変化

```text
変更前
────────────────
- 複数文書とログを辿り、現在地を自分で合成する
- 要約が完全かどうかを推測する
        │
        │ 出典と不完全性を保つプロジェクト全体の表示が変える体験
        ▼
変更後
────────────────
- プロジェクト全体の表示から現在地、根拠、観測時点および不足を同時に理解する
- `missing`、`restricted`、`stale`、`conflicting`を識別する
```

プロジェクトの要約が短くても、どの情報源をいつ読んだ結果か分からなければ判断には使えない。欠測や古い観測を隠した見やすさは、利用者を誤った確信へ導く。

この変化で守るのは操作手順ではない。プロジェクト運営者／PMがプロジェクトの現在地を根拠と不完全性付きで理解することで、不足・競合・古さを踏まえて次の判断を選べるようになることを守る。

## 4. 利用者成果への統合

```text
REQ-000007
   │
   └─ New  → UX-000009 プロジェクトの現在地を根拠と不完全性付きで理解する
```

| 利用者成果 | 処置 | 判断理由 | この要求が補う内容 |
|---|---|---|---|
| プロジェクトの現在地を根拠と不完全性付きで理解する | `New → UX-000009` | 本要求が「物理構成を意識せずプロジェクトの現在地を理解し、欠測・制限・競合・古さと情報源へ戻れる」という独立した利用者成果を最初に定義する。 | 状態・情報源・網羅範囲をまとめて確認することが、この要求固有の成立条件になる |

`Same`／`New`は技術用語の近さや件数目標では決めない。「利用者は、どの状況で、何をするためにシステムと関わり、何ができるようになるか」が同じかを比較する。提供能力、必要情報、品質、妥当性確認または下流の実現要素は、独立UXへ分割せず対応する成果の成立条件として保持する。

## 5. 重要な体験

### この要求での利用の流れ

```text
プロジェクト状況を確認する時
        ↓
状態・情報源・網羅範囲をまとめて確認する
        │
        ├─ ★ 重要場面: 現在の表示を信じる直前
        ├─ ⚠ 失敗:  欠測や古い値を完全な現在値と誤認する
        └─ ✓ 守る品質:  根拠、不完全性、観測時点を同時に示す
        ↓
不足・競合・古さを踏まえて次の判断を選べる
```

### サービス提供の流れの処置

処置: `作成`

```text
【利用者・責任者】プロジェクト運営者／PM
        │ 利用者行動: 現在地と不足を確認し、次の判断または情報源の確認を選ぶ
        ▼
【利用者接点】プロジェクト状況を確認する時
        │
        ├─ 時間差: 複数の情報源の観測時点が異なるため、投影時に鮮度差が生じる
        ├─ 完了時: プロジェクト状態、情報源、観測時点、欠測・制限・競合
        └─ 失敗時: 不足または競合する情報源と判断不能な項目を正本責任者へ返す
                     │
                     ▼
             【回復・判断する人】正本責任者
                     │ 返却された事実と判断不能範囲を確認
                     └─ 次の行動: 利用可能範囲で判断するか、情報源の更新を依頼する

---------------- 可視境界 ----------------
                     │ 時間関係: 複数の情報源の観測時点が異なるため、投影時に鮮度差が生じる
                     ▼
【提供側】提供システム
        └─ 提供責務: 取得範囲と不完全性を保った表示を返す
```

この図は、利用者行動、利用者が観測する接点、提供責務および失敗時の引き渡しを示す。内部構成要素の構造やプロトコルは下流工程で具体化する。

### 製品全体の整理への接続

- 利用の流れの統合先: [プロジェクトの現在地を判断する](../../03_Experience_Map.md#プロジェクトの現在地を判断する)
- サービス提供の流れの統合先: [共同のサービス提供の流れ](../../04_Service_Blueprint.md#1-共同のサービス提供の流れ)
- 横断成果物はこの個別分析から共通パターンを合成する。この要求での利用の流れ、責任境界または品質の代替にはしない。

### この要求での責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| プロジェクト運営者／PM | 現在地と不足を確認し、次の判断または情報源の確認を選ぶ | 欠測を推測で補うことを要求されない |
| 正本責任者 | 担当する状態と根拠を現行性付きで提供する | 他責任者の状態を代替して確定しない |
| 提供システム | 取得範囲と不完全性を保った表示を返す | 一部だけの結果を完全な結果として表示しない |

### 補足する品質

- 結果または状態を最初に受け取る時: 結論から情報源、改訂版、観測時点へ戻れる。（避ける失敗: 複数文書とログを辿り、現在地を自分で合成する）
- 結果を判断または引き継ぐ時: 一部取得成功を完全なプロジェクト状態へ畳まない。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 結果を判断または引き継ぐ時: 制限された情報源の存在を開示できない場合、その件数や名称も漏らさない。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 失敗・不足から次の行動を選ぶ時: 要約だけで判断できない時は、正本へ進む経路が分かる。（避ける失敗: 成立不能の理由や回復先が分からないまま作業が止まる）


## 6. 下流への引き渡し

```text
この要求で確定した利用者成果
        │
        ├─→ IA: 必要な情報・関係・見つけ方
        ├─→ UI: 誤認させない表示・操作意図
        ├─→ SPEC: 振る舞い・失敗・体験品質の条件
        └─→ Verification: 仮説を破る反例と観測
```

### 妥当性確認と未確認事項

| 確認する仮説 | 観測方法 | 現在未確認の範囲 |
|---|---|---|
| プロジェクト全体の表示から現在地、根拠、観測時点および不足を同時に理解する／missing、restricted、stale、conflictingを識別することで、複数文書とログを辿り、現在地を自分で合成するという負担または誤認を減らせる。 | 代表シナリオの利用者確認、利用者体験の専門レビュー、および品質期待を破る反例による下流検証 | プロジェクト運営者／PMが「プロジェクトの現在地を根拠と不完全性付きで理解する」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |

### 工程別の引き渡し

| 引き渡し先 | 具体化する義務 |
|---|---|
| 下流工程 | IAは項目ごとの情報源、現行性、網羅範囲および競合を表現する。UIは不完全性を0件や正常状態と同じ見た目にせず、Verificationは完全性を崩す反例を使う。 |

Discoveryへ戻す条件は、想定した利用者、問題または「プロジェクトの現在地を根拠と不完全性付きで理解する」という必要性が誤っていると分かった場合である。下流は実現方式を具体化してよいが、「不足・競合・古さを踏まえて次の判断を選べる」という成果を無断で弱めない。
