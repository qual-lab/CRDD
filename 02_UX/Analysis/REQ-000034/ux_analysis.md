# REQ-000034の利用者体験分析

成果物種別: UX分析

状態: UX再統合済み・独立再レビュー待ち
分析対象: [REQ-000034 リポジトリ固定Commitから使える標準ツール](../../../01_Discovery/Definitions/REQ-000034/requirement.md)

## 1. 要求の一次分析

```text
別配布ツールとのVersion対応を手で調べ、誤った組合せで実行する
        ↓
解決策を先に固定せず、人の仕事として読み替える
        ↓
利用者に必要なこと
リポジトリに対応する標準ツールを迷わず使う
```

この要求で解くのはツールの有無だけではない。CRDD採用リポジトリの利用者が、取得した固定Commitに対応するツール／実行基盤を自分で別リリースと照合せず、版不一致や改ざんを避けて利用できる状態へ進めないことを問題として扱う。具体的な配布方式、OS別形式または更新頻度はここで確定しない。

| 観点 | 内容 |
|---|---|
| 解決する問題 | 別配布ツールとのVersion対応を手で調べ、誤った組合せで実行する |
| 利用者に必要なこと | リポジトリに対応する標準ツールを迷わず使う |
| 対象範囲 | CRDD採用リポジトリの利用者が、「別配布ツールとのVersion対応を手で調べ、誤った組合せで実行する」状態から「現在リポジトリへ結び付いた標準ツール入口を選び、対応関係を手動照合せず利用できる」状態へ移る場面 |
| 対象外 | 具体的な画面、データ構造、実装方式および数値閾値の確定 |

## 3. 利用者に起きる変化

```text
変更前
────────────────
- 別配布ツールとのVersion対応を手で調べ、誤った組合せで実行する
        │
        │ リポジトリ固定Commitから使える標準ツールが変える体験
        ▼
変更後
────────────────
- 現在リポジトリへ結び付いた標準ツール入口を選び、対応関係を手動照合せず利用できる
```

リポジトリ固定Commitから使える標準ツールは、単に内部方式を成立させる要求ではない。「別配布ツールとのVersion対応を手で調べ、誤った組合せで実行する」状態から、「現在リポジトリへ結び付いた標準ツール入口を選び、対応関係を手動照合せず利用できる」状態へ変わり、利用者が次の判断へ進めることまでを体験として扱う。

この変化で守るのは特定の配布方式ではない。CRDD採用リポジトリの利用者が、リポジトリに対応する標準ツールを迷わず選び、固定Commit対応のツール／実行基盤を手動Version照合なしに利用できることを守る。

統合理由: Commit・配布集合・Manifest・実行基盤の整合は、同じツール選択成果を安全に成立させる条件であり、別の利用者成果ではない。

`Same`／`New`は技術用語の近さや件数目標では決めない。「利用者は、どの状況で、何をするためにシステムと関わり、何ができるようになるか」が同じかを比較する。提供能力、必要情報、品質、妥当性確認または下流の実現要素は、独立UXへ分割せず対応する成果の成立条件として保持する。

## 5. 重要な体験

### この要求での利用の流れ

```text
ツールを導入または起動する時
        ↓
Commit・配布集合・Manifest・実行基盤の対応を確認する
        │
        ├─ ★ 重要場面: 発見したツール／実行基盤を起動する直前
        ├─ ⚠ 失敗:  版不一致・欠落実行基盤・改ざんManifestを対応版と誤認する
        └─ ✓ 守る品質:  固定Commitと配布物の対応を検証し、不一致は外部変更の前に拒否する
        ↓
固定Commitに対応するツール／実行基盤を手動Version照合なしに利用できる
```

### サービス提供の流れの処置

処置: `作成`

```text
【利用者・責任者】CRDD採用リポジトリの利用者
        │ 利用者行動: リポジトリから標準ツール入口を発見して起動する
        ▼
【利用者接点】ツールを導入または起動する時
        │
        ├─ 時間差: clone／submodule取得後、起動時にCommitと配布物の対応を確認する
        ├─ 完了時: リポジトリCommit、Manifest、配布集合、実行基盤の識別情報、代表起動結果
        └─ 失敗時: 版不一致・欠落・改ざんをCRDD／ツールの配布者へ返す
                     │
                     ▼
             【回復・判断する人】CRDD／ツールの配布者
                     │ 返却された事実と判断不能範囲を確認
                     └─ 次の行動: 正しい固定Commit／配布物を取得するか、配布状態の確認を依頼する

---------------- 可視境界 ----------------
                     │ 時間関係: リポジトリ取得とツール起動の間に配布物が別更新されても固定Commitを基準にする
                     ▼
【提供側】提供システム
        └─ 提供責務: 固定CommitとManifest／実行基盤の対応を検証して起動する
```

この図は、利用者行動、利用者が観測する接点、提供責務および失敗時の引き渡しを示す。内部構成要素の構造やプロトコルは下流工程で具体化する。

### 製品全体の整理への接続

- 利用の流れの統合先: [実行基盤を導入・更新・回復する](../../03_Experience_Map.md#実行基盤を導入更新回復する)
- サービス提供の流れの統合先: [共同のサービス提供の流れ](../../04_Service_Blueprint.md#1-共同のサービス提供の流れ)
- 横断成果物はこの個別分析から共通パターンを合成する。この要求での利用の流れ、責任境界または品質の代替にはしない。

### この要求での責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| CRDD／ツールの配布者 | 固定Commitに対応するManifestと実行基盤を同梱・提示する | 別リリースとの手動照合を利用者へ転嫁しない |
| リポジトリ利用者 | リポジトリから標準入口を選び、不一致時は起動を止める | 名前やVersionを推測して別配布物を混ぜない |
| 提供システム | Commit・配布集合・Manifest・実行基盤を検証して起動する | 不一致・欠落・改ざん状態で機能を発行しない |

### 補足する品質

- ツールを発見する時: 現在の固定Commitに対応する入口を提示し、別リリースの手動照合を要求しない。
- 起動する時: Commit・配布集合・Manifest・実行基盤の不一致、欠落または改ざんを外部変更の前に拒否する。
- 拒否された時: 不整合の対象と正しい取得先を示し、Version推測を利用者へ要求しない。
