# REQ-000018の利用者体験分析

成果物種別: UX分析

状態: UX再統合済み・独立再レビュー待ち
分析対象: [REQ-000018 実行環境の信頼要素の分離](../../../01_Discovery/Definitions/REQ-000018/requirement.md)

## 1. 要求の一次分析

```text
公式署名があれば準拠・安全・利用許可もすべて成立したと思う
        ↓
解決策を先に固定せず、人の仕事として読み替える
        ↓
利用者に必要なこと
実行環境の信頼の各要素を別々に評価する
```

この要求で解くのは機能の有無だけではない。導入責任者が「公式版・派生版・組織版を自分の方針で選べる」状態へ進めないことを問題として扱う。具体的な画面、データ構造、API、構成要素または数値閾値はここで確定しない。

| 観点 | 内容 |
|---|---|
| 解決する問題 | 公式署名があれば準拠・安全・利用許可もすべて成立したと思う |
| 利用者に必要なこと | 実行環境の信頼の各要素を別々に評価する |
| 対象範囲 | 実行基盤を導入・実行する人が、「公式署名があれば準拠・安全・利用許可もすべて成立したと思う」状態から「準拠、改ざん有無、配布者、公式配布の違いを理解して利用判断できる」状態へ移る場面 |
| 対象外 | 具体的な画面、データ構造、実装方式および数値閾値の確定 |

## 3. 利用者に起きる変化

```text
変更前
────────────────
- 公式署名があれば準拠・安全・利用許可もすべて成立したと思う
        │
        │ 実行環境の信頼要素の分離が変える体験
        ▼
変更後
────────────────
- 準拠、改ざん有無、配布者、公式配布の違いを理解して利用判断できる
```

実行環境の信頼要素の分離は、単に内部方式を成立させる要求ではない。「公式署名があれば準拠・安全・利用許可もすべて成立したと思う」状態から、「準拠、改ざん有無、配布者、公式配布の違いを理解して利用判断できる」状態へ変わり、利用者が次の判断へ進めることまでを体験として扱う。

この変化で守るのは操作手順ではない。導入責任者が実行環境の信頼の各要素を別々に評価することで、公式版・派生版・組織版を自分の方針で選べるようになることを守る。

## 4. 利用者成果への統合

```text
REQ-000018
   │
   └─ New  → UX-000020 利用環境の信頼方針で実行基盤を選ぶ
```

| 利用者成果 | 処置 | 判断理由 | この要求が補う内容 |
|---|---|---|---|
| 利用環境の信頼方針で実行基盤を選ぶ | `New → UX-000020` | 本要求が「準拠、改ざん有無、配布者、公式表示および実行許可を区別し、自分の環境の方針で公式版・派生版・組織版を選べる」という独立した利用者成果を最初に定義する。 | 準拠・改ざん有無・配布者・実行許可を確認することが、この要求固有の成立条件になる |

`Same`／`New`は技術用語の近さや件数目標では決めない。「利用者は、どの状況で、何をするためにシステムと関わり、何ができるようになるか」が同じかを比較する。提供能力、必要情報、品質、妥当性確認または下流の実現要素は、独立UXへ分割せず対応する成果の成立条件として保持する。

## 5. 重要な体験

### この要求での利用の流れ

```text
実行基盤を導入または更新する時
        ↓
準拠・改ざん有無・配布者・実行許可を確認する
        │
        ├─ ★ 重要場面: 実行を信頼すると判断する場面
        ├─ ⚠ 失敗:  一つの署名表示を全保証と誤認する
        └─ ✓ 守る品質:  保証要素と決定権限を分離表示する
        ↓
公式版・派生版・組織版を自分の方針で選べる
```

### サービス提供の流れの処置

処置: `作成`

```text
【利用者・責任者】導入責任者（実行環境の導入・運用者）
        │ 利用者行動: 実行環境の信頼の各要素を別々に評価する
        ▼
【利用者接点】実行基盤を導入または更新する時
        │
        ├─ 時間差: 配布者の提示後、導入責任者が導入時に各信頼要素を評価する
        ├─ 完了時: 準拠、改ざん有無、配布者、公式表示、実行許可
        └─ 失敗時: 不足または不一致の信頼要素を導入責任者へ返す
                     │
                     ▼
             【回復・判断する人】導入責任者（信頼判断役割へ切替）
                     │ 返却された事実と判断不能範囲を確認
                     └─ 次の行動: 信頼方針に従って採用、拒否または追加確認する

---------------- 可視境界 ----------------
                     │ 時間関係: 配布者の提示後、導入責任者が導入時に各信頼要素を評価する
                     ▼
【提供側】提供システム
        └─ 提供責務: 方針に従って許可・拒否と根拠を返す
```

この図は、利用者行動、利用者が観測する接点、提供責務および失敗時の引き渡しを示す。内部構成要素の構造やプロトコルは下流工程で具体化する。

### 製品全体の整理への接続

- 利用の流れの統合先: [実行基盤を導入・更新・回復する](../../03_Experience_Map.md#実行基盤を導入更新回復する)
- サービス提供の流れの統合先: [共同のサービス提供の流れ](../../04_Service_Blueprint.md#1-共同のサービス提供の流れ)
- 横断成果物はこの個別分析から共通パターンを合成する。この要求での利用の流れ、責任境界または品質の代替にはしない。

### この要求での責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| 実行基盤の配布者 | Artifactの出所と自身が保証する範囲を提示する | 利用環境の実行許可まで保証したと表示しない |
| 導入責任者 | 保証要素と自環境の方針から利用可否を判断する | 公式表示だけで全信頼を推定しない |
| 提供システム | 方針に従って許可・拒否と根拠を返す | 配布者の信頼を利用者に代わって生成しない |

### 補足する品質

- 結果または状態を最初に受け取る時: 一つの信頼表示へ畳まない。（避ける失敗: 公式署名があれば準拠・安全・利用許可もすべて成立したと思う）
- 結果を判断または引き継ぐ時: 未確認を不正と同じ表示にしない。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 失敗・不足から次の行動を選ぶ時: 公式でない派生版も方針に従って評価できる。（避ける失敗: 成立不能の理由や回復先が分からないまま作業が止まる）


## 6. 下流への引き渡し

```text
この要求で確定した利用者成果
        │
        ├─→ IA: 必要な情報・関係・見つけ方
        ├─→ UI: 誤認させない表示・操作意図
        ├─→ SPEC: 振る舞い・失敗・体験品質の条件
        └─→ Verification: 仮説を破る反例と観測
```

### 妥当性確認と未確認事項

| 確認する仮説 | 観測方法 | 現在未確認の範囲 |
|---|---|---|
| 準拠、改ざん有無、配布者、公式配布の違いを理解して利用判断できることで、公式署名があれば準拠・安全・利用許可もすべて成立したと思うという負担または誤認を減らせる。 | 代表シナリオの利用者確認、利用者体験の専門レビュー、および品質期待を破る反例による下流検証 | 実行環境の導入・運用者が「実行環境の信頼の各要素を別々に評価する」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |

### 工程別の引き渡し

| 引き渡し先 | 具体化する義務 |
|---|---|
| 下流工程 | IAは準拠状況、改ざん有無、配布者、配布物を分け、UI／SPECは根拠別の状態を提示する。 |

Discoveryへ戻す条件は、想定した利用者、問題または「実行環境の信頼の各要素を別々に評価する」という必要性が誤っていると分かった場合である。下流は実現方式を具体化してよいが、「公式版・派生版・組織版を自分の方針で選べる」という成果を無断で弱めない。
