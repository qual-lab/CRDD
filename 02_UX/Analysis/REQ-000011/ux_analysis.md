# REQ-000011の利用者体験分析

成果物種別: UX分析

状態: UX再統合済み・独立再レビュー待ち
分析対象: [REQ-000011 リモート接続の作業領域限定](../../../01_Discovery/Definitions/REQ-000011/requirement.md)

## 1. 要求の一次分析

```text
Serverへ接続できれば全プロジェクトを扱えると思う／取得不能を権限不足か障害か推測する
        ↓
解決策を先に固定せず、人の仕事として読み替える
        ↓
利用者に必要なこと
許可された作業領域だけへ接続する
```

リモートCROS利用者が「場所が変わっても開示範囲を理解して安全に使える」状態へ進めないことを問題として扱う。

| 観点 | 内容 |
|---|---|
| 解決する問題 | Serverへ接続できれば全プロジェクトを扱えると思う／取得不能を権限不足か障害か推測する |
| 利用者に必要なこと | 許可された作業領域だけへ接続する |
| 対象範囲 | リモート接続利用者、CROS管理者が、「Serverへ接続できれば全プロジェクトを扱えると思う」状態から「現在の接続単位で利用を許可された作業領域だけが利用できると分かる」状態へ移る場面 |
| 対象外 | 具体的な画面、データ構造、実装方式および数値閾値の確定 |

## 3. 利用者に起きる変化

```text
変更前
────────────────
- Serverへ接続できれば全プロジェクトを扱えると思う
- 取得不能を権限不足か障害か推測する
        │
        │ リモート接続の作業領域限定が変える体験
        ▼
変更後
────────────────
- 現在の接続単位へGrantされた作業領域だけが利用できると分かる
- `credential_required`、`restricted`、`unavailable`を区別する
```

リモート接続では、接続できたことと閲覧できる範囲を同一視しやすい。利用者は現在の接続資格情報で何を利用でき、何が見えず、次に何が必要かを誤認なく理解する必要がある。

リモートCROS利用者が許可された作業領域だけへ接続することで、場所が変わっても開示範囲を理解して安全に使えるようになることを守る。

## 4. 利用者成果への統合

```text
REQ-000011
   │
   └─ New  → UX-000013 許可された作業領域だけをリモート利用する
```

| 利用者成果 | 処置 | 判断理由 | この要求が補う内容 |
|---|---|---|---|
| 許可された作業領域だけをリモート利用する | `New → UX-000013` | 本要求が「接続元や接続資格情報が変わっても、現在許可された作業領域だけを利用し、利用不能理由と管理能力を内容閲覧から区別できる」という独立した利用者成果を最初に定義する。 | 接続資格情報から現在の作業領域 Grantを確認することが、この要求固有の成立条件になる |

`Same`／`New`は技術用語の近さや件数目標では決めない。「利用者は、どの状況で、何をするためにシステムと関わり、何ができるようになるか」が同じかを比較する。提供能力、必要情報、品質、妥当性確認または下流の実現要素は、独立UXへ分割せず対応する成果の成立条件として保持する。

## 5. 重要な体験

### この要求での利用の流れ

```text
リモート接続を開始・再接続する時
        ↓
接続資格情報から現在の作業領域 Grantを確認する
        │
        ├─ ★ 重要場面: 利用可能情報を表示する時
        ├─ ⚠ 失敗:  利用不能なリポジトリの存在や内容を推測表示する
        └─ ✓ 守る品質:  現在Grantだけを開示し不足を補完しない
        ↓
場所が変わっても開示範囲を理解して安全に使える
```

### サービス提供の流れの処置

処置: `作成`

```text
【利用者・責任者】プロジェクト運営者／PM
        │ 利用者行動: 現在許可された範囲を理解して利用する
        ▼
【利用者接点】リモート接続を開始・再接続する時
        │
        ├─ 時間差: 接続資格情報発行と接続単位接続は別時点で行われ、Grant変更は次の認証へ反映される
        ├─ 完了時: 現在の接続単位の作業領域 Grantと利用不能理由
        └─ 失敗時: 不足・失効したGrantを内容を開示せずCROS管理者へ返す
                     │
                     ▼
             【回復・判断する人】CROS管理者
                     │ 返却された事実と判断不能範囲を確認
                     └─ 次の行動: 別接続資格情報を使うか、Grant変更を管理者へ依頼する

---------------- 可視境界 ----------------
                     │ 時間関係: 接続資格情報発行と接続単位接続は別時点で行われ、Grant変更は次の認証へ反映される
                     ▼
【提供側】提供システム
        └─ 提供責務: 接続ごとに現在Grantを確認し、許可範囲だけを返す
```

- 利用の流れの統合先: [リモートで情報と結果へ戻る](../../03_Experience_Map.md#リモートで情報と結果へ戻る)
- サービス提供の流れの統合先: [共同のサービス提供の流れ](../../04_Service_Blueprint.md#1-共同のサービス提供の流れ)

### この要求での責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| CROS管理者 | 接続資格情報へ作業領域 Grantを設定・失効する | 内容閲覧権限をシステム管理能力から推定しない |
| プロジェクト運営者／PM | 現在許可された範囲を理解して利用する | 利用不能リポジトリの存在や内容を推測しない |
| 提供システム | 接続ごとに現在Grantを確認し、許可範囲だけを返す | 古いセッションの決定権限を再利用しない |

### 補足する品質

- 結果または状態を最初に受け取る時: 認証後もGrant外のリポジトリ名、件数、状態を漏らさない。（避ける失敗: Serverへ接続できれば全プロジェクトを扱えると思う）
- 結果を判断または引き継ぐ時: 接続資格情報切替や失効後は投影を再評価する。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 結果を判断または引き継ぐ時: 追加許可による解錠（`Unlock`）は別接続資格情報が必要で存在開示可能な場合だけ示す。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 失敗・不足から次の行動を選ぶ時: システム管理能力と内容閲覧範囲を混同しない。（避ける失敗: 成立不能の理由や回復先が分からないまま作業が止まる）

## 6. 下流への引き渡し

本節では、IAへの直後工程の引き渡し、UX工程に伴走する品質分析、およびIA完了後にUI／SPECが保持する契約を区別する。UXの完了だけを根拠にIAを飛び越えてUIまたはSPECを開始しない。

| 接続先 | この要求から保持する意味 |
|---|---|
| IA（直後工程への正式な引き渡し） | 必要な情報、理解すべき差、関係、現行性および利用者成果 |
| Quality Analysis / UX（伴走） | 得られる結果、重要場面、失敗、品質期待および検証意図 |
| UI（後続Contract Relation） | IA完了後にUX定義とIA定義の双方から分析する認識・操作・判断の意図 |
| SPEC（後続Contract Relation） | IA完了後にUX定義とIA定義の双方から分析する成立条件・失敗・利用者成果 |

```text
この要求で確定した利用者成果
├─→ IA                         直後工程への正式な引き渡し
├─→ Quality Analysis / UX      UX工程に伴走する検証義務分析
└─→ UI / SPEC                  IA完了後に保持するContract Relation
```

### 妥当性確認と未確認事項

| 確認する仮説 | 観測方法 | 現在未確認の範囲 |
|---|---|---|
| 現在の接続単位へGrantされた作業領域だけが利用できると分かる／credential_required、restricted、unavailableを区別することで、Serverへ接続できれば全プロジェクトを扱えると思うという負担または誤認を減らせる。 | 代表シナリオの利用者確認、利用者体験の専門レビュー、および品質期待を破る反例による下流検証 | プロジェクト運営者／PMが「許可された作業領域だけへ接続する」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |

人間への確認:
- 現在判定: 後続の実利用確認が必要。UX工程の構造整理を止める判断事項ではない。
- 確認事項: プロジェクト運営者／PMが「許可された作業領域だけへ接続する」を行う際の判断基準、許容負担、利用環境および失敗後の選択
- 判断者: [製品全体の利用者像](../../02_Personas.md)の「プロジェクト運営者／PM」を代表する利用者とQual-Lab。
- 未確認時の影響: 利用者成果と品質期待は仮説として保持し、負担、閾値、UIまたは実装方式を確定しない。

Discoveryへ戻す条件は、想定した利用者、問題または「許可された作業領域だけへ接続する」という必要性が誤っていると分かった場合である。IA以降は実現方式を具体化してよいが、利用者成果を無断で弱めない。
