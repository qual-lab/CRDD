## 1. 要求から起こしたい利用者変化

```text
Before
────────────────
- 複数文書とlogを辿り、現在地を自分で合成する
- 要約が完全かどうかを推測する
        │
        │ 出典と不完全性を保つProject Viewが変える体験
        ▼
After
────────────────
- Project Viewから現在地、根拠、観測時点および不足を同時に理解する
- `missing`、`restricted`、`stale`、`conflicting`を識別する
```

Projectの要約が短くても、どのSourceをいつ読んだ結果か分からなければ判断には使えない。欠測や古い観測を隠した見やすさは、利用者を誤った確信へ導く。

## 6. サービス提供上の責任境界

| 担い手 | 担うこと | 越えてはならない境界 |
|---|---|---|
| 人間 | 対象、目的、許可範囲を確認し、提示された根拠から採否または次の行動を判断する。 | 内部状態や不足情報を推測で補って判断することを要求されない。 |
| System／AI | 利用者が「Project Viewから現在地、根拠、観測時点および不足を同時に理解する」状態へ進めるよう、必要な状態、根拠および選択肢を示し、許可された処理だけを行う。 | 不明状態を成功へ畳まず、権限・対象・意味を無断で拡張しない。 |
| 運用・確認者 | 期待品質を検証し、成立不能時は根拠を保ったまま責任所有者または回復経路へ移送する。 | 人間の判断、観測事実または正本を便宜的に上書きしない。 |

## 7. 重要場面、失敗、品質期待

| 重要場面 | 避ける失敗 | 品質期待 |
|---|---|---|
| 結果または状態を最初に受け取る時 | 複数文書とlogを辿り、現在地を自分で合成する | 結論からSource、Revision、Observed Atへ戻れる。 |
| 結果を判断または引き継ぐ時 | 必要条件を満たしていないのに完了・正常と理解する | 一部取得成功を完全なProject状態へ畳まない。 |
| 結果を判断または引き継ぐ時 | 必要条件を満たしていないのに完了・正常と理解する | 制限されたSourceの存在を開示できない場合、その件数や名称も漏らさない。 |
| 失敗・不足から次の行動を選ぶ時 | 成立不能の理由や回復先が分からないまま作業が止まる | 要約だけで判断できない時は、正本へ進む経路が分かる。 |
