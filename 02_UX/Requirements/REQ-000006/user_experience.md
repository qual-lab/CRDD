## 1. REQの一次分析

```text
Transportごとに結果、状態、エラー、許可の意味が変わる
        ↓
解決策を先に固定せず、人の仕事として読み替える
        ↓
UXとして必要
stdioとHTTPで同じ意味の操作を行う
```

この要求で解くのは機能の有無だけではない。MCP／Tool利用者・統合者が「Transportを変えても結果を読み替えなくてよい」状態へ進めないことを問題として扱う。具体的な画面、データ構造、API、Componentまたは数値閾値はここで確定しない。

| 観点 | 内容 |
|---|---|
| 解決する問題 | Transportごとに結果、状態、エラー、許可の意味が変わる |
| UX Need | stdioとHTTPで同じ意味の操作を行う |
| 対象範囲 | Local MCPをstdioまたはHTTPで使う人・Toolが、「Transportごとに結果、状態、エラー、許可の意味が変わる」状態から「利用する接続方法を変えても同じ依頼が同じ意味の結果と停止理由を返す」状態へ移る場面 |
| 対象外 | 具体的な画面、データ構造、実装方式および数値閾値の確定 |

## 3. 利用者に起きる変化

```text
Before
────────────────
- Transportごとに結果、状態、エラー、許可の意味が変わる
        │
        │ Local MCP Transport間の意味統一が変える体験
        ▼
After
────────────────
- 利用する接続方法を変えても同じ依頼が同じ意味の結果と停止理由を返す
```

Local MCP Transport間の意味統一は、単に内部方式を成立させる要求ではない。「Transportごとに結果、状態、エラー、許可の意味が変わる」状態から、「利用する接続方法を変えても同じ依頼が同じ意味の結果と停止理由を返す」状態へ変わり、利用者が次の判断へ進めることまでを体験として扱う。

この変化で守るのは操作手順ではない。MCP／Tool利用者・統合者がstdioとHTTPで同じ意味の操作を行うことで、Transportを変えても結果を読み替えなくてよいようになることを守る。

## 5. 重要な体験

### このREQのJourney

```text
利用する接続方式を選ぶ時
        ↓
同じ公開契約へ要求を渡す
        │
        ├─ ★ Critical: Transport境界を越えた意味同値
        ├─ ⚠ Failure:  接続方式ごとに状態や結果が変わる
        └─ ✓ Quality:  入力・認可・結果の意味を共通化する
        ↓
Transportを変えても結果を読み替えなくてよい
```

### このREQのService Blueprint

```text
利用者: Developer
        │ 利用する接続方式を選ぶ時
        ▼
提供System／AI
        ├─ 支援: stdioとHTTPで同じ意味の操作を行う
        ├─ ★ 判断点: Transport境界を越えた意味同値
        ├─ ⚠ 防止: 接続方式ごとに状態や結果が変わる
        └─ ✓ 保証: 入力・認可・結果の意味を共通化する
        │
        ▼
利用者
        └─ Transportを変えても結果を読み替えなくてよい
                │
                ▼
運用・確認者
        └─ 品質とOutcomeを反例で確認する
```

この図は、このREQで利用者、提供System／AI、運用・確認者の間に生じる受け渡しを示す。詳細な責任と越えてはならない境界は次表で固定する。

### 横断Synthesisへの接続

- Journeyの横断統合先: [Repositoryで日常作業を進める](../../03_Experience_Map.md#repositoryで日常作業を進める)
- Service Blueprintの横断統合先: [共同Service Blueprint](../../04_Service_Blueprint.md#1-共同service-blueprint)
- 横断成果物はこの個別分析から共通パターンを合成する。このREQのJourney、責任境界または品質の代替にはしない。

### このREQでの責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| 利用者（MCP／Tool利用者・統合者） | stdioとHTTPで同じ意味の操作を行うために、提示された状態と根拠から次の行動を判断する | 不足情報や内部状態を推測で補うことを要求されない |
| 提供System／AI | 同じ公開契約へ要求を渡すための状態、根拠および選択肢を示す | 接続方式ごとに状態や結果が変わる状態を成功・完了として表示しない |
| 運用・確認者 | 「入力・認可・結果の意味を共通化する」ことと、Transportを変えても結果を読み替えなくてよい状態へ到達できることを反証する | 未確認範囲や人間の判断を便宜的に上書きしない |

### 補足する品質

- 結果または状態を最初に受け取る時: Transport差を業務状態として見せない。（避ける失敗: Transportごとに結果、状態、エラー、許可の意味が変わる）
- 結果を判断または引き継ぐ時: 同じ入力・権限なら同じ意味になる。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 失敗・不足から次の行動を選ぶ時: 接続失敗とRuntime失敗を区別できる。（避ける失敗: 成立不能の理由や回復先が分からないまま作業が止まる）


## 6. 下流への引き渡し

```text

        │
        ├─→ IA: 必要な情報・関係・見つけ方
        ├─→ UI: 誤認させない表示・操作意図
        ├─→ SPEC: 振る舞い・失敗・体験品質の条件

```

### 妥当性確認と未確認事項

| 確認する仮説 | 観測方法 | 現在未確認の範囲 |
|---|---|---|
| 利用する接続方法を変えても同じ依頼が同じ意味の結果と停止理由を返すことで、Transportごとに結果、状態、エラー、許可の意味が変わるという負担または誤認を減らせる。 | 代表シナリオの利用者確認、UX専門Review、および品質期待を破る反例による下流検証 | Developerが「stdioとHTTPで同じ意味の操作を行う」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |

### 工程別の引き渡し

| 引き渡し先 | 具体化する義務 |
|---|---|
| 下流工程 | SPECは公開結果とTransport errorを分け、ArchitectureとVerificationは両入口の意味同値性を保証する。 |

Discoveryへ戻す条件は、想定した利用者、問題または「stdioとHTTPで同じ意味の操作を行う」という必要性が誤っていると分かった場合である。下流は実現方式を具体化してよいが、「Transportを変えても結果を読み替えなくてよい」という成果を無断で弱めない。
