# REQ-000001の利用者体験分析

状態: UX意味再分析済み・独立レビュー待ち
要求: `REQ-000001` 決定論的なRepository事前確認
探索元: [EXP-000001](../../../01_Discovery/Explorations/EXP-000001_Deterministic_Repository_Checks/exploration.md)

## 1. REQの一次分析

```text
レビューへ渡してから形式不備が見つかり、意味確認と機械修正が混ざる
        ↓
解決策を先に固定せず、人の仕事として読み替える
        ↓
UXとして必要
意味レビュー前に機械判定できる不備を落とす
```

この要求で解くのは機能の有無だけではない。CRDD成果物の作成者・確認者が「人が意味と判断へ集中できる」状態へ進めないことを問題として扱う。具体的な画面、データ構造、API、Componentまたは数値閾値はここで確定しない。

| 観点 | 内容 |
|---|---|
| 解決する問題 | レビューへ渡してから形式不備が見つかり、意味確認と機械修正が混ざる |
| UX Need | 意味レビュー前に機械判定できる不備を落とす |
| 対象範囲 | CRDD成果物を作成・確認する人が、「レビューへ渡してから形式不備が見つかり、意味確認と機械修正が混ざる」状態から「意味レビューの前に直せる不備と、なお人が判断する事項を区別して把握できる」状態へ移る場面 |
| 対象外 | 具体的な画面、データ構造、実装方式および数値閾値の確定 |

## 2. 利用者・目標・成果

```text
CRDD成果物の作成者・確認者

        │
        │ so that

```

| 項目 | 内容 |

| 利用場面 | 成果物をレビューへ渡す前 |
| Goal | 意味レビュー前に機械判定できる不備を落とす |
| Outcome | 人が意味と判断へ集中できる |
| REQ固有の差 | 同じ対象を決定論的に確認することが、この要求固有の成立条件になる |
| 根拠・確信度 | 探索元の課題と採用要求から導いた設計上の想定。個人属性、利用頻度および許容負担は未実測。 |

## 3. 利用者に起きる変化

```text
Before
────────────────
- レビューへ渡してから形式不備が見つかり、意味確認と機械修正が混ざる
        │
        │ 決定論的なRepository事前確認が変える体験
        ▼
After
────────────────
- 意味レビューの前に直せる不備と、なお人が判断する事項を区別して把握できる
```

決定論的なRepository事前確認は、単に内部方式を成立させる要求ではない。「レビューへ渡してから形式不備が見つかり、意味確認と機械修正が混ざる」状態から、「意味レビューの前に直せる不備と、なお人が判断する事項を区別して把握できる」状態へ変わり、利用者が次の判断へ進めることまでを体験として扱う。

この変化で守るのは操作手順ではない。CRDD成果物の作成者・確認者が意味レビュー前に機械判定できる不備を落とすことで、人が意味と判断へ集中できるようになることを守る。

| UX成果候補 | 処置・接続先 | 判断理由とこの要求が補う内容 |
|---|---|---|
| 決定論的な事前確認 | `New → UX-000011` | 「同じ対象と条件なら、意味レビュー前に同じ機械的不備を確認できる」を独立して変更・検証する成果である。REQ-000001では「意味レビュー前に機械判定できる不備を落とす」をGoalとし、機械指摘と意味判断を分けるに検査範囲や理由が分からないことを防ぐため、既存成果への条件追加ではなくNewとして追跡する。 |
| 行動可能な機械指摘 | `New → UX-000012` | 「対象箇所と直せる理由を理解し、意味判断との境界を誤認しない」を独立して変更・検証する成果である。REQ-000001では「意味レビュー前に機械判定できる不備を落とす」をGoalとし、機械指摘と意味判断を分けるに検査範囲や理由が分からないことを防ぐため、既存成果への条件追加ではなくNewとして追跡する。 |

## 5. 重要な体験

```text
成果物をレビューへ渡す前
        ↓
同じ対象を決定論的に確認する
        │
        ├─ ★ Critical: 機械指摘と意味判断を分ける
        ├─ ⚠ Failure:  検査範囲や理由が分からない
        └─ ✓ Quality:  同じ入力へ同じ指摘と修正可能な場所を返す
        ↓
人が意味と判断へ集中できる
```

### JourneyとSupporting Model

要求固有の区間は上のFlowが所有し、長い時間軸や複数主体との関係は次の既存成果物へ接続する。統合図をこの文書へ複製しない。

| Supporting Model | 処置 | 理由・参照先 |
|---|---|---|
| Experience Change | `作成` | 本文冒頭で、この要求が変える利用前後の仕事・認知・判断を示した。 |
| Experience Flow／Journey | `既存参照` | 本要求が関わる時間軸は[CRDD標準を変更・公開するJourney](../../03_Experience_Map.md#標準を変更検証公開する)を参照し、要求固有の区間は上表で示す。 |
| Service Blueprint | `非該当` | 本要求では複数主体の協調そのものを新しい体験成立条件にせず、必要な責任境界は次節で示す。 |
| User／Task Flow／Storyboard | `非該当` | 具体的な操作、画面遷移または利用環境の描写はIA／UIで具体化し、この要求分析では先取りしない。 |

### 責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| 利用者（CRDD成果物の作成者・確認者） | 意味レビュー前に機械判定できる不備を落とすために、提示された状態と根拠から次の行動を判断する | 不足情報や内部状態を推測で補うことを要求されない |
| 提供System／AI | 同じ対象を決定論的に確認するための状態、根拠および選択肢を示す | 検査範囲や理由が分からない状態を成功・完了として表示しない |
| 運用・確認者 | 「同じ入力へ同じ指摘と修正可能な場所を返す」ことと、人が意味と判断へ集中できる状態へ到達できることを反証する | 未確認範囲や人間の判断を便宜的に上書きしない |

### 重要場面・失敗・品質期待の対応

| 重要場面 | 避ける失敗 | 品質期待 |
|---|---|---|
| 機械指摘と意味判断を分ける | 検査範囲や理由が分からない | 同じ入力へ同じ指摘と修正可能な場所を返す |

要求から得た追加の品質期待は次のとおりである。主Flowの品質を置き換えず、下流で具体化する観測点として保持する。

| 重要場面 | 避ける失敗 | 品質期待 |
|---|---|---|
| 結果または状態を最初に受け取る時 | レビューへ渡してから形式不備が見つかり、意味確認と機械修正が混ざる | 同じ入力には同じ指摘が返る。 |
| 結果を判断または引き継ぐ時 | 必要条件を満たしていないのに完了・正常と理解する | 指摘は対象Pathと修正可能な理由を示す。 |
| 失敗・不足から次の行動を選ぶ時 | 成立不能の理由や回復先が分からないまま作業が止まる | Checker合格を意味品質の合格と誤認させない。 |

## 6. 下流への引き渡し

```text
このREQで確定した利用者成果
        │
        ├─→ IA: 必要な情報・関係・見つけ方
        ├─→ UI: 誤認させない表示・操作意図
        ├─→ SPEC: 振る舞い・失敗・体験品質の条件
        └─→ Verification: 仮説を破る反例と観測
```

### 妥当性確認と未確認事項

| 確認する仮説 | 観測方法 | 現在未確認の範囲 |
|---|---|---|
| 意味レビューの前に直せる不備と、なお人が判断する事項を区別して把握できることで、レビューへ渡してから形式不備が見つかり、意味確認と機械修正が混ざるという負担または誤認を減らせる。 | 代表シナリオの利用者確認、UX専門Review、および品質期待を破る反例による下流検証 | 役割ごとの利用頻度、許容待ち時間・操作負担、用語理解および支援技術差 |

### 工程別の引き渡し

| 引き渡し先 | 具体化する義務 |
|---|---|
| IA以降 | Qualityは決定論性と誤検知を、Documentationは人が理解できる指摘を、Verificationは意味監査との境界を具体化する。 |

Discoveryへ戻す条件は、想定した利用者、問題または「意味レビュー前に機械判定できる不備を落とす」という必要性が誤っていると分かった場合である。下流は実現方式を具体化してよいが、「人が意味と判断へ集中できる」という成果を無断で弱めない。
