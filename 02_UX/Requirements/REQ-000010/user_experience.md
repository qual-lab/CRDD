## 1. REQの一次分析

```text
UI、AI、CLIで状態名や操作結果が違う／UIだけが持つ直接更新を信頼する
        ↓
解決策を先に固定せず、人の仕事として読み替える
        ↓
UXとして必要
入口が違っても同じProject操作を行う
```

この要求で解くのは機能の有無だけではない。Workbench・MCP・CLI利用者が「Surface固有の状態や意味を覚えず使い分けられる」状態へ進めないことを問題として扱う。具体的な画面、データ構造、API、Componentまたは数値閾値はここで確定しない。

| 観点 | 内容 |
|---|---|
| 解決する問題 | UI、AI、CLIで状態名や操作結果が違う／UIだけが持つ直接更新を信頼する |
| UX Need | 入口が違っても同じProject操作を行う |
| 対象範囲 | Workbench、MCPまたはCLIからCRDDを使う人が、「UI、AI、CLIで状態名や操作結果が違う」状態から「入口が違っても同じ状態、判断境界、結果へ到達する」状態へ移る場面 |
| 対象外 | 具体的な画面、データ構造、実装方式および数値閾値の確定 |

## 3. 利用者に起きる変化

```text
Before
────────────────
- UI、AI、CLIで状態名や操作結果が違う
- UIだけが持つ直接更新を信頼する
        │
        │ Workbench・MCP・CLIの公開契約共有が変える体験
        ▼
After
────────────────
- 入口が違っても同じ状態、判断境界、結果へ到達する
- 所有正本のCommandまたはCandidateを通じて反映する
```

同じProject状態が入口ごとに違う意味や結果を返すと、利用者はSurface固有のルールを覚え、どれを信じるか判断しなければならない。Workbenchは別の業務実装ではなく、人向けの薄い入口である必要がある。

この変化で守るのは操作手順ではない。Workbench・MCP・CLI利用者が入口が違っても同じProject操作を行うことで、Surface固有の状態や意味を覚えず使い分けられるようになることを守る。

## 4. UX成果への統合

```text
REQ-000010
   │
   └─ Same → UX-000012 入口を変えても同じ仕事を続ける
```

| UX成果 | 処置 | 判断理由 | この要求が補う内容 |
|---|---|---|---|
| 入口を変えても同じ仕事を続ける | `Same → UX-000012` | 既存UXのFailure: Workbench・MCP・CLIで状態や結果の意味が変わり、入口ごとに仕事を読み替える<br>現在REQのFailure: 入口ごとに別の業務ロジックまたは結果契約が動き、同じProject操作を継続できない<br>Failure差: 現在REQは公開契約共有という成立手段を具体化するが、入口変更で仕事が途切れる失敗は同じである<br>同一Outcomeへ統合できる理由: 公開契約共有は同じ仕事を継続するためのCapability条件であり、別Outcomeではない | 共通の公開Application Contractへ要求することが、この要求固有の成立条件になる |

Same／Newは技術用語の近さや件数目標では決めない。「利用者は、どの状況で、何をするためにSystemと関わり、何ができるようになるか」が同じかを比較する。Capability、Information、Quality、Validationまたは下流の実現要素は、独立UXへ分割せず対応する成果の成立条件として保持する。

## 5. 重要な体験

### このREQのJourney

```text
利用場面に合う入口を選ぶ時
        ↓
共通の公開Application Contractへ要求する
        │
        ├─ ★ Critical: 候補・採用・Effectを選ぶ時
        ├─ ⚠ Failure:  入口ごとに別の業務ロジックが動く
        └─ ✓ Quality:  同じ入力・権限へ同じ構造結果を返す
        ↓
Surface固有の状態や意味を覚えず使い分けられる
```

### Service Blueprintの処置

処置: `作成`

```text
利用者
   ├─ [接点] Workbench
   ├─ [接点] MCP
   └─ [接点] CLI
                │ 同じ意図を渡す
                ▼
提供System
        │ 同じ権限と仕事として処理
        ▼
[接点] Surfaceに合う表現の同じ結果
        │
        ▼
利用者
        └─ 失敗時: 入口ごとに別の業務ロジックが動く場合は成功へ進めず、判断または回復を担う主体へ戻す
```

この図は、利用者行動、利用者が観測する接点、提供責務および失敗時の引き渡しを示す。内部Componentの構造やProtocolは下流工程で具体化する。

### 横断Synthesisへの接続

- Journeyの横断統合先: [Repositoryで日常作業を進める](../../03_Experience_Map.md#repositoryで日常作業を進める)
- Service Blueprintの横断統合先: [共同Service Blueprint](../../04_Service_Blueprint.md#1-共同service-blueprint)
- 横断成果物はこの個別分析から共通パターンを合成する。このREQのJourney、責任境界または品質の代替にはしない。

### このREQでの責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| 利用者 | 場面に合う入口を選び、同じProject操作を続ける | 入口ごとの内部状態や別手順を覚えることを要求されない |
| 提供System | 入口間で入力・Authority・状態・結果の意味を保つ | Surface固有の第二正本を作らない |
| 運用・確認者 | 各入口の同値性と失敗時の差を確認する | 表示の類似だけで意味同値と判定しない |

### 補足する品質

- 結果または状態を最初に受け取る時: 接続成功と、内容取得、候補作成、採用、Effect許可を区別する。（避ける失敗: UI、AI、CLIで状態名や操作結果が違う）
- 結果を判断または引き継ぐ時: Workbench内部に第二の正本や独自Authority判断を持たない。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 結果を判断または引き継ぐ時: Structured Resultを画面・自然言語・CLIで矛盾なく表現する。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 失敗・不足から次の行動を選ぶ時: Surface障害後も所有正本から状態を再取得できる。（避ける失敗: 成立不能の理由や回復先が分からないまま作業が止まる）


## 6. 下流への引き渡し

```text
このREQで確定した利用者成果
        │
        ├─→ IA: 必要な情報・関係・見つけ方
        ├─→ UI: 誤認させない表示・操作意図
        ├─→ SPEC: 振る舞い・失敗・体験品質の条件
        └─→ Verification: 仮説を破る反例と観測
```

### 妥当性確認と未確認事項

| 確認する仮説 | 観測方法 | 現在未確認の範囲 |
|---|---|---|
| 入口が違っても同じ状態、判断境界、結果へ到達する／所有正本のCommandまたはCandidateを通じて反映することで、UI、AI、CLIで状態名や操作結果が違うという負担または誤認を減らせる。 | 代表シナリオの利用者確認、UX専門Review、および品質期待を破る反例による下流検証 | Project Operator／PMが「入口が違っても同じProject操作を行う」を行う際の判断基準、許容負担、利用環境および失敗後の選択 |

### 工程別の引き渡し

| 引き渡し先 | 具体化する義務 |
|---|---|
| 下流工程 | IAは公開結果と表示状態を分ける。UI／SPECは同じCanonical状態から表示と操作可否を導き、Architectureは公開Application Contractを唯一の意味境界にする。 |

Discoveryへ戻す条件は、想定した利用者、問題または「入口が違っても同じProject操作を行う」という必要性が誤っていると分かった場合である。下流は実現方式を具体化してよいが、「Surface固有の状態や意味を覚えず使い分けられる」という成果を無断で弱めない。
