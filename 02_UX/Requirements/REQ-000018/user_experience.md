# REQ-000018の利用者体験分析

探索元: [EXP-000028](../../../01_Discovery/Explorations/EXP-000028_User_Owned_Runtime_Trust/exploration.md)

## 1. REQの一次分析

```text
公式署名があれば準拠・安全・利用許可もすべて成立したと思う
        ↓
解決策を先に固定せず、人の仕事として読み替える
        ↓
UXとして必要
Runtime Trustの各要素を別々に評価する
```

この要求で解くのは機能の有無だけではない。Deployment Ownerが「公式版・Fork・組織版を自分の方針で選べる」状態へ進めないことを問題として扱う。具体的な画面、データ構造、API、Componentまたは数値閾値はここで確定しない。

| 観点 | 内容 |
|---|---|
| 解決する問題 | 公式署名があれば準拠・安全・利用許可もすべて成立したと思う |
| UX Need | Runtime Trustの各要素を別々に評価する |
| 対象範囲 | Runtimeを導入・実行する人が、「公式署名があれば準拠・安全・利用許可もすべて成立したと思う」状態から「準拠、改ざん有無、Publisher、公式配布の違いを理解して利用判断できる」状態へ移る場面 |
| 対象外 | 具体的な画面、データ構造、実装方式および数値閾値の確定 |

## 3. 利用者に起きる変化

```text
Before
────────────────
- 公式署名があれば準拠・安全・利用許可もすべて成立したと思う
        │
        │ Runtime Trust要素の分離が変える体験
        ▼
After
────────────────
- 準拠、改ざん有無、Publisher、公式配布の違いを理解して利用判断できる
```

Runtime Trust要素の分離は、単に内部方式を成立させる要求ではない。「公式署名があれば準拠・安全・利用許可もすべて成立したと思う」状態から、「準拠、改ざん有無、Publisher、公式配布の違いを理解して利用判断できる」状態へ変わり、利用者が次の判断へ進めることまでを体験として扱う。

この変化で守るのは操作手順ではない。Deployment OwnerがRuntime Trustの各要素を別々に評価することで、公式版・Fork・組織版を自分の方針で選べるようになることを守る。

## 5. 重要な体験

```text
Runtimeを導入または更新する時
        ↓
準拠・Integrity・Publisher・実行許可を確認する
        │
        ├─ ★ Critical: 実行を信頼すると判断する場面
        ├─ ⚠ Failure:  一つの署名表示を全保証と誤認する
        └─ ✓ Quality:  保証要素と決定権限を分離表示する
        ↓
公式版・Fork・組織版を自分の方針で選べる
```

### 責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| 利用者（Deployment Owner） | Runtime Trustの各要素を別々に評価するために、提示された状態と根拠から次の行動を判断する | 不足情報や内部状態を推測で補うことを要求されない |
| 提供System／AI | 準拠・Integrity・Publisher・実行許可を確認するための状態、根拠および選択肢を示す | 一つの署名表示を全保証と誤認する状態を成功・完了として表示しない |
| 運用・確認者 | 「保証要素と決定権限を分離表示する」ことと、公式版・Fork・組織版を自分の方針で選べる状態へ到達できることを反証する | 未確認範囲や人間の判断を便宜的に上書きしない |

### 重要場面・失敗・品質期待の対応

| 重要場面 | 避ける失敗 | 品質期待 |
|---|---|---|
| 実行を信頼すると判断する場面 | 一つの署名表示を全保証と誤認する | 保証要素と決定権限を分離表示する |

要求から得た追加の品質期待は次のとおりである。主Flowの品質を置き換えず、下流で具体化する観測点として保持する。

| 重要場面 | 避ける失敗 | 品質期待 |
|---|---|---|
| 結果または状態を最初に受け取る時 | 公式署名があれば準拠・安全・利用許可もすべて成立したと思う | 一つのTrust表示へ畳まない。 |
| 結果を判断または引き継ぐ時 | 必要条件を満たしていないのに完了・正常と理解する | 未確認を不正と同じ表示にしない。 |
| 失敗・不足から次の行動を選ぶ時 | 成立不能の理由や回復先が分からないまま作業が止まる | 公式でないForkもPolicyに従って評価できる。 |

## 6. 下流への引き渡し

```text
このREQで確定した利用者成果
        │
        ├─→ IA: 必要な情報・関係・見つけ方
        ├─→ UI: 誤認させない表示・操作意図
        ├─→ SPEC: 振る舞い・失敗・体験品質の条件
        └─→ Verification: 仮説を破る反例と観測
```

### 妥当性確認と未確認事項

| 確認する仮説 | 観測方法 | 現在未確認の範囲 |
|---|---|---|
| 準拠、改ざん有無、Publisher、公式配布の違いを理解して利用判断できることで、公式署名があれば準拠・安全・利用許可もすべて成立したと思うという負担または誤認を減らせる。 | 代表シナリオの利用者確認、UX専門Review、および品質期待を破る反例による下流検証 | 役割ごとの利用頻度、許容待ち時間・操作負担、用語理解および支援技術差 |

### 工程別の引き渡し

| 引き渡し先 | 具体化する義務 |
|---|---|
| IA以降 | IAはConformance、Integrity、Publisher、Distributionを分け、UI／SPECは根拠別の状態を提示する。 |

Discoveryへ戻す条件は、想定した利用者、問題または「Runtime Trustの各要素を別々に評価する」という必要性が誤っていると分かった場合である。下流は実現方式を具体化してよいが、「公式版・Fork・組織版を自分の方針で選べる」という成果を無断で弱めない。
