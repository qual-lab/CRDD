# REQ-000018の利用者体験分析

状態: UX成果統合済み・独立レビュー待ち
要求: `REQ-000018` Runtime Trust要素の分離
探索元: [EXP-000028](../../../01_Discovery/Explorations/EXP-000028_User_Owned_Runtime_Trust/exploration.md)

## 1. 要求から起こしたい利用者変化

```text
Before
────────────────
- 公式署名があれば準拠・安全・利用許可もすべて成立したと思う
        │
        │ Runtime Trust要素の分離が変える体験
        ▼
After
────────────────
- 準拠、改ざん有無、Publisher、公式配布の違いを理解して利用判断できる
```

Runtime Trust要素の分離は、単に内部方式を成立させる要求ではない。「公式署名があれば準拠・安全・利用許可もすべて成立したと思う」状態から、「準拠、改ざん有無、Publisher、公式配布の違いを理解して利用判断できる」状態へ変わり、利用者が次の判断へ進めることまでを体験として扱う。

## 2. REQの一次分析

| 観点 | 内容 |
|---|---|
| 課題 | 公式署名があれば準拠・安全・利用許可もすべて成立したと思う |
| 対象範囲 | Runtimeを導入・実行する人が、「公式署名があれば準拠・安全・利用許可もすべて成立したと思う」状態から「準拠、改ざん有無、Publisher、公式配布の違いを理解して利用判断できる」状態へ移る場面 |
| 対象外 | 具体的な画面、データ構造、実装方式および数値閾値の確定 |

## 3. 利用者の想定とペルソナ

| 主な利用者 | 利用場面 | 目標・困りごと | 根拠・確信度 |
|---|---|---|---|
| Runtimeを導入・実行する人 | 公式署名があれば準拠・安全・利用許可もすべて成立したと思う | 準拠、改ざん有無、Publisher、公式配布の違いを理解して利用判断できる | 探索元の課題と採用要求から導いた設計上の想定。個人属性、利用頻度および許容負担は未実測。 |

ここでのペルソナは架空の人物像ではなく、判断や体験差へ必要な役割と利用状況である。

## 4. 体験区間とSupporting Model

| 項目 | 内容 |
|---|---|
| 起点 | 公式署名があれば準拠・安全・利用許可もすべて成立したと思う |
| 行動・判断 | 利用者は提示された状態と根拠から、続行、確認、修正または回復を選ぶ。 |
| 接点・期待支援 | 一つのTrust表示へ畳まない。／未確認を不正と同じ表示にしない。 |

## 6. サービス提供上の責任境界

| 担い手 | 担うこと | 越えてはならない境界 |
|---|---|---|
| 人間 | 対象、目的、許可範囲を確認し、提示された根拠から採否または次の行動を判断する。 | 内部状態や不足情報を推測で補って判断することを要求されない。 |
| System／AI | 利用者が「準拠、改ざん有無、Publisher、公式配布の違いを理解して利用判断できる」状態へ進めるよう、必要な状態、根拠および選択肢を示し、許可された処理だけを行う。 | 不明状態を成功へ畳まず、権限・対象・意味を無断で拡張しない。 |
| 運用・確認者 | 期待品質を検証し、成立不能時は根拠を保ったまま責任所有者または回復経路へ移送する。 | 人間の判断、観測事実または正本を便宜的に上書きしない。 |

## 7. 重要場面、失敗、品質期待

| 重要場面 | 避ける失敗 | 品質期待 |
|---|---|---|
| 結果または状態を最初に受け取る時 | 公式署名があれば準拠・安全・利用許可もすべて成立したと思う | 一つのTrust表示へ畳まない。 |
| 結果を判断または引き継ぐ時 | 必要条件を満たしていないのに完了・正常と理解する | 未確認を不正と同じ表示にしない。 |
| 失敗・不足から次の行動を選ぶ時 | 成立不能の理由や回復先が分からないまま作業が止まる | 公式でないForkもPolicyに従って評価できる。 |
