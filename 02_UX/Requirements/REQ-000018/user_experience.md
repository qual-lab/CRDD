## 3. 利用者に起きる変化

```text
Before
────────────────
- 公式署名があれば準拠・安全・利用許可もすべて成立したと思う
        │
        │ Runtime Trust要素の分離が変える体験
        ▼
After
────────────────
- 準拠、改ざん有無、Publisher、公式配布の違いを理解して利用判断できる
```

Runtime Trust要素の分離は、単に内部方式を成立させる要求ではない。「公式署名があれば準拠・安全・利用許可もすべて成立したと思う」状態から、「準拠、改ざん有無、Publisher、公式配布の違いを理解して利用判断できる」状態へ変わり、利用者が次の判断へ進めることまでを体験として扱う。

この変化で守るのは操作手順ではない。Deployment OwnerがRuntime Trustの各要素を別々に評価することで、公式版・Fork・組織版を自分の方針で選べるようになることを守る。

## 5. 重要な体験

### このREQのJourney

```text
Runtimeを導入または更新する時
        ↓
準拠・Integrity・Publisher・実行許可を確認する
        │
        ├─ ★ Critical: 実行を信頼すると判断する場面
        ├─ ⚠ Failure:  一つの署名表示を全保証と誤認する
        └─ ✓ Quality:  保証要素と決定権限を分離表示する
        ↓
公式版・Fork・組織版を自分の方針で選べる
```

### Service Blueprintの処置

処置: `作成`

```text
Runtime Publisher
        │ 準拠・Integrity・Publisher情報を提示
        ▼
Deployment Owner
        │ [接点] 保証要素を分けて確認
        │ 自環境のTrust Policyで利用可否を判断
        ▼
提供System
        │ 許可されたArtifactだけを実行候補化
        ▼
[接点] 許可・拒否と根拠
        │
        ▼
Deployment Owner
        └─ 失敗時: 一つの署名表示を全保証と誤認する場合は成功へ進めず、判断または回復を担う主体へ戻す
```

この図は、利用者行動、利用者が観測する接点、提供責務および失敗時の引き渡しを示す。内部Componentの構造やProtocolは下流工程で具体化する。

### 横断Synthesisへの接続

- Journeyの横断統合先: [Runtimeを導入・更新・回復する](../../03_Experience_Map.md#runtimeを導入更新回復する)
- Service Blueprintの横断統合先: [共同Service Blueprint](../../04_Service_Blueprint.md#1-共同service-blueprint)
- 横断成果物はこの個別分析から共通パターンを合成する。このREQのJourney、責任境界または品質の代替にはしない。

### このREQでの責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| Runtime Publisher | Artifactの出所と自身が保証する範囲を提示する | 利用環境の実行許可まで保証したと表示しない |
| Deployment Owner | 保証要素と自環境のPolicyから利用可否を判断する | 公式表示だけで全Trustを推定しない |
| 提供System | Policyに従って許可・拒否と根拠を返す | Publisherの信頼を利用者に代わって生成しない |

### 補足する品質

- 結果または状態を最初に受け取る時: 一つのTrust表示へ畳まない。（避ける失敗: 公式署名があれば準拠・安全・利用許可もすべて成立したと思う）
- 結果を判断または引き継ぐ時: 未確認を不正と同じ表示にしない。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 失敗・不足から次の行動を選ぶ時: 公式でないForkもPolicyに従って評価できる。（避ける失敗: 成立不能の理由や回復先が分からないまま作業が止まる）
