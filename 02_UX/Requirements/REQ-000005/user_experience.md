## 1. REQの一次分析

```text
一つのComponent変更が無関係な入口や操作を壊し、原因を利用者が切り分ける
        ↓
解決策を先に固定せず、人の仕事として読み替える
        ↓
UXとして必要
責務分離後も成立済みCapabilityを使う
```

この要求で解くのは機能の有無だけではない。Runtime保守者・利用者が「内部変更の影響範囲を限定して更新できる」状態へ進めないことを問題として扱う。具体的な画面、データ構造、API、Componentまたは数値閾値はここで確定しない。

| 観点 | 内容 |
|---|---|
| 解決する問題 | 一つのComponent変更が無関係な入口や操作を壊し、原因を利用者が切り分ける |
| UX Need | 責務分離後も成立済みCapabilityを使う |
| 対象範囲 | CRDD Toolを利用する人、保守する人が、「一つのComponent変更が無関係な入口や操作を壊し、原因を利用者が切り分ける」状態から「責務の違いを意識せず同じ入口を使え、故障時は影響する範囲を正確に知れる」状態へ移る場面 |
| 対象外 | 具体的な画面、データ構造、実装方式および数値閾値の確定 |

## 3. 利用者に起きる変化

```text
Before
────────────────
- 一つのComponent変更が無関係な入口や操作を壊し、原因を利用者が切り分ける
        │
        │ Runtime責務と依存方向の分離が変える体験
        ▼
After
────────────────
- 責務の違いを意識せず同じ入口を使え、故障時は影響する範囲を正確に知れる
```

Runtime責務と依存方向の分離は、単に内部方式を成立させる要求ではない。「一つのComponent変更が無関係な入口や操作を壊し、原因を利用者が切り分ける」状態から、「責務の違いを意識せず同じ入口を使え、故障時は影響する範囲を正確に知れる」状態へ変わり、利用者が次の判断へ進めることまでを体験として扱う。

この変化で守るのは操作手順ではない。Runtime保守者・利用者が責務分離後も成立済みCapabilityを使うことで、内部変更の影響範囲を限定して更新できるようになることを守る。

## 5. 重要な体験

### このREQのJourney

```text
Runtime Componentを置換する時
        ↓
公開契約と置換後のOwnerを照合する
        │
        ├─ ★ Critical: 利用者向けCapabilityの継続
        ├─ ⚠ Failure:  内部Path変更で公開入口が壊れる
        └─ ✓ Quality:  公開結果と成立済み能力を維持する
        ↓
内部変更の影響範囲を限定して更新できる
```

### このREQのService Blueprint

```text
利用者: Runtime導入・運用者
        │ Runtime Componentを置換する時
        ▼
提供System／AI
        ├─ 支援: 責務分離後も成立済みCapabilityを使う
        ├─ ★ 判断点: 利用者向けCapabilityの継続
        ├─ ⚠ 防止: 内部Path変更で公開入口が壊れる
        └─ ✓ 保証: 公開結果と成立済み能力を維持する
        │
        ▼
利用者
        └─ 内部変更の影響範囲を限定して更新できる
                │
                ▼
運用・確認者
        └─ 品質とOutcomeを反例で確認する
```

この図は、このREQで利用者、提供System／AI、運用・確認者の間に生じる受け渡しを示す。詳細な責任と越えてはならない境界は次表で固定する。

### このREQでの責任境界

| 担い手 | この要求で担うこと | 越えてはならない境界 |
|---|---|---|
| 利用者（Runtime保守者・利用者） | 責務分離後も成立済みCapabilityを使うために、提示された状態と根拠から次の行動を判断する | 不足情報や内部状態を推測で補うことを要求されない |
| 提供System／AI | 公開契約と置換後のOwnerを照合するための状態、根拠および選択肢を示す | 内部Path変更で公開入口が壊れる状態を成功・完了として表示しない |
| 運用・確認者 | 「公開結果と成立済み能力を維持する」ことと、内部変更の影響範囲を限定して更新できる状態へ到達できることを反証する | 未確認範囲や人間の判断を便宜的に上書きしない |

### 補足する品質

- 結果または状態を最初に受け取る時: 内部配置を利用手順へ露出しない。（避ける失敗: 一つのComponent変更が無関係な入口や操作を壊し、原因を利用者が切り分ける）
- 結果を判断または引き継ぐ時: 一部故障を全体成功に見せない。（避ける失敗: 必要条件を満たしていないのに完了・正常と理解する）
- 失敗・不足から次の行動を選ぶ時: 置換後も成立済みCapabilityを失わない。（避ける失敗: 成立不能の理由や回復先が分からないまま作業が止まる）
