## 1. 製品全体で目指す利用体験

CRDDを使う人が本当に知りたいのは、内部のフォルダ構成や実行の仕組みではない。「今どうなっているか」「自分は何を判断すべきか」「次に何が起きるか」を、必要な根拠とともに理解できることを目指す。

現在は、単純な状況確認でも対話AI、コーディングAI、Git操作ツール、リポジトリ内の文書や実行ログを行き来し、利用者自身がプロジェクトの現在地を組み立て直す場面がある。横断機能を使うために、普段のリポジトリ作業まで複雑にすることも避けたい。

そこで、日常の開発は対象リポジトリのまま続け、プロジェクト全体を見たいときだけCROS／MCP、短時間で確認・比較・定型操作をしたいときだけWorkbenchを使う体験を作る。標準を保守・配布する人、実行環境を導入・回復する人、外部へ情報を渡す人も、内部実装を推測せず、現在状態、根拠、許可範囲、次の安全な行動を理解できるようにする。入口が違っても、同じ正本、同じ受付規則、同じ判断境界へ到達する。

| 現在起き得ること | 目指す体験 |
|---|---|
| 状態を知るために複数の文書・ログ・会話をたどる | プロジェクトの現在地、欠測、判断待ち、次の行動を一つの入口から理解する |
| 対話AIとコーディングAIの間を人間が転記する | 仕事に必要な情報を整理し、同じ依頼の識別情報を保って往復する |
| 横断機能のために日常のリポジトリ作業まで変える | 手元の作業は単独で成立し、必要なときだけ横断する |
| 接続できたことを、内容の完全性や実行許可と誤認する | 接続、閲覧、候補作成、採用、実際の変更や外部作用を明確に分ける |
| 応答を失った時に新しい依頼としてやり直す | 同じ依頼の状態、結果、回復義務へ戻る |

### 根拠、対象、対象外

利用者が内部の署名、資源管理、エージェント間の情報搬送を毎回操作せず、依頼、必要な判断、成果物の受入へ集中できることを目指す。安全に止まれるだけでなく、止まった理由と次に必要な行動が分かることも体験の成立条件とする。

本工程の主入力は、[Discoveryで統合した判断](../01_Discovery/01_Product_Discovery.md#current-discovery-decisions)で採用した36件の要求である。Workbench／MCPだけでなく、CRDD標準の作成・保守、実行環境の実行・配布・回復、外部情報、文書、検証、バージョン管理を利用者体験として読み直す。要求ごとの利用前後の変化、想定利用者、体験区間、責任境界、品質期待を個別に分析し、その結果を現在有効なUX成果へ横断的にまとめる。

## 2. 利用者成果と要求の網羅状況

WorkbenchとMCPは、同じ使い方を強制する入口ではない。利用者がその時に使いやすい入口を選んでも、同じプロジェクト、情報源、状態、判断の境界、結果へ到達できることを利用者成果とする。

### 2.5. 共通体験原則

- **入口より意味を安定させる。** Workbench、AI＋MCP、CLI／TS APIで、同じ状態を成功、失敗または判断待ちへ別解釈しない。
- **手元をリモートの都合で複雑にしない。** 一つのリポジトリで足りる作業にCROS Server、接続資格情報切替または横断統合理解を要求しない。
- **全体像と不完全性を同時に示す。** 要約を簡単にしても、欠測、制限、競合、古い観測を消さない。
- **結論から正本へ戻れる。** プロジェクト／複数プロジェクトの一覧 表示は情報源、改訂版および所有成果物への導線を失わない。
- **人間の判断点だけを前面に出す。** 内部タスク、Lock、通信方式またはAgent間搬送を通常操作にしない。
- **接続、閲覧、候補作成、採用、外部作用（Effect）を分ける。** 一つが成立しても次の決定権限が成立したとは表示しない。
- **再接続を新規実行にしない。** 応答喪失時は同じ依頼の状態確認を先に示し、再実行を既定にしない。
- **選べない選択肢を見せない。** 存在開示不可の情報源、利用不能な接続資格情報または未登録機能を推測表示しない。
- **安全な停止を行動可能にする。** 拒否だけで終えず、発生地点、外部作用（Effect）状態、保持物、次に許される操作および判断主体を示す。
- **内部変更を利用者の意味変更にしない。** 責務分離、接続部化、通信方式変更または履歴管理実装の差し替え後も、公開結果と成立済み機能を保つ。
- **品質を後工程で突然発明しない。** 速さ、可用性、信頼性、安全性、鮮度、回復可能性、可読性および追跡可能性を、利用者が期待する体験として下流へ渡す。
