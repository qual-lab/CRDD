# CRDD／CROSの利用者像

状態: 候補（v0.21.0、公開済みの基準版: v0.20.1）
担当責任者: Qual-Lab
最終更新日: 2026-09-14
工程規則: [UX](../22_UX.md)

本書は、CRDD／CROSを使う人を、仕事、判断、困りごと、必要な支援の違いから整理する。ここで示す利用者像は、固定した役割や権限の階層ではない。同じ人でも、対象リポジトリ、接続先、認証情報、現在の仕事によって利用場面は変わる。

## 1. 利用者像の全体像

```text
日常の作業                         プロジェクト全体の判断

開発者 ─────────→ プロジェクト運営者／PM ─────→ 経営・管理層
    │                       │                         │
    │ リポジトリで働く       │ プロジェクト全体を見る   │ 複数プロジェクトを比べる
    ▼                       ▼                         ▼
ローカルAI／CLI        CROS／MCP／Workbench      複数プロジェクトの一覧


CRDD標準と実行環境を支える利用場面

CRDD閲覧者 ──→ CRDD作成者・保守者 ──→ 実行環境の導入・運用者 ──→ 外部へ渡す情報の所有者
```

この図は権限階層ではない。利用できる情報と操作は、リポジトリの既存権限、検証済みの接続関係、作業領域 Grant、開示制約、操作ごとの決定権限から決まる。`Workspace Grant`のような正式名称は、その仕組み自体を説明する箇所でだけ使う。

## 2. 製品全体の想定利用者

| 想定利用者 | 目的 | 主な困りごと | 主な利用場面 | 判断・責任 | 根拠・確信度 |
|---|---|---|---|---|---|
| 開発者 | 自分のリポジトリで日常の仕事を進める | 横断機能のために通常作業を複雑にされたくない。利用できない情報を推測で補いたくない | 実装、文書、論点、会議、品質確認 | 自分の作業内容と技術判断 | 課題探索で確認した方向。横断機能追加後の実負担は未実測 |
| プロジェクト運営者／PM | 一つの論理プロジェクトの現在地を理解し、次の判断を決める | 複数リポジトリ、文書、実行状態を毎回自分で統合したくない | 節目、論点、会議、品質、判断待ち、商務情報の可視性 | プロジェクトの進行と優先判断 | 保守・設計対話から導出。必要な表示と許容できる操作負担は未実測 |
| 経営・管理層 | 複数プロジェクトの重要な差と根拠を比較する | 詳細を全て読まずに判断したいが、単一の点数や不完全な要約にも依存したくない | 複数プロジェクトの一覧から個別の要因へ段階的に進む | 複数プロジェクトの優先順位と上位判断 | 構想上の利用者像。実組織で必要な情報の細かさは未確認 |
| CRDD閲覧者 | 公式入口や素材を見分け、工程成果物の意図を組み立て直さずに理解し、次の工程へ引き継ぐ | 見た目を保証と誤認したくない。確認項目順の文章や説明のない図から、問題・判断・引き渡す意図を再構成したくない | CRDDの文書、ツール、公開案内、視覚素材を初めて読む場面、および後工程の担当者として成果物を受け取る場面 | 使う入口、信頼判断に必要な根拠、次工程へ引き継ぐ意味を選ぶ | REQ-000031、REQ-000032、REQ-000035の要求定義から導出。初見読者と後工程担当者が同じ成果物から必要な意味を得られるかは未実測 |
| CRDD作成者・保守者 | 課題、変更、成立条件、影響先を収束させる | 確認項目、監査、署名、検証の状態を取り違えたくない | 標準の探索、設計、変更、監査、公開 | 標準変更と公開判断の支援 | CRDD自身の保守実績を根拠にする |
| 実行環境の導入・運用者 | 配布物を安全に導入・更新し、停止後に正しい回復を選ぶ | 内部状態を推測したり、再試行と回復を取り違えたりしたくない | 実行環境の導入、更新、診断、回復、清掃 | 配置環境で信頼する発行元と運用上の処置 | v0.19～v0.20の実運用を根拠にする |
| 外部へ渡す情報の所有者 | 許可した情報だけを外部へ渡し、出所付き結果を受け取る | 接続済みや過去の同意を包括許可へ広げられたくない | 外部AI、MCP、API、外部コミュニケーションへの送受信 | 送信先、目的、分類、同意、採否 | 外部情報境界と利用者判断を根拠にする |

## 3. 利用場面による違い

```text
同じ人
  │
  ├─ 現在のリポジトリだけで仕事する
  │      → 開発者としての利用場面
  │
  ├─ プロジェクト全体の状態を判断する
  │      → プロジェクト運営者／PMとしての利用場面
  │
  └─ 実行環境の停止後に回復を行う
         → 実行環境の導入・運用者としての利用場面
```

個別要求の分析は本書の想定利用者を参照し、その要求に固有の利用のきっかけ、制約、知識差、決定権限、失敗時の影響だけを補足する。想定利用者名を要求ごとに言い換えて、新しい人物像を量産しない。

## 4. 未確認事項

- 開発者、PM、経営・管理層それぞれが許容できる確認回数、待ち時間および情報量。
- Workbenchを使う場面と、対話AIまたは静的文書だけで足りる場面の境界。
- 支援技術、端末差、知識差によって成果へ生じる格差。
- 共有CROS Serverを実組織で使う場合の、既存の認証基盤とリポジトリ権限の接続。

これらは架空の属性で補わず、Prototype、代表利用者確認または実運用観測で更新する。
