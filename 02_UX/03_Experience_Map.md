# CRDD／CROSの利用体験の全体像

状態: 候補（v0.21.0、公開済みの基準版: v0.20.1）
担当責任者: Qual-Lab
最終更新日: 2026-09-14
工程規則: [UX](../22_UX.md)

本書は、利用者がどこから仕事を始め、何を理解・判断し、どこへ進むかを製品全体の時間軸で示す。リポジトリ構造や画面遷移ではなく、利用者の仕事と得られる結果を主語にする。

## 1. 製品全体の利用の流れ

```text
                    仕事を始める       状態を理解する       判断する          継続する
────────────────────────────────────────────────────────────────────
開発者              リポジトリ ────→ 手元の情報 ─────→ 実装・技術判断 ──→ リポジトリ作業
                                           │
                                           └─ 横断情報が必要 ─────────────┐
                                                                            ▼
プロジェクト運営者／PM  プロジェクト ─→ 状態＋不足＋根拠 ─→ 次の判断 ─────→ 論点／変更／実行
                                           │
                                           └─ 上位比較が必要 ─────────────┐
                                                                            ▼
経営・管理層         複数プロジェクト一覧 → 重要な差＋網羅範囲 → 優先判断 ──→ 個別の根拠確認

実行環境の運用者      配布物・現在状態 ─→ 信頼条件＋停止理由 ─→ 導入／回復判断 ─→ 実行または安全停止

外部へ渡す情報の所有者 送信候補 ──────→ 送信先＋目的＋範囲 ─→ 許可／拒否 ─────→ 出所付き結果の採否
```

通常の開発は一つのリポジトリだけで成立する。プロジェクト横断や複数プロジェクトの比較が必要になった時だけCROSへ進み、利用できない情報は推測で補わない。

## 2. 主な利用の流れ

| 利用の流れ | 主な想定利用者 | 起点 | 望む結果 | 関係する主なREQ |
|---|---|---|---|---|
| リポジトリで日常作業を進める | 開発者 | 対象リポジトリで仕事を始める | 横断機能を強制されず、入口が変わっても同じ正本と判断を使い、必要時だけCROSへ進める | `REQ-000006`、`REQ-000008`、`REQ-000010`、`REQ-000014`、`REQ-000028`、`REQ-000036` |
| プロジェクトの現在地を判断する | プロジェクト運営者／PM | プロジェクト全体を確認する必要がある | 状態、欠測、競合、根拠、判断待ちを理解して次へ進める | `REQ-000003`、`REQ-000007`、`REQ-000009`、`REQ-000012`、`REQ-000020` |
| 複数プロジェクトを比較する | 経営・管理層 | 複数プロジェクトの一覧上の注意対象を見つける | 許可範囲と網羅範囲を失わず、プロジェクトの根拠へ戻れる | `REQ-000013` |
| 対話と構築を往復する | 依頼者、対話AI、コーディングAI | 合意した仕事を構築へ渡す | 会話全文を転記せず、同じタスクへ判断と結果が戻る | `REQ-000002`、`REQ-000017`、`REQ-000029` |
| リモートで情報と結果へ戻る | リモート利用者 | 別Hostからプロジェクトへ接続する | 現在の作業領域範囲だけを使い、応答喪失後も同じ依頼へ戻れる | `REQ-000011`、`REQ-000021` |
| 実行基盤を導入・更新・回復する | 実行環境の導入・運用者 | 配布物を利用または停止後に再開する | 信頼要素、現在状態、残存、再試行、回復を取り違えない | `REQ-000004`、`REQ-000005`、`REQ-000015`、`REQ-000016`、`REQ-000018`、`REQ-000022`、`REQ-000023`、`REQ-000025`、`REQ-000034` |
| 外部情報を送受信する | 外部へ渡す情報の所有者 | 外部利用の候補が生じる | 許可範囲だけを送り、同じタスクへ出所付き結果を戻す | `REQ-000017`、`REQ-000024`、`REQ-000027` |
| 標準を変更・検証・公開する | CRDD作成者・保守者 | 課題または変更を受け取る | 意図、利用側、検証、根拠、公開状態を閉じる | `REQ-000001`、`REQ-000019`、`REQ-000026`、`REQ-000030`、`REQ-000031`、`REQ-000032`、`REQ-000033`、`REQ-000035` |
| 公式入口と素材を扱う | 閲覧者、CRDD作成者・保守者 | 公式らしい入口を選ぶ、または素材を収載する | 識別と保証を混同せず入口を選び、権利・原本・派生関係を確認して素材を使える | `REQ-000035` |

### リポジトリで日常作業を進める

```text
対象リポジトリを開く → 利用可能な正本・ツールを確認 → 作業・判断 → そのリポジトリで完了
                                      │
                                      └─ 横断情報が本当に必要 → CROSへ移る
```

### 公式入口と素材を扱う

```text
公式らしい入口を発見 → 識別表示と保証根拠を分けて確認 → 誤認なく入口を選ぶ

素材を収載・再利用   → 出所＋権利＋原本＋派生関係を確認 → 許可用途だけで使う
```

### プロジェクトの現在地を判断する

```text
プロジェクトを選ぶ → 状態＋不足＋根拠を確認 → 判断が必要な箇所を選ぶ → 正本または次の仕事へ
```

### 複数プロジェクトを比較する

```text
複数プロジェクトの一覧を見る → 網羅範囲付きの差を比較 → 注意プロジェクトを選ぶ → プロジェクトの根拠へ戻る
```

### 対話と構築を往復する

```text
対話で目的・判断を固める → 構造化情報を渡す → 構築する → 結果・不足・判断要求を同じタスクへ戻す
```

### リモートで情報と結果へ戻る

```text
接続する → 現在の作業領域範囲を確認 → 要求する → 応答喪失？
                                                   │
                                      Yes ─────────┘
                                       ↓
                              同じ依頼の状態を再取得
```

### 実行基盤を導入・更新・回復する

```text
配布物を選ぶ → 改ざん有無・配布者・信頼方針を確認 → 導入／更新 → 停止？
                                                                   │
                                                     Yes ──────────┘
                                                      ↓
                                      残存と外部変更の状態を確認して回復
```

### 外部情報を送受信する

```text
送信候補 → 送信先・目的・分類・範囲を確認 → 許可範囲だけ送信 → 出所付き結果 → 採否判断
```

### 標準を変更・検証・公開する

```text
課題・要求 → 設計・変更 → 利用側閉包 → 段階検証 → 独立確認 → 署名・E2E → 公開
```

## 4. 体験をまたぐ分岐

```text
現在の入口で必要情報が揃う？
        │
     ┌──┴──┐
    Yes    No
     │      │
     ▼      ▼
その場で継続  不足の種類を確認
              │
       ┌──────┼─────────┐
       ▼      ▼         ▼
   横断情報源  接続資格情報  未観測／競合
       │      │         │
       ▼      ▼         ▼
   CROSへ移る 再接続     推測せず判断待ち
```

横断移行、認証、再取得または回復は、失敗を隠すFallbackではない。利用者が不足の種類と次の行動を理解できる場合だけ選択肢として示す。

## 5. 現在未確認の体験

- Workbench、対話AI、CLIのどれが各利用の流れで最も少ない再探索で得られる結果へ届くか。
- 複数リポジトリやリモート接続でも、物理構造を隠しつつ根拠へ戻れるか。
- プロジェクト、複数プロジェクトの一覧および実行基盤運用で必要な情報量と認知負荷の上限。
- Topic／Meetingの候補化が、転記漏れを減らしながら確認負担を増やしすぎないか。
