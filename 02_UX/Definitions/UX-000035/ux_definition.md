# UX-000035 軽量なユーザー管理でRemote Accessを維持・回復する

成果物種別: UX定義
UX ID: `UX-000035`
状態: Canonical
確認状態: 初回Host設定の採用済み要求を候補伝播。契約・品質の限定独立レビュー済み・残指摘0。IA以降は初回設定未伝播、先の限定レビュー結果は今回へ流用しない。UX全体Ready・実装成立は未主張。
維持責任者: Qual-Lab

## 利用者成果

共有AI Profile管理では、manager／administratorが[UX-000018](../UX-000018/ux_definition.md)の設定変更を自分の担当範囲で完結できる。鍵を管理するadministratorの作業とは分け、管理表示があっても次の操作時の現在認可を省略しない。developerはProfile管理情報を取得せず、Repository単体の通常利用をこの管理拒否で妨げない。

未初期化CROSではHost操作者が最初のadministratorと鍵を安全に成立させて通常管理へ入れる。その後、managerとadministratorが対象ユーザーと業務の利用範囲を明示管理し、administratorが管理者資格・Credentialを維持することで、資格の漏洩・喪失後もProduct Dataを失わず通常管理へ戻れる。

```text
業務管理のmanager／administrator、鍵管理のadministrator／Server Host運用者
        │ Remote利用範囲を用意・回復する時
        ▼
対象ユーザーとRole権限・Credentialを安全に維持する
        │
        ▼
軽量な管理で接続を継続し、管理不能時も再入場できる
```

## 成立条件

利用者は鍵を定期的に取り直さず、明示失効・交換まで同じ鍵を使える。期限なしと内容へのアクセス許可は別で、現在のRole・公開範囲により利用できない場合がある。漏えいが疑われる場合は既存の明示失効・交換を選べる。自動更新を体験要件にしない。

- 鍵の発行・独立失効・交換はadministrator専用固定でON／OFF設定なし。通常は同一Process Workbench、MCPに鍵操作は非公開。Host回復はログイン済みローカル操作者の対話CLIで交換2操作だけを行い、追加認証・専用資格・承認コード・OS管理者昇格を要求しない。既存Root／Path検証を維持し、全4組で対象・影響を事前表示、Hostまたは全員交換の3組だけ明示確認する。

- managerとadministratorはユーザー登録・表示名変更、developer／managerの割当て・詳細権限、Repository登録・登録解除・公開範囲を管理する。administratorの付与・解除・降格を含むRole変更、administrator詳細権限と鍵3操作はadministratorだけが管理し、設定からdeveloperへ管理操作やmanagerへ管理者専用操作を委譲しない。
- manager自身の内容範囲も、変更前の現在権限による管理操作の認可とRole詳細権限・公開範囲の明示更新を経て変更できる。更新後は既存実アクセスを含めて次要求から評価し、管理能力だけで内容を自動付与しない。Repository登録だけで公開せず、登録解除は登録と対応する公開設定を同時に解除し、CROSから対象へ以後アクセスできなくする。他Repositoryの登録・公開設定と対象Repository／Product Dataは保持する。
- 標準Roleは`administrator`／`manager`／`developer`とし、詳細権限はRoleが所有する。ユーザーやCredentialへ個別追加権限を持たせない。
- 表示名の同名・改名でIDや権限が変わったと誤認せず、本人確認にも使わない。
- リセットでID・Roleを保持し旧資格を以後の要求で拒否する。開始済み操作の取消完了とは区別する。
- Role権限変更は次の認可へ反映し、Credentialへ古い権限を固定しない。
- Secretは発行時に一度だけ受け取り、再表示やRepository保存をしない。
- Administrator能力とManagement／Development内容へのアクセスを分ける。
- 鍵交換は「指定ユーザーの鍵交換」と「全員の鍵を無効化して指定既存管理者へ再発行」の2操作とする。通常管理とHost回復はAuthorityと入口を分け、鍵交換の意味は共通にする。
- 処置前に対象ユーザーID・表示名、失効範囲、新資格の発行先と保持する情報を確認できる。Host入口と全員交換は人間が明示確認する。
- Recovery途中の失敗を成功へ畳まず、同じRecoveryへ再入場できる。
- Repository単体利用へCROS RoleまたはCredentialを要求しない。

## 重要な体験・失敗・品質期待

指定ユーザー交換はそのユーザーの旧有効資格すべてを失効して新資格を一度発行し、他ユーザーの鍵を維持する。全員交換は全旧有効資格を失効し、指定した既存administratorへ新資格を一度発行する。その管理者が他ユーザーへ再発行・再配布するまで、他ユーザーは旧資格で接続できない。表示名ではなくuserIdで対象を固定する。

交換後の発行自体または結果記録が未確定となる発行失敗・応答喪失・Process喪失では、既知の失効範囲と発行結果の不明を同じRecoveryに保持し、利用者へ安全な確認先を示す。再入場時は現在状態を再観測し、再観測なしに完了・rollbackへ畳まない。旧資格が使える、処置が取り消された、開始済み操作も取消済みと説明せず、Secretを再表示しない。初回設定は未初期化を確定できる場合の別場面として下記に定義し、既存ユーザーの交換2操作とは分ける。

```text
Credential状態を管理する
        ↓
対象ユーザーを確認し、表示名／Role変更・資格リセットを選ぶ
        │
        ├─ ★ 重要場面: administrator Roleのユーザー資格をすべて失った時
        ├─ ⚠ 失敗: Remote認証へ依存する／Product Dataを削除する／Secretを記録する
        └─ ✓ 守る品質: ログイン済みHost操作者と明示確認でユーザー・Role・権限を保持し、鍵だけを交換する
        ↓
指定した既存管理者の新Credentialで通常管理へ戻る
```

業務管理の通常導線は「managerまたはadministratorが対象ユーザー・業務Roleと公開範囲を用意 → administratorが必要な鍵を発行 → 利用者が接続」である。登録済みと公開済み、業務設定完了と鍵発行完了を別の結果として理解できる必要がある。administratorの表示名変更は業務管理として許可され、管理者資格の変更とは区別する。

### 初回設定で利用可能にする体験

未初期化を確定できるCROSで、ログイン済みHost操作者が明示的な初回設定を選び、管理用表示名を入力する。最初のadministratorをUUIDで識別し、そのユーザーに結び付く鍵を一度だけ受け取って通常管理へ入れる。初回設定は既存ユーザーの鍵回復とは別の開始場面であり、Remote Credential、追加認証、専用資格、承認コード、OS管理者昇格を要求しない。

| 重要場面 | 利用者が理解する状態・次の行動 |
|---|---|
| 正しいHost Rootで管理状態と初回処理の記録がともに未初期化と確定 | 表示名を入力し、最初のadministrator UUIDとその鍵を一度だけ受け取る。Repository登録・公開・内容アクセスは自動付与されない |
| 既存状態・管理者がある | 初回設定を繰り返さず通常管理へ進む。鍵を失った場合は既存ユーザーのHost交換へ進む |
| 読取不能・破損・対象不明・Lock競合・回収待ち | 未初期化と説明せず、新しいユーザー・鍵を作らない。判定不能理由と再確認先を示し、元試行の存在を推定しない |
| 確認できた開始済み初回試行 | 同じ試行の非秘密相関と既知事実を保持し、現在状態を再観測する。新しい初回設定へ戻さない |
| ユーザー作成・発行・結果記録の一部まで成立 | 最初からやり直したと説明しない。作成済みUUID、発行・記録・受け渡しの各事実を分け、別UUIDの作成やSecret再表示をしない |
| 発行・結果記録は確定し、受け渡しだけ未確認 | 初回設定を再実行せず、作成済みadministratorを指定する既存Host交換を明示的に選ぶ |
| 発行自体・結果記録が不明 | 新しい交換へ進まず、元試行の現在状態を再観測する。通常発行に交換用Recoveryを新設しない |

必要な情報は、正しいHost Root、未初期化／既存／途中／観測不能の区別、管理用表示名、作成済みuserId、発行・結果記録・受け渡しの各事実、元試行への非秘密の相関、内容アクセス非付与および次の行動である。具体Schema、CLI引数、保存方式、相関値の物理形式は下流で決める。

MCPや自動起動から初期化しない。表示名を認可の根拠にしない。既存ユーザーまたは管理状態があれば初期化を拒否する。

### 登録解除と鍵の受け渡し未確認の体験

| 場面 | 利用者が理解できる結果と次の行動 |
|---|---|
| Repository登録解除 | 登録と対応する公開設定を同時に解除し、CROSから対象へ以後アクセスできなくなる。他Repositoryの登録・公開設定、対象Repository本体・Product Dataは残る。開始済み操作の取消完了とは別である |
| 発行と結果記録が確定し、受け渡しだけ未確認 | 「発行済み・受け渡し未確認」と示す。確実な未受領とは言わず、Secretの保存・再表示・自動再発行はしない。現在認可されたadministratorが、既存の交換操作を明示的に新しく実行できる |
| 指定ユーザーへの新しい交換 | 未受領の可能性がある発行済み資格を含め、そのユーザーの旧有効資格すべてを失効し、同じ既存ユーザーへ新資格を発行する。他ユーザーの鍵は保持する |
| 全員への新しい交換 | 発行済み資格を含め全ユーザーの旧有効資格を失効し、指定した既存administratorへ新資格を発行する。他ユーザーは通常の再発行・再配布が必要となる |
| 発行自体または結果記録が不明 | 新交換を案内せず、元発行のIdentityと既知事実に相関した現在状態の再観測へ戻す。元処理が交換の場合だけ同じexact Recoveryを保持する。通常発行に交換用Recoveryを新設しない |
| 現在の管理者認証が使えない | 通常Workbenchの認可を迂回せず、既存のログイン済みHost操作者向け交換入口へ案内する |

新しい交換は旧処理の再試行・再開ではなく、別Operation／別Recoveryとして扱う。旧発行の既知事実を保持し、新交換の成功から旧Secretの受領・rollback・取消を推定しない。処置前には現在の資格・権限を再確認し、遅延した旧応答から失効済み鍵を利用可能と案内しない。新交換にも指定ユーザー／全員の範囲、4組の事前表示・3組の明示確認、ユーザー情報・Role・権限・Product Data保持を適用する。

### 重要な失敗

- Administrator能力からProject内容へのAccessを自動的に得る。
- managerがadministratorを付与・解除・降格・詳細権限変更する、鍵を扱う、または設定で固定制限を迂回する。
- developerが管理操作を行う。
- Repository登録を公開と誤認し、登録解除でRepository／Product Dataを削除する。
- 生Secretまたは受信可能な同等値を保存・再表示する。
- Access RecoveryでRepositoryやProject Context等のProduct Dataを削除する。
- 元処理の発行自体または結果記録が未確定のまま別Recoveryを重ね、失効範囲や再入場先を失う。

### 体験品質への期待

- 日常管理はID・表示名・Role・Credentialだけで理解でき、メール・Password・申請等を要求しない。
- 業務設定をmanagerへ任せ、鍵が必要な時だけadministratorへ引き継げる。公開範囲の変更対象と次要求からの影響を理解し、manager自身の設定変更を内容の自動取得と誤認しない。
- 登録と公開、登録解除とデータ削除を区別し、未公開状態を接続可能と表示しない。
- 処置前に対象のIDと表示名、変更するRoleまたはリセットの影響を確認できる。
- 破壊的な失効範囲と保持するProduct Dataを実行前に理解できる。
- 秘密値を含めず、Recoveryの現在地と次の行動を追跡できる。

## 検証意図

登録解除では登録と対応公開設定の同時解除、他対象とRepository本体の保持、以後のCROSアクセス停止と開始済み取消の非同一性を観測する。重要な体験の3分岐（発行・記録確定／受け渡し未確認、発行・記録不明、管理者認証喪失）から、明示新交換・元Identity再観測・既存Host入口を正しく選べることを確認する。秘密再表示・自動再発行・不明時の新交換・通常発行への交換Recovery新設・遅延旧応答から失効済み鍵を利用可能と案内することを反証する。

鍵3操作を区別して観測する。administratorの同一Process Workbenchによる通常発行は新Secretの一度受領と既存資格不変、独立失効は旧資格の拒否と新資格・Secretの非発行を確認する。交換は定義済み失効範囲・新Secretの一度発行・情報保持・同じRecoveryを確認する。交換専用の回復条件を他の2操作へ転用せず、MCP鍵非公開・Host交換2操作だけを維持する。既存administratorの有効Credential全喪失からの再入場と、administrator不存在・Role／認可設定破損での処置前停止を区別する。

現在許可された主体が対象IDと表示名を区別して登録・変更し、administratorが鍵交換し、同名・改名で認可が変わらず、ID・名前・Role・権限が保たれて旧資格が拒否されることを観測する。指定ユーザー／全員の処置範囲と通常／HostのAuthority差、既存administratorの有効Credential全喪失から指定既存管理者への再発行、認可設定破損での処置前停止を確認する。Secret非保存、Administratorの内容非保有、失効後の発行失敗・応答喪失・Process喪失時の既知処置保持、同じRecoveryへの再入場と再観測なしの完了・rollback拒否、Repository単体非依存を含める。 MCPから鍵操作を呼べないこと、通常Host回復に追加認証を要求せず交換2操作以外へ広げないこと、4組表示・3組確認とRoot／Path境界を確認する。manager／administratorの許可範囲、developer管理拒否、managerによる管理者資格・鍵の操作と設定迂回の拒否、manager自身の明示範囲変更の次要求反映、登録≠公開・解除≠削除を観測する。

## 下流への引き渡し

初回設定のIA正式入力には上記の状態・情報・責任・時間関係を渡す。Qualityには、未初期化確定時の一度作成・一度受領、既存／途中／不明からの新作成0、Secret再表示0、内容自動付与0を観測する意図を渡す。UI／SPECへの後続関係では初回設定と通常Host回復を別場面として保持し、発行・記録不明の再観測と確定発行後の受け渡し不明の既存交換を混同しない。IA以降は今回未伝播である。

各引渡し先は、上記の登録・公開設定同時解除と、発行／結果記録／受け渡しの区別を保持する。各交換操作内では同じexact Recoveryを保持する。元交換の未確定結果への再入場と、確定発行後に明示する別Operation／別Recoveryの新交換を区別し、通常発行へ交換用Recoveryを新設しない。

Quality／UI／SPECを含む各引渡し先は、通常発行＝新Secret一度・既存資格失効なし、独立失効＝指定資格失効・新資格とSecret発行なし、交換＝定義済み失効範囲＋一度発行・情報保持・同じRecoveryを区別する。鍵3操作はadministratorの同一Process Workbench、MCP非公開、通常Host回復は交換2操作だけ。交換専用の回復条件を他操作へ転用しない。
