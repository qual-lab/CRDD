# UX-000035 軽量なユーザー管理でRemote Accessを維持・回復する

成果物種別: UX定義
UX ID: `UX-000035`
状態: Canonical
確認状態: Googleログイン・管理セッション・共有MCP認可への切替を反映。実サービスでの利用体験と下流全体の成立は未評価。
維持責任者: Qual-Lab

## 利用者成果

管理担当者は利用者と対象を取り違えずに共有アクセスを用意・維持できる。管理者がログインできなくなった場合も、Hostから既存の本人紐付けを直し、利用者IDと設定、プロダクトデータを保持して通常管理へ戻れる。

## 利用者・状況・目的

| 項目 | 内容 |
|---|---|
| 主な想定利用者／利用状況 | 業務範囲を管理するmanager／administrator、招待された共有利用者、初回設定と復旧を行うHost操作者 |
| 利用のきっかけ／場面 | 共有利用開始、招待、ロールや公開範囲の変更、管理者のログイン不能 |
| 目的 | 通常利用、管理、復旧で必要な権限を分けながら、接続を維持する |
| 得られる結果 | 通常利用には必要な許可だけを与え、回復で別人や別対象の設定を変えずに管理へ戻れる |

## 利用者に起きる変化

```text
変更前
接続鍵を発行・配布し、喪失時に交換する。
        ↓
変更後
Hostで最初の管理者を確認して設定する。
管理担当者はWorkbenchで招待し、利用者は本人確認して接続する。
管理者のログイン不能時は、Hostで同じ管理者の紐付けを直す。
```

## 成立条件

- 招待された本人がGoogleでログインして既存の利用者と紐付く。本人が使う招待引受、通常ログイン、ログアウトは管理操作と分ける。表示名やメールだけで以後の本人を決めない。
- アクセス管理の書込みには、同じ本人の短命管理セッションと現在の操作権限が必要である。業務管理はmanager／administratorで分担し、管理者ロールの付与・解除と既存利用者への招待再発行はadministratorだけが扱う。共有AI選定の体験は[UX-000018](../UX-000018/ux_definition.md)へつなぎ、設定管理を実行許可と混同しない。
- 共有MCPは別のOAuth認可を通し、許可された読取りと開発操作だけを使う。クライアント自体へのログインと、CRDDの本人・対象への許可を分ける。
- 共有リポジトリの登録では、管理担当者が対象とGitホストの本人連携を照合する。登録だけでは内容を利用できず、本人のGitホストでの実効権限が読み書きを決める。管理ロールを内容の権限と混同しない。登録解除はCRDDからの利用を止めるが、本体は消さない。

## 重要な体験・失敗・品質期待

### 初回設定で利用可能にする体験

Hostで未初期化を確認して最初の管理者とログイン主体を結び付ける。既存管理者のログイン不能は別の再紐付けへ案内する。対象と影響を確かめ、同じ既存利用者の紐付けだけを処置する。途中結果や不明を未初期化と見なさない。

### 重要な失敗

招待の期限切れ、別主体、権限不足、実サービスの観測不能、初回設定や再紐付けの途中失敗を区別する。処置結果が不明な場合は元の対象と既知結果へ戻り、自動再実行しない。実行中に対象への認可を失った場合、その対象で新しいTaskを始めたり結果を閲覧したりできない。実行への取消要求を「終了済み」「変更なし」と表示しない。

### 体験品質への期待

本人はどの入口・対象の利用を許可するかを理解できる。管理担当者には対象と影響を示し、非認可の人へ他者・対象の存在を出さない。共有モードの手順を、単体の信頼できる個人PC利用へ適用しない。

## 必要な情報

利用者の表示名・管理ロール・登録対象、招待と本人紐付けの状態、本人の現在の読み取り・書き込み可否、初回設定・再紐付けの既知結果と次の行動。秘密値を画面の参照情報や履歴として扱わない。

## 責任境界・制約・対象外

Workbenchは人間による管理、MCPは許可された操作、Hostは初回設定と既存管理者の回復を担う。接続鍵の手配布・交換、自己登録、Gitホスト上のアカウント作成を含めない。CRDDへのログイン、Gitホスト連携、クライアントへの利用許可のどれかが成立しても、他の権限の成立とは扱わない。

## 未確認事項と戻り条件

- 現在判定: 現行要求へ追従した体験定義。実利用の成立は未評価。
- 確認事項: 招待受取人・管理者・MCP利用者の本人確認と対象選択、およびHost復旧の操作負担。
- 判断者: 共有利用者、管理担当者、Host操作者およびQual-Lab。
- 未確認時の影響: 外部サービスでの体験品質を合格と扱わない。
- 戻り条件: 事前登録、管理境界、外部サービス対応や回復の範囲を変える必要が出た場合は要求へ戻す。

## 検証意図

新規Hostと既存管理者の回復、招待の正当な引受と再利用・別主体、権限付き管理書込みと通常接続での拒否、共有MCPと単体、登録解除と本体保持を別の観測とする。処置が確定した事実と応答が届かなかった事実、実行取消と終了も区別できることを確認する。

## 下流への引き渡し

| 接続先 | 保持する意味 |
|---|---|
| IA（直後工程への正式な引き渡し） | 利用者と外部主体、招待、通常／管理セッション、MCP同意、Gitホスト連携、本人の実効権限、初回と回復の状態を区別する |
| Quality Analysis / UX（伴走） | 本人・対象・権限の取り違え、旧方式への戻り、途中結果の成功誤認を反証する |
| UI（後続Contract Relation） | 通常と管理、招待発行と引受、MCP利用許可、再ログインとHost復旧を別導線にする |
| SPEC（後続Contract Relation） | 入口ごとの状態・公開範囲、権限再評価、同じ対象と回復結果の保持を扱う |
