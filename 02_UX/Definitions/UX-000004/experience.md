# UX-000004 失敗後の再試行・回復を選ぶ

成果物種別: UX定義
UX ID: `UX-000004`
状態: 現行正本
維持責任者: Qual-Lab

## 利用者成果

失敗後に状態確認、再試行、回復および清掃を取り違えず、二重外部への変更を避けて次の行動を選べる

```text
プロジェクト運営者／PM
        │ 失敗・取消・切断後に仕事を続ける時
        ▼
再試行・回復・清掃の違いを理解する
        │
        ▼
二重外部への変更を起こさず同じ仕事へ戻れる
```

## 利用者・状況・目的

| 項目 | 内容 |
|---|---|
| 主な想定利用者／利用状況 | [製品全体の利用者像](../../02_Personas.md)の「プロジェクト運営者／PM」 |
| 利用のきっかけ／場面 | 失敗・取消・切断後に仕事を続ける時 |
| 目的 | 再試行・回復・清掃の違いを理解する |
| 得られる結果 | 二重外部への変更を起こさず同じ仕事へ戻れる |

## 成立条件

- 失敗後に状態確認、再試行、回復および清掃を取り違えず、二重外部への変更を避けて次の行動を選べる
- 重要場面「同じ外部への変更を再発行する直前」で、避ける失敗を利用者が正常状態や完了として誤認しない。
- 入口、実装または利用主体が変わっても、この利用者成果の意味を維持する。

## 重要な体験と品質期待

```text
失敗・取消・切断後に仕事を続ける時
        ↓
再試行・回復・清掃の違いを理解する
        │
        ├─ ★ 重要場面: 同じ外部への変更を再発行する直前
        ├─ ⚠ 失敗:  結果不明の処理を新規実行して二重外部への変更を起こす
        └─ ✓ 守る品質:  外部への変更状態・回復対象の識別情報・終了条件を示す
        ↓
二重外部への変更を起こさず同じ仕事へ戻れる
```

## 必要な情報

失敗、外部変更の状態、回復、Retryを分ける

## 制約

- 画面、通信方式、内部構成要素または特定の実装方式をUX成果そのものにしない。
- 下流工程は利用者成果を弱めず、情報構造、操作、振る舞いおよび実現方式へ具体化する。
- 想定した利用者、状況または目的が誤っていると判明した場合は、元の要求分析とDiscoveryへ戻す。

## 検証意図

無条件Retry、古い決定権限、AI提供元差の隠蔽および二重外部への変更を反証する

具体的な試験段階、試験場面、期待結果は品質保証工程で設計し、この体験定義には実行結果を書き込まない。

## 下流への引き渡し

IAはタスク、担い手、決定権限、結果、回復の関係を分け、SPECとArchitectureは一連の状態変化全体の成立条件を定める。
