# UX-000015 複数プロジェクトを根拠付きで比較する

成果物種別: UX定義
UX ID: `UX-000015`
状態: Canonical
維持責任者: Qual-Lab

## 利用者成果

許可されたプロジェクトの重要差を比較し、網羅範囲と根拠を保ったまま必要なプロジェクトだけを掘り下げられる

```text
経営・管理層
        │ 複数プロジェクトの一覧の優先度を判断する時
        ▼
複数プロジェクトを根拠付きで比較する
        │
        ▼
重要差分から必要なプロジェクトだけを掘り下げられる
```

## 利用者・状況・目的

| 項目 | 内容 |
|---|---|
| 主な想定利用者／利用状況 | [製品全体の利用者像](../../02_Personas.md)の「経営・管理層」 |
| 利用のきっかけ／場面 | 複数プロジェクトの一覧の優先度を判断する時 |
| 目的 | 複数プロジェクトを根拠付きで比較する |
| 得られる結果 | 重要差分から必要なプロジェクトだけを掘り下げられる |

## 利用者に起きる変化

```text
変更前
────────────────
- プロジェクトごとの資料を開いて比較表を手で作る
- 集計結果を根拠不明のまま受け取る
        │
        │ 根拠と不完全性を保つ複数プロジェクトの一覧が変える体験
        ▼
変更後
────────────────
- 許可されたプロジェクトの要点を同じ観点で比較する
- 注意事項からプロジェクト、情報源、観測時点へ段階的に辿る
```

複数プロジェクトを比較する人には要約が必要だが、単一Scoreや色だけでは、なぜ注意が必要か、どの情報が欠けているかを判断できない。

経営・管理層／複数プロジェクトの一覧利用者が複数プロジェクトを根拠付きで比較することで、重要差分から必要なプロジェクトだけを掘り下げられるようになることを守る。

## 成立条件

- 許可されたプロジェクトの重要差を比較し、網羅範囲と根拠を保ったまま必要なプロジェクトだけを掘り下げられる
- 重要場面「要約から優先判断へ進む直前」で、避ける失敗を利用者が正常状態や完了として誤認しない。
- 入口、実装または利用主体が変わっても、この利用者成果の意味を維持する。

## 重要な体験・失敗・品質期待

```text
複数プロジェクトの一覧の優先度を判断する時
        ↓
複数プロジェクトを根拠付きで比較する
        │
        ├─ ★ 重要場面: 要約から優先判断へ進む直前
        ├─ ⚠ 失敗:  単一Scoreや欠測した集計で健全性を断定する
        └─ ✓ 守る品質:  比較値から根拠・古さ・不足へ戻れる
        ↓
重要差分から必要なプロジェクトだけを掘り下げられる
```

### 重要な失敗

- 単一Scoreや欠測した集計で健全性を断定する

### 体験品質への期待

- 比較値から根拠・古さ・不足へ戻れる

## 必要な情報

プロジェクト Summary、網羅範囲、観測時点、開示範囲を分ける

## 責任境界・制約・対象外

- UXが定義すること: 利用者、状況、目的、得られる結果、重要場面、失敗および品質期待。
- 下流工程へ残すこと: 情報構造、表示、操作、振る舞いおよび実現方式。
- 対象外: 特定画面、通信方式、内部構成、試験段階または実装方式の決定。

- 画面、通信方式、内部構成要素または特定の実装方式をUX成果そのものにしない。
- 下流工程は利用者成果を弱めず、情報構造、操作、振る舞いおよび実現方式へ具体化する。
- 想定した利用者、状況または目的が誤っていると判明した場合は、元の要求分析とDiscoveryへ戻す。

## 未確認事項と戻り条件

未確認事項は、統合元の要求ごとに次を保持する。

- REQ-000013: 経営・管理層が「複数プロジェクトを根拠付きで比較する」を行う際の判断基準、許容負担、利用環境および失敗後の選択
- 現在判定: 後続の実利用確認が必要。現在のUX定義をCanonical化する判断を止める事項ではない。
- 確認事項: REQ-000013: 経営・管理層が「複数プロジェクトを根拠付きで比較する」を行う際の判断基準、許容負担、利用環境および失敗後の選択
- 判断者: 経営・管理層を代表する利用者とQual-Lab。
- 未確認時の影響: 利用者成果、重要場面、失敗および品質期待を仮説として保持し、定量条件や実現方式を確定しない。
- Discoveryへ戻す条件: 想定した利用者、問題、望ましい変化または制約が誤っていると判明した場合。
- UX分析へ戻す条件: 利用場面、目的、得られる結果、重要場面、失敗または品質期待の統合判断が変わる場合。

## 検証意図

非開示プロジェクトの存在漏えい、単一Score断定および網羅範囲差の消去を反証する

具体的な試験段階、試験場面、期待結果は検証（Verification）工程で設計し、この体験定義には実行結果を書き込まない。
