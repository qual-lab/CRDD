# UX-000020 利用環境の信頼方針で実行基盤を選ぶ

成果物種別: UX定義
UX ID: `UX-000020`
状態: Canonical
維持責任者: Qual-Lab

## 利用者成果

準拠、改ざん有無、配布者、公式表示および実行許可を区別し、自分の環境の方針で公式版・派生版・組織版を選べる

```text
実行環境の導入・運用者
        │ 実行基盤を導入または更新する時
        ▼
実行環境の信頼の各要素を別々に評価する
        │
        ▼
準拠、改ざん有無、配布者、公式表示および実行許可を区別し、自分の環境の方針で公式版・派生版・組織版を選べる
```

## 利用者に起きる変化

```text
変更前
────────────────
- 公式署名があれば準拠・安全・利用許可もすべて成立したと思う
        │
        │ 実行環境の信頼要素の分離が変える体験
        ▼
変更後
────────────────
- 準拠、改ざん有無、配布者、公式配布の違いを理解して利用判断できる
```

実行環境の信頼要素の分離は、単に内部方式を成立させる要求ではない。「公式署名があれば準拠・安全・利用許可もすべて成立したと思う」状態から、「準拠、改ざん有無、配布者、公式配布の違いを理解して利用判断できる」状態へ変わり、利用者が次の判断へ進めることまでを体験として扱う。

導入責任者が実行環境の信頼の各要素を別々に評価することで、公式版・派生版・組織版を自分の方針で選べるようになることを守る。

## 成立条件

- 準拠、改ざん有無、配布者、公式表示および実行許可を区別し、自分の環境の方針で公式版・派生版・組織版を選べる
- 重要場面「実行を信頼すると判断する場面」で、避ける失敗を利用者が正常状態や完了として誤認しない。
- 入口、実装または利用主体が変わっても、この利用者成果の意味を維持する。

## 重要な体験・失敗・品質期待

```text
実行基盤を導入または更新する時
        ↓
実行環境の信頼の各要素を別々に評価する
        │
        ├─ ★ 重要場面: 実行を信頼すると判断する場面
        ├─ ⚠ 失敗:  一つの署名表示を全保証と誤認する
        └─ ✓ 守る品質:  保証要素と決定権限を分離表示する
        ↓
準拠、改ざん有無、配布者、公式表示および実行許可を区別し、自分の環境の方針で公式版・派生版・組織版を選べる
```

### 重要な失敗

- 一つの署名表示を全保証と誤認する

### 体験品質への期待

- 保証要素と決定権限を分離表示する

## 必要な情報

## 責任境界・制約・対象外

- UXが定義すること: 利用者、状況、目的、得られる結果、重要場面、失敗および品質期待。
- 下流工程へ残すこと: 情報構造、表示、操作、振る舞いおよび実現方式。
- 対象外: 特定画面、通信方式、内部構成、試験段階または実装方式の決定。

- 画面、通信方式、内部構成要素または特定の実装方式をUX成果そのものにしない。
- 下流工程は利用者成果を弱めず、情報構造、操作、振る舞いおよび実現方式へ具体化する。
- 想定した利用者、状況または目的が誤っていると判明した場合は、元の要求分析とDiscoveryへ戻す。

## 未確認事項と戻り条件

未確認事項は、統合元の要求ごとに次を保持する。

- REQ-000018: 実行環境の導入・運用者が「実行環境の信頼の各要素を別々に評価する」を行う際の判断基準、許容負担、利用環境および失敗後の選択
- REQ-000025: 実行環境の導入・運用者が「信頼する配布者と手元例外を自分で定める」を行う際の判断基準、許容負担、利用環境および失敗後の選択
- 現在判定: 後続の実利用確認が必要。現在のUX定義をCanonical化する判断を止める事項ではない。
- 確認事項: REQ-000018: 実行環境の導入・運用者が「実行環境の信頼の各要素を別々に評価する」を行う際の判断基準、許容負担、利用環境および失敗後の選択／REQ-000025: 実行環境の導入・運用者が「信頼する配布者と手元例外を自分で定める」を行う際の判断基準、許容負担、利用環境および失敗後の選択
- 判断者: 実行環境の導入・運用者を代表する利用者とQual-Lab。
- 未確認時の影響: 利用者成果、重要場面、失敗および品質期待を仮説として保持し、定量条件や実現方式を確定しない。
- Discoveryへ戻す条件: 想定した利用者、問題、望ましい変化または制約が誤っていると判明した場合。
- UX分析へ戻す条件: 利用場面、目的、得られる結果、重要場面、失敗または品質期待の統合判断が変わる場合。

## 検証意図

一つの署名やブランド表示への全保証集約とQual-Lab署名だけの実行資格化を反証する

具体的な試験段階、試験場面、期待結果は検証（Verification）工程で設計し、この体験定義には実行結果を書き込まない。
