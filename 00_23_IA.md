# 1. Purpose and Boundary

Information Architecture（IA）は、UXの体験とService Blueprintを、利用者が理解、探索、比較、判断、操作できるObject、Relation、Information Structure、Responsibility、Lifecycle Concept、Navigation、Languageへ変換する工程である。

```text
利用者は何を一つの対象として考えるか
対象のIdentityとRelationは何か
どの情報を、どの単位と観点で探し比較するか
誰が何を知り、作成し、更新し、判断するか
どの責務からどの責務へ移動するか
UIとBehavior Specificationへ何を明確化させるか
```

IAはSitemap、Screen一覧、DB Schema、Backend Entityを作る工程ではない。それらをInputまたは下流候補として参照できるが、利用者と業務の意味を置き換えない。

# Phase Process Contract

本章はIA工程の入口、変換、責務Coverage、出口、Phase Gate、Auditの正本である。後続章は本ContractをArtifact構造とSkill実行へ具体化し、独自の完了条件を持たない。Artifactの統合・分割・配置は[`00_03_Documentation.md`](00_03_Documentation.md)に従う。

## Phase Entry Contract

IAは対象Scopeについて、次を受け取る。

- Source REQ / UX、Target Actor、Persona / Situation
- UX Outcome、Journey / Scenario、Service Blueprint、Critical Moment
- Experience Principle、Non-goal、Constraint
- Human / System / AI Responsibility、Trust / Consent / Control上のObligation
- Control / Adaptation Need、Candidate Disposition、Configuration Candidate
- Success / Risk、Assumption、Open Question
- UX Coverage Summary、Unresolved Gap、Human Review Result
- UX → IA Phase Transition Review Result、Reviewed Revision、または明示された`review_exception`

通常は[UXのExit and Handoff](00_22_UX.md#exit-and-handoff)から受け取る。UX Outcome、Service Blueprint、対象Scope、人間Reviewが不足する場合はUXへ戻す。UXが`Partial — Human Authorized`の場合、IAは承認されたScopeだけを扱い、未網羅項目、Risk、後続Ownerを引き継ぐ。

## Transformation Contract

UXの体験と提供責務を、Object / Identity / Relation、Hierarchy / Grouping / Facet / Metadata、Information Source、Ownership / Authority、Lifecycle / State Concept、Responsibility、Navigation / Findability、Glossary、Configuration Model、およびUI / Behavior SpecificationへのObligationへ変換する。

Screen、Component、DB Table、API、詳細なState TransitionをIAの起点または結論として先取りしない。既存構造はEvidenceまたはConstraintとして扱い、利用者のMental Modelと区別する。

## Required Responsibility Coverage

対象Scope全体について、次の責務を網羅する。

| Responsibility | Required Context |
|---|---|
| Blueprint Mapping | UX Step、User Goal / Action、Object / Information、Source、Actor、責任、Failure / Recovery |
| Object Model | Object、Definition、Identity、Relation、Cardinality / Constraint Candidate、Lifecycle、Ownership |
| Information Structure | Hierarchy、Grouping、Facet、Metadata、List / Detail / History、Comparison、Findability |
| Responsibility Model | Actor / Role、Create / Read / Update / Decide / Approve、Authority、Surface Responsibility |
| Navigation / Flow | Entry、Task / Navigation Path、Cross-responsibility Flow、Return / Recovery、重要なContext維持 |
| State and Language | State Concept、用語、Synonym、禁止語、同名異義・異名同義、利用者向けMeaning |
| Configuration Structure | Preference / Policy / Setting Candidate、Owner / Authority、適用対象とScope、Inheritance / Override、現在値とEffective ValueのConcept、Visibility、変更・撤回・Reset、固定理由 |
| Governance Structure | Trust Surface、Data / Inference Provenance、Visibility、Current Assurance、Future-plan Informationの分離 |
| Downstream Obligation | Pairing Unit Candidate、UIとBehavior Specificationへ渡す責務の分離、Source Trace、Coverage Summary、Unresolved Gap |

Service Blueprintの全Action / Stepを、必要なObject / Information、情報源、更新・利用・判断主体、責任、Failure / Recoveryへ対応づける。BlueprintをScreen一覧へ直接変換しない。

## Scope and Coverage State

各UX Scenario / Blueprint行、Object / Relation、Actor / Responsibility、Navigation Pathと各IA責務を対応づけ、`Complete for Scope`、`Partial — Human Authorized`、`Blocked`、`Not Started`、`Not Applicable`で追跡する。`Not Applicable`には人間が確認した理由を必要とする。

一部のObject Model、Sitemap、主要Flow、または代表Screenの構造ができたことを、対象Scope全体のIA完了と表現してはならない。

## Human Decisions

人間はBusiness Concept、Objectの意味、責任境界、Ownership / Authority、Configurationの意味・Owner・Subject・適用Scope、およびInheritance / Override関係を設けるか、用語、重要Navigation、Data Visibility、`Not Applicable`、部分Handoffを決定する。正確なOption、Default、Precedence、Permission、適用・Reset・失敗時BehaviorはBehavior Specificationが所有する。AIは候補、Conflict、Gapを提示できるが、Domain Boundary、Authority、Data Ownership、Policyを自己決定しない。

## Exit and Handoff

通常Handoff候補をHuman Gateへ提示する前に、[Phase Transition Review](00_10_Agent.md#72-phase-transition-review-and-remediation-loop)を対象Scope / Revisionへ実行する。移行に影響するFindingはIAまたは責務を持つ工程で修正し、修正後Revisionの再Reviewで`Pass`を得る。Review省略または未解消Findingを伴う移行は[Human-directed Review Exception](00_10_Agent.md#73-human-directed-review-exception)がある場合だけ通常Routeと区別して扱う。

通常のUI / Behavior Specification Handoffは、対象Scopeが`Complete for Scope`で、人間Reviewを通過し、[UI Phase Entry Contract](00_25_UI.md#phase-entry-contract)と[Behavior Specification Phase Entry Contract](00_26_Behavior_Specification.md#phase-entry-contract)の両方を満たす場合に限る。

UIとBehavior Specificationは[`00_24_UI_Behavior_Specification.md`](00_24_UI_Behavior_Specification.md)に従って並行・反復してよい。ただし、一方の着手をIA全体の完了または他方のEntry充足とみなさない。一方だけを先行させる場合は、対象Scope、未網羅項目、Risk、受信先、後続Ownerを人間が承認した`Partial — Human Authorized`として扱う。

## Phase Gate Criteria

- UX Scope、Source REQ / UX、Service BlueprintへTraceできる
- 全Blueprint Step、Actor / ScenarioをIA Coverageへ対応づけている
- Object、Identity、Relation、Hierarchy、Grouping / Facet / Metadata、Responsibility、Lifecycle / State Concept、Navigation、Glossaryを対象Scopeで判定している
- UXのControl / Adaptation NeedをConfiguration Candidateへ変換し、Owner、適用Scope、Inheritance / Override、Visibility、固定理由を判定している
- ObjectをScreenやDB Tableと、NavigationをScreen Flowと、State Conceptを詳細Behaviorと同一視していない
- 同一責務の重複、用語Conflict、Ownership / Authority Conflictを解消または明示している
- Trust Surface、Consent / Settings、現在の保証、Future-plan Informationを必要範囲で区別している
- UIとBehavior SpecificationへのObligationを分離し、両Entry Contractを満たしている
- Coverage Gapと部分Handoff承認を記録している
- 対象RevisionのPhase Transition Reviewが`Pass`であり、移行に影響するFindingのRemediationと再Reviewが完了している

## Phase Audit Checklist

- UX Scenario / Blueprintに対応しないObject、未変換Step、未対応Failure / Recovery
- Screen-first、Tree-first、DB-first、Backend Entity-firstの構造
- Object、Identity、Relation、Responsibility、Lifecycle、Navigation、Glossaryの欠落または重複
- Control / Adaptation Needに対応するConfiguration Candidate、Owner、Scope、Inheritance / Overrideの欠落
- ObjectとScreen、IA NavigationとUI Screen Flow、State ConceptとSPEC State Transitionの混同
- 単一Treeへの強制、Facet不足、一覧・詳細・履歴・比較・検索責務の欠落
- 現在の保証、Consent / Settings、将来情報を同じ責務へ混在させる構造
- UI / Behavior Specification Obligationの混同、片側だけへの暗黙Handoff
- Source Trace、Coverage Summary、Unresolved Gap、Human Review、Decision / Rationaleの欠落
- UI / Behavior Specification Entry ContractとHandoff内容の不一致
- Independent Review未実施、旧RevisionのReview流用、Finding未修正の持ち越し、Audit Run完了をTarget Passとみなしていないか

# 2. IA Artifact Model

## 2.1. Blueprint-to-Information Mapping

Service Blueprintの各Stepについて、少なくとも次を対応づける。

```text
Blueprint Step / User Goal / User Action
Object / Information / Meaning
Information Source / Provenance
Create / Update / Use / Decide Actor
Responsibility / Authority
Navigation or Context Continuity Need
UI Obligation
Behavior Obligation
Failure / Recovery
```

MappingはScreen名の割当表ではない。体験を成立させる情報と責任を先に明らかにする。

## 2.2. Object, Identity, and Relation

Objectは利用者または業務が一つの意味単位として扱う対象である。Definition、Identity、他ObjectとのRelation、Lifecycle、Ownershipを説明できなければならない。

```text
Good:
Topic = 複数のMessageやEvidenceを横断して追跡する、
        一つの判断対象または問題のLifecycle単位。

Screen-first:
Topic = Topic画面に表示されるもの。

Database-first:
Topic = topics tableの一行。
```

Technical EntityとIA Objectは一致する場合もあるが、実装上同じことを理由に意味まで同一視しない。Relationは「関連する」だけでなく、包含、根拠、解決、所有、前後関係等の意味を示す。

## 2.3. Information Structure and Findability

利用者がObjectを探し、比較し、理解する単位として、Hierarchy、Grouping、Facet、Metadata、List、Detail、History、Searchを定義する。

分類軸が複数ある場合、単一Treeへ押し込まず、独立して組み合わせられるFacetを検討する。

```text
Type / State / Owner / Period / Importance / Source / Keyword
```

一覧、詳細、履歴、検索が同じ情報とActionを無目的に重複しないよう、各責任を説明する。

## 2.4. Responsibility, Authority, and Lifecycle Concept

Objectごとに、誰が作成、閲覧、更新、判断、承認、廃止できるかを整理する。Data OwnershipとAccessの基本原則は[`00_01_Principles.md`](00_01_Principles.md)を正本とし、IAでは対象ObjectとActorへの適用結果を表現する。

Lifecycle / State Conceptは、利用者が区別すべき意味と遷移候補を示す。詳細なTrigger、Precondition、State Transition、Exception、Permission RuleはBehavior Specificationへ渡す。

同じ`Status`という語でも、Business State、Processing State、Presentation Stateが異なる場合は分離する。OwnershipまたはBounded Contextの判断が必要な場合は、人間、Domain Expert、ArchitectureへEscalateする。

## 2.5. Navigation, Flow, and Language

IA Navigationは、利用者が目的から対象責務へ到達し、関連Object間を移動し、元のContextへ戻れる構造を定義する。具体的なScreen Transition、Interaction、ComponentはUIが担う。

GlossaryはObjectのMeaning、Preferred Term、Synonym、禁止語、同名異義、異名同義を扱う。名称を統合するだけで異なる概念を潰したり、同じ概念を画面ごとに別名で放置したりしない。

## 2.6. Configuration Model

UXのControl / Adaptation Need、Actor差、組織差、Consent、通知、自動化、Visibility、保持、Threshold等から、Configuration Candidateを抽出する。

UXのCandidate Dispositionをそのまま全件Settingへ変換しない。`User Preference`、`Organization Policy`等、利用者またはAuthorityがProduct上で理解・変更するものをConfiguration Modelへ入れる。`Fixed Product Rule`は固定理由とSPEC Obligation、`Contextual / Automatic Adaptation`と`Derived Value`は情報源・説明・制御とSPEC Obligation、`Operational / Technical Configuration`はProduct上の影響をSPECへ残したうえでArchitecture Obligation、`Deferred / Out of Scope`はUnresolved GapまたはDisposition Traceとして接続する。

```text
Preference = 個人または利用者が選択する調整
Policy     = 組織またはAuthorityが対象Scopeへ適用するRule
Setting    = Preference / Policy等から決まる変更可能な値または状態
```

各Candidateについて、Purpose、Owner / Authority、Subject、適用Scope、Inheritance / Override、現在値とEffective ValueのMeaning、Visibility、変更・撤回・Reset、Lifecycle、Source UX Need、UI Obligation、Behavior Obligationを必要な粒度で整理する。分析結果からCandidateを抽出せず、UIや実装へ暗黙の固定値として渡してはならない。

IAは設定画面、Field、Option値、Default値、Validation、保存方式を確定しない。正確なOption、Default、Permission、変更効果、Failure / RecoveryはBehavior Specification、認識・変更・影響確認・Resetの体験はUI、環境変数やProvider Parameter等のTechnical ConfigurationはArchitectureへ渡す。

## 2.7. Governance Information Structure

必要なScopeでは次を別責務として構造化する。

```text
Trust Surface
= 現在のData利用、AI動作、根拠、保証、制限を理解する

Consent / Settings
= これからのData送信、Permission、AI動作を許可・変更・撤回する

Future-plan Information
= 利用者へ開示する未実装・開発中・将来予定を理解する
```

`Future-plan Information`は利用者向けProduct情報であり、Repositoryの`99_Roadmap`そのものをProduct IAへ露出する意味ではない。現在保証されること、変更可能な設定、将来予定を同一の画面責務やObjectへ無自覚に混在させない。

Data / AI Scopeでは、Observed Fact、AI Inference、Human-confirmed Information、Source / Provenance、Visibility、Correction / Deletionの責務も区別する。

## 2.8. Stable Context, Evidence, and Decision

`IA-*`は複数Artifactや下流工程から参照し、独立Review、置換、影響追跡を必要とするObject、Responsibility、Navigation等の意味単位へ付与する。文書名・文書番号とStable Context IDを同一視せず、一つのIA Artifact内に複数の`IA-*`が存在してよい。Evidence、Diagram File、Decision、Screen、DB TableへIA IDを代用発行しない。

Objectや責任の根拠は対象Artifact内または最も近い親Folderの`Evidence/`へ置く。Business Concept、Identity、Responsibility、Authority、用語、Navigationの重要判断は、結果となるCanonical IA Artifactの`Decision / Rationale`へ理由、Evidence、代替、影響を残す。

# 3. Guided Skill Adapter

## 3.1. Runtime Authority

`skill.ia.structure`は、Phase Process Contractを[`00_11_Skill.md`](00_11_Skill.md)のRun Lifecycle、Guided Interaction、Human Review、Handoffに従って実行するIA固有Adapterである。本書ではRun Status、Pause / Resume、共通Question Rule、Subagent Lifecycle、Artifact Registrationを再定義しない。

開始時は画面やDatabaseを決める前に、利用者が何を別の対象として理解し、どの単位で確認、比較、判断、操作するかを整理することを説明する。

## 3.2. IA-specific Progression

| Step | IA固有の変換 | Result |
|---|---|---|
| Load and Scope | UX CoverageとBlueprint Stepを対応づける | IA Coverage Queue |
| Extract | Noun、Action、Information、Actor、Sourceを抽出する | Concept Candidate |
| Model | Object、Identity、Relation、Lifecycle、Ownershipを定義する | Object Model |
| Structure | Hierarchy、Grouping、Facet、Metadata、Responsibility、Configuration Candidateを整理する | Information / Responsibility / Configuration Model |
| Connect | Navigation、Glossary、UI / SPEC Obligationを分離する | Downstream Contract |
| Review and Handoff | 全Coverage、Conflict、人間判断を確認する | UI / SPEC Handoffまたは別Route |

## 3.3. IA-specific Question Topics

| Topic | Question Intent |
|---|---|
| Object | 利用者が別のものとして名前を付ける対象は何か |
| Identity | 何が同じなら同じObjectで、何が変わると別か |
| Relation | 対象間の関係は何を意味するか |
| Responsibility | 誰が何を知り、操作し、判断するか |
| Lifecycle | 時間とともに何が変わり、何を区別するか |
| Structure | 何を一覧、詳細、履歴、比較として扱うか |
| Findability | 何を手掛かりに探し、絞り、並べるか |
| Navigation | どの目的から入り、どの責務へ進み、戻るか |
| Ownership | 誰が作成、更新、承認、閲覧するか |
| Configuration | 誰が何を、どの対象Scopeで変更し、継承・上書き・Resetできるか |

Screen名で回答された場合は中心Objectと責任へ、Backend Entityで回答された場合は利用者がそのTechnical Entityを直接意識するかへ戻す。名称ConflictはGlossaryだけで表面的に統合せず、意味の同一性を確認する。

## 3.4. Adaptive Route and Escalation

| Condition | Route |
|---|---|
| UX Outcome、Journey、Blueprintが不足 | UX |
| Business Concept、Authority、Ownershipが未決 | Human Decision / Domain Expert |
| Bounded ContextやSystem Boundaryが支配的 | Architecture |
| Screen表現、Interactionが主題 | UI |
| State Transition、Permission、Exceptionが主題 | Behavior Specification |
| Option、Default、Validation、変更効果が主題 | Behavior Specification / Pair Review |
| 現行構造のEvidence不足 | Research / Legacy Reverse |

AIへBusiness Concept、Domain Boundary、Authority、Data Ownershipの最終決定を要求された場合は確定しない。同一概念に矛盾した定義がある、責任を置けない、Source Authorityが競合する場合もHandoffを止める。

Subagentを使う場合は[`00_10_Agent.md`](00_10_Agent.md)に従い、Object Model、Information Structure、Navigation、Consistency Review等の限定Scopeを委譲できる。中心Object、責任境界、下流Handoffの統合と人間確認はParent Agentが行う。

# 4. Review, Handoff View, and Feedback

## 4.1. IA-specific Human Review

共通Review Contractは[`00_11_Skill.md`](00_11_Skill.md#61-human-review)に従う。IA Reviewでは追加で次を確認する。

- Object、Relation、言葉が利用者と業務の意味に合う
- Screen、DB、既存組織構造へ無批判に引きずられていない
- Blueprint Step、Failure / Recovery、Actor / Responsibilityを網羅している
- 同一責務、同名異義、異名同義、Authority Conflictを隠していない
- UIとBehavior SpecificationへのObligationを混同していない
- UXのControl / Adaptation NeedがConfiguration ModelとUI / SPEC Obligationへ変換されている
- 対象Scope全体のCoverageと部分承認範囲を誤認なく示している

## 4.2. IA Artifact / Handoff View

次はIA責務をProject内で表現する標準Viewであり、独立File数を要求しない。

```text
Scope / Coverage Summary / Unresolved Gap
Source REQ / UX / Blueprint Relation
IA ID / Revision
Blueprint-to-Information Mapping
Pairing Unit Candidate / Feature / Use Case / User Action
Object / Definition / Identity / Relation / Lifecycle
Hierarchy / Grouping / Facet / Metadata / List / Detail / History
Actor / Responsibility / Ownership / Authority
Navigation / Task Flow / Context Continuity
State Concept / Glossary
Configuration Candidate / Preference / Policy / Setting / Scope / Inheritance / Override
Governance Information Structure
UI Obligation
Behavior Specification Obligation
Decision / Rationale
Human Review Result
Phase Transition Review Result / Reviewed Revision / Finding Disposition / Review Exception
```

UIには認識すべきObject、情報優先度、Grouping / Findability、Navigation、主要Action、Presentation上区別すべきState Concept、用語、Configuration CandidateのMeaning / Owner / Scope / Inheritance / Overrideを渡す。Behavior SpecificationにはObject Lifecycle、State Concept、Actor / Authority、Relation Constraint、Behavior / Failure / Recovery Obligation、ConfigurationのOption / Default / Precedence / Permission / Apply / Reset Obligationを渡す。共有Concernは[`00_24_UI_Behavior_Specification.md`](00_24_UI_Behavior_Specification.md)でPairing対象として示す。

HandoffはこのViewを縮小再掲して受信条件を減らさず、UIとBehavior Specificationの各Phase Entry Contractが要求する全Contextを、Canonical IA Artifactへの参照とCoverage State付きで渡す。

## 4.3. Feedback to IA Context

UI / Behavior Specification設計、Architecture、実装、Verification、運用から、Object、Relation、Responsibility、Navigation、用語に関するLearningが得られた場合はIAへ戻す。同じ意味の明確化は同じ`IA-*`のRevisionを更新し、意味を置換する場合は新しい`IA-*`を発行して`supersedes`で接続する。

下流の画面、DB、API、実装都合だけでIA Contextを無断変更せず、Evidenceと人間判断を結果となるIA Artifactへ反映し、影響するUI / Behavior Specificationを再確認する。

# 5. Final Principle

```text
IAは、Object ModelやSitemapを一つ作って終わる工程ではない。
対象Scopeの全Journey、Blueprint Step、Actor、Failureについて、
利用者が理解する意味、情報、責任、移動と下流Obligationを接続する。
```
